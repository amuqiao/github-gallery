SwiftUI
你不写界面，你声明状态

SwiftUI 是 Apple 官方的声明式 UI 框架，用一套 Swift 代码构建 iPhone、iPad、Mac、Watch 的界面。这篇文章不教你背 API，而是帮你建立开发心智模型：需求放进哪个文件、状态归谁管、用什么词跟 AI 描述你要的东西。

面向 Swift 5.9+ / iOS 17+ / Xcode 15+ · 涉及 iOS 16 及更早写法时会单独标注

body 是纯描述 · UI = f(State) · 改数据，不改界面

WaterView.swift — 试着点右边手机里的按钮
import SwiftUI struct WaterView: View { @State private var cups = 0状态源 var body: some View { VStack(spacing: 16) { Text("今天喝了 \(cups) 杯水") Button("喝一杯 💧") { cups += 1 // 只改数据 } } } }
▷ PREVIEW · 实时预览
喝水打卡
今天喝了 0 杯水

看到了吗:按钮里没有任何"更新界面"的代码,它只做了 cups += 1。@State 变了,SwiftUI 自动重算 body,界面跟着变。这就是你要建立的第一个直觉——永远描述"界面长什么样",永远不要命令"界面怎么改"。

01 · 心智模型

View 是状态的函数,不是要操纵的对象

如果你写过 jQuery、Android View 或 UIKit,请先卸下"拿到控件引用 → 调它的方法改它"的习惯。SwiftUI 里没有 label.setText(),也没有 findViewById。

  • View 是轻量 struct,不是控件实例。每个界面都是一个遵循 View 协议的 struct,它的 body 属性返回"此刻界面应该长什么样"的描述。struct 会被频繁地销毁重建,这很便宜、很正常。
  • 状态是唯一的真相来源(Source of Truth)。数据存在 @State、@Observable 模型等地方;界面永远由数据推导出来。你改数据,框架负责 diff 和刷新。
  • 修饰符(Modifier)链式描述样式与行为。没有 CSS,没有样式表。.padding()、.font(.title)、.onTapGesture { } 这些方法每次返回一个新的包装 View,顺序有意义:.padding().background(.red) 和 .background(.red).padding() 效果不同。
  • 布局靠容器组合,不靠坐标。竖排用 VStack、横排 HStack、叠放 ZStack、留白 Spacer。你几乎不写 frame 坐标,而是描述"这些东西怎么摆在一起"。
心智对比 · 命令式 vs 声明式ContentView.swift
// ✗ UIKit 思维:拿到控件,命令它变化
// countLabel.text = "\(count)"   ← SwiftUI 没有这种操作

// ✓ SwiftUI 思维:声明界面与数据的关系,然后只改数据
Text("共 \(items.count) 条")          // 声明:文本 = 数据的投影
items.append(newItem)                 // 行为:只动数据,UI 自动更新

这个模型和 React 高度同构:View ≈ 函数组件,@State ≈ useState,Modifier ≈ props/样式。如果你熟 React,迁移成本主要在术语而不是思想。

02 · 从一个真实任务开始

需求:做一个记账 App「钱迹Lite」

与其罗列 API,不如看一个完整需求如何落进 SwiftUI 工程。需求是:记录每笔支出(金额、分类、备注),列表展示,可新增、可删除,数据要存下来,下次打开还在。

这个需求在 SwiftUI 生态里会被拆解成:

  • 数据模型 → 一个 @Model 类 Expense(SwiftData 负责持久化)
  • 列表页 → ExpenseListView,用 List + @Query 读数据,.onDelete 支持滑动删除
  • 新增页 → AddExpenseView,用 Form + TextField + Picker,以 .sheet 弹出
  • 入口 → MoneyLiteApp.swift 里挂上 modelContainer,声明第一个窗口显示列表页
  • 验证 → Xcode Preview 实时看 UI;⌘R 跑模拟器;单元测试验证模型逻辑

点击下面目录树里的文件,看每个文件承担什么职责 👇

MoneyLite/ ├ Models/ ├ Views/ ├ Assets.xcassets/

SwiftUI 对目录没有硬性约定(不像 Next.js 的文件路由),Models/、Views/ 只是社区习惯。真正有约束力的是 Xcode 工程文件(.xcodeproj)把哪些文件编进 target——所以跟 AI 说"新建文件"时,记得说明"加入 app target"。

03 · 项目结构与入口

程序从 @main 开始,窗口由 Scene 声明

SwiftUI App 没有 main() 函数,也没有 storyboard。入口是一个标了 @main 的 struct,它遵循 App 协议,body 返回 Scene(场景)——最常用的 Scene 是 WindowGroup,代表"一组主窗口"。

App 入口 · 全工程唯一的 @mainMoneyLiteApp.swift
import SwiftUI
import SwiftData

@main
struct MoneyLiteApp: App {
    var body: some Scene {
        WindowGroup {
            ExpenseListView()          // 根视图:App 打开看到的第一屏
        }
        .modelContainer(for: Expense.self)  // 注入 SwiftData 数据库
    }
}

层级关系:App → Scene → View

  • App:进程级入口,放全局依赖注入(数据库容器、全局设置)。整个工程只有一个。
  • Scene:窗口级。iPhone 上通常感知不到,iPad/Mac 上一个 App 可开多窗口。除 WindowGroup 外还有 Settings(Mac 设置窗)、MenuBarExtra(Mac 菜单栏)等。
  • View:界面本体,99% 的代码写在这层。

和 UIKit 的边界(维护老项目会遇到)

2019 年之前的 Apple UI 框架叫 UIKit(命令式,ViewController + storyboard)。两者可以互嵌:SwiftUI 里包 UIKit 组件用 UIViewRepresentable,UIKit 里嵌 SwiftUI 用 UIHostingController。跟 AI 交流时务必说清你的项目是"纯 SwiftUI"还是"UIKit 混编",生成的代码结构完全不同。

04 · 状态管理

状态归谁管:五个属性包装器的分工

SwiftUI 的状态工具都是属性包装器(以 @ 开头的注解)。选错包装器是新手(和被模糊指挥的 AI)最常见的 bug 来源。核心问题只有一个:这份数据的"所有权"在哪里?

视图私有的简单状态。本视图拥有、本视图修改,生命周期跟着视图走。适合开关、输入草稿、计数这类"界面自己的小事"。

@State private var isOn = false
@State private var keyword = ""   // 配合 TextField 的输入草稿
什么时候用值类型(Bool/String/Int/小 struct)、只影响当前视图及其子树、退出页面就可以丢弃的状态。永远加 private。
不要拿它做什么不要存跨页面共享的数据、不要存业务模型列表、不要从外部初始化它当参数用(那是 @Binding 或普通 let 的活)。

借来的读写权。子视图不拥有数据,但需要修改父视图的 @State。父传子时加 $ 前缀取得绑定:ChildView(isOn: $isOn)。系统控件全靠它工作。

struct SettingsRow: View {
    @Binding var isOn: Bool          // 不拥有,只是能读写
    var body: some View {
        Toggle("夜间模式", isOn: $isOn)  // $ = 取绑定而非取值
    }
}
什么时候用子组件要双向修改父状态:自定义输入控件、可复用的表单行、弹层里的确认操作回写。
不要拿它做什么只读展示用普通 let 就够了;跨很多层传 Binding 会变成"钻孔",该升级成 @Observable 模型 + @Environment。

共享的业务模型(iOS 17+ 主流方案)。把业务状态和逻辑放进一个 @Observable class,多个视图观察同一个实例;哪个视图读了哪个属性,只有那个属性变化时它才刷新——细粒度、高性能。

@Observable class CartModel {
    var items: [Product] = []
    var total: Double { items.reduce(0) { $0 + $1.price } }
    func add(_ p: Product) { items.append(p) }
}

// 视图里:谁创建谁用 @State 持有(iOS 17 写法)
@State private var cart = CartModel()
什么时候用跨视图共享的业务状态、带方法的领域逻辑、需要和网络/数据库交互的 ViewModel 层。
不要拿它做什么iOS 17+ 新项目别再用旧三件套 ObservableObject / @StateObject / @ObservedObject / @Published——那是 16 及更早的写法,详见「版本边界」。

依赖注入通道。祖先视图放进环境,任意深度的后代直接取用,不用一层层传参。既能读系统值(深色模式、动态字号),也能注入自己的模型。

// 注入(通常在 App 入口或根视图)
ExpenseListView().environment(cart)

// 任意后代读取
@Environment(CartModel.self) private var cart
@Environment(\.colorScheme) private var scheme  // 系统值:深/浅色
@Environment(\.dismiss) private var dismiss     // 关闭当前弹层/页面
什么时候用App 级共享模型(用户会话、购物车)、读系统环境、在弹层里拿 dismiss 关闭自己。
不要拿它做什么不要什么都塞环境——只被一两个视图用的数据直接传参更清晰;忘了注入会直接崩溃,测试和 Preview 里要记得补 .environment(...)。

直通 UserDefaults 的轻量偏好。读写自动持久化、自动刷新 UI,一行顶三行。本质是 key-value 明文存储。

@AppStorage("hasSeenOnboarding") private var hasSeenOnboarding = false
@AppStorage("currency") private var currency = "CNY"
什么时候用用户偏好、开关、上次选中的 tab、是否看过引导页——小而简单的标量。
不要拿它做什么不存业务数据列表(用 SwiftData)、不存密码 token(用 Keychain)、不存大对象。

05 · 导航与页面跳转

「页面跳转」在这里叫什么

SwiftUI 没有 Router 配置文件,导航是数据驱动的:栈是一个数组,push 就是往数组里 append 一个值。三种主要形态对应三种中文需求:

  • 层级推进(左滑进入详情页) → NavigationStack + NavigationLink / navigationDestination
  • 模态弹出(从底部升起的临时页) → .sheet(半屏可下滑关闭)/ .fullScreenCover(全屏)
  • 平级切换(底部标签栏) → TabView + .tabItem
典型导航:列表 → 详情,值驱动ExpenseListView.swift
NavigationStack(path: $path) {          // path: [Expense] — 栈即数组
    List(expenses) { expense in
        NavigationLink(value: expense) {  // 点击 = 把值推进 path
            ExpenseRow(expense: expense)
        }
    }
    .navigationTitle("账单")
    .navigationDestination(for: Expense.self) { expense in
        ExpenseDetailView(expense: expense)  // 值的类型 → 目标页面
    }
}

弹层同样是状态驱动:.sheet(isPresented: $showingAdd) { AddExpenseView() }——没有 present() 方法可调,把 showingAdd 设为 true 弹层就出现,弹层内部用 @Environment(\.dismiss) 关闭自己。深链、返回多级、程序化跳转,全都通过操作 path 数组实现。

⚠️ 版本边界:NavigationStack 是 iOS 16+ 的方案;老代码里的 NavigationView 已废弃,让 AI 生成新代码时明确说"用 NavigationStack"。

06 · 数据流与异步

网络请求:async/await + .task

现代 SwiftUI 的异步主路径是 Swift 并发(async/await),不是回调也不是 Combine。三件套:URLSession 发请求、Codable 解 JSON、.task 修饰符把异步任务绑到视图生命周期上。

完整链路:模型 → 请求 → 视图状态机RateView.swift
struct Rate: Codable { let currency: String; let value: Double }

enum LoadState { case loading, loaded([Rate]), failed(Error) }

struct RateView: View {
    @State private var state: LoadState = .loading

    var body: some View {
        Group {
            switch state {                   // UI 是加载状态的函数
            case .loading:        ProgressView("加载中…")
            case .loaded(let r):  List(r, id: \.currency) { Text("\($0.currency) \($0.value)") }
            case .failed:         ContentUnavailableView("加载失败", systemImage: "wifi.slash")
            }
        }
        .task {                              // 视图出现时启动,消失时自动取消
            do {
                let (data, _) = try await URLSession.shared.data(from: url)
                state = .loaded(try JSONDecoder().decode([Rate].self, from: data))
            } catch { state = .failed(error) }
        }
    }
}
  • 错误处理的惯用法:把「加载中/成功/失败」建模成一个 enum 状态机,而不是散落的 isLoading + errorMessage 布尔汤。空态/错误态用 ContentUnavailableView(iOS 17+)。
  • 项目大了以后:请求逻辑从视图里抽出去,进 @Observable 的 ViewModel 或独立的 APIClient service;视图只消费状态。这条分层习惯直接决定 AI 生成代码的可维护性。
  • 后台任务边界:App 切后台后代码基本被冻结,长任务不是开线程能解决的——真正的后台刷新走 BackgroundTasks 框架(BGAppRefreshTask),推送走 APNs,别让 AI 用 Timer 假装后台任务。

07 · 持久化怎么选

「把数据存下来」的四条路线

这是需求最容易说糊、AI 最容易选错的地方。四种方案各管一段,选择边界很清晰:

@AppStorage / UserDefaults

全版本 · 明文 plist

存:用户偏好、开关、小标量。

别存:列表数据、敏感信息、大于几 KB 的东西。

SwiftData

iOS 17+ · 推荐的结构化存储

存:业务对象和关系(账单、笔记、待办)。@Model 声明模型、@Query 在视图里查询、modelContext.insert/delete 写入,schema 变更做 Migration。

别存:图片视频等大文件本体(存文件,库里存路径)。

Core Data

全版本 · SwiftData 的前身

用在:需要支持 iOS 16-、或接手的老项目。概念对应:NSManagedObject≈@Model,@FetchRequest≈@Query。新项目不选它。

Keychain / FileManager

全版本

Keychain:token、密码等敏感凭证(系统加密,无官方 SwiftUI 包装,常用 KeychainAccess 库)。

FileManager:导出文件、图片缓存,写进 Documents / Caches 目录。

SwiftData 最小闭环:声明 → 查询 → 写入Expense.swift / ExpenseListView.swift
@Model class Expense {                       // 声明即建表
    var amount: Double; var category: String; var date: Date
    init(amount: Double, category: String, date: Date = .now) { … }
}

// 视图里
@Query(sort: \Expense.date, order: .reverse) var expenses: [Expense]
@Environment(\.modelContext) private var context

context.insert(Expense(amount: 28, category: "咖啡"))  // 写入,@Query 自动刷新列表

08 · 生命周期与副作用

没有 viewDidLoad,只有「出现·变化·消失」

View struct 随时重建,所以 SwiftUI 不谈对象生命周期,只给你几个挂副作用的时机点:

  • .task { } — 视图出现时跑异步任务,视图消失自动取消。加载数据的首选,优于 onAppear。
  • .onAppear { } / .onDisappear { } — 同步副作用:埋点、开始/停止动画。
  • .onChange(of: value) { old, new in } — 监听某个状态变化后做事(iOS 17 起回调带新旧两值)。
  • @Environment(\.scenePhase) — App 级前后台切换(.active / .inactive / .background),在这里保存草稿、暂停计时。

直觉校准:「页面加载时请求接口」对应 .task,不是 init。View 的 init 会被调用很多次,别在里面做任何重活或副作用。

10 · 版本边界

新旧写法分水岭:AI 最容易生成过时代码的三处

SwiftUI 每年随 iOS 大版本演进,训练语料里混着大量旧写法。让 AI 生成代码前,先声明目标版本;看到下面左列的写法,要意识到那是旧方案:

ObservableObject + @Published + @StateObject / @ObservedObject / @EnvironmentObject(iOS 16-)
iOS 17+ 用 @Observable 宏:类上一个注解搞定,视图里 @State 持有、@Environment 注入,刷新粒度更细、性能更好。
NavigationView(已 deprecated)
iOS 16+ 用 NavigationStack(单栈)或 NavigationSplitView(iPad/Mac 分栏),支持 path 数组做程序化导航和深链。
Core Data(NSPersistentContainer、@FetchRequest)用于新项目
iOS 17+ 新项目用 SwiftData(@Model / @Query);Core Data 仅用于兼容老系统或维护存量代码。

同理:异步优先 async/await 而非 Combine 或回调;预览用 #Preview { } 宏而非旧的 PreviewProvider struct。跟 AI 说一句「目标 iOS 17,用 @Observable 和 SwiftData,不要 ObservableObject 和 Core Data」,能消掉一大半过时代码。

11 · AI Coding 提示词

把模糊需求翻译成 SwiftUI 的语言

同一个需求,两种说法,产出质量天差地别。好 prompt 的配方:版本约定 + 文件位置 + 框架术语 + 状态流 + 分层边界 + 错误处理 + 验证方式。点击切换对比:

"帮我做个记账功能,能加账单,能看列表,数据别丢。"

  1. 目标 iOS 17+ / Swift 5.9,纯 SwiftUI 新项目,持久化用 SwiftData,不要 Core Data 和 ObservableObject。
  2. 在 Models/Expense.swift 定义 @Model 类 Expense:amount(Double)、category(String)、note(String?)、date(Date)。
  3. 在 Views/ExpenseListView.swift 用 List + @Query(按 date 倒序)展示;.onDelete 滑动删除;空态用 ContentUnavailableView。
  4. 导航栏 .toolbar 放 + 按钮,点击置 @State showingAdd = true,以 .sheet 弹出 Views/AddExpenseView.swift:Form 含 TextField(金额,.keyboardType(.decimalPad))、Picker(分类)、保存时经 modelContext.insert 写入并 dismiss;金额 ≤ 0 时保存按钮 .disabled。
  5. 入口 MoneyLiteApp.swift 挂 .modelContainer(for: Expense.self)。每个视图给一个 #Preview(用内存容器 mock 数据),我会用 Preview 和模拟器验证。

"列表从接口拉数据,加个加载中和失败重试,顺便支持下拉刷新。"

  1. 分层:在 Services/RateClient.swift 写一个 struct,方法 func fetchRates() async throws -> [Rate],内部用 URLSession + JSONDecoder;Rate 遵循 Codable, Identifiable。视图层不直接碰 URLSession。
  2. 视图状态建模为 enum LoadState { loading, loaded([Rate]), failed(Error) },存在 @Observable 的 RateModel 里,不要 isLoading 布尔散装。

12 · 常见误说法

这些描述会把 AI 带偏

"给这个 div 加个样式 / 改下 CSS"
SwiftUI 没有 div 和 CSS。说:"给这个 VStack 加 .padding() 和 .background(...) modifier",样式即修饰符链。
"点击后更新一下那个文本控件的内容"
说:"点击后修改 @State 变量 xxx,Text 里插值显示它"。命令式的"更新控件"会诱导 AI 写出反模式。
"弹一个 Toast 提示成功"
SwiftUI 无原生 Toast。说:"用 .overlay 自定义一个 2 秒后消失的提示条",或明确要 .alert。
"把用户数据放到全局变量里"
说:"建一个 @Observable 的 SessionModel,在 App 入口用 .environment() 注入,子视图用 @Environment 读取"。
"onClick 事件里…" / "监听 onChange 事件"
按钮动作是 Button("…") { } 的尾随闭包;任意视图点击是 .onTapGesture;监听状态变化才是 .onChange(of:)。
"页面初始化的时候(init)去请求接口"
说:"在 .task 里请求"。View 的 init 会被反复调用,放副作用是经典 bug。
"数据库随便,存本地就行"
明确路线:偏好 → @AppStorage;业务对象 → SwiftData;凭证 → Keychain;文件 → FileManager。"随便"通常换来 UserDefaults 存万物。

13 · 验证与测试

怎么确认 AI 写的代码是对的

  • Xcode Preview(最快回路):每个 View 文件底部写 #Preview { MyView() },右侧画布实时渲染、可交互,不用启动整个 App。让 AI"给每个视图带 #Preview 和 mock 数据"是最划算的一句要求。
  • 模拟器运行:⌘R 编译运行到 iOS Simulator,验证完整流程;⌘U 跑全部测试。
  • 单元测试:XCTest(或 Xcode 16 的 Swift Testing)测模型与 service 逻辑;给 service 定义 protocol,测试时注入替身(mock)。UI 流程用 XCUITest,但性价比低,优先把逻辑抽出视图来测。
  • 命令行构建(CI 用):xcodebuild -scheme MoneyLite -destination 'platform=iOS Simulator,name=iPhone 15' build test。
  • 发布链路:Archive → App Store Connect → TestFlight 内测 → 审核上架。个人调试免费,真机分发需要 Apple Developer Program($99/年)。
