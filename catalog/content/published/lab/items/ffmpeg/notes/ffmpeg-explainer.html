FFmpeg：几乎所有音视频软件
脚下的那层地基

你看视频、开会、刷短视频、听播客时，大概率有一段数据刚刚穿过 FFmpeg 的代码。它是一套用 C 写成的多媒体处理工具集与库：把任意格式的音视频读进来、解开、加工、再打包出去。YouTube、VLC、OBS、HandBrake、Chrome 的部分能力，底层都站在它上面。

01 / 项目定位

它是什么，为什么会存在

先把三件事讲清：它解决的问题、它的组成、以及它的边界在哪。

它解决的问题：多媒体世界的“碎片化”

音视频领域天然碎片化：同一段画面可以用 H.264、HEVC、VP9、AV1 等几十种编码压缩；压缩后的流又能装进 MP4、MKV、TS、FLV 等几十种容器；传输时还要走 HTTP、RTMP、RTSP、HLS 等不同协议。任何一个要处理视频的软件，如果自己实现这些格式，工程量是天文数字。

FFmpeg 的回答是：把所有格式的读、写、编、解、加工做成一套统一的 C 库和命令行工具，其他软件只需调用它。这就是它成为“地基”的原因——不是因为它做了某个产品，而是因为它把整个领域最脏最重的兼容性工作一次做完了。

它由什么组成

CLI 工具（fftools/）

ffmpeg · ffprobe · ffplay

ffmpeg 是转换与处理的主工具；ffprobe 只读不写，用来探测媒体文件的结构与参数；ffplay 是一个基于 SDL 的极简播放器，主要用于调试。三者都是薄薄的一层入口，真正的能力在下面的库里。

库（libav*）

libavformat / libavcodec / libavfilter …

八个共享库构成能力本体：封装与协议（format）、编解码（codec）、滤镜（filter）、缩放（swscale）、重采样（swresample）、设备采集（avdevice）、基础设施（avutil）。VLC、Chrome、HandBrake 链接的正是这些库。

边界：它不做什么

  • 不是编辑器：没有 GUI、没有时间线；剪映、Premiere 解决“人怎么剪”，FFmpeg 解决“机器怎么算”。
  • 不是媒体服务器：它能推流、拉流，但会话管理、分发、鉴权要靠 nginx-rtmp、SRS、MediaMTX 这类服务，FFmpeg 常作为它们的推流端或转码 worker。
  • 不负责专利授权与 DRM：它实现编解码算法，但 H.264/HEVC 的专利费、Widevine 之类的 DRM 不在它的范围内，商用时要自己评估。
  • 许多明星编码器不在仓库内：最常用的 H.264 编码器 libx264、AV1 的 libsvtav1 都是外部项目，FFmpeg 通过统一接口包装它们；仓库自带的是解码器全家桶和一部分原生编码器。

一句话生态位：FFmpeg 之于音视频，约等于 libc 之于系统编程——你可以不直接用它，但你用的工具几乎都在用它。

两个贯穿全局的数据结构

整条流水线上只流动两种东西：AVPacket（压缩后的数据包，属于某条流）和 AVFrame（解码后的原始帧：视频是像素平面，音频是采样）。所有库之间的接口，本质都是这两个结构体的搬运与变换。首屏动画里数据块中途“变圆再变方”，画的就是 packet → frame → packet 这次形态转换。

为什么原始帧不能直接存？1080p30 的未压缩视频约 1.5 Gbps，一分钟就超过 11 GB。所以“解码后的世界”只存在于内存和流水线中段，落盘和传输永远是压缩形态——这也是编码器成为整条链路算力瓶颈的原因。

03 / 仓库结构

源码目录与流水线一一对应

FFmpeg 的仓库结构极其“直译”：一个库一个目录，目录名就是库名。点击左侧目录查看它承担流水线的哪一段、里面有什么。

ffmpeg/

从结构能读出的三件事

  • 分层非常干净：libavutil 在最底层，其余库单向依赖它；fftools 里的三个 CLI 只是库能力的编排者。你在命令行做的每件事，理论上都能通过 C API 在自己进程里完成。
  • 能力靠注册表扩展：每个 demuxer/codec/filter 都是一个静态注册的 C 结构体（如 FFInputFormat、FFCodec、AVFilter），新增一种格式 ≈ 新增一个 .c 文件 + 挂进注册列表。这就是它能长到数百种格式还不散架的机制。
  • configure 决定“你的 FFmpeg 是哪个 FFmpeg”：外部编码器（libx264、libvpx…）、硬件加速、GPL 开关全在编译期决定。两台机器上的 ffmpeg 能力可以差别巨大，排障先跑 ffmpeg -version 看编译选项。
04 / 命令解剖

读懂一条典型的 ffmpeg 命令

ffmpeg 的命令行只有一条核心语法规则，但 90% 的困惑都来自没掌握它：选项是位置敏感的，作用于紧随其后的那个文件。点击下面命令中的任意片段查看解释。

ffmpeg-y-ss 00:01:00-i input.mp4-t 30-vf "scale=1280:-2"-c:v libx264-crf 23-preset veryfast-c:a aac-b:a 128kclip.mp4
语法骨架：ffmpeg [全局选项] [输入选项] -i 输入文件 … [输出选项] 输出文件 …　·　同色 ≈ 同类：全局 / 输入侧 / 视频输出 / 音频输出

两个立刻用得上的推论：① -ss 放在 -i 之前是“先跳转再解码”（快），放在之后是“解码到那一刻”（慢但更准）；② -c:v、-b:a 这类带 :v :a 后缀的选项叫 stream specifier，让你对视频流和音频流分别下指令——比如视频重编码、音频原样复制（-c:v libx264 -c:a copy）。

06 / 集成方式

把 FFmpeg 装进你的系统的三条路

从“最省心”到“最贴身”，成本和收益都单调递增。绝大多数团队应该从第一条路开始。

路线 A · 最常见

子进程调用 CLI

后端起一个 ffmpeg 进程干活，解析退出码和 stderr 进度。上传转码、生成缩略图、切 HLS 都是这个模式。

接口稳定、崩溃隔离、任何语言可用

升级 = 换二进制，几乎零迁移成本

进程启动开销；帧级数据拿不到手

路线 B · 语言绑定

PyAV / ffmpeg-python / fluent-ffmpeg

两个流派：ffmpeg-python、fluent-ffmpeg(Node) 只是帮你拼命令行，本质仍是路线 A；PyAV、go-astiav 则真正绑定 C API，能逐帧读写、和 NumPy 互通。

在宿主语言里逐帧处理，适合 CV/ML 管线

绑定库的维护质量参差，选型要看活跃度

路线 C · 链接 C API

直接使用 libav* 库

播放器、剪辑软件、浏览器走这条路：进程内解码，帧数据零拷贝送渲染管线，延迟与内存完全可控。

性能与控制力的天花板

API 学习曲线陡；大版本升级常有破坏性变更（弃用周期约两年），要预留跟进成本

选型经验法则：你的需求能用一条命令行描述 → 路线 A；需要逐帧进出你的代码 → 路线 B（PyAV 类）；你在做播放器/编辑器本体 → 路线 C。

07 / 对比与边界

和邻居们的关系，以及常见误区

同类与近邻

项目是什么与 FFmpeg 的关系
GStreamer基于插件图（pipeline graph）的多媒体框架，面向嵌入式与桌面应用内的长驻管线定位最接近的“对手”，但哲学不同：FFmpeg 是“一把工具 + 一组库”，GStreamer 是“搭管线的框架”。GStreamer 还有插件直接包了 libav*。
HandBrakeGUI 转码器下游用户：核心转码能力来自 libav* 与 x264/x265，相当于给常用转码场景配了界面和预设。
VLC / mpv播放器下游用户：解码几乎全靠 libavcodec。mpv 项目本身就诞生于 FFmpeg 社区周边。
OBS Studio录屏与直播推流工具下游用户：录制封装与推流输出用 libavformat/libavcodec。
MediaInfo / MP4Box探测工具 / MP4 封装工具（GPAC）功能与 ffprobe、mp4 muxer 部分重叠；GPAC 在 MP4/DASH 细节上更专精。

常见误区（点开看）

“用 -c copy 就能精确剪到任意时间点”
流复制不重新编码，切点只能落在关键帧（keyframe）上，所以剪出的片段开头可能提前或黑屏几秒。要帧级精确，必须让视频段重编码（去掉 -c copy，或只对切口做重编码的"smart cut"方案）。
"FFmpeg 转码慢，说明它性能差"
速度几乎全由编码器和参数决定：-preset veryslow 与 ultrafast 差一个数量级；换 h264_nvenc / h264_videotoolbox 等硬件编码器又是另一个数量级。FFmpeg 本身的解封装/解码开销通常不是瓶颈。
"FFmpeg 和 Libav 是两个东西？我该装哪个？"
2011 年社区分裂出过一个叫 Libav 的分叉（Debian/Ubuntu 一度只带它），后来 FFmpeg 吸收了对方大部分改动，发行版陆续迁回，Libav 已停止维护。今天只需认准 FFmpeg；注意"Libav 项目“和 FFmpeg 自己的”libav* 库"是重名的两回事。
“开源的，商用随便用”
两层问题要分开：许可证——默认构建是 LGPL 2.1+，动态链接即可闭源商用；但 --enable-gpl（为了 libx264 等）后整体变 GPL，静态链接或分发时要履行相应义务。专利——H.264/HEVC 等编解码算法的专利授权与许可证无关，规模化商用需单独评估。
"报错 Unknown encoder 'libx264'，是我命令写错了"
多半是你这份二进制编译时没启用该编码器。跑 ffmpeg -encoders | grep 264 确认；发行版仓库的包为了许可证干净常常裁剪功能，换 static build 或自编译即可。这类“同名不同能力”是 FFmpeg 排障第一大坑。

适用 / 不适用

适合

批处理与服务端媒体管线

上传转码、HLS/DASH 打包、截图与缩略图、音频归一化、格式归档迁移、直播转推、CV/ML 的帧抽取——一条命令或一个 worker 能描述的活，它都是默认答案。

不适合

需要“人”或“平台”的场景

可视化剪辑与调色（用 NLE）、多人连麦低延迟互动（用 WebRTC 栈）、内容分发与鉴权（用媒体服务器/CDN）、DRM。这些场景里 FFmpeg 最多当一个部件，不能当整个方案。
