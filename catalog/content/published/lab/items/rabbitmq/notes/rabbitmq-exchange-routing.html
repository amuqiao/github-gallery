发给队列的

几乎所有 RabbitMQ 的困惑，都来自同一个错误的心智模型：
以为「生产者把消息投进队列」。它不是。
生产者只把消息交给 exchange，并附上一个 routing key。至于这条消息去哪个队列、去几个队列、还是直接被丢掉， 由 broker 上的绑定关系决定——生产者对此一无所知。理解了这一点，路由、丢消息、重复消费、死信，全都能顺着推下去。

01 / 起点

一个下单接口，是怎么被拖垮的

先别管 exchange 和 binding。看一段每个后端都写过的代码。

# 下单接口：同步串行
def create_order(req):
    order = db.insert_order(req)      # 30ms   必须成功
    inventory.deduct(order)           # 80ms   必须成功
    points.grant(order)               # 120ms  失败了……订单要回滚吗？
    sms.send(order)                   # 400ms  短信网关抖动，用户在转圈
    es.index(order)                   # 200ms  搜索索引慢，关我下单什么事
    return order                      # 合计 830ms，且任一环节挂 = 下单挂
问题一

响应时间被最慢的下游绑架

用户只关心「订单创建成功」，却要为短信网关的 400ms 买单。

问题二

可用性做乘法

5 个 99.9% 的服务串起来，整体只剩 99.5%。加一个下游，下单就更脆一分。

问题三

改一处，动全身

风控要接入？改下单代码。推荐要接入？再改一次。下单成了所有人的挂钩点。

这三件事有一个共同解法：把「订单已创建」这个事实写到一个中间人那里，谁关心谁自己去取。 下单只对「订单入库 + 事实已投递」负责，剩下的异步发生。这就是消息中间件干的事。

RabbitMQ 的定位：一个实现 AMQP 0-9-1 协议的消息 broker， 2007 年由 Rabbit Technologies 用 Erlang 写成。Erlang 不是趣闻——它带来的轻量进程模型和 OTP 监督树， 正是 RabbitMQ 能稳定维持几十万条连接、单条消息级别精细调度的底子。

它的性格是：聪明的 broker + 简单的消费者。路由逻辑、投递状态、重试、死信，全在 broker 里。 这跟 Kafka「笨 broker + 聪明消费者（自己管 offset）」是两种哲学，也决定了两者的适用场景完全不同（见 08）。

边界先说清楚：消息队列不是万能垫片。 需要立即拿到结果的调用（查余额、校验库存后返回可否下单）不要塞进队列； 需要强一致事务的操作（扣款与记账）不要指望 MQ 帮你保证； 需要海量数据回放/重算（把上个月的行为日志再跑一遍）RabbitMQ 也不合适——消息一旦被 ack 就没了。

02 / 心智模型

五个名词，一条单行道

整个 RabbitMQ 就是这条链路的展开。任何复杂配置，都是在给这条链路的某一段加约束。

Producer  ──publish(routing_key)──▶  Exchange  ──binding──▶  Queue  ──deliver / ack──▶  Consumer

左半段（Producer → Exchange → Queue）决定消息去哪；右半段（Queue → Consumer）决定消息什么时候算处理完。
绝大多数线上事故，不是左边路由错了，就是右边 ack 错了。

交换机

EXCHANGE

消息的唯一入口，本身不存储任何消息。它只做一件事：拿到 routing key 和 headers，按自己的类型规则算出该投给哪些队列。算不出来就丢弃。

队列

QUEUE

消息真正的落脚点，FIFO 的缓冲区。队列属于 broker，不属于消费者。多个消费者连同一个队列，是竞争关系，不是广播。

绑定

BINDING

exchange 与 queue 之间的一条规则，携带一个 binding key。它是路由表里的一行。同一对 exchange/queue 之间可以有多条绑定。

路由键

ROUTING KEY

发消息时贴在信封上的地址标签，如 order.created.vip。生产者只写地址，不指定收件人。

信道

CHANNEL

建立在 TCP 连接之上的轻量虚拟连接。所有 publish/consume 都发生在 channel 上。channel 不是线程安全的，一线程一 channel。

虚拟主机

VHOST

命名空间隔离。不同 vhost 下的 exchange、queue、权限完全独立，像同一台 broker 上的多个逻辑 broker。

先记住这句：「发到队列」这句话在 RabbitMQ 里不存在。 你以为的「发到队列」，其实是发到 default exchange（名字为空字符串的 direct exchange）， 而每个队列都自动以自己的队列名绑定在它上面。所以 publish(exchange="", routing_key="task_queue") 看起来像直投队列—— 那只是一个贴心的默认值，规则从未改变。

03 / 核心机制

路由台：亲手把消息投出去

四种 exchange 类型，区别只在「怎么把 routing key 和 binding key 做匹配」。 改绑定、换类型、点发布，看消息落到哪几个队列——比读十段文档都快。

EXCHANGE TYPE
X : orders.direct
改改绑定，然后点「发布消息」。

topic 的两个通配符，别记反

routing key 用 . 分成若干个单词。

* = 恰好一个单词。order.* 匹配 order.created，不匹配 order.created.vip。

# = 零个或多个单词。order.# 两个都匹配，连 order 本身也匹配。

没匹配上的消息去哪了

默认：静默丢弃。broker 不会报错，生产者也拿不到任何提示——这是新手最常见的「消息凭空消失」。

两个补救：发布时带 mandatory=true 并注册 return 回调，broker 会把无法路由的消息退回来； 或给 exchange 配 alternate-exchange，所有落空的消息统一进兜底队列。

选型直觉： 要广播用 fanout；要精确点名用 direct； 要「按业务层级订阅」（order.*.vip / *.created.#）用 topic； headers 类型灵活但慢、可读性差，实践中极少用，遇到需求先想想能不能用 topic 表达。 真实项目里 90% 的场景一个 topic exchange 就够了，因为 topic 在 binding key 不含通配符时行为等同于 direct。

04 / 可靠性

一条消息，可以在六个地方丢掉

「加了 MQ 消息还会丢吗？」会。而且丢法不止一种。 下面每个开关对应一段真实的防护，勾选后看右边三盏灯的变化。

网络抖动 / broker 拒收

路由落空

broker 进程重启

消费者处理到一半崩溃

业务逻辑处理失败

没有 exactly-once。RabbitMQ 提供的是 at-least-once： 只要你打开了上面这些防护，消息不会丢，但一定可能重复—— 消费者处理完业务、还没来得及发 ack 就崩了，这条消息会被重新投递给别人。

所以真正的可靠性等式是： 持久化 + 确认机制 + 消费端幂等。前两项 broker 帮你，第三项只能你自己做： 用业务唯一键（订单号 + 操作类型）做去重表，或让操作本身天然幂等（SET status='paid' 而不是 balance -= 100）。

还有一个更隐蔽的丢法：单机持久化的 fsync 窗口

即使 queue durable + message persistent，消息也是先写进操作系统页缓存，隔几百毫秒才批量刷盘。 如果这期间机器断电（不是进程退出，是整机掉电），这批消息就没了。publisher confirm 会等到真正落盘后才返回， 所以开了 confirm 才是真的安全——这也是 confirm 会拖慢吞吐的原因。

要跨机器容灾，用 quorum queue（基于 Raft，多副本、写多数派才确认）。它是 3.8+ 的推荐做法， 已取代旧的 classic mirrored queue（后者在网络分区时有已知的数据丢失风险，4.0 起被移除）。 代价是延迟更高、内存占用更大，且不支持优先级队列等少数特性。

05 / 消费侧

三个旋钮，决定你的消费者好不好用

ack 模式管「丢不丢」，prefetch 管「快不快、稳不稳」，并发数管「扛不扛得住」。

旋钮一

ack 模式

auto_ack=True：消息一送出 broker 就删除，消费者崩了就没了。只适合可丢的心跳、埋点。

manual ack：处理完再 basic_ack。这是生产环境的唯一正确选择。

旋钮二

prefetch (QoS)

basic_qos(prefetch_count=N)：每个消费者最多同时持有 N 条未 ack 的消息。

默认是无限——broker 会把队列里的消息一股脑推给第一个连上来的消费者。

旋钮三

并发与预取的关系

经验值：prefetch ≈ 消费者线程数 × 1.5 ~ 2。

任务重（秒级）取 1~5；任务轻（毫秒级）可取 100+，否则网络往返成为瓶颈。

看看 prefetch 是怎么把快消费者饿死的

为什么 RabbitMQ 能做到这种精细调度，Kafka 不能？ 因为 Kafka 的并行度上限是分区数，一个分区只能被同一消费组里的一个消费者读，且消费进度是一个单调递增的 offset； 而 RabbitMQ 的队列可以挂任意多个消费者，每条消息独立 ack，天然适合耗时不均的任务分发。 这正是「智能 broker」的价值所在。

06 / 进阶

死信队列，和用它拼出来的延迟队列

DLX 是 RabbitMQ 里复用度最高的一个机制：它既是错误兜底，也是延迟消息的实现基础。

消息在三种情况下会变成死信（dead letter），被自动转投到队列声明时指定的 x-dead-letter-exchange：

被拒绝

NACK / REJECT · requeue=false

消费者明确说「这条我处理不了，别再给我」。这是最常用的入口。

过期

TTL EXPIRED

消息或队列设置了 x-message-ttl，在队列里躺够了时间还没被消费。

队列满了

MAX-LENGTH EXCEEDED

队列设了 x-max-length，新消息挤掉了最老的消息。

所以延迟队列怎么落地

方案 A · 固定档位队列：为每种延迟时长建一个队列（5s / 1min / 30min / 24h），各自 TTL 固定。避开队头阻塞，代价是档位不灵活。

方案 B · 官方插件：装 rabbitmq_delayed_message_exchange，声明 x-delayed-message 类型的 exchange，发消息时带 x-delay header，任意延迟。消息在 exchange 里等待（存在 Mnesia），代价是不适合海量延迟消息、且插件消息不参与镜像/仲裁复制。

死信队列的正确用法

不要在消费失败时 requeue=true。如果失败是确定性的（比如脏数据解析不了）， 消息会立刻回到队列、立刻再被投递、再失败——形成毫秒级死循环，CPU 打满，日志刷屏。

正确姿势：本地重试 2~3 次（带退避），仍失败就 basic_nack(requeue=False) 让它进 DLX。 死信队列要配监控告警，它不是垃圾桶，是待人工处理的收件箱。

08 / 取舍

什么时候别用 RabbitMQ

跟 Kafka 的差别不是「谁更快」，而是两种根本不同的模型：队列与日志。

维度RabbitMQ（队列模型）Kafka（日志模型）
消息消费后 ack 之后从队列删除，不可回放 按保留期留在磁盘上，任意消费组可从任意 offset 重读
路由能力 强。exchange + binding 可表达复杂的分发拓扑 弱。生产者直接写指定 topic/partition，路由逻辑在应用层
并行度 一个队列可挂任意多个消费者，逐条竞争 受分区数限制，一个分区同组内只能一个消费者
顺序保证 单队列单消费者才有序；多消费者立即失序 分区内严格有序，是它的核心卖点
吞吐量级 万～十万 msg/s，消息通常较小、有单条业务含义 百万 msg/s，为顺序批量写盘优化
典型场景 任务分发、RPC 解耦、延迟任务、复杂事件路由、需要逐条重试的业务 日志采集、埋点流、数据管道、流式计算、事件溯源
运维心智 Erlang 生态，管理界面友好，队列堆积很直观 需要理解分区、副本、ISR、rebalance，门槛更高
选 RabbitMQ

当你的消息是「任务」

每条消息代表一件必须被某一个工人做完的事，处理耗时不均，失败要单独重试， 不同类型的事要发给不同的工人组。典型：发短信、生成报表、图片转码、订单超时关闭。

选 Kafka

当你的消息是「事实流」

每条消息是一个不可变的事件，可能有多个互不相干的下游各读各的， 将来还可能新增一个下游要从头重放。典型：用户行为埋点、数据库 CDC、监控指标。

还有一类情况是两个都不选： 如果你只有一个服务、任务量每天几千条、且能容忍延迟——数据库里加一张 tasks 表 + 定时轮询， 比引入一个需要高可用运维的中间件划算得多。MQ 的复杂度是有成本的，别为了「架构看起来正规」而付费。

09 / 验证

五分钟跑通最小可验证例子

包含了上文所有关键防护：持久化、publisher confirm、mandatory、手动 ack、prefetch、DLX。

# 带管理界面的官方镜像，管理台 http://localhost:15672 （guest/guest）
docker run -d --name rabbit \
  -p 5672:5672 -p 15672:15672 \
  rabbitmq:3.13-management

pip install pika
import pika, json

conn = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
ch = conn.channel()

# 1. 拓扑：业务 exchange + 死信 exchange
ch.exchange_declare("orders", "topic", durable=True)
ch.exchange_declare("orders.dlx", "fanout", durable=True)

ch.queue_declare("q.order.email", durable=True, arguments={
    "x-dead-letter-exchange": "orders.dlx",   # 处理不了的进死信
})
ch.queue_declare("q.order.dead", durable=True)

ch.queue_bind("q.order.email", "orders", "order.created.#")
ch.queue_bind("q.order.dead", "orders.dlx", "")

# 2. 打开 publisher confirm：publish 会阻塞到 broker 确认落盘
ch.confirm_delivery()

def send(rk, body):
    try:
        ch.basic_publish(
            exchange="orders", routing_key=rk,
            body=json.dumps(body),
            properties=pika.BasicProperties(
                delivery_mode=2,            # 消息持久化
                message_id=body["order_id"],  # 供消费端幂等去重
            ),
            mandatory=True,                  # 路由不到就退回，而不是静默丢弃
        )
        print("confirmed:", rk)
    except pika.exceptions.UnroutableError:
        print("！路由落空，没有队列接收:", rk)
    except pika.exceptions.NackError:
        print("！broker 拒绝了这条消息:", rk)

send("order.created.vip", {"order_id": "A1001", "amount": 99})
send("order.paid",        {"order_id": "A1002"})  # 没有队列绑定它 → 会被退回
conn.close()
import pika, json, time

conn = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
ch = conn.channel()

# 关键：限制未 ack 的消息数，让快的消费者能多干活
ch.basic_qos(prefetch_count=5)

seen = set()  # 真实项目里换成 Redis / 唯一索引

def on_message(ch_, method, props, body):
    mid = props.message_id
    if mid in seen:                       # 幂等：at-least-once 必然有重复
        ch_.basic_ack(method.delivery_tag)
        return
    try:
        data = json.loads(body)
        print("处理中", data)
        time.sleep(1)
        seen.add(mid)
        ch_.basic_ack(method.delivery_tag)     # 处理完才确认
    except Exception as e:
        print("失败，投递到死信:", e)
        ch_.basic_nack(method.delivery_tag,
                       requeue=False)         # 不 requeue，避免死循环

ch.basic_consume("q.order.email", on_message,
                 auto_ack=False)              # 手动 ack
print("waiting...")
ch.start_consuming()
# A. 看队列深度与未 ack 数（ready = 待投递，unacked = 已投递未确认）
docker exec rabbit rabbitmqctl list_queues name messages_ready messages_unacknowledged

# B. 看路由表：哪个 exchange 通过什么 key 绑到哪个队列
docker exec rabbit rabbitmqctl list_bindings

# C. 亲手验证「不 ack 会怎样」
#    1) 启动 consumer.py，让它开始 sleep
#    2) 立刻 Ctrl-C 杀掉它
#    3) 再跑 A，会看到 unacked 归零、ready 变回 1 —— 消息被自动重新投递了
#    4) 把 auto_ack 改成 True 重做一遍，消息直接消失，这就是「丢消息」

# D. 验证持久化：重启 broker，消息应该还在
docker restart rabbit && sleep 15
docker exec rabbit rabbitmqctl list_queues name messages
#    把 durable=True 或 delivery_mode=2 去掉任意一个再试，队列或消息就没了

# E. 观察 producer 输出：order.paid 那条会打印「路由落空」
#    这就是 mandatory 的价值 —— 不开的话你永远不知道它消失了

C 和 E 这两步一定要亲手做一遍。 「消息被自动重投」和「消息静默消失」这两个现象，看一次比读十遍文档记得牢， 它们也是后面所有可靠性设计的直觉来源。

— / 上线前速查

把这张单子过一遍

  • exchange、queue 都声明了 durable=true，消息带 delivery_mode=2
  • 生产端开了 publisher confirm，并处理了 nack 分支（不是只 try/except 吞掉）
  • 发布带 mandatory=true 或 exchange 配了 alternate-exchange，路由落空不会无声消失
  • 消费端 auto_ack=false，业务处理完成后才 ack
  • 设置了合理的 prefetch_count，而不是用默认的无限预取
  • 消费逻辑幂等，有基于业务唯一键的去重
  • 失败路径是 nack(requeue=false) → DLX，不是无脑 requeue
  • 死信队列有监控告警，堆积时有人知道
  • 关键队列用 quorum queue，而不是单机队列或已废弃的镜像队列
  • 队列深度、unacked 数、连接数、内存/磁盘水位都进了监控面板
  • channel 不跨线程共享，连接有自动重连与拓扑重建逻辑
  • 压测过消费者全挂的场景：队列堆积到什么量级会触发内存告警、阻塞生产者
回到那句话 消息不是发给队列的，是发给 exchange 的。
路由由 broker 决定，可靠性由两端的确认共同保证，重复由你自己消化。
