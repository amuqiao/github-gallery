一文读懂 · DOCKER

把「在我机器上能跑」
变成「在哪都能跑」

Docker 做的事其实只有一件：把你的程序连同它依赖的一切打包成一个标准「集装箱」，然后在任何装了 Docker 的机器上，以完全相同的方式运行起来。

▼ 鲸鱼背上的每个货柜都可以点击 / 悬停，它们就是镜像的「层」

提示点一个货柜看看：一个 Docker 镜像不是一整块，而是像集装箱一样，一层一层码起来的。
01 · WHY

它为什么出现：一次经典的部署事故

你在自己电脑上写好了一个服务，测试全绿。部署到服务器上——启动失败。你没改一行代码，变的是「环境」。

💻 你的开发机macOS
  • Python 3.12
  • libssl 3.x
  • requests 2.31（虚拟环境里）
  • 环境变量 TZ=Asia/Shanghai
✓ 测试全部通过
🖥 生产服务器CentOS 7
  • Python 3.6（系统自带）
  • libssl 1.0（太旧）
  • requests 另一个项目装的 2.18
  • 环境变量 没配
✕ ImportError / SSL 握手失败

问题的本质：程序从来不是独立运行的，它依赖解释器版本、系统库、配置文件、环境变量……这些东西在每台机器上都可能不一样。传统做法是写一份部署文档、一台台机器手工对齐——慢、易错、还会互相污染（A 项目要 libssl 1.0，B 项目要 3.x，装在同一台机器上就打架，这就是「依赖地狱」）。

问题

「程序」和「它运行所需的环境」是分离的，环境靠人肉复现，必然漂移。

Docker 的答案

把程序 + 依赖 + 配置整体打包成镜像，运行时用容器把它和宿主机隔离开。环境跟着程序走。

边界

容器共享宿主机的内核——它隔离的是文件、进程、网络的「视图」，不是一台完整的虚拟电脑。这是理解后面一切的钥匙。

02 · MENTAL MODEL

两个词就够：镜像 是模板，容器 是实例

如果你写过面向对象的代码，这个类比一步到位：镜像（image）是类，容器（container）是对象。一个镜像可以 run 出任意多个互不干扰的容器。

镜像是一摞只读的「层」点击每一层

OS 基础层 alpine 的文件系统🔒 只读
运行时层 node 20🔒 只读
依赖层 npm ci 的产物🔒 只读
代码层 COPY 进来的源码🔒 只读
容器可写层 运行时才有✏️ 可写

↖ 点左边任意一层

镜像 = 下面四层只读层叠加后的结果。启动容器时，Docker 在最上面「盖」一层薄薄的可写层——容器里所有的修改都只发生在这一层。

所以：删掉容器 = 扔掉可写层，镜像毫发无损；同一镜像跑 100 个容器，只读层只存一份。

💡 分层带来两个实惠：① 省空间——10 个基于 node:20-alpine 的镜像共享同一份基础层，不会存 10 遍；② 省时间——重新构建 / 拉取时，没变的层直接用缓存，只传输变了的层。
03 · HOW IT WORKS

拆开看：容器其实是「戴着 VR 眼镜的普通进程」

Docker 没有发明黑魔法。容器就是宿主机上的一个普通 Linux 进程，只是内核用三样现成的技术骗了它，让它「以为」自己独占一台机器。

命名空间（namespaces）负责「隔离视野」。内核给容器进程发了一副 VR 眼镜：pid 命名空间让它只能看到自己的进程（自己就是 1 号进程）；net 命名空间给它独立的网卡和 IP；mnt 命名空间给它独立的文件系统视图；还有主机名、用户、进程间通信等，各管一摊。

验证：在容器里执行 ps aux，只能看到寥寥几个进程；而在宿主机上执行 ps aux，能直接看到容器里的进程——因为它本来就是宿主机的进程之一。

控制组（cgroups）负责「限制用量」。光隔离视野还不够——一个失控的容器可能吃光整机的 CPU 和内存。cgroups 给每个容器划定资源配额：docker run --memory=512m --cpus=1.5 就是在设置 cgroup，超过内存上限的容器会被内核直接杀掉（OOM Kill）。

一句话分工：namespaces 管「能看见什么」，cgroups 管「能用多少」。

联合文件系统（UnionFS，如 overlay2）负责「把层叠成一个整体」。上一节说的「层」如何变成容器里那个看起来完整的文件系统？UnionFS 把多个只读层 + 一个可写层「叠」在一起，向上呈现为单一目录。读文件时从上往下找，谁在上层用谁的；写文件时把原文件复制到可写层再改（copy-on-write），下面的只读层永远不动。

这解释了为什么容器里 rm -rf 也伤不到镜像，以及为什么删容器后改动会消失。

和虚拟机到底差在哪？

关键差别：虚拟机为每个实例虚拟出整套硬件 + 完整客户机操作系统，隔离最彻底但笨重；容器共享宿主机内核，只隔离用户态，所以秒级启动、以 MB 计——代价是隔离强度更弱，且 Linux 容器只能跑在 Linux 内核上（Mac/Windows 上的 Docker Desktop 其实是先起了一个 Linux 虚拟机再在里面跑容器）。

04 · WHAT HAPPENS

按下回车之后：docker run 的 5 步

这是你会敲的第一条命令。点「下一步」，看它在幕后经过了哪些角色。

$ docker run -d -p 8080:80 nginx
docker CLI你敲命令的地方
▶
dockerd 守护进程真正干活的后台服务
▶
Registry (Docker Hub)镜像仓库，像 npm / 应用商店
本地镜像 nginx只读的层
▶
容器镜像 + 可写层 + 隔离的进程
▶
端口映射 8080→80外界流量的入口

记住分工：CLI 只是遥控器，dockerd 才是引擎；镜像不在本地就去 Registry 拉；容器 = 镜像之上盖一层可写层，再套上 namespace / cgroup 启动进程。

05 · BUILD

镜像从哪来：Dockerfile，环境的「源代码」

镜像不是手工捏的，而是由一份叫 Dockerfile 的脚本描述、用 docker build 构建出来的。环境从此变成可版本控制、可评审、可复现的代码。悬停 / 点击每一行看解释。

Dockerfile · 一个最小的 Node 服务
1FROM node:20-alpine基础层
2WORKDIR /app元数据
3COPY package*.json ./新的层
4RUN npm ci --omit=dev新的层
5COPY . .新的层
6EXPOSE 3000元数据
7CMD ["node", "server.js"]元数据

← 点左边任意一行

每条 FROM / COPY / RUN 都会生成一个新的只读层；WORKDIR / EXPOSE / CMD 只是记录元数据，不产生层。

🎯 想一想：为什么第 3~4 行不直接写成 COPY . . 然后再 npm ci？点第 3 行找答案。

构建 → 推送 → 运行：完整闭环

$ docker build -t myapp:1.0 . # 按 Dockerfile 逐行构建，每层都有缓存
$ docker push registry.example.com/myapp:1.0 # 推到镜像仓库
$ docker run -d -p 3000:3000 registry.example.com/myapp:1.0 # 任何机器，一行启动

这就是 Docker 口号 Build once, run anywhere 的落点：交付物从「代码 + 部署文档」变成了「一个自带环境的镜像」。

07 · DATA & NETWORK

两个必踩的坑：数据放哪，端口怎么通

容器是「用完即弃」的，但数据和流量不能跟着一起消失。两个机制各解决一半：

数据卷 Volume：数据活得比容器久

可写层随容器删除而消失，所以数据库这类有状态数据必须挂到容器外面。Volume 把宿主机的存储「挂载」进容器路径，容器删一百次，数据都还在。

容器 /var/lib/mysql⇄volume: mydata
容器可以随意重建 ↑ 数据独立存续
$ docker run -d -v mydata:/var/lib/mysql mysql:8

端口映射 -p：给隔离的网络开门

容器有自己的网络命名空间，外界默认访问不到它。-p 宿主机端口:容器端口 在两者之间搭一座桥。

宿主机 :8080→容器 :80 (nginx)
浏览器访问 localhost:8080 ↑ 流量被转发进容器
$ docker run -d -p 8080:80 nginx
08 · MYTHS

五个最常见的误区（点卡片翻面）

误区 1
「容器就是轻量级虚拟机」
点击翻面 →
不是。虚拟机虚拟硬件、各带一个完整 OS；容器只是被 namespace/cgroup 包装的宿主机进程，共享同一个内核。这决定了容器更快更省，但隔离强度也更弱。
误区 2
「我在容器里改了文件，镜像就变了」
点击翻面 →
不会。所有修改都发生在容器的可写层，镜像的只读层永远不变。想把改动固化下来，正确姿势是改 Dockerfile 重新 build（而不是 docker commit——它能用但不可复现，仅适合临时调试）。
误区 3
「数据放容器里就行了」
点击翻面 →
危险。docker rm 会连可写层一起删掉。任何需要持久化的数据（数据库、上传文件、日志）都应该挂 volume。把容器当随时可丢弃的进程看待，是使用 Docker 的核心纪律。
误区 4
「latest 标签 = 最新版，很安全」
点击翻面 →
latest 只是个默认标签名，不保证是最新，更不保证不变——今天和下个月拉到的 nginx:latest 可能完全不同，构建随之不可复现。生产环境永远钉住具体版本，如 nginx:1.27-alpine。
误区 5
「学 Docker = 学 Kubernetes」
点击翻面 →
是两层问题。Docker 解决「单机上如何打包和运行一个容器」；当容器多到要跨机器调度、扩缩容、自愈时，才轮到 Kubernetes。先把单机容器玩明白，K8s 的概念都建立在这之上。
辨析
「镜像」和「容器」我还是会说混
点击翻面 →
一句口诀：镜像是安装包，容器是运行中的程序。镜像可以 push/pull/build，容器可以 start/stop/exec。docker rmi 删镜像，docker rm 删容器——命令都分成两套。

什么时候该用，什么时候别硬用

✓ 适合

  • 交付 Web 服务 / API / 后台任务，保证环境一致
  • 本地一键起依赖：数据库、Redis、消息队列，用完就删
  • CI/CD 流水线：构建、测试都在干净的容器里跑
  • 微服务：每个服务独立打包、独立部署
  • 复现别人的项目 / 论文环境

✕ 不适合 / 需三思

  • 桌面 GUI 应用（技术上可行，但体验别扭）
  • 需要不同内核的程序：Linux 容器跑不了 Windows 程序
  • 把容器当强安全边界的多租户场景（共享内核，逃逸面比 VM 大）
  • 对性能 / 硬件有极端要求且不接受任何抽象层的场景
  • 数据没挂卷就跑有状态服务（不是不能，是别裸跑）

容易混淆的三兄弟

Docker单机上打包（build）、分发（push/pull）、运行（run）容器。本文主角。
Docker Compose还是单机，但用一个 compose.yaml 声明多个容器（如 web + db + cache），一条 docker compose up 全部拉起。
Kubernetes跨一群机器编排容器：调度、扩缩容、故障自愈、滚动发布。规模上去了才需要。
09 · TRY IT

10 分钟最小验证：亲手跑一遍闭环

读懂不等于会用。装好 Docker 后（docker.com 下载 Docker Desktop，或 Linux 上装 docker-ce），照抄下面四步，每一步都能亲眼验证前文的结论。

跑起来：体验「拉取 → 创建 → 启动」

$ docker run -d --name web -p 8080:80 nginx
Unable to find image 'nginx:latest' locally ← 本地没有，去 Registry 拉
Status: Downloaded newer image ... ← 分层下载，能看到多个进度条

浏览器打开 localhost:8080，看到 nginx 欢迎页 → 端口映射生效。

钻进去：验证「容器只是被隔离的进程」

$ docker exec -it web sh
/ # ps aux # 只看得到 nginx 自己 → pid namespace
/ # hostname # 是一串容器 ID，不是你的机器名 → uts namespace

改一改再删掉：验证「可写层随容器消失」

/ # echo broken > /usr/share/nginx/html/index.html; exit
$ docker rm -f web # 删掉容器（改动一起没了）
$ docker run -d --name web -p 8080:80 nginx

再刷新 localhost:8080——欢迎页完好如初：镜像只读层从未被动过。

收尾：删干净

$ docker rm -f web && docker rmi nginx

机器上不留任何痕迹——这正是 Docker 相比「直接在系统里装一堆东西」最舒服的地方。

RECAP

带走这张心智地图

一句话定义容器 = 共享宿主机内核、被 namespace 隔离视野、被 cgroup 限制用量的普通进程。
核心类比镜像是类 / 安装包（只读、分层、可分发），容器是对象 / 运行实例（镜像 + 一层可写层）。
工作流Dockerfile 描述环境 → build 成镜像 → push 到仓库 → 任何机器 pull + run。环境即代码。
两条纪律容器随时可丢弃：数据必须挂 volume；版本必须钉死 tag，别依赖 latest。
边界共享内核 ⇒ 跑不了异构系统、不是强安全边界；跨机器编排是 Kubernetes 的事。
