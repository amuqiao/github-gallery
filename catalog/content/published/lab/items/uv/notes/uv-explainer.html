uv

一个用 Rust 写的 Python 包与项目管理器：把 pip、venv、pyenv、pipx、poetry 的活儿收进一个二进制、一套命令，并且快一到两个数量级。

由 Astral（ruff 的作者）开发，2024 年发布，开源（MIT/Apache-2.0）。下面这个演示先给你一个直观感受——

重装一次中型项目的依赖，谁先跑完？

按官方基准的量级示意（依赖已在本机缓存过的常见场景），动画按比例加速播放。

pip + venv逐个下载、解压、拷贝
27 s
poetry自带解析器，仍是 Python 实现
17 s
uv命中全局缓存，硬链接落盘
0.4 s
01

它为什么出现：一个新人的第一天

想理解 uv，先回忆一下没有它的世界。

你入职第一天，克隆了项目仓库，README 写着：

# 1. 先安装 pyenv，然后装对 Python 版本
pyenv install 3.11.9 && pyenv local 3.11.9
# 2. 创建虚拟环境并记得激活（每次开终端都要记得！）
python -m venv .venv && source .venv/bin/activate
# 3. 装依赖……哦对，还有 dev 依赖是另一个文件
pip install -r requirements.txt -r requirements-dev.txt

每一步都有翻车点：系统里装了三个 Python 不知道用哪个；忘了 activate 把包装进了全局环境；requirements.txt 和同事机器上实际装的版本早就漂移了。

问题的本质：Python 官方只提供了两块底层积木——pip 负责装包、venv 负责隔离。而「一个工程从创建到复现」的完整闭环，长期靠社区工具东拼西凑，每个工具解决一小块，彼此还要互相配合：

pip安装包慢；本身没有锁文件概念
venv / virtualenv隔离环境要手动创建、手动激活
pyenv管理多个 Python 版本编译安装慢，shim 机制易出玄学问题
pip-tools把宽松依赖编译成精确锁定又一个要学的工具，且只锁单平台
pipx隔离安装命令行工具只管工具，不管项目
poetry / PDM项目管理 + 锁文件不管 Python 版本本身；解析速度一般

uv —— 一个二进制，全部接管

  • 装包（兼容接口）uv pip install
  • 隔离环境自动创建 .venv
  • Python 版本uv python install
  • 锁定依赖uv.lock（自动维护）
  • 命令行工具uvx / uv tool
  • 项目管理uv init / add / run / sync
边界先说清：uv 统一的是 Python 生态内的工程工作流。它不做两件事：① 不替代 conda 的跨语言二进制分发；② 它默认也不是构建后端——打包发布时它调用标准后端，而不是取而代之。
02

心智模型：三个文件，一条单行道

记住这张图，uv 的所有命令都只是在这条流水线上推动数据。

意图 · 手写

pyproject.toml

你想要什么。只写直接依赖和宽松范围，例如 requests>=2.31。这是唯一需要人来编辑的文件（通常也由 uv add 代劳）。

resolve
事实 · 机器生成

uv.lock

解析后的精确答案：每个包（含传递依赖）的确切版本与哈希。跨平台通用，提交进 git，团队人人复现同一环境。

sync
落地 · 可丢弃

.venv/

按 lock 真正装好的包。它只是缓存产物：删掉随时能秒级重建，永远不进 git。

数据只朝一个方向流：意图 → 事实 → 落地。你改了 pyproject.toml，uv 就重新解析出 uv.lock，再把 .venv 对齐到 lock。反过来永远不会发生——环境里手动装的东西不会「回写」到声明里，所以环境永远可解释、可复现。

更妙的是这条流水线是自动的：每次 uv run 之前，uv 会闪电般检查三者是否一致，不一致就先对齐再运行。所以在 uv 的世界里，「忘了装依赖」「忘了激活环境」这两类事故在结构上消失了。

一句话心法：pyproject.toml 是你写给机器的愿望清单，uv.lock 是机器给出的精确答卷，.venv 只是答卷的一份打印件。打印件脏了就撕掉重印，没人会心疼。
03

五步上手：一个最小可验证的项目

点击步骤切换，左边是你敲的命令，右边是磁盘上真实发生的事。全程没有一次 source activate。

创建项目骨架

$ uv init hello && cd hello

一条命令生成标准项目：pyproject.toml 声明元信息，.python-version 钉住解释器版本（本例为 3.13）。注意此刻还没有虚拟环境——uv 按需才创建。

✓ 验证：打开 pyproject.toml，能看到 [project] 段和空的 dependencies = []。

磁盘上

hello/
├── pyproject.toml
├── .python-version
├── main.py
└── README.md

添加第一个依赖

$ uv add requests
Creating virtual environment at: .venv
Resolved 6 packages in 121ms
Installed 5 packages in 18ms

一条命令连做四件事：写入 pyproject.toml → 解析全部依赖生成 uv.lock → 自动创建 .venv → 安装。18ms 装完，是因为包来自全局缓存的硬链接。

✓ 验证：pyproject.toml 里多了 "requests>=2.32.4"，且出现了 uv.lock。

磁盘上

hello/
├── pyproject.toml ← 依赖 +1
├── uv.lock ← 精确锁定 6 个包
├── .venv/ ← 自动创建
├── .python-version
├── main.py
└── README.md

运行代码，无需激活

# main.py 里写：import requests; print(requests.get("https://httpbin.org/ip").json())
$ uv run main.py
{'origin': '203.0.113.7'}

uv run 是「在本项目环境里执行」的统一入口。它运行前会自动校验 lock 和 .venv 是否最新，不新就先对齐——所以它永远不会用错环境。

✓ 验证：直接运行 python main.py（不带 uv）会报 ModuleNotFoundError，因为你的全局 Python 依然干净——隔离生效了。

uv run 背后

① 读 .python-version → 需要 3.13？
　 没有就自动下载
② uv.lock 和 pyproject 一致？
　 不一致就重新 resolve
③ .venv 和 uv.lock 一致？
　 不一致就增量 sync
④ 在 .venv 里执行命令 ✓

队友一条命令复现

$ git clone …/hello && cd hello
$ uv sync
Using CPython 3.13.5
Creating virtual environment at: .venv
Installed 5 packages in 22ms

队友机器上哪怕连 Python 3.13 都没有也不要紧：uv 会自动下载一个独立的解释器，再按 uv.lock 里的精确版本还原环境。README 里那五行祈祷文，变成了一行。

✓ 验证：两台机器上 uv pip list 输出逐字节相同。

复现三要素（都在 git 里）

.python-version → 解释器版本
pyproject.toml → 依赖意图
uv.lock → 精确事实

.venv/ 不进 git， 本地按需重建

日常维护的三板斧

$ uv add --dev pytest # 开发依赖，进 dev 分组
$ uv lock --upgrade # 升级锁文件到范围内最新
$ uv remove requests # 卸载并同步清理

开发依赖（测试、格式化工具）用 --dev 与生产依赖分组管理；升级不是散弹枪式的 pip install -U，而是先改 lock、再同步，每次变更都留在 git diff 里可审查。

✓ 验证：uv tree 一眼看清整棵依赖树是谁引入了谁。

常见搭配

uv run pytest → 跑测试
uv tree → 查依赖来源
uv export > requirements.txt
　 → 给旧系统一个台阶
04

为什么这么快：不是魔法，是四个工程决定

「快 10~100 倍」听起来像营销话术，拆开看其实每一条都很朴素。

①

Rust 编译产物

pip 每次启动都要先拉起一个 Python 解释器再解释执行自己；uv 是原生二进制，敲下回车的瞬间已经在干活。

②

全局缓存 + 硬链接

每个包全机只存一份，「安装」退化为创建硬链接。这是热缓存下 0.x 秒的最大功臣。

③

激进并行 + 按需元数据

下载、解压全并行；解析时用 HTTP Range 只抓 wheel 里几 KB 的 METADATA 文件，而不是把整个包拖下来看一眼。

④

PubGrub 解析器

现代版本解析算法：冲突时快速定位根因，报错信息直接告诉你「谁和谁打架」。

图解全局缓存：第二个项目装 numpy 时发生了什么

对比：pip 会把包完整拷贝进每个 venv——10 个项目就是 10 份 torch，磁盘和时间双输。uv 的缓存偶尔清理用 uv cache clean 即可。

05

项目之外：另外四个高频场景

uv 的野心不止于「更快的 poetry」。这四个能力各自替掉了一个老工具。

不安装，直接用 —— 替代 pipx

想用 ruff 检查一下代码、用 httpie 发个请求，但不想让它们污染任何环境？uvx 在临时隔离环境里跑完即走（有缓存，第二次几乎瞬时）：

$ uvx ruff check . # 用完即弃
$ uvx --from httpie http GET httpbin.org/ip
$ uv tool install ruff # 常用的就常驻安装，全局可用且互相隔离

心智区分：依赖用 uv add（进项目），工具用 uvx / uv tool（不进项目）。

连解释器也归它管 —— 替代 pyenv

uv 直接下载预编译的独立 Python，不用等本机编译半小时，也永远不会弄坏系统自带的 Python：

$ uv python install 3.12 3.13 # 并排安装多个版本
$ uv python pin 3.12 # 写入 .python-version，钉住本项目
$ uv run --python 3.13 main.py # 临时换个版本试试

配合 Step 4 看到的行为：队友没装对应版本时，uv sync 会自动补齐——「装 Python」从入职仪式变成了透明细节。

一个 .py 文件就是一个完整应用 —— PEP 723

写个抓数据的小脚本要发给同事，以前得附一份「先建 venv 再装这三个包」的说明。现在把依赖声明在脚本头部注释里（标准语法，非 uv 私有）：

# fetch.py
# /// script
# requires-python = ">=3.12"
# dependencies = ["requests", "rich"]
# ///
import requests
…
$ uv run fetch.py # uv 读到声明，自动建临时环境并运行
$ uv add --script fetch.py polars # 给脚本加依赖也有专门命令

收到文件的人只需要装了 uv——脚本自己会解释自己需要什么。这是「把脚本发给别人」体验上最大的一次进步。

不想改工作流？只换引擎 —— uv pip

老项目、CI 脚本、教程照抄的命令,可以原样保留,只在前面加 uv 两个字母,立刻获得同样的速度:

$ uv venv # 代替 python -m venv .venv
$ uv pip install -r requirements.txt # 接口兼容 pip
$ uv pip compile requirements.in -o requirements.txt # 代替 pip-tools

这是给存量世界的渐进迁移通道：先当快版 pip 用，尝到甜头再整体切到 uv add / run / sync 的项目模式。注意两套接口别混用管理同一件事（见下面的误区 ③）。

07

五个最常见的误区

点开每一条。它们几乎覆盖了新手前两周会踩的所有坑。

误区 ①「uv 是一套新的包格式 / 新的软件源吧？」
事实：uv 用的仍是 PyPI、仍是标准的 wheel 和 sdist，私有源、镜像源照常配置。它换掉的是客户端工具，不是生态本身——所以任何能用 pip 装的包，uv 都能装，反之亦然。这也是它能被快速采用的关键：迁移没有生态风险。
误区 ②「那我还要不要 source .venv/bin/activate？」
事实：不需要。uv run xxx 已经等价于「激活 → 执行 → 退出」。.venv 还在老地方，你想手动激活也完全可以（IDE 选解释器时就指向它），但日常心智可以简化为：项目里的一切命令都加 uv run 前缀。
误区 ③「uv add 和 uv pip install 差不多吧，随便用哪个？」
事实：层级完全不同。uv add 走项目流水线：写 pyproject.toml → 更新 uv.lock → 同步环境，变更可追溯；uv pip install 是底层兼容接口,只把包塞进当前环境,声明和锁文件毫不知情——下次 uv sync（默认精确对齐）还可能把它清掉。管理项目请始终用 uv add/remove,把 uv pip 留给临时实验和旧流程。
误区 ④「lock 文件是生成的，就不用提交 git 了」
事实：恰恰相反——应用项目必须提交 uv.lock,这是「所有人、CI、生产环境装到完全相同版本」的唯一凭证。例外是发布到 PyPI 的库:库的版本约束应该宽松（由使用者的项目去锁定）,此时 lock 只对库自己的 CI 有意义,提交与否团队自定。
误区 ⑤「requirements.txt 可以进博物馆了」
事实：在你的团队内部,是的;但世界上还有大量部署平台、Docker 基础镜像、安全扫描器只认 requirements.txt。所以 uv 提供 uv export --format requirements.txt:内部用现代工作流,对外随时导出一份兼容格式。新旧世界不冲突。
08

带走这张速查表

按场景分组。前两组覆盖 90% 的日常。

▸ 项目起步

  • 新建项目uv init myapp
  • 加依赖 / 开发依赖uv add requests · uv add --dev pytest
  • 克隆后复现环境uv sync
  • 运行任何命令uv run main.py · uv run pytest

▸ 日常维护

  • 看依赖树（谁引入的谁）uv tree
  • 升级全部 / 单个依赖uv lock --upgrade · uv lock --upgrade-package requests
  • 移除依赖uv remove requests
  • 导出兼容格式uv export --format requirements.txt

▸ 工具与脚本

  • 临时跑一个 CLI 工具uvx ruff check .
  • 常驻安装工具uv tool install ruff
  • 跑带内联依赖的脚本uv run script.py
  • 给脚本加依赖uv add --script script.py rich

▸ Python 版本与救火

  • 安装 / 钉住 Pythonuv python install 3.13 · uv python pin 3.13
  • 看有哪些解释器uv python list
  • 缓存占用 / 清理uv cache dir · uv cache clean
  • 环境彻底坏了rm -rf .venv && uv sync（放心删，秒级重建）
迁移心法（收尾）：存量项目先用 uv pip 换引擎尝甜头 → 新项目直接 uv init 走三件套 → 团队约定「一切命令过 uv run」。当你发现自己已经一个月没输入过 source activate,迁移就完成了。
