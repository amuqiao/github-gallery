它不是队列,
是一盘只增不删的日志磁带

进入 Kafka 世界前先扔掉"消息队列"的直觉:消息不因消费而删除,消费者只是拿着一个书签(offset)在磁带上移动。读懂"日志 + 书签"这两个词,Kafka 的一切设计都会变得顺理成章。

它为什么出现:N×M 的数据管道灾难

Kafka 诞生于 2010 年的 LinkedIn。当时的问题不是"发消息",而是数据搬运:页面点击、日志、指标等十几个数据源,要送进搜索、监控、数仓、推荐等十几个下游系统。点对点地接,就是 N×M 条各自为政的管道:

改造前:每对系统一条专线,N 个源 × M 个下游 = 几十条脆弱管道 点击流 ──┬──▶ 数仓 改造后:所有系统只对接一条"中央日志" 应用日志 ─┼──▶ 监控 订单事件 ─┼──▶ 搜索 源们 ──▶ ┃K a f k a 日志┃ ──▶ 下游们 ...... ─┴──▶ 推荐 (写一次) (各自按需读、互不干扰)

要当好这根"中央数据总管",必须同时满足三个当时的消息队列给不了的条件:①吞吐够大(每秒百万条事件);②数据可保留可重放(新上线的下游要能从头补数据);③下游互不影响(数仓读得慢,不能拖累监控)。Kafka 的答案是回到一个古老的结构——追加日志(append-only log),数据库 WAL 用了几十年的东西,把它拆分、复制、暴露成服务。

核心模型:Topic = 分成几段的日志

Topic "orders"(逻辑名)= 3 个 partition(物理日志,可分布在不同机器) partition-0 │ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │◀─ 追加 ── 同一 partition 内严格有序 partition-1 │ 0 │ 1 │ 2 │ 3 │◀─ 追加 ── partition 之间没有顺序保证 partition-2 │ 0 │ 1 │ 2 │ 3 │ 4 │◀─ 追加 ── 消息按 key 哈希选 partition ▲ 消费者的 offset(书签)只前进不删数据;数据按时间/大小策略过期(如保留 7 天)

四个概念一次立稳:

概念它是什么关键推论
Partition真正的日志文件,只能追加并行度的单位:分区越多,能同时读写的"车道"越多
Offset消息在分区内的序号,也是消费者的书签消费 = 移书签。书签归你管,所以重放 = 把书签拨回去
Key可选的消息键,同 key 必进同分区用 user_id 做 key,同一用户的事件天然有序
Retention数据按时间/大小过期,与消费无关"被消费了"和"被删除了"彻底解耦,一份数据服务无数下游

消费组:分区怎么分给消费者

组内扩容的规则只有一条:一个分区同一时刻只属于组内一个消费者(独占),一个消费者可以负责多个分区。拖动下面的人数,看分配如何变化:

消费组内的消费者数量: 2 (topic 固定 3 个分区)

重要推论:分区数是消费并行度的天花板。3 个分区的 topic,组里挂 10 个消费者,7 个只能干瞪眼。所以分区数要按目标吞吐预估、宁多勿少——分区数只能加不能减,且改分区数会打乱 key 的哈希分布。另外,消费者加入/退出会触发重平衡(rebalance),期间整组短暂停止消费,频繁重启消费者是生产常见的性能坑。

为什么快:把随机 IO 变成顺序 IO

Kafka 数据落磁盘却能跑出百万级 QPS,不靠魔法,靠四个"顺着硬件脾气来"的决定:

手段原理
顺序写日志只追加不改写。磁盘顺序写的速度(数百 MB/s)接近内存,慢的从来是随机 IO,不是磁盘本身。
页缓存读写都走操作系统 Page Cache,不自建进程内缓存。热数据的读基本命中内存,还免了 GC 压力。
零拷贝消费时用 sendfile 让数据从页缓存直达网卡,跳过"内核→用户态→内核"的两次搬运。
批量 + 压缩生产者攒一批一起发,整批压缩;consumer 也整批拉。摊薄每条消息的网络与系统调用成本。

反过来读这张表更有收获:Kafka 快,是因为它放弃了逐条消息的花活——没有逐条路由、没有逐条删除、没有优先级插队。简单的数据结构换来了极端的吞吐,这正是它与 RabbitMQ 分道扬镳的地方。

不丢数据:副本、ISR 与 acks

每个分区有多个副本(replica)分布在不同 broker 上:一个 leader 负责读写,其余 follower 拉取同步。追得上 leader 的副本集合叫 ISR(In-Sync Replicas)。leader 挂了,从 ISR 里选新 leader——这是高可用的基础。

交付语义速记:默认配置是 at-least-once(至少一次,可能重复)→ 消费端要幂等;acks=0 滑向 at-most-once(可能丢);开启幂等生产者 + 事务才能到 exactly-once(限 Kafka 内部流转)。和 RabbitMQ 一样,那个等式仍然成立:可靠 = 至少一次 + 消费幂等。

误区、反例与边界

误区①:"Kafka 消息是有序的"
只在单个 partition 内有序。跨分区没有任何顺序保证。需要"同一订单的事件有序",就用订单 ID 做 key;需要全局有序,只能单分区——同时也就放弃了并行,吞吐退化,这种需求要先质疑自己。
误区②:"消费过的消息就没了 / 堆积了要赶紧扩队列"
消息按 retention 过期,与消费无关。所谓"堆积"在 Kafka 里叫 lag(书签落后最新 offset 的距离),数据本来就躺在磁盘上,lag 大不会压垮 broker——但意味着下游处理不过来,该扩的是消费者(以及提前留够的分区数)。
误区③:"Kafka 更先进,所以任何 MQ 场景都该用它"
Kafka 缺少任务队列的精细工具:没有逐条 ack(只有 offset 提交,跳过失败消息很别扭)、没有原生死信/延迟/优先级、消费并行度被分区数锁死。"给每个订单发一封邮件、失败重试三次进死信"这种任务分发场景,RabbitMQ 顺手得多。Kafka 的主场是事件流:日志管道、埋点、CDC、流计算源头、事件溯源。
误区④:"随便什么规模都值得上 Kafka"
Kafka 是分布式系统,分区规划、副本、rebalance、监控 lag,运维成本实打实。每秒几百条消息的业务,一个 RabbitMQ 甚至一张数据库表就够了。选型的第一问永远是:我真的有"流"吗,还是只有几个异步任务?
一张表收尾:Kafka vs RabbitMQ 心智对照
KafkaRabbitMQ
本质分布式日志(留存+重放)消息分拣站(路由+确认)
消息生命周期按时间过期,消费不删消费确认即删
消费单位分区独占 + offset 书签队列内竞争 + 逐条 ack
擅长高吞吐事件流、重放、多下游任务分发、灵活路由、死信/延迟
一句话"发生过什么"的事实账本"要去办什么"的待办派发

命令行上手:5 分钟验证日志模型

# 起一个单机 Kafka(KRaft 模式,无需 ZooKeeper)
docker run -d --name kafka -p 9092:9092 apache/kafka:latest

# 1. 建一个 3 分区的 topic —— 对应沙盘里的三条日志
kafka-topics.sh --create --topic orders --partitions 3 \
  --bootstrap-server localhost:9092

# 2. 带 key 生产:同 key 必进同分区(验证沙盘结论①)
kafka-console-producer.sh --topic orders --bootstrap-server localhost:9092 \
  --property parse.key=true --property key.separator=:
> user-A:下单
> user-A:支付
> user-B:下单

# 3. 用消费组 g1 消费,然后 Ctrl-C 再重跑 —— 从书签处继续,不重复
kafka-console-consumer.sh --topic orders --group g1 \
  --bootstrap-server localhost:9092

# 4. 换个组名 g2 并 --from-beginning —— 同一份数据完整再读一遍(结论②③)
kafka-console-consumer.sh --topic orders --group g2 --from-beginning \
  --bootstrap-server localhost:9092

# 5. 看两组各自的书签(offset)和落后量(lag)
kafka-consumer-groups.sh --describe --group g1 --bootstrap-server localhost:9092
迁移清单:接手任何用 Kafka 的系统,先问这 5 个问题

① 每个 topic 的分区数、key 策略是什么(有序性靠什么保证)?② retention 设多久,谁依赖重放?③ 有哪几个消费组,各自 lag 多少?④ 生产端 acks/幂等开没开,消费端怎么做幂等?⑤ 副本因子和 min.insync.replicas 配了几?——答完这五问,这套事件流的可靠性边界就清楚了。
