一文读懂 · TEMPORAL · DURABLE EXECUTION

进程会死，流程不会。

扣款成功了，但服务器在发货前崩溃了——这是分布式系统里最经典的噩梦。Temporal 的答案是把「可靠的多步业务流程」写成一段普通的顺序代码：崩溃、重启、断网、等 30 天，它都能从断点精确恢复。下面这个演示就是它的全部秘密，请随时按下红色按钮。

注：本文讲的是工作流引擎 temporal.io。如果你在找 JavaScript 新的日期时间 API Temporal，那是另一个同名的东西。

    § 1

    它解决什么问题

    先看清痛点，再谈机制。

    一个再普通不过的订单流程：扣款 → 预留库存 → 创建物流单 → 通知用户。难点从来不是写这四步，而是回答四个问题：第 2 步失败了怎么重试？重试多次仍失败，第 1 步的钱怎么退（补偿）？机器在第 3 步之前断电，怎么知道“已经扣过款了”？如果第 4 步要等 7 天后再发一封提醒邮件呢？

    传统做法是把流程拆碎，塞进一堆基础设施里：

    传统拼装：流程被打碎在 5 个地方

    订单服务
    发起扣款，写“进行中”
    消息队列 (MQ)
    解耦各步骤
    库存消费者
    收消息，更新状态表
    DB 状态机表
    status = 'PAID' ?
    cron 补偿任务
    扫“卡住”的单子
    重试 + 死信队列
    失败消息去哪了？

    业务逻辑（先后顺序、重试、补偿、超时）散落在生产者、消费者、状态表和定时任务里。没有一处代码能读出完整流程，每个箭头都是一个可能丢状态的缝隙。

    Temporal：流程就是一个函数

    async function orderWorkflow(order) { await charge(order); // 自动重试 await reserveStock(order); // 失败可补偿 await ship(order); await sleep('7 days'); // 真的等 7 天 await notify(order); }

    顺序、重试、补偿、定时器全部回到代码里，用 if / for / try-catch 表达。崩溃了？换台机器接着跑，就像什么都没发生过。

    这种能力有个名字：Durable Execution（持久执行）——函数的执行状态不依赖任何一台机器的存活。听起来像魔法，机制其实只有两个词：事件溯源 + 重放。

    § 2

    核心机制：Event History + Replay

    理解了这一节，你就理解了 Temporal 的一切。

    Temporal 把代码分成两种角色：

    Workflow（工作流）——编排逻辑本身。它必须是确定性的：同样的输入、同样的历史，重跑一遍必须走到完全相同的地方。它不做任何真实的副作用。

    Activity（活动）——所有“会碰真实世界”的操作：调支付 API、写数据库、发邮件。Activity 允许失败，由 Temporal 按策略自动重试；它的返回值会被记录进 Event History。

    每当 Workflow 走一步——调了哪个 Activity、拿到什么结果、定时器何时到期——Temporal Server 就往这条流程的 Event History（事件历史）里追加一条记录。这份 History 存在数据库里，它才是流程的真身；内存里跑着的那个函数只是它的投影。

    于是崩溃恢复变成了一件机械的事——重放（Replay）。切换下面的开关，看同一段代码在两种情形下的行为：

    async function orderWorkflow(order) {
    await charge(order);
    await reserveStock(order);
    await ship(order); // ← 💥 上一个 Worker 死在这里
    await notify(order);
    }

    重放时代码逐行重新运行，但每个 await activity() 都不再真的发请求，而是从 History 里取出当年的结果立刻返回——几毫秒内函数就“快进”回崩溃点，局部变量、调用栈、循环进度全部原样重建，然后继续向前。这也解释了 sleep('30 days') 为什么不浪费：定时器是 History 里的一条事件，由 Server 持久保管，等待期间 Workflow 直接从内存卸载，不占任何线程；到点后被唤醒、重放、继续。上百万个沉睡中的流程，成本几乎为零。

    § 3

    三个角色，一条铁律

    谁存状态，谁跑代码。

    你的代码

    Client / Starter

    • 发起流程：start(orderWorkflow)
    • 发信号、查状态、拿结果
    • 嵌在你的 API 服务里
    ⇄gRPC
    Temporal Server（自建或 Cloud）

    调度与记账中枢

    • 持久化每条流程的 Event History
    • 管理 Task Queue（任务队列）
    • 持久定时器、自动重试、超时判定
    • 从不执行你的任何代码
    ⇄长轮询
    你的代码

    Worker（可以很多个）

    • 从队列领任务
    • 执行 Workflow 与 Activity
    • 无状态，可随意重启、扩容
    铁律：Temporal Server 只存事件、派任务，你的代码、依赖、数据库密码永远只存在于你自己的 Worker 进程里。这也是它能安全使用 Temporal Cloud 的原因——云端只看得到事件流水，看不到业务实现。Worker 死了随便再拉一个，因为状态全在 History 里，Worker 本身一无所有。首屏演示里你杀掉的正是 Worker。
    § 4

    代价：Workflow 必须确定性

    重放的前提是“重跑一遍走同一条路”。

    Replay 机制有一个硬前提：拿着同一份 History 重放代码，必须走出一模一样的执行路径。如果 Workflow 里混进了每次运行结果不同的东西（随机数、当前时间、直接的网络请求），重放时代码会拐进另一条分支，和 History 对不上——Temporal 会直接抛出 non-determinism error。

    所以规则很简单：一切副作用进 Activity；Workflow 里的“时间”和“随机”用 SDK 提供的确定性替身。来做个小测验，下面这些代码能不能直接写在 Workflow 函数里？

    同一条铁律还有一个推论：改代码也是一种“不确定性”。线上还有跑到一半的旧流程时，如果新代码的执行路径变了，旧实例重放就会崩。Temporal 为此提供 patched() / Worker Versioning 等版本化机制——这是上手后绕不开的第一个进阶课题，先知道它存在即可。

    § 5

    最小可运行例子

    四个文件，就是首屏演示的真实代码（TypeScript SDK，Go/Java/Python 结构相同）。

    // 编排逻辑：确定性代码，跑在“沙箱”里
import { proxyActivities, sleep } from '@temporalio/workflow';
import type * as acts from './activities';

const { charge, reserveStock, ship, notify } =
  proxyActivities<typeof acts>({
    startToCloseTimeout: '30 seconds',
    retry: { maximumAttempts: 5 },   // 每个 Activity 自动重试
  });

export async function orderWorkflow(order: Order) {
  await charge(order);          // 每一步结果都写入 Event History
  await reserveStock(order);
  const tracking = await ship(order);
  await sleep('7 days');        // 持久定时器：重启也不会丢
  await notify(order.userId, tracking);
  return tracking;
}
    // 副作用都在这里：普通函数，随便用 fetch / DB / SDK
export async function charge(order: Order) {
  // 注意幂等：用 order.id 做支付去重键，重试才安全
  return paymentApi.charge({ idempotencyKey: order.id, ...order });
}
export async function reserveStock(order: Order) { /* ... */ }
export async function ship(order: Order) { /* ... */ }
export async function notify(userId: string, tk: string) { /* ... */ }
    // Worker：你部署的长驻进程，从队列领任务执行上面两种代码
import { Worker } from '@temporalio/worker';
import * as activities from './activities';

const worker = await Worker.create({
  workflowsPath: require.resolve('./workflows'),
  activities,
  taskQueue: 'orders',
});
await worker.run();   // 多起几个进程即水平扩容
    // 在你的 API 服务里发起一条流程
import { Client } from '@temporalio/client';

const client = new Client();
const handle = await client.workflow.start(orderWorkflow, {
  taskQueue: 'orders',
  workflowId: 'order-8102',   // 业务 ID = 天然去重
  args: [order],
});
// 之后随时：await handle.result() / handle.signal(...) / handle.query(...)

    本地体验只需 temporal server start-dev（官方 CLI 自带单机版 Server 和 Web UI），再 npm run worker 起 Worker。在 Web UI 里能看到每条流程的完整 Event History——和首屏演示右边那块一模一样。

    § 6

    和相近方案摆在一起

    名字都带“工作流”，定位差得很远。

    自己拼：MQ + 状态表 + cronAirflow / Dagster 类调度器Temporal
    定位通用积木数据管道（ETL / 批处理）业务流程 / 长事务的持久执行
    流程定义散落在多个服务与配置里静态 DAG，任务粒度是“作业”通用代码：if / for / try-catch 任意组合
    状态在哪你自己设计的状态表，缝隙多调度器元数据库（任务级）Event History，精确到每个函数调用
    崩溃之后靠补偿任务扫表“捞”回来重跑失败的任务节点重放，秒级回到崩溃前一行代码
    能等多久等待逻辑要自己持久化按调度周期（分钟级起步）毫秒到数月，可等外部信号（如“用户点了确认”）
    典型场景——每晚跑数、报表、ML 训练管道支付/订单 Saga、注册引导、资源开通、AI Agent 编排

    一句话区分：Airflow 编排“数据的批处理作业”，Temporal 编排“每一个用户/订单各自的业务流程实例”。前者一天跑一次 DAG；后者可能同时有一千万条各走到不同步骤的流程在“活着”。AWS Step Functions 与 Temporal 定位最接近，但它用 JSON 状态机描述流程且绑定 AWS，而 Temporal 用你熟悉的编程语言、可自托管。

    § 7

    五个常见误解

    点开每一条，都是新手真实踩过的坑。

    “Workflow 等待时占着一个线程，等 30 天太浪费了”

    不占。await sleep('30 days') 会在 History 里记一条 TimerStarted，然后这个 Workflow 就从 Worker 内存中整个卸载。到期时 Server 派发任务，任意一个 Worker 通过重放把它复活。“沉睡的流程”只是数据库里的几行记录。

    “Temporal Server 会运行我的代码，把代码传上去就行”

    Server 从不运行用户代码，它只是记账员 + 派单员。代码永远部署在你自己的 Worker 里——所以升级依赖、连接内网数据库、读密钥都和普通服务一样，Temporal Cloud 也碰不到你的业务逻辑。

    “有自动重试了，Activity 就不用考虑幂等”

    恰恰相反。重试意味着 Activity 是至少执行一次：如果 Worker 在“扣款成功、结果还没写回 History”的瞬间崩溃，恢复后这个 Activity 会整个重跑。所以碰钱、碰库存的 Activity 必须用幂等键（如订单 ID）去重。首屏演示里如果你在某步“执行中”时杀掉 Worker，就能看到这条提示。

    “Event History 想记多长记多长”

    有硬上限（约 51,200 条事件 / 50MB）。永续型流程（比如“用户的整个订阅生命周期”）要定期调用 continueAsNew：结束当前流程，带着精简后的状态开一条新 History 接着跑，像链表一样续下去。

    “它这么可靠，用来处理高吞吐数据流吧”

    方向错了。可靠性的代价是每一步都要持久化事件（单步几十毫秒级开销）。每秒百万条消息的流式处理是 Kafka / Flink 的地盘；Temporal 的账按“流程的步骤数”算，适合“单条流程很值钱、必须万无一失”的场景，而不是海量廉价事件。

    § 8

    什么时候该用，什么时候别用

    迁移判断标准，拿走即用。

    ✓ 强信号：上 Temporal

    • 跨多个服务、必须最终完成的流程：支付、退款、订单履约（Saga 补偿用 try-catch 写）
    • 流程里有长时间等待：等人工审批、等回调、等 7 天后发提醒
    • 注册引导、订阅计费周期、基础设施开通（provisioning）
    • AI Agent / LLM 多步任务：步骤贵、易失败、要断点续跑
    • 你正打算“加一张状态表 + 一个补偿 cron”——这就是信号本身

    ✕ 别硬套

    • 单次请求-响应、几十毫秒内要返回的同步路径（每步持久化有延迟开销）
    • 高吞吐事件流、日志管道 → Kafka / Flink
    • 面向数据表的定时批处理 → Airflow / Dagster 更顺手
    • 一个简单 cron 能解决的事——别为它引入一套集群
    • 团队无法承担新组件运维，又不接受托管云服务

    真实的代价清单：要么自建 Temporal 集群（Server + 数据库，需要运维），要么付费用 Temporal Cloud；团队要学会确定性约束和版本化（patched()）；每一步几十毫秒的事件写入开销；History 上限与 continueAsNew 的心智负担。换来的是：删掉状态表、补偿 cron、重试框架和它们之间所有对不上账的缝隙。流程越关键、越长、分支越多，这笔交换越划算。

    Temporal = 事件溯源 + 自动重放。
    它把“流程走到哪了”从每台机器的内存里拿走，变成一份谁都可以接着读的存档——于是进程的死活，第一次与流程的死活无关。
