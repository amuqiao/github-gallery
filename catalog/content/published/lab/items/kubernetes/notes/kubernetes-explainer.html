KUBERNETES · 容器编排

你只描述想要的世界,
Kubernetes 负责让世界变成那样。

Kubernetes(简称 K8s)不是"更高级的 Docker",而是一台永不停歇的调和机器:你提交期望状态,它持续对比实际状态,发现差异就动手修正。读懂这一句,就读懂了它的一切。

01 · 它为什么出现

从 1 台机器到 50 台机器,到底难在哪?

先看一个真实演化路径。你写了个 Web 服务,打成 Docker 镜像,docker run 跑在一台服务器上——一切都好。业务增长后,你有了 50 台机器、200 个容器,这时"跑容器"本身依然简单,难的全是围绕它的运维问题:

  • 放哪儿? 新容器该部署到哪台机器?哪台内存还够?
  • 挂了谁管? 半夜某台机器宕机,上面 12 个容器谁来发现、谁来在别处重启?
  • 怎么找到彼此? 容器重启后 IP 变了,调用它的其他服务怎么办?
  • 怎么发版? 200 个容器滚动升级、出问题回滚,手工操作要多久?
  • 怎么扩缩容? 大促要从 20 副本扩到 200,过后再缩回来。

这些问题合起来叫容器编排(orchestration)。K8s 是 Google 基于内部 Borg 系统十几年经验做的开源答案,2014 年发布后成为事实标准。

它的边界:管什么,不管什么

✓ K8s 负责

容器的调度(放到哪台机器)、生命周期(挂了重建、按需扩缩)、服务发现与负载均衡、滚动更新与回滚、配置与存储的抽象。

✗ K8s 不负责

构建镜像(那是 Docker/CI 的事)、写代码、数据库本身的高可用逻辑、开箱即用的监控告警。它是平台的地基,不是拎包入住的 PaaS。

02 · 核心心智模型

声明式 API + 控制循环:K8s 唯一需要背下来的原理

面对上面那堆问题,有两种思路。第一种是命令式:写脚本,一步步告诉系统"做什么"。第二种是 K8s 选的声明式:只告诉系统"我要什么",让系统自己想办法。

命令式 描述动作

"在机器 A、B、C 上各启动 1 个容器。"

机器 B 挂了?脚本早就跑完退出了,没人知道、没人补救。你得再写监控脚本、重启脚本、扩容脚本……每种意外都要一段新逻辑。

声明式 描述结果

"我要 replicas: 3,任何时刻都保持 3 个副本在跑。"

机器挂了、Pod 被误删、有人手动多开了一个——系统持续对比现实与目标,自动把现实掰回来。意外不需要逐个编程。

实现声明式的引擎叫控制循环(control loop / reconciliation loop),原理和家里的恒温器一模一样:你设 26℃(期望),温度计读 29℃(实际),空调启动制冷(调和动作),循环往复,永不下班。

记住一条铁律:所有组件都只和 apiserver 对话,彼此从不直接通信。scheduler 不会打电话给 kubelet,它只是把"这个 Pod 去 Node-A"写进 apiserver;Node-A 的 kubelet 一直在 watch apiserver,看到与自己有关的变更就去执行。这种"以状态为中心、以 watch 为纽带"的松耦合,正是几十个控制循环能各自独立、互不踩踏的原因。

06 · 核心对象

四个对象,覆盖 80% 的日常:Pod、Deployment、Service、ConfigMap

Pod:最小调度单位(它不是容器!)

Pod 是一个或多个容器的组合,组内容器共享同一个 IP、端口空间和存储卷,永远被调度到同一台机器。为什么不直接调度容器?因为有些进程天生要"贴身"部署——比如主应用旁挂一个日志收集 sidecar。90% 的 Pod 只有一个容器,但抽象层留出了余地。

Deployment → ReplicaSet → Pod:为什么隔了一层?

Deployment ← 你写 YAML 面对的对象

声明"我要哪个镜像、几个副本、怎么更新"。它不直接管 Pod,而是管理 ReplicaSet。

ReplicaSet ← 由 Deployment 自动创建

只干一件事:让符合 label 的 Pod 数量 == replicas。少了补、多了删。

Pod ×3 ← 由 ReplicaSet 自动创建

真正跑容器的地方,随时可被替换。

隔这一层是为了滚动更新:发新版时,Deployment 新建一个 ReplicaSet 逐步扩容,同时把旧 ReplicaSet 逐步缩容——拖动滑块体验一次发布:

rs-old (v1)
rs-new (v2)

回滚也因此变得廉价:旧 ReplicaSet 并没被删除,只是缩到了 0,kubectl rollout undo 就是把两边的数字再反着调一遍。

Service:给一群朝生暮死的 Pod 一个永久门牌

Pod 会不断被销毁重建,IP 说变就变,调用方不可能追着 IP 跑。Service 提供一个稳定的虚拟 IP 和 DNS 名(如 web.default.svc),并用 label selector 动态圈定后端:凡是带 app: web 标签的健康 Pod,自动成为流量目标。Pod 换了一批又一批,门牌号永远不变——这是"牲口不是宠物"能够成立的另一半拼图。

ConfigMap / Secret:把配置从镜像里拆出去

同一个镜像要跑在测试和生产,差异(数据库地址、密钥)不该烧进镜像。ConfigMap 存普通配置、Secret 存敏感信息,以环境变量或文件形式注入 Pod。镜像负责"程序",对象负责"环境",这才能做到一次构建、处处运行。

07 · 最小可验证实验

15 行 YAML,亲手复现本文所有结论

用 kind 或 minikube 在本机起个集群,保存下面文件为 web.yaml:

apiVersion: apps/v1
kind: Deployment          # 我声明的对象类型
metadata:
  name: web
spec:
  replicas: 3               # 期望状态:任何时刻 3 个副本
  selector:
    matchLabels: { app: web }  # RS 用这个标签认领 Pod
  template:                  # Pod 的模板
    metadata:
      labels: { app: web }
    spec:
      containers:
      - name: web
        image: nginx:1.27

然后依次执行,每一步都在验证前文的一个论断:

kubectl apply -f web.yaml        # 提交期望状态(第 05 节的旅程就此开始)
kubectl get deploy,rs,pods       # 看到三层对象:deploy → rs → 3 个 pod
kubectl delete pod <某个pod名>    # 杀一个 Pod……
kubectl get pods                 # 数量还是 3,但有个名字是新的(自愈!)
kubectl scale deploy web --replicas=5  # 改期望,现实随之而来
kubectl rollout status deploy web      # 观察调和过程收敛

如果 delete pod 之后副本数没有恢复,先怀疑自己删的是不是"裸 Pod"(没有控制器管的 Pod)——没有循环盯着的期望,不会自愈。

08 · 误区、对比与边界

最容易踩的 5 个坑,与"什么时候别用它"

"Pod 就是容器的别名吧?"
不是。Pod 是一组共享网络与存储的容器,是调度的原子单位。混淆的代价:多容器 Pod 里用 localhost 互访、探针作用在整个 Pod 等行为会让你莫名其妙。
"我删了 Pod,服务怎么还在跑?"
因为 ReplicaSet 控制循环立刻补了一个新的。想真正下线,要删除上层的 Deployment(即删除期望状态本身)。反过来这也是新手困惑"Pod 杀不死"的原因。
"Service 是一个负载均衡进程?"
ClusterIP 类型的 Service 不对应任何进程,它只是 kube-proxy 写在每台节点上的 iptables/IPVS 转发规则,那个虚拟 IP 甚至 ping 不通。这解释了为什么 Service 几乎没有性能瓶颈,也解释了为什么排查它要看规则而不是找进程。
"上了 K8s 就自动弹性扩缩容了?"
默认不会。K8s 只维持你声明的固定副本数;按 CPU/QPS 自动伸缩需要额外声明 HorizontalPodAutoscaler——它本质上也是一个控制循环,只不过它调和的对象是"replicas 这个数字本身"。
"K8s 是高级版 Docker,会取代它?"
两者是上下游而非竞争:Docker(或 buildkit)负责构建镜像,containerd 之类的 runtime 负责在单机跑容器,K8s 站在更上层,负责"很多机器上的很多容器"的编排。K8s 弃用的只是 Docker 作为 runtime 的历史包袱(dockershim),不是镜像生态。

横向对比:什么规模用什么工具

方案心智模型擅长不擅长
docker compose单机上的一组容器,命令式启停本地开发、单机小应用,分钟级上手✗ 跨机器、自愈、滚动发布
Kubernetes集群级期望状态 + 控制循环多机器、多团队、需要自愈与灰度的生产系统✗ 运维复杂度高,小项目属于用大炮打蚊子
Serverless (FaaS)只交函数,平台全权托管事件驱动、流量骤变、不想碰基础设施✗ 长连接、重状态、需要掌控运行环境的场景

什么时候不该用 K8s:个人项目、单机可承载的业务、团队没有专职运维精力时。K8s 用复杂度换弹性——你得先有"弹性"的问题,这笔交易才划算。一台 docker compose up -d 能解决的服务,引入 K8s 只会把故障面从应用扩大到平台本身。

带走的迁移工具:学任何 K8s 新概念,只问三个问题

HPA、Ingress、StatefulSet、CronJob、Operator……K8s 概念看似无穷,但全是同一模式的实例:

  1. 它声明了什么期望状态? (HPA:CPU 利用率维持 60%)
  2. 谁在负责调和? (HPA 控制器,跑在 controller-manager 里)
  3. 调和动作是什么? (修改 Deployment 的 replicas 字段,交给下游循环继续)

能回答这三问,这个概念你就"读懂"了;连自定义资源 + Operator(把运维经验写成你自己的控制循环)也不例外。
