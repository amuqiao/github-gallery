KUBERNETES · 一文读懂

你不是在指挥容器,
而是在声明世界应有的样子

半夜三点,一台服务器宕机,上面 12 个容器全灭。谁去发现?谁决定在哪台机器上重启?谁把流量切过去?Kubernetes 的回答是:没有"谁",只有一群永不停歇的控制循环。读完这一篇,你会带走它最核心的心智模型——声明式 API + 调谐循环(reconcile),并且知道它的边界在哪。

CARGO 01 · 它为什么出现

一台机器时岁月静好,二十台机器时问题爆炸

Docker 解决了"应用怎么打包、在一台机器上怎么跑"。但真实业务很快越过一台机器的边界——于是一批全新的问题冒出来,而且每一个都不是容器本身能回答的。

调度 SCHEDULING

50 个容器,20 台机器

哪个容器放哪台机器?要看剩余 CPU / 内存、亲和性、是否同一服务要分散防单点。人肉 Excel 排布,改一次崩溃一次。

自愈 SELF-HEALING

半夜挂了谁来救

进程崩了、机器宕了,得有人发现、有人在别处重启、有人把流量摘掉再挂回来。靠告警短信叫醒工程师,不可持续。

发布 ROLLOUT

更新 30 个实例不停机

逐台替换、失败回滚、新旧版本并存时流量怎么分。手写发布脚本,每家公司都写一遍,每遍都有坑。

扩缩容 SCALING

流量高峰 10 倍

大促前手动加机器、加实例、改负载均衡配置;凌晨再缩回去省钱。慢、易错、没人愿意值这个班。

服务发现 DISCOVERY

IP 一直在变

容器重启换 IP、换机器更换 IP。调用方写死 IP 列表必然过期,配置中心又是一套自建系统。

资源利用 BIN-PACKING

机器一半在空转

为了隔离,一个服务一组机器,利用率 15%。混部又怕互相打架——需要有资源配额与限制的统一裁判。

本质定位
这些问题的共性是:它们都发生在"多台机器 + 多个副本 + 持续变化"的场景里。Kubernetes 就是把这一整层问题打包解决的容器编排系统——它把一堆机器抽象成一台"大电脑",你只描述要跑什么,它负责放哪、挂了怎么办、流量怎么进来。它源自 Google 内部系统 Borg 十几年的实践,2014 年开源,如今是事实标准。
边界预告
反过来说:如果你只有一台服务器、三五个容器,上面这些问题你根本没有——那 docker compose 就够了,k8s 的复杂度是纯支出。边界问题我们在 第 08 节细算。
CARGO 02 · 核心心智模型

声明式 API + 调谐循环:整个 k8s 只有这一招

先对比两种思路。命令式是"告诉系统做什么动作",声明式是"告诉系统我要什么结果"。这不是语法风格差异,而是故障恢复能力的分水岭。

命令式 imperative

你下发动作序列,系统执行完就结束。执行过程中环境变了、执行后进程挂了,没有任何东西负责善后——因为你的意图没有被记录下来,系统不知道"应该有 3 个"。

# 在机器 A、B 上各启动一个,再来一个放 A ssh a docker run -d web:v1 ssh b docker run -d web:v1 ssh a docker run -d web:v1 # 半夜容器挂了?机器 b 宕了?——无事发生

声明式 declarative

你提交一份"期望状态"的描述并存进集群。它是持续有效的合同,而不是一次性命令:任何时刻实际状态偏离它,控制器都会自动把世界修回来。

# deploy.yaml:我要 3 个 web:v1 的副本,一直要 kubectl apply -f deploy.yaml # 容器挂了 → 自动补;机器宕了 → 挪到别处重建 # 改成 replicas: 5 再 apply → 自动补 2 个 # 你维护的是"目标",不是"过程"
一句话版本
k8s = 一个存放期望状态的数据库(通过 API Server 读写)+ 一群各管一摊的控制器(controller)。每个控制器死循环地做三件事:观测实际状态 → 比对期望状态 → 用最小动作消除差异。这个循环叫 reconcile(调谐)。副本数、调度、发布、扩缩容、DNS……全部是这一个模式的不同实例。

为什么这个设计能扛住混乱
控制器不记"我上次做了什么",每一轮都重新看世界、重新算差异(level-triggered,基于状态而非事件)。所以丢一条消息、控制器自己重启、动作执行到一半失败,都不要紧——下一轮循环会兜底。这是 k8s 在不可靠的分布式环境里保持稳健的根本原因,也是你读懂一切 k8s 组件的钥匙:看到任何组件,先问"它调谐的是什么差异"。
CARGO 03 · 架构

架构 = 一个中枢 + 一群循环

有了心智模型,架构图就不再是零件清单:控制平面(control plane)负责存放期望状态并运行各种控制器,工作节点(node)负责真正跑容器。所有组件只跟 API Server 说话,彼此从不直连。点击任意组件查看它调谐什么。

为什么一切都绕经 API Server?

单一入口意味着统一的认证、鉴权、准入校验、审计,以及最重要的:所有人看到同一份真相(etcd 里的状态)。组件间解耦为"都盯着同一块黑板",谁挂了重启后接着看黑板即可,不存在丢失的会话。

控制平面挂了,业务会挂吗?

不会立刻挂。节点上的 kubelet 和容器照常运行、流量照常转发——只是集群暂时失去"变更与自愈"能力:不能发布、Pod 挂了没人补。这正好印证:控制平面是"大脑",数据平面是"手脚",大脑短暂离线,手脚还在动。

CARGO 05 · 关键概念

对象为什么要分这么多层?

初学最劝退的就是:明明只想跑个容器,却冒出 Pod、ReplicaSet、Deployment、Service 四五个名词。其实每一层只回答一个问题,点击每一层看它存在的理由——理解了"为什么",名词就不用背了。

Deployment回答:怎么"换版本"?
管理版本与发布。你改了镜像版本再 apply,Deployment 不会粗暴地杀旧建新,而是创建一个新的 ReplicaSet,新的逐步扩、旧的逐步缩(滚动更新);出问题一条命令回滚——本质是把旧 ReplicaSet 的副本数再调回来。这就是为什么它不直接管 Pod:每个版本一个 ReplicaSet,版本历史被完整保留。日常工作里你 95% 的时间只跟 Deployment 打交道。
ReplicaSet回答:怎么"保持 N 个"?
管理副本数量。就是你在上面玩过的那个控制循环:通过 label selector 认领 Pod,少了补、多了删。它只认"数量",不懂"版本",所以发布逻辑放在它上面一层。你几乎不会手写 ReplicaSet——它是 Deployment 的实现细节,但理解它才能看懂 kubectl get rs 里那些名字带哈希的家伙。
Pod回答:什么是"一个实例"?
最小调度单位:一个或多个必须同生共死的容器,共享同一个 IP、localhost 和存储卷。为什么不用容器当最小单位?因为很多场景需要"贴身伙伴":主容器 + 日志收集 sidecar、主容器 + 代理。它们必须在同一台机器、同一网络里。Pod 是易逝的:重建后名字、IP 全变——所以别对着 Pod 编程。

▲ 记忆法:Deployment 管版本,ReplicaSet 管数量,Pod 管运行。同族亲戚:有状态应用用 StatefulSet(稳定的名字与存储),每节点一个的守护进程用 DaemonSet,一次性任务用 Job / CronJob——都是"某种控制器 + Pod 模板"这一个配方。

粘合剂:label 与 selector
层与层之间不是硬引用,而是标签匹配:Pod 身上贴 app: web,ReplicaSet 用 selector: app=web 认领它们,下一节的 Service 也用同样的方式挑选流量后端。松耦合意味着你可以给 Pod 打个新标签把它"摘出"排查问题,控制器会自动补一个新的顶上。
CARGO 06 · 流量入口

Pod 会死会换 IP,那请求发给谁?

上一节的结论是"别对着 Pod 编程"——它的 IP 随时会变。于是需要一个稳定的门牌:Service。它有一个不变的虚拟 IP 和 DNS 名字,用 label selector 实时圈定一批健康的 Pod,把到达的流量分发过去。

Service 同样是一个调谐循环:Endpoint 控制器持续把"selector 命中且 readiness 探针通过的 Pod IP"写入端点列表;每台节点上的 kube-proxy 再把这份列表变成本机的转发规则。Pod 生生死死,调用方始终只认 http://web 这个 DNS 名字。

从集群外进来:四种暴露方式

方式它是什么可从哪访问典型用途
ClusterIPService 默认类型集群内部虚拟 IP + DNS 名仅集群内服务间调用(绝大多数)
NodePortService 类型在每台节点开同一个高位端口(30000+)转发进来能连到任一节点 IP 的地方开发调试、简易暴露
LoadBalancerService 类型找云厂商申请一个真实负载均衡器和公网 IP公网云上暴露单个服务,一个服务一个 LB,费钱
Ingress独立对象,不是 Service 类型七层路由规则:按域名/路径把 HTTP 流量分发给不同 Service,需装 Ingress Controller(如 nginx)公网生产常态:一个入口托管 N 个服务
常见混淆
Service 的"负载均衡"只是每台机器上的转发规则(iptables/IPVS),不是一台中心化的 LB 设备;Ingress 不是 Service 的第四种类型,而是叠在 Service 之上的 HTTP 路由层。生产里最常见的组合:外部 LB → Ingress → 各服务的 ClusterIP → Pod。

CARGO 08 · 误区与边界

相近概念、常见误区与"什么时候别用它"

先横向对比一次定位,再逐个拆穿新手最容易踩的认知陷阱,最后把适用边界说清楚——工具的边界感,和工具本身一样重要。

维度docker rundocker composeKubernetes
作用域单容器单机、多容器多机集群
机器挂了全灭全灭Pod 在别的节点重建
进程挂了restart 策略可拉起同左,仅限本机调谐循环持续补齐副本
滚动发布 / 回滚手工基本靠脚本内建,一条命令
服务发现—单机内网络别名集群级 DNS + Service VIP
心智负担 / 运维成本极低低高,需要专门投入

一句话:compose 和 k8s 不是竞品,而是不同规模问题的答案。很多团队本地开发用 compose,生产用 k8s。

六个最常见的误区

误区 01“Pod 就是容器的别名”
Pod 是一组共享网络与存储的容器 + 最小调度单位。多数 Pod 确实只有一个容器,但"共享 localhost 的贴身伙伴"(sidecar)模式依赖这个抽象。推论:同一 Pod 里的容器不能各自伸缩、必然同机同生死。
误区 02“kubectl delete pod 可以下线服务”
你删的是实际状态,期望状态(Deployment)还写着 replicas: 3,控制器几秒内就补一个新的。这不是 bug,这正是系统在履行合同。想下线,改的是期望:kubectl delete deployment web 或把副本数调为 0。
误区 03“k8s 会自动帮我扩容”
默认不会。自动扩容是独立的控制器 HPA(HorizontalPodAutoscaler),而且它依赖你给容器声明了 resources.requests、装了 metrics 采集。没有这些前提,流量再大副本数也纹丝不动。同理,"资源隔离"也依赖你写 requests/limits——k8s 只裁判你声明过的东西。
误区 04“流量会自动避开有问题的实例”
Service 只摘除 readiness 探针失败的 Pod。你不配 readinessProbe,进程假死、还在启动预热,流量照样打过来。存活性(liveness,失败则重启容器)和就绪性(readiness,失败则摘流量)是两个探针、两种后果,生产必配。
误区 05“Pod 里写的文件,重启后还在”
Pod 是易逝的,容器文件系统随容器消失,emptyDir 卷随 Pod 消失。持久数据必须显式声明 PersistentVolumeClaim 挂载外部存储。心法:把 Pod 当牲畜,不当宠物——任何"这个 Pod 有点特殊"的念头都是架构隐患。
误区 06“组件之间互相调用,像微服务一样”
恰恰相反:scheduler 不调用 kubelet,controller 不调用 scheduler,它们只读写 API Server 上的状态,通过 watch 各自认领差异。理解这一点,你才能解释为什么组件可以任意重启而集群不乱——状态在黑板上,不在谁的内存里。

适用边界:先自检,再上船

✓ 适合上 k8s

· 多台机器、多个服务、副本数 ≥ 两位数
· 需要频繁不停机发布、快速回滚
· 需要故障自愈与弹性伸缩,SLA 有要求
· 团队有(或愿意培养)专门的平台运维投入
· 想要一套跨云厂商的统一部署语言

✗ 先别上 k8s

· 单机能扛的个人项目、内部小工具 → docker compose
· 不想管任何基础设施 → PaaS / Serverless(如 Cloud Run、Fly.io)
· 团队没人能值守集群本身——k8s 把"运维应用"变成了"运维平台",这层成本不会消失,只会转移
· 强单机性能、极简依赖的场景(如嵌入式、桌面软件)

取舍的实话
k8s 用前期复杂度换后期确定性:YAML 多、概念多、排障链路长,但换来的是"任何公司、任何云、任何规模,部署语言一致,故障处理自动化"。规模不到,这笔交换是亏的;规模到了,它几乎是唯一标准答案。托管服务(EKS / GKE / ACK)能帮你抹掉控制平面的运维,但抹不掉概念本身的学习成本——所以才有这篇文章。
CARGO 09 · 迁移与下一步

把这个模型带走,它比 k8s 本身更值钱

"声明期望 + 循环调谐"不只是 k8s 的实现细节,它是驯服复杂分布式系统的一种通用范式,你会在越来越多的地方认出它。

k8s 内部的复用

HPA 调谐"负载 vs 副本数",cluster-autoscaler 调谐"待调度 Pod vs 节点数",证书轮转、DNS 记录……全是同一个循环换了比对对象。看到新组件,先问:它调谐什么差异?

Operator 模式

你可以自定义资源(CRD)+ 自写控制器,把"运维一个数据库集群"的专家经验写成调谐循环——声明 kind: PostgresCluster,控制器负责建库、备份、故障切换。这是 k8s 从"跑容器"进化成"平台的平台"的原因。

GitOps

把"期望状态"再往外推一层:YAML 全部进 Git,集群里的 Argo CD / Flux 调谐"Git 里的声明 vs 集群现状"。发布 = 提交 PR,回滚 = git revert,审计 = git log。同一个模型,套娃使用。
