> 01  从一个真实需求开始

下单成功之后，还有一堆事要做

用户点了「提交订单」。主流程写完数据库就该返回了，但后面还挂着一串杂活：发短信、加积分、通知仓库、写数据报表。 这些事不该卡住用户的那 200 毫秒，于是你想到把它们丢到队列里慢慢做。

此刻你的系统里已经有一台 Redis 在做缓存。要不要为了这个需求单独搭一套 Kafka 或 RabbitMQ？ 大多数团队的第一反应是：先用 Redis 顶一下。这个判断通常是对的 —— 但「用 Redis 顶一下」有好几种写法， 它们在正常情况下表现一模一样，只有在出事的时候才会露出差别。

A LIST

LPUSH 生产，BRPOP 消费。 五分钟能上线，是绝大多数人的起点。

B PUB/SUB

PUBLISH 广播，多个订阅者同时收到。 听起来更像「消息队列」，其实陷阱最深。

C STREAM

XADD 追加，消费者组分发 + XACK 确认。 Redis 5.0 才有，命令多，但把前两者的坑都补上了。

本文要回答的问题

这三条路各自的投递语义是什么？为什么 Redis 已经有了 List 和 Pub/Sub，还要在 5.0 再造一个 Stream？ 以及最实际的：你的场景该选哪个，以及选完之后有哪些坑在等你。

> 02  先把 Redis 本身的心智模型建对

它不是「缓存」，是一台跑在内存里的数据结构服务器

很多人对 Redis 的印象停在「一个远程的 HashMap」。这个印象会让你在读到 Stream 时完全无法理解它为什么长这样。 换成下面这个模型，后面的一切都会顺：

① key 指向的是「结构」，不是「字符串」

每个 key 背后可以是 string、list、hash、set、zset、stream…… 服务端认识这些结构，于是你可以只推入一个元素、只读一段范围，而不必把整个值拉回本地改完再写回。 网络往返从 N 次变成 1 次 —— 这才是 Redis 快的真正原因之一。

② 命令在一条线程上排队执行

Redis 用 I/O 多路复用接收成千上万个连接，但命令的执行是串行的。 这意味着每条命令天然原子，不需要加锁； 也意味着任何一条 O(N) 的大命令都会卡住所有人。 （6.0 之后的多线程只负责网络收发和协议解析，执行仍是单线程。）

DEMO  三个客户端同时发命令，会发生什么
单线程执行队列
并发到达 → 排队 → 逐条执行
记住这一句

「命令串行」是 Redis 一切设计的地基。 正因为串行，BRPOP 才敢保证一条消息只会给一个消费者； 也正因为串行，Stream 才能用一个简单的自增 ID 保证全局有序，不需要任何分布式共识。

> 03  List：一根两头都能进出的管子

把它想成双端队列，而不是数组

Redis List 的心智模型只有一句话：一个有序的元素序列，两端的插入和弹出都是 O(1)，中间的随机访问是 O(N)。 所有命令的名字都在提示你这件事 —— 以 L 开头的操作左端（Left / head）， 以 R 开头的操作右端（Right / tail）。

底层是什么

早期是 ziplist（小列表）和 linkedlist（大列表）两种编码，3.2 之后统一成 quicklist： 一个由若干「压缩小块」串起来的双向链表。所以它既有链表的两端 O(1)，又不至于为每个元素付出一个完整节点的内存开销。 你不需要记住细节，只需要记住结论：两端快，中间慢，元素本身按插入顺序排列。

动手推一推：List 操作台

点下面的命令按钮，观察元素在两端进出。重点体会两组对比：LPUSH + RPOP 组成先进先出的队列，LPUSH + LPOP 则组成后进先出的栈； 以及 BRPOP 在列表为空时会「挂起」而不是返回 nil。

List 真正好用的几个场景

简单任务队列

生产者 LPUSH，消费者 BRPOP 阻塞等待。 不用轮询，不用锁，一条消息只会被一个消费者拿到。

生产者> LPUSH orders '{"id":1001}' 消费者> BRPOP orders 0 # 0 = 一直等

固定长度的最新 N 条

写入后立刻裁剪，天然是一个「只保留最近 100 条」的环形缓冲， 适合做操作日志、最近浏览、简易时间线。

LPUSH user:1:feed "item" LTRIM user:1:feed 0 99 # 只留 100 条
一个立刻能用上的改进

如果你正在用 BRPOP 做队列，把它换成 BLMOVE source dest RIGHT LEFT 0。 它在弹出的同一个原子操作里，把消息放进一个「处理中」列表：

1> BLMOVE orders orders:processing RIGHT LEFT 0 # 取出，同时留底 2> # ... 业务处理 ... 3> LREM orders:processing 1 "$msg" # 处理成功才删掉

这就是所谓的 reliable queue 模式。它能救回崩溃时丢的消息，但你要自己写一个扫描 orders:processing 的超时重投程序 —— 而这，正是 Stream 的消费者组内置替你做好的事。 （旧代码里的 RPOPLPUSH / BRPOPLPUSH 是同样的东西，6.2 之后已标记为废弃。）

> 04  边界：List 做队列，会在哪一秒出事

「弹出即删除」是它的全部优点，也是它的全部问题

BRPOP 返回的那一刻，这条消息在 Redis 里已经不存在了。它现在只活在你的进程内存里。 接下来发生的任何意外 —— 进程被 OOM Killer 杀掉、机器断电、一次没接住的异常 —— 都会让它永久消失， 而且没有任何地方留下它存在过的痕迹。

A · LIST  BRPOP
1. 队列中有消息 job:42
2. c1 执行 BRPOP，拿到 job:42
3. Redis 中已无此消息，LLEN = 0
4. c1 处理到一半，进程崩溃 ✖
5. job:42 永久丢失，无人知情
B · STREAM  XREADGROUP
1. Stream 中有消息 1720-0
2. c1 读到它，同时写入 PEL（待确认列表）
3. 消息仍在 Stream 里，PEL 记着 c1 欠一笔
4. c1 处理到一半，进程崩溃 ✖
5. c2 用 XAUTOCLAIM 接管，继续处理 ✔

把三个缺口摆在一起看

List 做不到的事具体表现什么时候会咬你
消息不可重投 弹出即删除，没有确认机制，没有「处理中」状态 任何一次进程重启、部署、崩溃
无法多方消费 一条消息只能被一个客户端拿走；想让风控和报表各收一份，只能生产者写两个 key 下游系统从 1 个变成 3 个的那天
没有历史与位点 消费过的数据不存在了，不能回放，不能查「昨天那条消息到底发出去没有」 线上排查问题、需要重跑数据时

那 Pub/Sub 呢？

Pub/Sub 解决了「多方消费」：一次 PUBLISH，所有订阅者都收到。但它走向了另一个极端 —— 它是彻底的 fire-and-forget：消息不存储，谁在线谁收到，离线的订阅者什么都拿不到， 连「我错过了几条」都无从得知。客户端网络抖动 3 秒，这 3 秒的消息就凭空蒸发了。

判断口诀

需要可靠投递就别用 Pub/Sub，它适合的是「实时通知、丢了也无所谓」的场景： 在线状态推送、配置变更广播、聊天室在线消息。 （Redis 7 的 Sharded Pub/Sub 解决的是集群下的扩展性问题，不改变「不存储」这个本质。）

到这里，需求已经很清楚了：我们想要一个东西，既像 List 一样能可靠地把任务分给一组 worker， 又像 Pub/Sub 一样支持多方独立消费，还得把消息留下来能回看。 2018 年 Redis 5.0 给出的答案，就是 Stream。

> 05  Stream：一条只能往后写的账本

它借来了日志的抽象，而不是队列的抽象

List 的模型是「容器」：东西放进去、拿出来，拿走就没了。 Stream 的模型是账本：只能在末尾追加新的一行，已经写下的行不会因为「被读过」而消失， 每一行都有一个单调递增的编号。谁读到哪一行，是读者自己的事，记在读者名下。

这个差别听起来抽象，但它直接推导出 Stream 的所有能力： 因为数据留着，所以能回放、能查历史、能让多个消费者组各读各的； 因为有编号，所以「我读到哪了」可以被精确记录和恢复。这正是 Kafka 的核心思路，Redis 把它做成了一个 key 的类型。

先认识那个 ID

Stream 里每条消息的 ID 不是随便给的。把鼠标移到下面各部分（或用键盘 Tab 聚焦）看看它们分别是什么：

1720506000000 - 0
把指针移上去，看每一段的含义。

为什么必须单调递增

ID 决定了全局顺序，也决定了「读到哪了」这件事可以只用一个数表示。 Redis 会保证新 ID 一定大于当前最大 ID —— 即使服务器时钟回拨，它也会退化成只递增序列号，绝不倒退。 你几乎总是应该用 * 让 Redis 自动生成。

几个特殊 ID，读命令里天天见

- 和 +：最小 / 最大，用于 XRANGE 全量扫描。
$：当前最后一条，意思是「只给我之后的新消息」。
0：从头开始。
>：只在 XREADGROUP 里有效，意思是「组里还没分发给任何人的新消息」。

最小可验证例子：三条命令跑通一个 Stream

打开 redis-cli，逐行敲下去，注意每一步的返回值：

> XADD orders * id 1001 amount 59.9 "1720506000000-0" # 返回自动生成的 ID > XADD orders * id 1002 amount 12.0 "1720506000318-0" > XLEN orders (integer) 2 > XRANGE orders - + # 全量读，消息读完仍然留在 Stream 里 1) 1) "1720506000000-0" 2) 1) "id" 2) "1001" 3) "amount" 4) "59.9" 2) 1) "1720506000318-0" 2) 1) "id" 2) "1002" 3) "amount" 4) "12.0" > XLEN orders # 关键：读过之后长度没变 (integer) 2 # ← List 在这里会变成 0
这一行就是分水岭

读取不消费数据。 Stream 里删除数据只有两个途径：主动 XDEL，或者按容量/时间裁剪 XTRIM。 「读过了」和「可以删了」是两件完全独立的事 —— 这是理解 Stream 最重要的一句话。

每条消息是一组 field-value，不是一个字符串

XADD key * f1 v1 f2 v2 的结构类似一个小 hash。这鼓励你把消息写成结构化的字段， 而不是塞一坨 JSON 字符串。不过实践中两种都常见：字段多用于需要被消费者按需读取的场景， 单个 payload 字段塞 JSON 则更方便做版本演进。

> 06  消费者组：Stream 真正的核心机制

让一组 worker 分担一条流，还不丢消息

只用 XREAD 的话，Stream 只是个能回放的日志：每个客户端各读各的， 同一条消息所有人都会读到。要实现「一组 worker 分工处理、每条消息只处理一次」，就需要 consumer group。它引入了三个新东西：

last-delivered-id

组的游标。记录这个组已经把哪些消息发出去过了。 用 > 读取时，只会拿到游标之后的消息，然后游标前移。

PEL（Pending Entries List）

每个组维护的「已投递但未确认」清单。 记录了消息 ID、当前归属的消费者、投递时间、投递次数。它是可靠性的全部来源。

XACK

消费者处理成功后主动确认，这条记录才会从 PEL 移除。 不 ACK，它就一直挂在那里，等着被别人认领。

分步跑一遍：从投递到崩溃到接管

组内是分工，组间是广播

这是最容易搞混的一点。同一个组里的 c1、c2 竞争消息，每条只给一个人； 不同的组则各有各的游标和 PEL，同一条消息每个组都会收到一份。 所以「订单流同时给库存服务和风控服务」的正确做法是：建两个组。

XGROUP CREATE orders inventory 0 XGROUP CREATE orders riskctl 0 # 各读各的

崩溃恢复的两种姿势

消费者重启后，先用 XREADGROUP ... STREAMS orders 0 （注意是 0 不是 >）把自己 PEL 里的旧账捞回来重做； 对于再也起不来的消费者，则由存活的实例定期 XAUTOCLAIM 把超时未确认的消息接管过去。

# 接管 idle 超过 60s 的消息 XAUTOCLAIM orders g1 c1 60000 0 COUNT 10
别忽略这个字段

PEL 里的 delivery-count 会在每次被 claim 时加一。 如果某条消息反复被接管却始终没人 ACK，它大概率是一条能把消费者撑死的毒消息（poison message）。 生产代码里应该判断这个计数，超过阈值就 XACK 掉并转投死信队列，否则整个组会被它反复卡住。

Stream 的定位非常清楚：在你已有的 Redis 上，用最小的运维代价换到接近 Kafka 的消费语义。 它换不来的是 Kafka 的存储规模 —— 因为数据在内存里。 所以判断标准往往不是「哪个更强」，而是你的留存需求会不会撑爆内存。

> 08  那些看起来对、其实不对的说法

七个高频误区

点开每一条看看它错在哪。

Stream 的「持久」是相对 Pub/Sub 而言的：它把数据保存在内存里，落盘与否取决于你的 RDB / AOF 配置。 默认 appendfsync everysec 意味着断电最多丢一秒的写入；关掉 AOF 只用 RDB，能丢的更多。

还有一个更隐蔽的洞：主从复制是异步的。主节点 XADD 成功并返回给客户端后， 如果它在数据同步到从节点之前宕机、从节点被提升为主，这些消息就没了。这不是 Stream 的缺陷，而是 Redis 的整体架构决定的。

→ 需要金融级不丢，用真正的持久化消息中间件；用 Redis 就要接受这个概率并做好幂等与对账。

不是。设想：消费者处理完业务、还没来得及发 XACK 就崩了。这条消息仍在 PEL 里， 迟早会被别人接管并再处理一次。反过来，如果先 ACK 再处理，就变成了可能丢。

这不是 Redis 的问题 —— 任何跨进程的消息系统都无法在通用情况下白送你 exactly-once。

→ 正确姿势：接受 at-least-once，把消费逻辑做成幂等（用业务唯一键去重，或把「处理结果 + 已处理消息 ID」写在同一个数据库事务里）。

取决于你有没有写那个波浪号。MAXLEN 1000 是精确裁剪， 而 MAXLEN ~ 1000 是近似裁剪 —— 后者只在能整块删除底层节点时才动手， 实际长度可能是 1000 出头。

为什么要有近似模式？因为精确裁剪在极端情况下会退化成一次删很多条的 O(N) 操作， 而 Redis 是单线程的，这一下就会卡住所有客户端。

XADD orders MAXLEN ~ 10000 * id 1001 # 推荐：近似裁剪 XTRIM orders MINID ~ 1720506000000 # 也可按时间裁剪

→ 除非有硬性长度要求，一律用 ~。

完全不会。XACK 动的只是 PEL —— 它把「这条消息某人还欠着」这条记录抹掉， 消息本体原封不动留在 Stream 里。这也正是别的消费者组还能读到它的原因。

如果你从不 XTRIM，这个 key 会一直涨，直到吃光内存。 这是 Stream 在生产环境最常见的事故来源，没有之一。

→ 每个 XADD 都带上 MAXLEN ~ N，或者用定时任务按 MINID 裁掉过期数据。

PEL 也占内存，而且它只增不减直到消息被 ACK 或被 XACK 强制清掉。 一个只读不确认的消费者，能在几个小时里堆出几百万条 pending 记录。

更麻烦的是：即使你 XTRIM 掉了消息本体， 对应的 PEL 记录仍然存在（它们会变成指向不存在消息的「幽灵条目」，claim 时会被自动清理）。

XPENDING orders g1 # 概览：总数、最小/最大 ID、各消费者欠账 XPENDING orders g1 - + 10 c1 # 明细：ID、idle 时长、投递次数 XINFO GROUPS orders # 看每个组的 pending 与 lag

→ 把 XINFO GROUPS 的 pending 和 lag 接进监控，它比 QPS 更能提前发现问题。

不成立。List 在两类场景里仍然是更好的选择：

一是它根本不是队列的时候。「最近浏览的 20 个商品」「一个用户的操作栈」这类需求， List + LTRIM 就是最省事的数据结构，用 Stream 反而要自己处理裁剪和读取语义。

二是极简的一次性任务分发。没有多消费方、丢一条也无所谓、追求最低延迟和最小内存开销时， BRPOP 的开销和心智负担都比消费者组小得多。Stream 的每条消息要额外存 ID、field 结构和可能的 PEL 记录，内存占用明显更高。

→ 选择的依据是「消息丢了会不会有人来找你」，而不是「哪个更新」。

可以写，但不会阻塞。BRPOP、BLMOVE、 XREAD BLOCK 在 MULTI/EXEC 里执行时，行为会退化成非阻塞版本 —— 因为 Redis 是单线程的，让一条命令在事务中间挂起，等于让整个服务器停摆。

同理，任何 O(N) 的大命令都要警惕：LRANGE mylist 0 -1 在一个百万元素的 list 上执行， 会让所有其他客户端等它。

→ 阻塞留给单条命令；批量读取用小 COUNT 分页；线上禁用 KEYS 这类全扫命令。

命令速查

LPUSH / RPUSH key v [v ...]
从左 / 右插入，返回插入后的长度
LPOP / RPOP key [count]
从左 / 右弹出，弹出即删除
BRPOP key [key ...] timeout
阻塞版弹出，timeout 为 0 表示一直等；可同时监听多个 key
BLMOVE src dst RIGHT LEFT 0
阻塞弹出并原子地转移到另一个 list，实现可靠队列的关键
LMPOP / BLMPOP numkeys key ... LEFT
7.0 新增，一次从多个 key 中的第一个非空 list 弹出
LRANGE key start stop
读取区间，不删除；大 list 上是 O(N)，慎用 0 -1
LTRIM key start stop
只保留区间内的元素，其余全部删除，做定长列表用
LLEN / LINDEX / LSET / LREM
长度 / 按下标读 / 按下标写 / 按值删除（后三个都是 O(N)）
XADD key [MAXLEN ~ N] * f v [f v ...]
追加一条，* 表示自动生成 ID；顺手裁剪是好习惯
XLEN / XRANGE key - + [COUNT n]
长度 / 按 ID 区间读取，读取不消费；XREVRANGE 反向读
XREAD [BLOCK ms] STREAMS key $
不带组的读取，各读各的，$ 表示只要新消息
XGROUP CREATE key group 0 | $ [MKSTREAM]
建组。0 = 从头消费，$ = 只消费建组之后的新消息
XREADGROUP GROUP g c [BLOCK ms] STREAMS key >
> 取组内未分发的新消息；换成 0 则取自己 PEL 里的旧账
XACK key group id [id ...]
确认处理完成，从 PEL 移除（消息本体仍在 Stream 里）
XPENDING key group [- + n [consumer]]
查看待确认清单：idle 时长、投递次数、归属者
XAUTOCLAIM key group c min-idle-time 0
6.2 新增，批量接管超时未确认的消息（旧写法是 XCLAIM 逐条）
XTRIM key MAXLEN ~ N | MINID ~ id
按条数或时间裁剪，控制内存的唯一手段
XINFO STREAM / GROUPS / CONSUMERS key
运维必备：看长度、组游标、pending 与 lag

一份能直接改的消费循环骨架

# 1. 建组（已存在会报 BUSYGROUP，忽略即可） XGROUP CREATE orders g1 $ MKSTREAM # 2. 启动时先处理自己的旧账（崩溃重启后的第一件事） XREADGROUP GROUP g1 c1 COUNT 100 STREAMS orders 0 # 3. 主循环：阻塞读新消息 → 处理 → 确认 XREADGROUP GROUP g1 c1 BLOCK 5000 COUNT 10 STREAMS orders > XACK orders g1 <id> # 4. 后台定时：接管掉线消费者留下的消息 XAUTOCLAIM orders g1 c1 60000 0 COUNT 20 # 5. 后台定时（或写入时顺手）：控制内存 XTRIM orders MAXLEN ~ 1000000
最后收束成三句话

List 是容器，拿走就没了；Stream 是账本，读过也还在。
Stream 的可靠性全部来自 PEL —— 没有 XACK，就没有可靠投递；不做 XTRIM，就会吃光内存。
Redis 给你的是「够用的消息语义 + 零新增运维」，一旦留存需求超过内存，就该换 Kafka 了。
