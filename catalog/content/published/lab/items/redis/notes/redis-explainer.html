一文读懂 · REDIS

把热数据放进内存,
让读写快一万倍

Redis 不是"更快的 MySQL",而是一个用内存换速度、用数据结构换表达力的存储。理解它的第一步,是先感受内存和磁盘之间那道数量级的鸿沟。

↑ 延迟标尺(对数刻度):每向右一格,慢 10 倍以上 — 悬停查看换算
亲手跑一次:1000 个请求,内存 vs 磁盘数据库
Redis(内存,~0.1ms/次)0 / 1000
MySQL 磁盘随机查询(~5ms/次)0 / 1000

同样的 1000 次点查,差距不是"快一点",是差两个数量级。这就是缓存存在的全部理由。

它为什么出现:数据库扛不住"读"

一个真实场景:电商首页要展示商品详情,每秒 5 万次读请求。MySQL 单机撑死几千 QPS——不是 MySQL 不行,而是它每次查询都要走 B+ 树索引 → 可能触发磁盘 IO → 加锁 → 解析 SQL 这一整套为"可靠持久存储"设计的流程。

但这 5 万次请求里,99% 在反复读同一批热门商品。为一份几乎不变的数据反复付出磁盘级的代价,是纯粹的浪费。于是自然的想法是:把这批热数据整个放进内存,请求先问内存,问不到再去数据库。Redis 就是把这个想法产品化:一个通过网络访问的、共享的、带丰富数据结构的内存。

一句话定位

Redis = Remote Dictionary Server,远程字典服务。本质是一张巨大的 key → 数据结构 哈希表,整张表住在内存里,通过 TCP 提供给所有服务进程共享。

边界先立好:Redis 用内存换速度,代价是①容量贵且有限(内存价格是磁盘的几十倍);②默认可靠性弱于数据库(宕机可能丢最近的写)。所以它的主战场是可以重建的热数据——缓存、会话、计数、排行——而不是唯一存储业务事实的地方。

心智模型:一张会过期的共享哈希表

读 Redis 文档时,把一切映射回这张图,就不会迷路:

┌──────────────── Redis 进程(内存)────────────────┐ 客户端A ──┤ key value(可选 TTL) │ 客户端B ──┤ "user:1001" → Hash {name, age, vip} │ 客户端C ──┤ "rank:daily" → ZSet [(u3,98),(u1,95),...] │ ... │ "cart:1001" → Hash {sku42: 2, sku7: 1} ⏱30m │ │ "page:home" → String "<html>..." ⏱60s │ └──────────────────────┬───────────────────────────────┘ │ 可选:定期把内存快照/日志写到磁盘 ▼ 磁盘(RDB / AOF,用于重启恢复)

三个要点:① key 永远是字符串,靠命名约定组织(如 user:1001:cart);② value 是数据结构而不只是字符串,这是 Redis 和 Memcached 的分水岭;③ 每个 key 可以设置 TTL,到点自动消失——"会过期"是缓存语义的核心。

反直觉:单线程,为什么还这么快?

Redis 执行命令的核心是单线程的(6.0 后网络 IO 可多线程,但命令执行仍是单线程)。直觉上单线程应该慢,实际它单机能跑 10 万+ QPS。原因在于它把瓶颈换了个位置:

传统数据库的开销Redis 的对应做法
磁盘 IO(毫秒级)数据全在内存,操作是纳秒~微秒级
多线程 → 锁竞争、上下文切换单线程串行执行,零锁,天然原子性
每连接一个线程,连接数受限epoll 多路复用,一个线程盯着几万个连接
SQL 解析、优化器命令即操作,O(1)/O(log n) 直达数据结构

当数据都在内存里时,CPU 根本不是瓶颈,网络往返才是。单线程反而省掉了锁和切换的税。这也带来一条重要推论:

推论:一条慢命令会卡住所有人。因为命令串行执行,一个 KEYS * 或对百万成员集合执行 SMEMBERS,会让后面所有请求排队。生产环境禁用 KEYS,用 SCAN 渐进遍历;大集合用 SSCAN/HSCAN 分批取。

五种核心数据结构:按场景选,不按名字背

点击切换。每种结构记住一句话:它天然擅长什么操作——选型就是把业务动作翻译成这个操作。

选型口诀:存整段就 String;存对象且要改字段就 Hash;要顺序/队列就 List;要去重/关系运算就 Set;要排序榜单就 ZSet。如果你发现自己在用 String 存 JSON 然后整取整存地改一个字段——那是 Hash 的活。

持久化:断电后,你丢多少数据?

内存断电即失,所以 Redis 提供两种落盘方式。理解它们的关键不是背配置,而是回答一个问题:"如果现在断电,我丢失最近多久的写入?" 拖动下面的时间轴感受两者的差异:

RDB:定期快照 默认

每隔一段时间(如 5 分钟)把整个内存 fork 出来写成一个紧凑的二进制文件。恢复快、文件小,但两次快照之间的写全部会丢。

时间 →断电!
丢失窗口:—

AOF:追加日志 更安全

把每条写命令追加到日志文件,重启时重放。appendfsync everysec(推荐)下每秒刷盘一次,最多丢 1 秒。文件更大、恢复更慢。

时间 →断电!
丢失窗口:≤ 1 秒

生产常见组合:RDB + AOF 同时开(重启优先用 AOF 恢复),或 4.0+ 的混合持久化。但记住:即便如此,Redis 的持久化保证仍弱于数据库的事务日志——不要把它当唯一数据源。

标准用法:Cache-Aside 读写模式

最常用的缓存姿势只有一套,先把它焊在脑子里:

读: 查 Redis ──命中──▶ 直接返回(99% 的请求止步于此) │未命中 ▼ 查 MySQL ──▶ 写回 Redis(带 TTL)──▶ 返回 写: 先更新 MySQL ──▶ 再删除 Redis 里的对应 key (下次读会自然回填新值;"删缓存"优于"改缓存",避免并发写导致脏数据)

这套模式下,数据库始终是事实源,Redis 只是它的热数据投影。缓存和库之间允许短暂不一致,靠 TTL 兜底最终收敛——接受这一点,90% 的"缓存一致性焦虑"就消失了。

缓存三大事故:穿透、击穿、雪崩

名字很像,病因完全不同。点击卡片展开"事故现场 + 解法"。判别关键:问不存在的数据?一个热 key 过期?一批 key 同时过期?

缓存穿透 查"不存在"的数据

请求的 key 在缓存和数据库里都不存在(如恶意请求 id=-1),缓存永远无法命中,每次都打穿到数据库。

点击展开 ▾
请求 id=-1 ─▶ Redis(没有)─▶ MySQL(也没有)─▶ 返回空 攻击者循环这个请求 ─▶ 缓存形同虚设,DB 被打死
解法:① 缓存空值:查无此数据也写入 SET key "" EX 60,短 TTL;② 布隆过滤器:把全量合法 id 装进布隆过滤器,不在其中的请求直接拒绝,连 Redis 都不用问。

缓存击穿 一个热 key 过期

某个超高并发的热 key(如秒杀商品)恰好过期,瞬间成千上万请求同时未命中,一起涌向数据库——单点被"击穿"。

点击展开 ▾
t=0 热key过期 ─▶ 10000 个并发同时 miss ─▶ 10000 个相同 SQL 砸向 DB
解法:① 互斥锁重建:未命中时先 SET lock:key 1 NX EX 3 抢锁,只有抢到的那个请求去查库回填,其余等待重试;② 逻辑过期:key 永不过期,值里带过期时间字段,发现"逻辑过期"就返回旧值并异步刷新。

缓存雪崩 一大批 key 同时失效

大量 key 设置了相同的 TTL(比如凌晨批量预热,统一 1 小时),到点集体过期;或 Redis 实例整个宕机。海量请求同时落到数据库,连锁崩溃。

点击展开 ▾
00:00 预热 10 万个 key,TTL 全部 3600s 01:00 十万个 key 同一秒过期 ─▶ 未命中率从 1% 跳到 100% ─▶ DB 雪崩
解法:① TTL 加随机抖动:3600 + rand(0,600),把过期时刻打散;② 服务层限流/熔断兜底;③ Redis 侧做高可用(主从 + 哨兵 / 集群),防止实例级雪崩。

内存满了怎么办:过期与淘汰

两件事常被混为一谈:过期(expiration)是你主动给 key 设的寿命;淘汰(eviction)是内存到达 maxmemory 上限后 Redis 被迫删 key 的策略。

策略行为适用
noeviction内存满后写入直接报错(默认)Redis 当存储用、绝不能默默丢数据时
allkeys-lru在所有 key 里淘汰最久未使用的纯缓存场景的标准答案
volatile-lru只在设了 TTL 的 key 里做 LRU缓存与"常驻数据"混用同一实例时
allkeys-lfu淘汰访问频率最低的(4.0+)存在"偶尔被扫一遍"的冷数据污染 LRU 时
过期删除本身是惰性 + 定期抽样的:key 到期不会立刻消失,而是在被访问时或后台抽查时删除。所以"已过期但仍占内存"是正常现象,别惊讶。

误区与边界:什么时候不该用 Redis

误区①:"Redis 有持久化,所以能当主数据库"
AOF everysec 仍可能丢 1 秒写入;主从复制是异步的,故障切换可能丢更多。涉及钱、订单等业务事实,主数据库必须是 MySQL/PostgreSQL 这类有事务日志与强持久保证的系统。Redis 里放的应该是丢了可以重建的数据。
误区②:"用 Redis 的 List / Pub-Sub 就够当消息队列了"
Pub/Sub 不落盘、消费者离线消息直接丢;List 没有 ack 与重试语义。轻量通知可以凑合,但订单、支付类不能丢的消息应该交给 RabbitMQ/Kafka。Redis 5.0 的 Stream 补上了消费组和 ack,是折中方案,可靠性仍受制于 Redis 自身的持久化等级。
误区③:"命中率低,加大内存就好"
先看访问模式:如果请求分布极度分散(长尾)、几乎没有重复读,缓存天然无效,加内存只是烧钱。缓存的前提是热点存在——二八定律成立时它才值回票价。
误区④:"大 key、热 key 无所谓"
单个 value 几 MB 的"大 key"会造成网络阻塞与删除卡顿(用 UNLINK 异步删);单个 key 扛全站流量的"热 key"会打爆单个节点(集群下尤甚),需要本地缓存或 key 分片(key:{1..N} 随机读)分摊。
什么场景干脆别用 Redis?
① 数据量远超内存预算且无明显热点(直接读库+好索引);② 需要复杂查询/多条件过滤(那是数据库和 ES 的活);③ 强一致要求高于性能要求(缓存必然引入不一致窗口);④ 单机低并发的小项目——先别加中间件,复杂度也是成本。

5 分钟上手:最小可验证例子

装好后逐条敲进 redis-cli,每一条都在验证前文的一个概念:

# 1. 字符串 + TTL:缓存的最小单元
SET page:home "<html>...</html>" EX 60
TTL page:home          # → 剩余秒数,倒数到 -2 表示已消失

# 2. Hash 存对象:只改一个字段,不用整存整取
HSET user:1001 name "Alice" vip 1
HINCRBY user:1001 login_count 1

# 3. ZSet 排行榜:写入即排序
ZINCRBY rank:daily 10 "user:1001"
ZREVRANGE rank:daily 0 2 WITHSCORES   # 前三名

# 4. 原子计数:单线程 = 天然无锁安全
INCR stock:sku42       # 并发调用也绝不会算错

# 5. 分布式锁的原型:NX = 不存在才能设置
SET lock:order:9 "me" NX EX 3   # 返回 OK 才算抢到锁
迁移清单:接手任何用了 Redis 的系统,先问这 5 个问题

① 这里存的数据丢了能不能重建?(不能→设计有问题)② 每类 key 的 TTL 和命名约定是什么?③ maxmemory 和淘汰策略配的什么?④ 持久化开的 RDB 还是 AOF,能接受丢多少?⑤ 有没有大 key / 热 key / KEYS 这类慢命令?——答完这五问,你对这套缓存的理解就超过多数使用者了。
