把一个模型目录,变成一个能扛并发的在线推理服务

Triton Inference Server 镜像部署要解决的事只有一件:你手里有训练好的模型文件(ONNX、TorchScript、TensorRT、SavedModel……),你想让它按标准协议对外提供 HTTP/gRPC 推理接口,还要吃满 GPU。做法是:模型按约定放进 OSS,写一份服务 JSON,让 EAS 用官方 tritonserver 镜像把它跑起来。下面这条流水线就是全文的主线,点一下每个节点,或直接「运行一次部署」。

01 · WHY

它为什么出现:两个各管一段的问题

把模型放上线,实际上要同时解决两层问题,而它们分别由 Triton 和 EAS 负责:

训练框架PyTorch / TF / …→ 模型文件model.onnx / model.pt→ Triton Server推理运行时:加载、调度、batch→ PAI-EAS服务化:机器、网关、token、扩缩容→ 业务调用方HTTP / gRPC 客户端

Triton 管「推理这件事本身」。如果自己拿 Flask 包一层模型,很快会撞到:每个框架一套加载代码、单请求单前向导致 GPU 利用率极低、多模型抢卡没有调度、没有标准协议。Triton 是 NVIDIA 的开源推理服务框架,用统一的 backend 机制加载多种格式(onnxruntime、pytorch(libtorch)、tensorrt、tensorflow、python…),内置 dynamic batching、并发实例、多模型管理,对外统一暴露 KServe v2 协议。

EAS 管「让一个服务在生产里活着」。Triton 只是个进程,它不管你去哪找 GPU 机器、公网入口和鉴权怎么做、挂了谁拉起、流量大了怎么扩。EAS 的「镜像部署」方式正好补上:你声明镜像、启动命令、资源规格和存储挂载,EAS 负责实例调度、网关路由、token 鉴权、监控与扩缩容。

一句话心智模型:Triton 是「推理引擎的壳」,EAS 是「服务的壳」。镜像部署 Triton = 把前者作为容器塞进后者。理解了这个分工,后面每个配置项都能对号入座:出现在 config.pbtxt 里的归 Triton 管,出现在 service.json 里的归 EAS 管。

边界先说清:这套方案不负责训练、不负责把 PyTorch 代码变成模型文件(导出是你的事),也不内置业务前后处理——需要预处理就用 python backend / ensemble,或干脆换自定义镜像。超大 LLM 的推理如今通常走专门引擎(如 vLLM / BladeLLM 的部署方式)而不是经典 Triton 路线,见文末对比。

02 · MODEL REPOSITORY

核心对象:一个约定俗成的目录

Triton 启动时只做一件事:扫描 --model-repository 指向的目录,目录结构本身就是配置。约定是三层:仓库 → 模型名 → 数字版本号,版本目录里放固定名字的模型文件。本文自始至终用同一个例子:一个 ResNet50 的 ONNX 模型。点左侧文件树里的每一项,看它为什么必须长这样。

config.pbtxt 逐行拆解(点任意高亮行)

这是 Triton 一侧最重要的一份文件:它向服务器声明「这个模型是什么、输入输出长什么样、怎么调度」。带绿色左边线的行都可以点。

03 · DEPLOY PATH

部署主路径:四步,从 OSS 到可调用

每一步都写清「做什么 → 产出什么 → 怎么验证 → 哪里容易错」。全部走通后,你会得到一个带 token 的公网/内网 endpoint。

把模型仓库上传到 OSS产出:oss:// 路径

在本地按上一节的结构组织好目录,用 ossutil 或控制台上传。OSS bucket 需与 EAS 服务同地域。

# 本地目录 → OSS
ossutil cp -r ./model_repository \
  oss://examplebucket/model_repository/
验证:ossutil ls 能看到 …/resnet50/1/model.onnx易错:漏传 config.pbtxt;目录层级多套或少套一层
写 service.json(EAS 一侧的全部声明)产出:service.json

三块内容:metadata(服务名/实例/资源)、containers(镜像+启动命令+端口)、storage(把 OSS 挂成容器内目录)。点任意高亮行看解释。

TIP
点上面 JSON 里的某一行查看它的含义与易错点。
最容易错的一致性:storage.mount_path、command 里的 --model-repository,必须指向同一个路径(本例都是 /models);oss.path 要指到「仓库层」,不是模型层。
用 eascmd 或控制台创建服务产出:Running 的服务 
# 命令行方式(控制台「自定义部署→镜像部署」等价)
eascmd create service.json

# 部署过程 & 状态
eascmd desc triton_server_demo

控制台路径:PAI 控制台 → 模型在线服务 EAS → 部署服务 → 自定义部署,镜像选官方 tritonserver,其余字段与 JSON 一一对应。

验证:服务状态变为 Running;实例日志里出现模型 READY 表格易错:GPU 规格没选/配额不足,服务卡在 Waiting
健康检查 + 发一条真实请求产出:第一条推理结果

endpoint 和 token 在服务详情页「查看调用信息」里。先探活,再推理:

# 1) server 活着吗(HTTP 200 即 ready)
curl -H "Authorization: <token>" \
  http://<endpoint>/api/predict/triton_server_demo/v2/health/ready

# 2) 这个模型 READY 了吗
curl -H "Authorization: <token>" \

同一条请求的两种客户端写法

curl -X POST \
  -H "Authorization: <token>" \
  -H "Content-Type: application/json" \
  http://<endpoint>/api/predict/triton_server_demo/v2/models/resnet50/infer \
  -d '{
    "inputs": [{
      "name": "input",            # 必须等于 config.pbtxt 的 input.name
      "shape": [1, 3, 224, 224],  # 这里要带 batch 维!
      "datatype": "FP32",         # 协议写法,不是 TYPE_FP32
      "data": [0.1, 0.2, "..."]
    }]
  }'
# 返回:{"model_name":"resnet50","outputs":[{"name":"output","shape":[1,1000],...}]}
import numpy as np
import tritonclient.http as httpclient

# url 不带 http:// 前缀;token 放到每个请求的 header 里
client = httpclient.InferenceServerClient(
    url="<endpoint>/api/predict/triton_server_demo",
    headers={"Authorization": "<token>"})

x = np.random.rand(1, 3, 224, 224).astype(np.float32)
inp = httpclient.InferInput("input", x.shape, "FP32")
inp.set_data_from_numpy(x, binary_data=True)
out = httpclient.InferRequestedOutput("output", binary_data=True)

resp = client.infer(model_name="resnet50", inputs=[inp], outputs=[out])
print(resp.as_numpy("output").shape)   # (1, 1000) → 部署成功

这段就是最小可验证例子:随机张量喂进去,拿到 (1, 1000) 的输出,说明「协议 → 网关 → 模型 → 返回」全链路正确。换成真实图片只是把 np.random.rand 换成预处理后的像素。

gRPC 走 8001 端口,需在 service.json 里显式声明并开启网关 gRPC 支持(如 "metadata": {"enable_grpc": true} 并把 port 指到 8001),否则只有 HTTP 可用。指标端口 8002(Prometheus)同理。
05 · DYNAMIC BATCHING

为什么值得用 Triton:dynamic batching 亲手试

GPU 做一次 batch=8 的前向,耗时通常远小于做 8 次 batch=1。dynamic batcher 的做法:请求先进队列,在 max_queue_delay_microseconds 的窗口内攒单,再按 max_batch_size 打包执行。拖动滑杆、开关 batching,看同样的并发下 GPU 前向次数怎么变:

–

–
相对不攒批的前向次数缩减

注意取舍:攒批换吞吐的代价是每条请求最多多等一个 delay 窗口。延迟极端敏感(如单条请求要求 P99 几毫秒)或流量常年只有零星单条时,关掉 batching 反而更合适;这也是 config.pbtxt 把它做成可选块的原因。

06 · PITFALLS

常见坑:错误写法 vs 正确写法

下面每一条都是真实高频问题,按「症状」找最快。展开看对照与排查线索。

版本目录不是纯数字症状:模型静默不加载
✗ 错误
resnet50/
├── config.pbtxt
└── v1/            ← "v1"、"latest"
    └── model.onnx    都会被忽略
✓ 正确
resnet50/
├── config.pbtxt
└── 1/             ← 必须是正整数
    └── model.onnx    数字即版本号
排查线索:服务是 Running,但 /v2/models/resnet50/ready 返回 4xx;实例日志的模型表里根本没有这个模型,或版本列为空。Triton 对非数字目录不报错、直接跳过,这是它最"安静"的坑。
dims 里多写了 batch 维症状:启动报 shape 校验错误
✗ 错误
max_batch_size: 8
input [{
  dims: [ 1, 3, 224, 224 ]
}]   ← 首维 1 会被当成真实维度
✓ 正确
max_batch_size: 8
input [{
  dims: [ 3, 224, 224 ]
}]   ← batch 维隐含,不写
规则:max_batch_size > 0 时,dims 不含 batch 维;max_batch_size: 0 时模型不支持攒批,dims 写完整形状。可变维度用 -1(如变长文本 dims: [ -1 ])。排查线索:日志出现 "model configuration ... unexpected shape" 一类错误,或请求时报 input shape 不匹配。
模型文件名不符合 backend 约定症状:加载失败 failed to load
✗ 错误
1/
└── resnet50_v2_final.onnx
✓ 正确(按 backend 定名)
onnxruntime → model.onnx
libtorch    → model.pt
tensorrt    → model.plan
tensorflow  → model.savedmodel/
排查线索:日志报 "failed to load ... no model file found"。要用自定义文件名需在 config.pbtxt 里加 default_model_filename,否则老实用默认名。
挂载路径与启动命令不一致症状:server 起来了但 0 个模型
✗ 错误
"command": "tritonserver
  --model-repository=/models"
"storage": [{
  "mount_path": "/model_repo", ←
  "oss": {"path": "oss://b/model_repository/resnet50/"} ←
}]
✓ 正确
"command": "tritonserver
  --model-repository=/models"
"storage": [{
  "mount_path": "/models",
  "oss": {"path": "oss://b/model_repository/"}
}]  ← 指到仓库层,两处路径一致
排查线索:启动日志的模型表为空表。两个方向都会翻车:mount_path 和 --model-repository 对不上;或 oss.path 指到了「模型层」,导致 Triton 把 resnet50 当仓库、把 1/ 当模型名。
调用 URL / 协议字段写错症状:404 / 401 / 400
✗ 错误
POST http://<endpoint>/v2/models/resnet50/infer
(少了 EAS 前缀 → 404)
"datatype": "TYPE_FP32"  → 400
不带 Authorization 头     → 401
✓ 正确
POST http://<endpoint>
  /api/predict/<服务名>
  /v2/models/resnet50/infer
"datatype": "FP32"
-H "Authorization: <token>"
心法:URL = EAS 的路由前缀(/api/predict/服务名)+ Triton 的协议路径(/v2/…)。401/404 先怀疑前半段,400/422 先怀疑后半段(name/shape/datatype 是否与 config.pbtxt 一致)。TYPE_FP32 是 config.pbtxt 的写法,HTTP 协议里是 FP32。
07 · SCOPE & TRADEOFFS

边界与取舍:什么时候选它,什么时候不选

✓ 很适合

  • 多个不同框架的中小模型要统一方式上线,不想每个都写一套服务代码
  • 在线流量有并发,想靠 dynamic batching / 多实例吃满 GPU
  • 希望走标准 KServe v2 协议,客户端与云厂商解耦、可迁移
  • 一张卡上要同时服务多个模型(仓库里多放几个目录即可)

△ 慎用 / 不适合

  • 重前后处理、重业务逻辑:Triton 只吃张量。轻量的用 python backend / ensemble 拼进仓库,复杂的直接上自定义镜像
  • 大语言模型:优先 EAS 的 LLM 专用部署(vLLM / BladeLLM / SGLang 等),它们的 KV cache 与连续批处理是为 LLM 设计的
  • 模型还在频繁改接口的探索期:config.pbtxt 的强约定会变成负担,不如先用简单方式跑通
  • 对单条请求延迟极端敏感且无并发:Triton 的调度收益发挥不出来

和相邻方案摆在一起看

维度EAS 内置 processor镜像部署 Triton(本文)完全自定义镜像
你要准备什么模型文件,选好 processor模型仓库 + config.pbtxt + service.json自己写服务代码 + 打镜像
多框架统一✗ 一种 processor 对一种格式✓ backend 机制天然支持取决于你写的代码
dynamic batching / 并发实例部分支持,能力固定✓ 配置即得要自己实现
自由度(前后处理、任意协议)低中(python backend / ensemble)最高
维护成本最低低:镜像官方维护,只管配置高:安全补丁、依赖都归你

选型口诀:单模型图省事 → processor;多模型/要吞吐/要标准协议 → Triton 镜像;协议或逻辑高度定制 → 自定义镜像;LLM → 专用引擎。

08 · REUSE

迁移速查:换成你自己的模型,只改这五处

本文的 ResNet50 例子换成任何模型,变化点是固定的——这正是这套方案的价值:结构不变,填空即可。

  • 模型目录名 = 对外的 model_name:resnet50/ → your_model/,调用 URL 里的 /v2/models/your_model/infer 随之变化
  • 模型文件:导出成某个 backend 支持的格式,按约定命名放进 1/(onnx → model.onnx,TorchScript → model.pt…)
  • config.pbtxt:改 platform/backend、input/output 的 name / data_type / dims(用导出时的真实张量名;记住 batch 维规则)
  • service.json:改服务名、GPU/内存规格、oss.path;镜像 tag 按需选择版本
  • 客户端:改 endpoint、token、model_name 和 InferInput 的 name/shape/datatype——其余代码一行不动
