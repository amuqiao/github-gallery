01 · WHAT & WHY

它是什么、边界在哪、解决什么问题

这套方案由两个角色组成：Triton Inference Server 是 NVIDIA 开源的高性能推理服务框架， PAI-EAS（Elastic Algorithm Service）是阿里云 PAI 的模型在线服务平台。 「镜像部署」指的是：直接使用官方 Triton 镜像，把模型仓库挂载进去，由 EAS 托管这个容器并对外提供服务。

痛点训练完 ≠ 能上线

模型文件躺在 OSS 里不能直接被业务调用，自己写 Flask/FastAPI 包一层，性能、批处理、多模型管理都要重造轮子。

Triton 解决推理服务本身

统一加载 TensorRT / PyTorch / ONNX 等多框架模型，内置动态批处理、并发实例、模型编排，压榨 GPU 利用率。

EAS 解决部署与运维

提供托管资源、服务网关、鉴权、弹性伸缩、监控告警、灰度发布——你只需要一份 JSON 配置和一个 OSS 路径。

边界：它是什么 / 不是什么

IN SCOPE · 它负责

  • 模型 Serving：把模型文件变成 HTTP/gRPC 在线服务
  • 多框架统一：TensorRT、PyTorch (LibTorch)、ONNX Runtime、TensorFlow、Python Backend 等
  • 吞吐优化：dynamic batching 自动组批、instance_group 多实例并发
  • 多模型管理：一个服务同时挂多个模型、多个版本
  • 标准协议：KServe v2 推理协议，客户端生态现成

OUT OF SCOPE · 它不负责

  • 模型训练与调参——那是 PAI-DLC / DSW 的事
  • 模型转换优化——转 TensorRT、量化需提前自己做好
  • 业务逻辑编排——复杂前后处理建议用 Python/Ensemble，或放到业务侧
  • 数据存储——模型放 OSS，EAS 只负责挂载
  • 离线批量推理——大规模离线任务更适合批处理作业
一句话总结：Triton 是「推理引擎的服务化外壳」，EAS 是「这个外壳的云端托管底座」。镜像部署 = 官方镜像 + OSS 模型仓库 + 一份服务配置。
02 · MODEL REPOSITORY

一切从模型仓库开始

Triton 不关心你的代码，只关心一个约定俗成的目录结构——模型仓库（Model Repository）。 把它按规矩放在 OSS 上，启动时通过 --model-repository 指过去，Triton 会自动扫描并加载全部模型。 点击左侧文件树的任意节点，看看每一层的含义。

📁text_embed/
⚙️config.pbtxt

模型仓库根目录。部署时把它挂载到容器内（如 /models），启动命令写 tritonserver --model-repository=/models。根目录下的每个一级子目录就是一个独立模型，一个服务可以同时承载多个模型。
TIP：目录名 = 模型名，调用 URL 里会用到它。

config.pbtxt：模型的「说明书」

每个模型目录下的 config.pbtxt 告诉 Triton：用什么后端跑、输入输出长什么样、允许多大的 batch、开几个实例。 点击任意一行查看解释。

resnet50/config.pbtxt
name: "resnet50"platform: "onnxruntime_onnx"max_batch_size: 16input [  {    name: "input"    data_type: TYPE_FP32    dims: [ 3, 224, 224 ]  }]output [  {    name: "output"    data_type: TYPE_FP32    dims: [ 1000 ]  }]instance_group [  { count: 2, kind: KIND_GPU }]dynamic_batching {  max_queue_delay_microseconds: 100}version_policy: { latest: { num_versions: 1 } }
name
模型名，必须与所在目录名一致。它会出现在调用路径 /v2/models/resnet50/infer 中。

04 · DEPLOY WORKFLOW

部署四步走

在 PAI-EAS 上做 Triton 镜像部署，核心就是四步：准备模型仓库 → 写服务配置 → 部署 → 验证。 可以走控制台（场景化「Triton 部署」入口或自定义镜像部署），也可以用 eascmd 命令行——配置本质是同一份 JSON。

按第 ② 节的目录规范组织好模型仓库，用 ossutil 或控制台上传到你的 Bucket（注意选择与 EAS 服务同地域的 Bucket）：

shell
# 本地目录 ./triton/ 内是标准模型仓库结构
ossutil cp -r ./triton/ oss://examplebucket/models/triton/

# 检查：模型目录、版本目录、config.pbtxt 是否齐全
ossutil ls oss://examplebucket/models/triton/resnet50/
为什么用挂载而不是打进镜像？模型与镜像解耦：换模型/加版本只需更新 OSS 文件，无需重新构建镜像；配合版本策略还能热更新。

一份最小可用的服务配置。关键三件事：用哪个镜像、挂哪个 OSS 路径、启动命令指向挂载点：

service.json
{
  "name": "triton_demo",
  "containers": [
    {
      "image": "<region-registry>/pai-eas/tritonserver:23.02-py3",  // EAS 提供的官方镜像，按地域选择
      "command": "tritonserver --model-repository=/models",
      "port": 8000                                    // Triton HTTP 端口；用 gRPC 则改 8001
    }
  ],
  "storage": [
    {
      "oss": { "path": "oss://examplebucket/models/triton/" },
      "mount_path": "/models"                       // 与启动命令里的路径保持一致
    }
  ],
  "metadata": {
    "instance": 1,
    "cpu": 4,
    "memory": 8000,
    "gpu": 1                                        // GPU 卡数；纯 CPU 模型可为 0
  }
}

若要走 gRPC：把 containers.port 改为 8001，并在 metadata 中加 "enable_grpc": true，让网关按 gRPC 协议转发。 HTTP 与 gRPC 走网关时二选一。

两种等价方式，任选其一：

方式 A · eascmd 命令行
# 配置好 AK 与地域后
eascmd create service.json

# 输出中会给出服务的 Endpoint 与 Token；也可随时查询：
eascmd desc triton_demo

方式 B控制台部署

PAI 控制台 → 模型在线服务 EAS → 部署服务 → 镜像部署：选官方 Triton 镜像、填 OSS 挂载与启动命令，或直接使用场景化的 Triton 部署入口，表单项与 JSON 一一对应。

部署后状态流转

服务经历 Creating → Waiting → Running。进入 Running 前 Triton 会扫描 /models 并逐个加载模型，模型越大等待越久属正常现象。

先看健康检查，再看模型是否就绪，最后翻日志确认加载结果：

shell
# 服务整体就绪（把 endpoint 与 token 换成 eascmd desc 拿到的值）
curl -H "Authorization: <token>" \
  http://<service>.<region>.pai-eas.aliyuncs.com/api/predict/triton_demo/v2/health/ready

# 某个模型就绪
curl -H "Authorization: <token>" \
  .../triton_demo/v2/models/resnet50/ready

# 查看模型元信息（输入输出的名字、类型、形状）
curl -H "Authorization: <token>" \
  .../triton_demo/v2/models/resnet50

日志里看到每个模型 READY 的表格即加载成功；若显示 UNAVAILABLE，通常是 config.pbtxt 与模型文件不匹配（详见第 ⑦ 节常见坑）。

05 · INVOKE

调用服务：说 KServe v2 的「普通话」

Triton 实现了社区标准的 KServe v2 推理协议，所以调用方式与你部署在哪无关： 在 EAS 上只是把请求地址换成服务 Endpoint，并带上 Authorization Token。 下面给出两种最常用的姿势。

client.py
# pip install tritonclient[http] numpy
import numpy as np
import tritonclient.http as httpclient

url = "<service>.<region>.pai-eas.aliyuncs.com/api/predict/triton_demo"
headers = {"Authorization": "<token>"}          # EAS 的服务 Token

client = httpclient.InferenceServerClient(url=url)

# 构造输入：名字/类型/形状必须与 config.pbtxt 一致（batch 维在最前）
data = np.random.rand(1, 3, 224, 224).astype(np.float32)
inp = httpclient.InferInput("input", data.shape, "FP32")
inp.set_data_from_numpy(data, binary_data=True)

out = httpclient.InferRequestedOutput("output", binary_data=True)

resp = client.infer("resnet50", inputs=[inp],
                    outputs=[out], headers=headers)
print(resp.as_numpy("output").shape)   # (1, 1000)

gRPC 版本几乎同构：换成 tritonclient.grpc，url 不带 http 前缀、端到 gRPC 网关即可。

curl · KServe v2 JSON
curl -X POST \
  -H "Authorization: <token>" \
  -H "Content-Type: application/json" \
  http://<service>.<region>.pai-eas.aliyuncs.com/api/predict/triton_demo/v2/models/resnet50/infer \
  -d '{
    "inputs": [{
      "name": "input",
      "shape": [1, 3, 224, 224],
      "datatype": "FP32",
      "data": [0.1, 0.2, ...]
    }]
  }'

JSON 直传适合调试；生产上建议 tritonclient 的二进制传输（省去 JSON 序列化开销，大张量差距明显）。 URL 规律：EAS Endpoint + /v2/models/<模型名>[/versions/<n>]/infer。

06 · ADVANCED

进阶特性：Triton 的真正价值

只是「把模型跑起来」，Flask 也能做到。Triton 的护城河在于下面这些开箱即用的吞吐与工程能力——也是文档里容易被略过、却最值得「查漏补缺」的部分。展开了解。

DBDynamic Batching：自动组批，吞吐翻倍▶

GPU 天生喜欢大 batch。零散到达的单条请求若各自执行，GPU 大部分时间在空转。开启 dynamic_batching 后，调度器会把窗口期内（如 max_queue_delay_microseconds: 100）到达的请求自动拼成一个 batch 再执行，单条请求只多等微秒级延迟，整体吞吐常有数倍提升。

前提：max_batch_size > 0，且模型本身支持首维为可变 batch。对延迟极敏感的场景可调小等待窗口或不开启。

IGInstance Group：一张卡上跑多个模型副本▶

instance_group { count: 2, kind: KIND_GPU } 表示在 GPU 上同时保留 2 个模型执行实例。当一个实例在做 GPU 计算时，另一个可以并行做数据拷贝/预处理，把流水线填满。小模型尤其受益。

也可指定 KIND_CPU、或用 gpus: [0] 绑定具体卡。副本越多显存占用越大，需与 EAS 实例的 GPU 规格匹配。

ENEnsemble：把前后处理编成 DAG▶

Ensemble 模型是一种特殊的「虚拟模型」：用 platform: "ensemble" 声明一个 DAG，把「Python 预处理 → TensorRT 推理 → Python 后处理」串成一次调用，中间张量在服务端直接传递，省掉多次网络往返。

配合 Python Backend（模型目录里放 model.py，实现 initialize / execute / finalize 三个方法）几乎可以承载任意自定义逻辑。

MV多模型与版本策略：热更新的正确姿势▶

仓库根目录下每个子目录都是独立模型，一个服务可同时对外提供多个模型。每个模型目录下的数字子目录是版本，version_policy 控制暴露哪些：latest(n) 最新 n 个、all 全部、specific 指定版本。

调用时可用 /v2/models/name/versions/2/infer 指定版本，不指定则用最新。往 OSS 新增版本目录 + 相应的模型管理模式即可实现灰度与热更新。

MTMetrics：8002 端口的 Prometheus 指标▶

Triton 在 :8002/metrics 暴露标准 Prometheus 指标：请求量、排队时长、推理时长、GPU 利用率/显存等。结合 EAS 自身的服务监控（QPS、RT、实例水位），排障时能快速定位瓶颈在「排队」还是「计算」。

EASEAS 侧能力：弹性、灰度、专属资源组▶

这些不属于 Triton，但镜像部署后自动获得：按 QPS/GPU 利用率的水平自动扩缩容、蓝绿/灰度发布、公网与 VPC 双 Endpoint、专属资源组独占机器。也就是说，Triton 解决「单实例吃满一张卡」，EAS 解决「按流量弹出 N 个实例」。

07 · PITFALLS

常见坑速查

按出现频率排序，部署失败十有八九是前三条。

📁
目录结构不合规，模型加载失败

缺少版本子目录（模型文件直接放在模型目录下）、目录名与 config.pbtxt 的 name 不一致、模型文件名不符合后端约定（如 ONNX 需为 model.onnx）。

FIX → 严格遵循 模型名/版本号/模型文件 三层结构，先在本地用 tritonserver 镜像跑通再上传。

🔌
端口配置与协议不匹配

containers.port 写成别的端口、想用 gRPC 却仍指向 8000、或忘了在 metadata 开启 gRPC 支持，表现为网关 4xx/超时。

FIX → HTTP 用 8000；gRPC 用 8001 且 metadata 中 enable_grpc: true。

📐
输入张量与 config.pbtxt 对不上

名字、dtype、形状任一不符都会报错；注意 max_batch_size > 0 时 dims 里不写 batch 维，但请求数据里要带。

FIX → 先 GET /v2/models/<name> 查元信息，按返回构造输入。

🧠
显存不够 / 实例规格不匹配

instance_group 副本数 × 模型显存 超过所选 GPU 规格，容器反复重启；或大模型加载慢被误判为失败。

FIX → 按「副本数 × 单副本显存 + 余量」选卡；耐心等待 Waiting 阶段完成。

🌐
OSS 跨地域或权限不足

Bucket 与服务不同地域导致挂载慢/失败；或角色未授权 OSS 读取。

FIX → 同地域 Bucket + 按文档为 EAS 授予 OSS 访问权限。

🐍
Python Backend 缺依赖

model.py 里 import 的包官方镜像未必自带。

FIX → 基于官方镜像构建自定义镜像装依赖，或打包 conda 环境随模型仓库分发。
