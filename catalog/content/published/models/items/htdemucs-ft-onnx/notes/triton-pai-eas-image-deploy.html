阿里云 PAI-EAS · 镜像部署系列

一文读懂:用 Triton 镜像把模型变成在线服务 Triton Inference Server on PAI-EAS

你手里有一个训练好的模型文件,想让它 7×24 小时对外提供推理 API。 Triton 是 NVIDIA 开源的推理服务框架,PAI-EAS 提供了官方 Triton 镜像—— 把两者接起来,不写一行服务端代码就能得到一个支持动态批处理、多框架、GPU 高吞吐的生产级服务。

零散到达的请求被 Triton 攒成一个 batch,一次 GPU 前向算一批——这就是它高吞吐的核心手法(下文有可玩的模拟器)。
step: "01_problem" # 它解决什么问题

从"模型文件"到"在线服务",中间差什么?

训练结束你得到的是 model.pt、model.onnx 这类静态文件, 而业务要的是一个能扛并发的 HTTP 接口。中间这段"推理服务化"通常有三条路:

自由度高 · 全要自己扛

自己写 Flask / FastAPI

加载模型 + 写路由,demo 十分钟搞定。但并发模型、GPU 利用率、批处理、多模型管理、健康检查、指标监控……每一项都要自己造轮子,GPU 常年吃不满。

最省事 · 框架单一时

EAS 预置 Processor

PAI-EAS 为 TensorFlow、PyTorch 等提供内置处理器,传模型即部署。适合单框架、无特殊协议要求的常规场景。

本文主角 · 高性能通吃

Triton 镜像部署

EAS 提供官方 tritonserver 镜像:多后端(TensorRT / ONNX / PyTorch / TF / Python)、动态批处理、单卡多实例并发、多模型多版本、标准 KServe v2 协议,一套全包。

一句话定位:Triton 是"推理服务的运行时",EAS 是"托管它的云平台"。 你只负责两件事——按规矩摆好模型仓库 + 写一份部署配置,剩下的加载、调度、扩缩容都交给它们。

边界先说清:Triton 不做训练、不做复杂业务逻辑编排; 前后处理很重的场景要用它的 Python backend / ensemble,或退回自定义镜像。CPU 上的小模型用它属于"杀鸡用牛刀"。

step: "03_model_repository" # Triton 只认这个目录结构

模型仓库:一套"约定优于配置"的目录规矩

Triton 启动时扫描 --model-repository 指向的目录,按目录结构自动发现模型。 三层结构一层都不能少:仓库根 / 模型名 / 数字版本号 / 模型文件。 鼠标悬停或点击树上的任意节点看解释,再切到"错误示例"看看新手最常摆错的样子。

oss://examplebucket/models/triton/
  • triton/ # 仓库根 = 挂载到 /models 的那一层
  • ├─ resnet50_pt/ # 模型名,必须与 config 里 name 一致
  • │ ├─ 1/ # 版本目录,必须是纯数字
  • │ │ └─ model.pt # TorchScript 导出的模型
  • │ └─ config.pbtxt # 模型配置(下一节逐行拆)
  • └─ bert_onnx/ # 第二个模型?再来一套即可
  • ├─ 1/
  • │ └─ model.onnx
  • └─ config.pbtxt
  • triton/
  • ├─ resnet50_pt/
  • │ ├─ model.pt # ✗ 少了版本目录 1/
  • │ └─ config.pbtxt
  • └─ bert_onnx/
  • ├─ v1/ # ✗ 版本必须是纯数字,v1 不行
  • │ └─ model.onnx
  • └─ (缺 config.pbtxt) # 多数后端无法自动推断配置

点一个节点试试

左边这棵树就是要原样上传到 OSS 的内容。Triton 的"自动发现"完全依赖这个结构——它不看文件名花样,只看层级。

为什么要版本目录?同一模型可并存 1/、2/、3/ 多个版本, 配合 version_policy 控制加载最新版还是指定版,灰度、回滚都靠它——这不是繁文缛节,是内置的版本管理。

step: "04_config_pbtxt" # 模型的"接口说明书"

config.pbtxt 逐行拆解

config.pbtxt 告诉 Triton:这个模型用什么后端跑、输入输出长什么样、允许多大的 batch。 点击左侧任意高亮行(或右侧标签)查看该字段的门道。

resnet50_pt/config.pbtxt
name: "resnet50_pt" platform: "pytorch_libtorch" max_batch_size: 128 input [ { name: "INPUT__0" data_type: TYPE_FP32 dims: [ 3, 224, 224 ] # 注意:不含 batch 维 } ] output [ { name: "OUTPUT__0" data_type: TYPE_FP32 dims: [ 1000 ] } ] instance_group [ { count: 2, kind: KIND_GPU } ] dynamic_batching { max_queue_delay_microseconds: 100 }

step: "05_deploy" # 两种部署姿势

部署到 EAS:控制台点选,或一份 JSON

本质是同一件事:选 Triton 镜像 + 把 OSS 仓库挂载到容器的 /models + 启动命令指过去 + 暴露 8000 端口。 控制台适合首次上手,JSON + 客户端工具适合固化进 CI/CD。

  1. 进入 PAI 控制台 → 模型在线服务 (EAS) → 部署服务,选择镜像部署;
  2. 镜像选择:官方镜像列表中选 tritonserver(如 tritonserver:23.02-py3,版本以控制台为准);
  3. 模型配置:挂载 OSS,源路径填仓库根(如 oss://examplebucket/models/triton/),挂载路径填 /models;
  4. 运行命令:tritonserver --model-repository=/models,端口 8000;
  5. 资源规格:选 GPU 实例(如 A10 / GU30 系列);点击部署,等状态变为"运行中"。

控制台里那些表单项,和右边 JSON 的字段是一一对应的——理解了 JSON,控制台就不用背了。

{
  "metadata": {
    "name": "triton_server_demo",
    "instance": 1                  // 服务实例数(水平扩容改这里)
  },
  "containers": [{
    "image": "eas-registry-vpc.cn-hangzhou.cr.aliyuncs.com/pai-eas/tritonserver:23.02-py3",
    "command": "tritonserver --model-repository=/models",
    "port": 8000                    // Triton 的 HTTP 端口
  }],
  "storage": [{
    "oss": { "path": "oss://examplebucket/models/triton/" },
    "properties": { "resource_type": "model" },
    "mount_path": "/models"       // 必须与 command 里一致!
  }],
  "cloud": {
    "computing": { "instance_type": "ml.gu7i.c16m60.1-gu30" }
  }
}
# 用 eascmd 客户端创建 / 更新服务
eascmd create service.json
eascmd modify triton_server_demo -s service.json

最容易踩的一致性:mount_path 和 --model-repository 必须是同一个路径; OSS 的 path 必须指到仓库根(模型名的上一层),挂深一层或浅一层,Triton 都会"看不到模型"。

step: "06_invoke" # 调用与验证

调用服务:先验活,再推理

服务运行后,在 EAS 控制台"调用信息"里拿到两样东西:访问地址 (Endpoint) 和 Token。 Triton 说的是标准 KServe v2 协议,所以任何 Triton 客户端 / 标准 HTTP 都能直接对话, 只是要多带一个 Authorization 头。

# 1. 服务就绪了吗?(200 即就绪)
curl -H "Authorization: <Token>" \
  http://166233998075****.cn-hangzhou.pai-eas.aliyuncs.com/api/predict/triton_server_demo/v2/health/ready

# 2. 模型加载对了吗?看它声明的输入输出
curl -H "Authorization: <Token>" \
  .../api/predict/triton_server_demo/v2/models/resnet50_pt

# 3. 正式推理(KServe v2 JSON;shape 带上 batch 维)
curl -X POST -H "Authorization: <Token>" \
  -d '{"inputs":[{"name":"INPUT__0","shape":[1,3,224,224],"datatype":"FP32","data":[...]}]}' \
  .../api/predict/triton_server_demo/v2/models/resnet50_pt/infer

URL 规律:{EAS Endpoint}/api/predict/{服务名} 之后,拼接的就是 Triton 原生的 /v2/... 路径。把 EAS 想成一层带鉴权的反向代理即可。

# pip install tritonclient[http] numpy
import numpy as np
import tritonclient.http as httpclient

url = "166233998075****.cn-hangzhou.pai-eas.aliyuncs.com/api/predict/triton_server_demo"
client = httpclient.InferenceServerClient(url=url)  # 注意:不带 http:// 前缀

img = np.random.rand(1, 3, 224, 224).astype(np.float32)   # 第一维是 batch
inp = httpclient.InferInput("INPUT__0", img.shape, "FP32")
inp.set_data_from_numpy(img, binary_data=False)
out = httpclient.InferRequestedOutput("OUTPUT__0", binary_data=False)

res = client.infer(
    model_name="resnet50_pt",
    inputs=[inp], outputs=[out],
    headers={"Authorization": "<Token>"},   # EAS 鉴权,每次请求都要带
)
print(res.as_numpy("OUTPUT__0").shape)        # (1, 1000)

gRPC 怎么办?Triton 的 gRPC 走 8001 端口,在 EAS 上需要在服务配置中额外开启 gRPC 支持并按其网关方式访问,不是把 URL 换个端口就行——按需查阅官方文档的 gRPC 小节。

step: "07_why_fast" # 为什么 Triton 快

亲手玩一下:动态批处理如何换来吞吐

GPU 的天性是"一次算一批比一条条算划算得多"——每次前向都有固定开销,batch 内多一条样本只增加很小的边际成本。 Triton 的 dynamic_batching 就是在服务端把窗口期内到达的零散请求攒成一批再送进 GPU。 下面的模拟器里,琥珀色点是请求,绿框是 GPU 正在计算的批:

0
吞吐(已完成请求)
–
平均时延(模拟 ms)
–
平均 batch 大小
0
当前排队数

试试:把请求速率拉满、合批关闭——队伍越排越长;打开合批立刻消化。再观察"攒批窗口"的取舍: 窗口越大 batch 越大、吞吐越高,但每个请求要多等一会儿(时延上升)。吞吐和时延的这笔账,就是 max_queue_delay_microseconds 要你拍板的事。

另外两件加速利器

instance_group:单卡多实例

一张 GPU 上起 count: 2 个模型实例,一个在等数据拷贝时另一个在计算,把卡的空隙填满;也可用 KIND_CPU 把小模型放 CPU。

ensemble:服务端流水线

把"预处理 → 模型 → 后处理"编排成一个 ensemble 模型,数据在服务端各步骤间直接传递,免去多次网络往返;预处理可用 Python backend 写。

step: "08_pitfalls" # 常见坑与排错

报错对症下药

failed to load model模型死活加载不出来
九成是目录结构问题:少了数字版本目录(模型文件直接放在模型名下)、版本目录写成 v1、或 OSS 上传时层级带偏了。 对照第 3 节的树逐层检查;看服务日志中 Triton 启动时打印的模型表,状态应为 READY。
unexpected shape / tensor name推理时报输入名或形状不匹配
先 GET /v2/models/<name> 看模型实际声明的输入输出,再核对客户端。两个高频错误: ① PyTorch 后端的张量名是 INPUT__0/OUTPUT__0 这种双下划线约定; ② max_batch_size > 0 时 config 的 dims 不含 batch 维,但客户端请求的 shape 必须带 batch 维。
空模型仓库服务起来了,但一个模型都没有
mount_path 与 --model-repository 不一致,或 OSS path 指到了模型目录而不是仓库根。 Triton 扫的是参数指向的那层目录,挂错一层它就"什么也看不见"。
401 / 404curl 通不了
401:漏了 Authorization: <Token> 头,或 Token 复制不全。 404:URL 少了 /api/predict/{服务名} 前缀,或后面的 /v2/... 路径拼错。 Python 客户端还有一个隐蔽点:InferenceServerClient(url=...) 的 url 不带 http://。
CUDA error / 起不来镜像与资源不匹配
Triton 镜像版本对应特定的 CUDA / 驱动要求,选实例规格时用 EAS 提供的 GPU 机型搭配官方镜像即可; 自带社区镜像时要自己核对版本矩阵。CPU 规格上跑 GPU 编译的 TensorRT 模型也会直接失败。
吞吐没变化开了 dynamic_batching 却没效果
检查三点:① max_batch_size 是否为 0(为 0 则整个 batch 机制关闭); ② 压测并发是否够大——没有排队自然无批可攒;③ 窗口是否太小,请求还没凑齐就发车了。 用 :8002/metrics 的 Prometheus 指标看真实 batch 分布。
step: "09_when_to_use" # 适用边界与收尾

什么时候选它,什么时候不选

场景建议
GPU 推理、追求吞吐,流量有波峰波谷✓ Triton 镜像,dynamic_batching 是为此而生
一套服务同时跑 TensorRT + ONNX + PyTorch 多个模型✓ Triton 多后端 + 多模型仓库的主场
需要多版本灰度 / 回滚、标准协议、Prometheus 指标✓ 版本策略、KServe v2、:8002/metrics 全内置
单个 TensorFlow / PyTorch 模型,常规小流量✗ EAS 预置 Processor 更省事
业务逻辑重、前后处理复杂、协议定制✗ 自定义镜像(FastAPI 等)更自由;或 Triton + Python backend 折中
CPU 上的轻量小模型✗ 牛刀,收益撑不起复杂度

上线前 checklist(点一下打勾)

  • 目录三层结构:仓库根 / 模型名 / 数字版本 / 模型文件
  • config.pbtxt:name 与目录一致;dims 不含 batch 维;张量名与模型实际一致
  • 整个仓库上传 OSS,记下仓库根路径
  • 部署配置四件套:image / command / port 8000 / storage 挂载 /models
  • 部署后 GET /v2/health/ready 返回 200
  • GET /v2/models/<name> 核对元数据,再发第一条 infer
  • 压测之后,再回头调 dynamic_batching 窗口与 instance_group 数量

可迁移的心智模型:Triton 部署 = "按约定摆目录" + "声明式描述模型接口" + "容器挂载对齐"。 同一套仓库,换到自建 Kubernetes、其他云的托管服务,几乎原样可用——你学的不是某个控制台的按钮位置,而是 Triton 本身。

本文为学习性质的知识整理,示例中的镜像版本、实例规格、Endpoint 均为示意;实际部署时请以 阿里云 PAI 官方文档《部署 Triton Server 模型服务》及控制台展示为准。
