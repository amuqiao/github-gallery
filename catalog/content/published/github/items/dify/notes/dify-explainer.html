把「LLM 应用」从代码里搬到画布上,
再从画布变回一个 API

Dify 是一个开源的 LLM 应用开发平台:在可视化画布上编排提示词、知识库(RAG)、Agent 与工作流,一键发布成带鉴权的 Web 应用和 REST API。它想解决的问题只有一个——让"能跑的 Demo"到"能上线的 LLM 应用"之间不再隔着几个月的胶水代码。

后端 Python / Flask 前端 Next.js / React docker compose 一键自托管 Apache 2.0 系开源协议(附加条款)

01 · 它是什么

先说清楚:Dify 是"平台",不是"库"

名字取自 Define + Modify。理解 Dify 的关键是三个问题:它替你做了什么、为什么会出现、以及它的边界在哪。

Q1它替你做了什么?

把一个生产级 LLM 应用需要的全部后端基建打包:提示词编排、RAG 知识库流水线、Agent 与工具调用、工作流引擎、多模型接入、日志与用量监控、多租户与 API 网关。你在画布上"定义"应用,它负责把应用跑起来并暴露成 API。

Q2为什么会出现?

2023 年起,团队们发现:接一个模型 API 只要 10 分钟,但做出可上线的应用要处理文档切分、向量检索、提示词版本、会话记忆、模型切换、观测计费……每个团队都在重复造同一套胶水层。Dify 把这套胶水层产品化,开源自托管。

Q3边界在哪?

它是应用层的编排平台:不训练模型、不做推理加速(那是 vLLM/Ollama 的事),也不是通用代码框架(那是 LangChain 的事)。模型对它来说只是可插拔的供应商;你的业务系统通过 REST API 和它对接。

四个典型痛点 → Dify 的对应答案

提示词散落在代码里,改一句话要发版,产品经理插不上手
→
可视化 Prompt 编排 + 版本化,应用配置与代码解耦,发布即生效
RAG 全靠手搓:切分、embedding、向量库、召回、重排,每个环节都要选型踩坑
→
内置知识库流水线:上传文档 → 自动分段/向量化 → 混合检索 + Rerank,开箱即用
换个模型要改一片代码,OpenAI、Claude、本地模型接口各不相同
→
Model Runtime 统一抽象,数十家供应商以插件接入,界面上切换,应用无感
上线后是黑盒:哪次回答用了多少 token、检索命中了什么,无从追查
→
每次调用的完整执行轨迹可回放:节点耗时、token 计量、召回段落、标注反馈
它不是什么:不是模型托管服务(自己不跑推理)、不是 AI 编程助手、不是通用自动化工具(和 n8n 的定位不同)。如果你的需求只是"在 Python 里调一次 GPT",引入 Dify 是杀鸡用牛刀。
02 · 同类位置

在坐标系里找到它

横轴:交互方式(写代码 ↔ 可视化编排);纵轴:覆盖范围(单点能力 ↔ 一体化平台)。Dify 站在"可视化 + 一体化"的右上角,这也决定了它的取舍。

项目本质与 Dify 的差异
Dify开源一体化 LLM 应用平台画布编排 + RAG + Agent + 观测 + API 发布,自托管
LangChain代码框架 / SDK灵活度上限更高,但基建(UI、租户、观测)全要自建
Flowise / Langflow可视化编排工具更轻,偏"画流程";知识库、团队协作、企业能力较薄
Coze闭源 SaaS Bot 平台上手更快,但数据在别人手里,不能自托管、难深度二开
FastGPT开源知识库问答平台RAG 场景聚焦;Dify 的工作流/Agent/插件面更宽
n8n通用工作流自动化强在连接 SaaS 生态,LLM 只是其中一类节点,无 RAG 纵深
03 · 核心概念

五种应用形态,一套发布出口

在 Dify 里你创建的不是"脚本"而是"应用(App)"。五种形态覆盖从单轮生成到复杂编排;无论哪种,发布后都同时得到一个开箱可用的 WebApp 和一组 REST API。

多轮对话应用,最经典的形态

配置一段系统提示词、可选地挂上知识库和会话变量,就得到一个带记忆的问答机器人。适合直接从"客服 / 内部知识问答"落地,不需要理解工作流概念。开场白、下一步问题建议、引用溯源、语音输入都是现成开关。

典型场景:产品客服、员工手册问答、IT 帮助台

会自己决定"下一步做什么"的对话应用

在 Chatbot 之上赋予模型工具调用能力(Function Calling / ReAct):它自行推理该搜索、查数据库还是画图,循环"思考 → 调工具 → 观察结果"直到给出答案。工具来自内置集合、插件市场或你自定义的 OpenAPI 接口。

典型场景:联网检索助手、能查订单系统的客服、数据分析助手

单轮输入 → 单次输出的生成器

没有会话记忆,用户填一个表单(变量),模型产出一段结果。形态最简单,却是很多提示词工程的最佳载体:翻译器、文案生成、SQL 生成、摘要器,都是"一进一出"。

典型场景:营销文案批量生成、周报摘要、代码注释生成

对话版工作流:多轮 + 编排两者兼得

当一个"聊天机器人"复杂到需要先分类意图、再走不同分支、中途调 HTTP 接口时,就升级成 Chatflow:画布上编排节点,同时保留会话记忆与流式回复(Answer 节点)。首页 Hero 里那张画布就是一个 Chatflow。

典型场景:多意图客服(退款走 A 链路、咨询走 B 链路)、引导式问诊

面向任务的自动化流水线,无会话概念

一次触发、跑完整条 DAG、输出结构化结果,更像"用 LLM 节点武装起来的数据流水线":批量处理文档、内容审核、结构化抽取。支持条件分支、循环迭代、并行、代码节点,可被外部系统以 API 触发,嵌入你的业务流程。

典型场景:合同要素抽取、舆情打标、批量翻译流水线

04 · 核心运行链路

一条消息的旅程:从 HTTP 请求到流式回答

这是理解 Dify 的主线。假设你的系统调用了 POST /v1/chat-messages,消息在 Dify 内部会走完下面六站——点击每一站,看看它发生在哪、对应源码里的哪个目录。

STEP 1 · API 入口:nginx → api 服务(Flask)

请求带着 Bearer app-xxx 密钥打到 nginx,被转发给 api 容器。这里完成三件事:鉴权(密钥对应哪个应用、哪个租户)、限流与参数校验、以及创建本次会话/消息记录。Console 控制台与对外 Service API 走的是不同的 controller 蓝图,互不干扰。

api/controllers/service_api/ — /v1 对外接口
api/controllers/console/ — 控制台接口
nginx → api(Flask)鉴权、限流、参数校验
App Runner按应用类型装配执行计划
Workflow Engine按 DAG 依次/并行执行节点
RAG Retrieval向量库召回 + 重排
Model Runtime / 插件统一协议调用模型供应商
SSE 流 + PostgreSQL/Celery边生成边返回,异步记日志
05 · 知识库数据流

RAG 流水线:一份 PDF 如何变成"可被引用的答案"

运行链路里的 STEP 4 值得单独展开——知识库是 Dify 使用最重的能力。它分两条时间线:写入侧(上传文档时发生,一次性、异步)与查询侧(每次提问时发生,毫秒级)。点击步骤查看每一步的输入与输出。

写入 ① 解析(ETL):从文件到纯文本

上传的 PDF / Word / Markdown / 网页由 Celery worker 异步解析为统一的文本文档,抽取标题、来源等元数据。也可以接 Firecrawl/Notion 等数据源同步。这一步的质量决定后面一切——扫描版 PDF、复杂表格是常见的翻车点。

输出纯文本文档 + 元数据 {source, title, …}

写入侧:上传时执行一次,由 worker 异步完成

.env 里最先会碰到的几项

docker/.env(节选)
# 部署对外地址(反代/HTTPS 后必须改)
CONSOLE_WEB_URL=http://your-host
SERVICE_API_URL=http://your-host

# 会话与加密密钥,生产环境务必重新生成
SECRET_KEY=sk-...(openssl rand -base64 42)

# 向量库选型:weaviate / qdrant / milvus / pgvector ...
VECTOR_STORE=weaviate

# 上传文件存储:本地卷或 S3 兼容对象存储
STORAGE_TYPE=opendal

# 数据库与 Redis(compose 内置,外接生产库时改这里)
DB_HOST=db  REDIS_HOST=redis

经验法则:模型的 API Key 不在 .env 里配,而是在启动后的控制台「设置 → 模型供应商」中填写,存进数据库并加密。.env 管平台本身,控制台管模型与应用。

08 · 十分钟上手

从 clone 到第一个 API 调用

三步走:起服务 → 在界面上建应用 → 用 API Key 把它接进你的系统。机器要求不高:2 核 4GB 起步,需装好 Docker。

terminal
# 1. 拉代码,进入部署目录
git clone https://github.com/langgenius/dify.git
cd dify/docker

# 2. 生成配置并启动全家桶(api/worker/web/db/redis/向量库…)
cp .env.example .env
docker compose up -d

# 3. 验证:应能看到 api、worker、web、db、redis、nginx 等容器 Up
docker compose ps

然后浏览器打开 http://localhost/install,设置管理员账号;进入控制台后先去 「设置 → 模型供应商」 安装模型插件并填入 API Key(或接 Ollama 本地模型)——没有这一步,任何应用都跑不起来。

用界面完成,零代码

以最常见的"知识库客服"为例,控制台里的操作路径:

① 知识库 → 创建:拖入几份 PDF/Markdown,选默认分段与"高质量"索引,等待 worker 完成向量化;
② 工作室 → 创建应用 → Chatbot:写好系统提示词,在「上下文」里挂上刚建的知识库,右侧调试区直接对话验证,可看到每次回答引用了哪些文档段落;
③ 发布:得到一个可直接分享的 WebApp 链接,以及本应用专属的 API 密钥(app- 开头)。

提示:调试区右上角的「日志与标注」是 Dify 的隐藏财富——上线后回看真实用户的问题与检索命中,是迭代提示词和分段策略的依据。

curl — 调用刚发布的 Chatbot
curl -X POST 'http://localhost/v1/chat-messages' \
  -H 'Authorization: Bearer app-xxxxxxxxxxxx' \
  -H 'Content-Type: application/json' \
  -d '{
    "inputs": {},
    "query": "退货流程是什么?",
    "user": "user-42",
    "response_mode": "streaming"
  }'
响应(SSE 流,节选)
data: {"event": "message", "answer": "您好,", "conversation_id": "c1a2…"}
data: {"event": "message", "answer": "退货可在订单页发起…"}
data: {"event": "message_end", "metadata": {"usage": {"total_tokens": 356}, "retriever_resources": […命中的知识段落…]}}

要点:API Key 按应用签发(不是按账号),带上稳定的 user 标识即可获得多轮会话;后续轮次传回 conversation_id。Workflow 类应用则调用 POST /v1/workflows/run。官方提供 Python / Node SDK,本质是这组 REST 接口的封装。

09 · 适用边界与采用风险

什么时候用它,什么时候别用

一体化平台的取舍是恒定的:换来速度与完整度,付出的是灵活性天花板与平台绑定。诚实地列在这里。

适合

  • 企业内部知识问答 / 客服:RAG + 引用溯源 + 日志标注,一条龙现成
  • 需要频繁调提示词的团队:产品、运营可直接在画布上迭代,不依赖发版
  • 多模型策略:今天 GPT 明天 DeepSeek 后天本地化,应用层零改动
  • 数据必须留在自己机房:全栈自托管,合规审计友好
  • 把 LLM 能力包装成 API 供多个业务系统复用,统一计量与观测

不适合

  • 极简单的一次性调用:直接十行代码调模型 API 更快,别引入一套平台
  • 需要非常规编排逻辑(复杂状态机、自定义调度、深度多智能体协作):画布表达力有上限,代码框架(LangGraph 等)更合适
  • 极致性能 / 超大并发场景:平台层有额外开销,且默认 compose 部署非高可用
  • 重前端定制的 C 端产品:自带 WebApp 只适合轻量使用,深度 UI 要自建前端走 API
中版本迭代快,升级需要当回事 +
社区版发布节奏很快,涉及数据库 migration;主版本(如 0.x → 1.x 引入插件体系)升级有迁移步骤。建议:固定镜像 tag、升级前备份 PostgreSQL 与 volumes、先在预发环境演练,不要 latest 裸奔。
中License 不是标准 Apache 2.0 +
Dify 采用 Apache 2.0 附加条款的开源协议:自用、内部商用、二次开发基本自由,但用它运营多租户 SaaS、或移除 Logo/版权信息需要商业授权。打算基于它做商业化产品前,读一遍仓库根目录的 LICENSE。
中应用逻辑沉淀在平台里,存在迁移成本 +
编排以 DSL(YAML)形式存在,可导出导入,但它是 Dify 自己的格式——迁去别的框架等于重写。缓解方式:把关键业务逻辑放在你自己的服务里,让 Dify 专注"模型编排"这一层,通过 API 边界解耦。
低默认部署是"能用",不是"生产级" +
docker compose 单机全家桶适合试用与小团队;上生产要考虑:外接托管 PostgreSQL/Redis、独立向量库、对象存储、HTTPS、备份策略。官方提供 Helm/K8s 社区方案,但运维复杂度是实打实的成本。
低深度二开需要吃透两套技术栈 +
改后端要熟 Python/Flask/Celery/SQLAlchemy,改画布要熟 Next.js/React Flow。好消息是分层清晰(controllers → services → core),且大部分扩展需求(新模型、新工具)可以用插件解决而不必动源码。
10 · 一分钟自测

该不该引入 Dify?勾一勾就知道

这五个问题浓缩了前面所有分析。命中越多,Dify 越可能是正确选择。

✓我们要做的是应用层的事(问答、生成、流程自动化),而不是训练或托管模型
✓团队里不止工程师需要参与提示词与流程的迭代
✓需求里有知识库 / RAG,且不想从零搭建检索流水线
✓数据合规要求自托管,或希望在多家模型间保持切换自由
✓可以接受平台的编排范式,把非常规逻辑留在自己的服务里通过 API 对接
还没有勾选。如果多数不命中——尤其第一条——直接写代码或选更轻的工具可能更合适。
