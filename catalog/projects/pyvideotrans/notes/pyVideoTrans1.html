L0

项目概览

本层只回答:它是个什么东西?边界在哪?——只看轮廓,不看内部。

一句话定位:pyVideoTrans 是一个开源的视频翻译配音工具—— 输入一个中文视频,输出一个"说着英语、带英语字幕"的同一个视频(语言任选)。

痛点场景:手工做视频本地化的链条是:听录文稿 → 翻译 → 找配音 → 对时间轴 → 压字幕, 一个 10 分钟视频耗一整天。pyVideoTrans 把这条人工链变成了一条自动数据链, 并且链上每个环节(识别、翻译、配音)都支持二三十种引擎自由替换,可完全离线。

L1

核心流程抽象

本层回答:用一个脚本概括,它怎么跑?——剥掉全部工程,只剩主干道。

标准模式(视频翻译配音)的主链,本质就是这个函数。编号 ①–⑨ 与官方架构文档的九阶段一致,也与 L2 的九张卡片一一对应:

# pyVideoTrans 标准模式主链 · 伪代码骨架(编号对应 L2 各步)
def translate_video(video, src_lang, dst_lang, voice):

    # ① 预处理:视频 → 无声视频 + 音频(可选:人声/背景分离)
    novoice, audio      = prepare(video)
    vocal, bgm          = separate(audio)          # 可选,保 BGM

    # ② 语音识别:音频 → 带时间戳的源语言字幕
    src_srt = recogn(vocal)                        # 默认 Faster-Whisper

    # ③ 说话人分离:给每条字幕标注"谁在说"(可选)
    src_srt = diariz(src_srt, vocal)

    # ④ 字幕翻译:源语言字幕 → 目标语言字幕(时间轴不动)
    dst_srt = trans(src_srt, dst_lang)

    # ⑤ 配音:逐条字幕 → 一段段语音片段
    segments = dubbing(dst_srt, voice)

    # ⑥ 音画对齐:配音加速 / 视频慢放,贴回原时间轴
    dub_wav, novoice = align(segments, novoice)

    # ⑦ 二次识别:对配音重新出短句精确字幕(可选)
    final_srt = recogn2pass(dub_wav)

    # ⑧ 最终合成:无声视频 + 配音 + 背景乐 + 字幕 → 成品
    result = assembling(novoice, dub_wav, bgm, final_srt)

    # ⑨ 收尾:移动产物、清缓存、发通知
    return task_done(result)

注意数据形态的接力:视频在 ① 被拆成 无声画面与音频两条支流, 音频支流经 ②③④ 变成字幕文本、再经 ⑤⑥ 变回音频, 最后 ⑧ 把两条支流缝合成成品。 字幕(SRT)是全链的枢纽格式——翻译改的只是它的文本,配音消费的只是它的文本+时间轴。

①

预处理

prepare()
入参
视频文件
# 示意 · ffprobe 摘要 input.mp4 · 时长 00:10:23 · 流0: h264 1920x1080 · 流1: aac 44100Hz 立体声
处理
FFmpeg 把视频拆成两条支流:抽出无声视频流(-an)与完整音频(-vn); 可选再做人声/背景分离与降噪。 为什么必须做:后面只翻译替换"人声",画面与 BGM 要原封不动地留到 ⑧ 再缝回来。
出参
novoice.mp4audio.wav(可选 vocal.wav / background.wav)
验收
👁 缓存目录出现上述文件;
⌨ ffprobe novoice.mp4 应只有视频流没有音频流;ffprobe audio.wav 时长 = 原视频时长。
流向
音频(或 vocal)→ ②;无声视频 → ⑥⑧;背景乐 → ⑧(两条"越线"直达)。
②

语音识别

recogn()
入参
人声音频(16kHz 单声道)
处理
VAD 切段 → ASR 引擎(默认 Faster-Whisper,共 22 种渠道)逐段转写并打时间戳;可选标点恢复、LLM 智能断句。 为什么必须做:这一步把"声音"第一次变成"带时间坐标的文本"——之后所有加工都基于它。
出参
source.srt
# 示意 · SRT 格式(序号/时间轴/文本 三行一组) 1 00:00:01,200 --> 00:00:04,800 今天我们来聊聊开源项目。 2 00:00:05,100 --> 00:00:08,300 先从整体结构说起。
验收
👁 打开 srt:时间轴单调递增、无空文本行、语言是源语言;
⌨ head -8 source.srt 抽查;grep -c " --> " source.srt 得到字幕条数备用。
流向
→ ③(开了说话人分离)或直接 → ④。
③

说话人分离(可选)

diariz()
入参
source.srt + 人声音频
处理
说话人分离模型(pyannote、阿里 CAM++ 等四种后端)判断每条字幕"是谁说的",写入 spk 标记。为多角色配音(⑤ 换不同音色)做准备。此步异常不阻断整体流程。
出参
带 spk 标注的 srt
# 示意 2 00:00:05,100 --> 00:00:08,300 [spk1]先从整体结构说起。
验收
👁 spk 标签种类数 ≈ 视频中实际说话人数(明显偏多=过分割)。
流向
→ ④。
④

字幕翻译

trans()
入参
source.srt + 目标语言代码
处理
翻译渠道(24 种:DeepSeek/ChatGPT/Gemini 等 LLM,或谷歌/微软传统机译,或本地 Ollama)逐批翻译。 关键约束:只换文本,不动时间轴、不增减条数——时间轴是 ⑤⑥ 的坐标系,动了全链失准。可选输出双语字幕。
出参
target.srt
# 示意 · 时间轴与 source.srt 完全一致 1 00:00:01,200 --> 00:00:04,800 Today, let's talk about open-source projects.
验收
👁 抽读 3 条译文是否通顺、术语是否一致;
⌨ grep -c " --> " target.srt 必须等于 source.srt 的条数;时间轴逐条相同。
流向
→ ⑤(要配音)/ 直接 → ⑧(仅嵌字幕模式,见 L3)。
⑤

配音

dubbing()
入参
target.srt + 配音角色(可按 spk 分配多音色)
处理
TTS 引擎(34 种:Edge-TTS 免费款 / OpenAI·Azure 商业款 / F5-TTS·CosyVoice·GPT-SoVITS 克隆款)逐条字幕生成一个语音片段; 克隆引擎会自动从 ① 的原音频里截取该说话人的参考片段——"用原声的嗓子说外语"。
出参
N 个语音片段(按字幕序号命名)
# 示意 · 缓存目录 0001.mp3 (对应字幕1, 3.9s) 0002.mp3 (对应字幕2, 3.4s) # 注意:时长≠字幕槽位,交给⑥解决
验收
👁 片段数 = 字幕条数;抽听 2 条:内容对、音色对;
⌨ ls | wc -l 对比 grep 出的条数。
流向
→ ⑥。
⑥

音画对齐

align()
入参
语音片段们 + target.srt(槽位)+ novoice.mp4
处理
全链最见功力的一步。翻译后句子长度必然变化(中译英通常变长),片段塞不进原时间槽。 SpeedRate 策略组合:配音加速、 该段视频慢放、挪用字幕间隙的静音、强制对齐,自动求平衡;完成后可调音量。
出参
整轨 dubbing.wav + (可能局部调速的)novoice.mp4
验收
👁 抽查任一句:配音起点 ≈ 字幕起点(±0.1s);语速无明显"抢拍"感;
⌨ ffprobe dubbing.wav 总时长 ≈ 视频时长。
流向
→ ⑦(启用了配音且非双字幕嵌入)/ → ⑧。
⑦

二次识别(可选)

recogn2pass()
入参
dubbing.wav(⑥ 的成品配音)
处理
对配音再跑一遍 ②:因为 ⑥ 的加速/挪移已让 target.srt 的时间轴与实际配音有偏差, 重新识别能得到时间轴精确、句子更短的最终字幕——保证观众看到的字与听到的音严丝合缝。
出参
final.srt(短句化、贴音版)
验收
同 ②:时间轴单调、无空行;抽 1 句与配音对播,字音同步。
流向
→ ⑧。
⑧

最终合成

assembling()
入参
novoice.mp4 + dubbing.wav + background.wav(来自①的越线)+ final.srt
处理
FFmpeg 一次缝合:混音(配音+背景乐)、封装音视频、字幕硬嵌或软封装。 ① 拆开的所有支流在此全部汇合,闭环完成。
出参
result.mp4
验收
⌨ ffprobe result.mp4:1 条视频流 + 1 条音频流(软字幕另有字幕流);时长 ≈ 原视频;
👁 拖动播放抽查开头/中段/结尾三处:口播、字幕、背景乐三者同步。
流向
→ ⑨。
⑨

收尾

task_done()
入参
result.mp4 及全部中间产物
处理
把成品与保留产物(双语 srt、配音轨)从临时目录移入输出目录,清理缓存,发送完成通知。
出参
输出目录里的最终交付物——即 L0 边界图的输出。
验收
👁 输出目录包含 result.mp4 与 srt 文件;临时目录已清空。
流向
链路终点。
知其所以然 · 一句话总结本层:整条链就是"拆流—换声—缝合"三段: ① 把画面/人声/背景拆成三条支流;②–⑦ 只加工"人声"这一条(声→字→译→声→对齐);⑧ 三流汇合。 理解了 ① 的三条越线(无声视频、背景乐直达后段),你就理解了为什么成品能保住画面与 BGM。

L3

功能模式组合

本层回答:菜单里那么多功能,怎么由同一批步骤拼出来?——换乘图视角。

软件没有为每个功能写一套代码。每个任务创建时会算出 5 个开关,决定九步中哪些执行、哪些跳过:

# videotrans/task/_base.py · 五个流程开关(示意) should_recogn # 需要识别吗?(没有现成字幕 → True) should_trans # 需要翻译吗?(源语言 ≠ 目标语言 → True) should_dubbing # 需要配音吗?(选了配音角色 → True) should_hebing # 需要合并嵌入吗?(有配音或要嵌字幕 → True) should_separate # 需要人声/背景分离吗?

①→⑨ 全部执行,即 L2 讲的完整链。CLI 代号 vtv。四个开关全开。

提取模式(tiqu):只走 ①→②(→③→④ 可选翻译),产物是 SRT 字幕,不配音不合成。 CLI 代号 stt。等于把主链在 ④ 之后"剪断",⑤–⑧ 全部跳过。批量转录播客、生成双语字幕就是它。

字幕翻译:入口直接是一个 srt 文件,只执行 ④。CLI 代号 sts。 验收标准与 L2-④ 完全相同(条数相等、时间轴不动)——同一道工序,单独出售。

字幕配音:入口是 srt,执行 ⑤→⑥→⑧(以字幕为剧本合成整轨配音,可与已有视频合并)。CLI 代号 tts。 注意它复用的正是主链的配音与对齐工序,没有任何新逻辑。

功能(CLI 代号)识别②翻译④配音⑤⑥合成⑧
视频翻译配音(vtv)✓✓✓✓
音视频转字幕(stt / tiqu)✓可选✗✗

L4

工程化设计(附录)

本层回答:脚本怎么变成产品?——⚠️ 跳过本层完全不影响理解原理。

L1 的伪代码一次只能处理一个视频,而且跑起来界面会卡死。真实项目在它外面包的每层壳,都对应裸脚本的一个痛点:

工程设施解决裸脚本的什么痛点
九条队列 + 专职 Worker 线程裸脚本 for video in videos 串行太慢 → 每个阶段一条队列、一类 Worker(QThread)接力,第 1 个视频在配音时第 2 个可同时在识别,流水线并行
按开关路由下一跳不同模式要走不同分支 → Worker 干完活按五个开关决定把任务丢进哪条队列(L3 的开关在此落地)
BaseWorker 统一容错一个视频报错全批崩掉 → 基类统一捕获异常、翻译成人话、单任务失败不影响队列里其他任务
TaskCfg 分层 dataclass几十个参数散着传容易错 → 任务配置按 STT/TTS/STS/VTT 分层继承,一个对象随任务全程流转
GUI(PySide6)/ CLI / WebUI / Docker不同人群不同用法 → 同一条流水线的四个入口;重活全在后台线程,界面永不冻结

与 L1 对照:伪代码里顺序执行的九个函数,工程里变成了九条队列间的"击鼓传花"; 传的"花"就是任务对象(带着五个开关和 TaskCfg)。结构一模一样,只是从单人作业变成了流水线车间。

队列流水线相比 for 循环串行,换来的两个直观好处是什么?五个开关在工程层的哪个环节被真正"消费"?
尾声

快速上手

跑通第一个例子的最短路径。

最短路径

  1. Windows:Releases 下载整合包 → 解压到纯英文无空格路径 → 双击 sp.exe。
  2. 源码(macOS/Linux):装好 FFmpeg 后:
    git clone https://github.com/jianchang512/pyvideotrans.git cd pyvideotrans && uv sync && uv run sp.py
  3. 零成本引擎组合:识别 Faster-Whisper(本地)+ 翻译 Google + 配音 Edge-TTS——不要任何 API Key 即可跑通全链。
  4. CLI 一条命令复现主链:
    uv run cli.py --task vtv --name "./video.mp4" \ --source_language_code zh-cn --target_language_code en \ --voice_role "en-US-GuyNeural"

常见坑

源音频质量决定上限

② 是第一道工序,嘈杂/带混响的音频会让全链走偏;BGM 重的视频务必开人声分离(①)。

善用暂停校对

② 和 ④ 完成后可暂停人工修字幕再继续——花几分钟,成品质量远超全自动一把梭。

路径避开中文与空格

Windows 下软件与素材都用纯英文路径,可绕开大量 FFmpeg 诡异报错。

GPU 值得上

CPU 能跑,但 Faster-Whisper 在 NVIDIA GPU 下快数倍;整合包需 CUDA 12.8 + cuDNN 9.11。

关键概念速查

SRT 字幕
全链枢纽格式:序号/时间轴/文本三行一组。类比:一张带时间坐标的"台词表",翻译只改台词,配音照表演出。
ASR / TTS / VAD
ASR=听写员(声→字,②);TTS=配音员(字→声,⑤);VAD=场记(判断哪些时段有人说话,②内部)。
人声/背景分离
把一条音轨拆成"人声"与"BGM"两轨(①,UVR5/Spleeter)。目的:只翻译人声,BGM 原样保留到 ⑧。
硬字幕 / 软字幕
硬=烧进画面像素,不可关;软=独立字幕轨,播放器可开关(⑧ 二选一)。
音画对齐(SpeedRate)
⑥ 的策略集:配音加速、视频慢放、挪用句间静音,让变长的译文仍贴住原时间轴。

一段话总结:pyVideoTrans = 一条"拆流—换声—缝合"的视频本地化流水线: ① 拆出三条支流,②–⑦ 只加工人声(声→字→译→声→对齐),⑧ 汇合成品; SRT 是全链枢纽,五个开关把九道工序拼成菜单里的全部功能,队列与线程只是让这条链能并行、不卡、不怕错的外壳。
