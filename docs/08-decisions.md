# 决策记录(Decisions)

这篇是 GitHub Gallery 设计过程中**已拍板的关键决策台账**。它不重复各分册的细节,只做一件事:
**把每个决策"定成了什么、为什么这么定、在哪篇文档展开"记下来,供日后追溯。**

- 想读某决策的完整上下文,顺着"详见"链接去对应分册。
- 决策一旦推翻或修订,在此更新并同步相关分册的 `> 已定稿` 标注。

> 前提:本项目是**全新项目、不考虑向后兼容、单人本地使用**。下述决策大量遵循"保持简单、
> 不为未定的未来过度设计"这一取向。

## 决策详情与理由

### D1 · AI 分析触发时机 = 按需分析
候选(candidate)只展示 GitHub 原始信息、**不调 LLM**;仅在**收藏晋升**(`POST /api/candidates/{id}/save`)
那一刻触发 AI 生成 summary/category/tags。
**理由**:流是易逝、量大的,对每个候选都跑 AI 既贵又浪费;"值得收藏"正是"值得花 AI 成本"的天然分界。
这也正是用户最初"如果我需要,我可以选择进行分析"的意图。

### D2 · 手动添加默认即时分析
`POST /api/repos` 的 `analyze_now` 默认 `true`;可显式传 `false` 先入库、稍后手动 `analyze`。
**理由**:手动贴单个 URL 的场景通常就是想立刻看到分析结果,默认即时最顺手;保留 `false` 兼顾"先囤后看"。

### D3 · 状态机:轻收藏、自由流转
初始 `watching`;`watching`/`to-learn`/`learning`/`using` 四态**自由双向流转、不限制任何跳转**;
收藏晋升时**不弹初始状态选择**,状态在库里随时改。
**理由**:单人工具,收藏动作要轻;状态调整是低频后续行为,不值得为它增加晋升时的决策负担。

### D4 · 移除:归档优先、硬删除设防
归档(置 `archived_at`)是默认"移除"动作,可恢复;硬删除是次级操作,**藏在归档区内且需二次确认**,
主视图不暴露。
**理由**:日常"移除"多是"不再关注"而非"判垃圾",默认可恢复最安全;不可逆操作刻意抬高门槛。
归档与 `status` 正交,归档不丢失学习状态。

### D5 · 归档列表复用主列表端点
不拆独立端点,由 `GET /api/repos` + `archived` 参数承载(不传/`false` → 未归档;`true` → 已归档)。
**理由**:归档项目与库项目结构完全相同,只是可见性维度不同,复用同一端点最简洁,库/归档共享同一套
筛选与分页逻辑。

### D6 · 归档区入口在库页侧栏底部
`/archive` 是独立路由但非顶层 Tab,入口放在库页面筛选侧栏底部的次级文字链接。
**理由**:低频回顾入口,不该占用顶层导航,视觉上与常用筛选分层。

### D7 · 不做数据迁移,直接重建
新项目不考虑兼容,**不写迁移脚本**;Phase 1 直接按 [02](./02-domain-model.md) 的四表 schema 重建本地库,
丢弃现有 `gallery.db` 示例数据。
**理由**:尚无有价值的历史数据,迁移工具纯属额外复杂度。

### D8 · Dashboard 固定 7 字段
`today_new_candidates`、`pending_count`、`library_total`、`archived_total`、`status_counts`、
`latest_batch`、`recent_repos`。
**理由**:恰好覆盖三层模型的态势(流 / 库 / 快捷入口),不多不少。

### D9 · 文档列表省略正文
`GET /api/repos/{id}/docs` 只返回文档元数据,`content` 走 `GET /api/docs/{id}` 按需拉取。
**理由**:一篇 repo 可能挂多篇长文,列表带回全部正文浪费带宽;详情页文档 tab 列表只需元数据。

### D10 · AI 起草文档:显式、落库、不降级
用户在详情页文档区显式点击「AI 起草 + 类型」触发,生成后直接持久化为新 `doc` 供编辑;
LLM 未配置时返回 `422` 明确禁止,**不造占位文案**。
**理由**:起草是主动的深度操作,非自动/批量;未配置就明确失败,符合"不擅自降级兜底"原则。

### D11 · 卡片配色
语言色点用 GitHub Linguist 官方语言配色;分类色标由分类名稳定 hash 映射到固定柔和色板(约 8–12 色),
同类恒定同色;状态徽章 4 态固定色系——`watching`→`slate`、`to-learn`→`amber`、`learning`→`emerald`、
`using`→`violet`。具体 hex 在实现期的 Tailwind theme token 定义。
**理由**:语言色沿用约定俗成;分类 hash 保证一致又克制;状态色承载语义、辅助扫读。

### D12 · 前端类型生成
`openapi-typescript` 从 FastAPI `/openapi.json` 生成类型,配 `openapi-fetch` 做类型安全调用;
开发期手动脚本(`npm run gen:api`)生成,不进构建关键路径。
**理由**:单一真源(后端 Pydantic → OpenAPI → 前端类型)避免类型漂移;手动生成避免每次 build 依赖后端在线。
