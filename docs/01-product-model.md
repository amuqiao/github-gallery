# 01 · 产品模型

> 这篇是什么:GitHub Gallery 的**产品心智模型**——用户在系统里如何思考、内容如何组织、一个项目在其生命周期中会经历哪些状态。
> 解决什么:回答「东西存在哪几层」「怎么在层之间流动」「一个收藏的项目有哪些状态、怎么流转」「移除意味着什么」「AI 什么时候介入」。
> 谁读:所有需要理解产品语义的人——设计、前后端、以及回头看设计意图的自己。
> 不负责什么:不讲字段类型与表结构(见 [02-domain-model.md](./02-domain-model.md)),不讲分层与模块解耦(见 [03-architecture.md](./03-architecture.md)),不讲页面路由与交互(见 [04-navigation-ux.md](./04-navigation-ux.md)),不讲端点入参出参(见 [06-api-contract.md](./06-api-contract.md))。

---

## 心智模型:三层内容,一条动线

GitHub Gallery 把内容分成**物理上分开存储的三层**。理解产品的第一件事,就是理解「东西在哪一层、为什么在那一层」。

| 层 | 中文名 | 本质 | 承载的用户诉求 |
|---|---|---|---|
| ① Flow | 流 | 抓取批次组成的时间线,易逝、可清理 | 每天/每周有新东西流进来,我快速筛 |
| ② Library | 库 | 我明确收藏、长期管理的项目资产,稳定 | 分类、标签、学习状态、移除 |
| ③ Knowledge | 知识 | 优质项目的多角度详情文档,深度沉淀 | 安装使用/项目讲解/我的笔记 |

三层各司其职,**层与层之间不是同一份数据的不同视图,而是不同性质的内容**:

- **流**是易逝的。它由一次次抓取批次(crawl_batch)堆叠成时间线,里面是临时卡片(candidate)。流会不断有新东西涌入,旧的可以清理,不承诺长期保存。
- **库**是稳定的。它是用户明确收藏、愿意长期管理的项目资产(repo)。分类、打标、学习状态、移除,都发生在这一层。
- **知识**是沉淀。它是挂在优质项目下的多角度详情文档(doc):安装使用、项目讲解、我的笔记等。深度内容,不是每个项目都值得写。

### 两个关键实体不要混用

> **候选(candidate)= 流里的临时卡片;收藏(repo)= 库里的正式项目。** 二者是**不同实体**,存在不同的表里,不要当成同一个东西的两个状态。

一个 candidate 只携带 GitHub 原始信息;它被「收藏晋升」后,才在库里诞生一个 repo。晋升是一次跨层的实体转换,不是原地改个标记。字段层面的差异见 [02-domain-model.md](./02-domain-model.md)。

## 跨层动线:核心是流动,不是驻留

用户的核心动线是**跨层连续流动**,而不是在某一层里长期停留:

```
流里发现  →  收藏晋升进库  →  库里点开  →  写详情文档
(Flow)      (candidate→repo)   (Library)     (Knowledge)
```

逐段来看:

1. **流里发现**:在流的 feed 里刷抓取来的候选卡片,快速判断「值不值得留」。这里只看 GitHub 原始信息(名称、描述、stars、语言、topics)。
2. **收藏晋升**:对一个 candidate 执行「收藏」,它就晋升进库,成为一个 repo。这一刻是流→库的跨层跳转,也是 AI 分析的触发点(见下文「AI 分析触发时机」)。晋升后,原 candidate 会带上「已收藏」角标,指回新生成的 repo。
3. **库里点开**:在库里靠筛选(分类/标签/状态/语言)和搜索找到项目,点开进入 repo 详情页。
4. **写详情文档**:在详情页里为这个 repo 沉淀多角度文档(doc),内容进入知识层。

这条动线是产品的主心跳。导航设计因此**不采用「做完回中心」的 Hub-and-Spoke 作主结构**,以免打断心流——详见 [04-navigation-ux.md](./04-navigation-ux.md)。

> 知识层目前不独立成 Tab,而是合进「库」的详情页;等出现跨项目检索文档的需求再拆(可延后,不重构)。

## 生命周期状态机:一个收藏项目的学习进度

进入库之后,每个 repo 带一个 `status`,表示**用户对它的学习/使用进度**。取值 4 个,英文存储、中文展示:

| 存储值 | 中文标签 | 含义 |
|---|---|---|
| `watching` | 关注中 | 留意着,还没深入 |
| `to-learn` | 想学 | 排进学习队列 |
| `learning` | 正在学 | 当前在啃 |
| `using` | 在用 | 已用在我的项目里 |

### 流转规则

- **默认新收藏为 `watching`**:candidate 晋升为 repo 时,status 初始化为 `watching`。
- **可自由流转,不强制单向**:四个状态之间任意跳转。它反映真实的学习节奏——可以从 `learning` 退回 `to-learn`,也可以直接从 `watching` 跳到 `using`。

用一张图看典型流向(实线为常见路径,但任意方向都允许):

```
              收藏晋升
candidate ─────────────▶ [watching 关注中]
                              │
                              ▼
                        [to-learn 想学]
                              │
                              ▼
                        [learning 正在学]
                              │
                              ▼
                        [using 在用]

任意两态之间均可双向流转,上图仅示意最常见的推进方向。
```

> **已定稿**:`status` 初始值为 `watching`;四态自由双向流转,**不限制任何跳转**。收藏晋升时**不弹初始状态选择**,保持「一键收藏」,状态在库里随时手动改。理由:单人本地工具,收藏动作要轻,状态调整是低频后续行为,不值得为它增加晋升时的决策负担。

## 软删除语义:归档 vs 硬删除

「移除一个项目」在本产品里有**两种不同语义**,必须区分清楚。这是显式的产品设计,**不是**「删除失败就藏起来」的隐式降级。

### 归档(软删除)= 默认的「移除」动作

- 操作:置 `archived_at` 时间戳(非空即为已归档)。
- 效果:项目退出流/库的主视图,但仍可在「归档区」和搜索里找到。
- 理由:用户口中的「移除」多数是「不再关注」,而不是「判定为垃圾」。保留判断痕迹,能避免日后重复研究、重复抓取同一个项目。

### 硬删除 = 真正物理删除

- 操作:从库里彻底删除该 repo(及其挂载的 doc)。
- 定位:**次级操作**,只用于误加、重复、纯垃圾等确实不该留痕的情况。

### 归档与 status 正交(关键设计)

**归档不是一个 `status` 取值**,而是与 `status` 完全正交的另一个维度:

- `status`(`watching`/`to-learn`/`learning`/`using`)描述「学习进度」。
- `archived_at`(空 / 非空)描述「是否已从主视图移除」。

二者互不干扰。所以**一个已归档的项目仍保留它最后的学习状态**——比如一个 `learning` 中的项目被归档,日后取消归档时,它依然是 `learning`,不必重新设定进度。这正是把归档做成独立维度、而不是塞进 status 的原因。

> **已定稿**:归档 = 默认「移除」动作(库/流卡片上的移除按钮即归档)。硬删除是次级操作,**藏在归档区内、且需二次确认**;库/流主视图不直接暴露硬删除入口。这样日常「移除」永远是安全可恢复的,不可逆操作被刻意抬高门槛。

## AI 分析触发时机

AI 分析(生成 `summary` 中文摘要 / `category` 中文分类 / `tags` 标签)是**按需触发**的,不对流里的每个候选无差别调用。

> **已定稿**:采用下述「按需分析」策略。

策略——**按需分析**:

- **流里的 candidate**:只展示 GitHub 原始信息,**不调 LLM**。流是易逝的、量大的,对每个候选都跑一遍 AI 既贵又浪费。
- **收藏晋升那一刻**(`POST /api/candidates/{id}/save`):才触发 AI 分析,为新生成的 repo 填充 summary/category/tags。「值得收藏」是「值得花 AI 成本」的自然分界。
- **手动贴 URL 进库**(`POST /api/repos`):默认 `analyze_now=true`,即时分析——单个手动添加通常就是想立刻看到 AI 结果;可显式传 `analyze_now=false` 先入库、稍后再点「AI 分析」按钮手动触发(`POST /api/repos/{id}/analyze`)。
- **AI 未配置时**:优雅降级为 GitHub 描述 + 「未分类」(沿用现有 `llm.py` 行为)。

对应的端点语义见 [06-api-contract.md](./06-api-contract.md);「为什么 candidate 不含 AI 字段、不调 LLM」的数据模型体现见 [02-domain-model.md](./02-domain-model.md)。
