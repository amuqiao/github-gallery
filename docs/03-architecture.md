# 03 · 后端架构

## 这篇文档是什么

这篇文档回答一个问题:**代码怎么分层、怎么切模块,才能让"单人本地小项目"在长期迭代中不腐化**。

覆盖范围:
- 四层架构(API/路由 → 服务/用例 → 仓储 Repository → 领域模型/契约)及其依赖方向
- 仓储层作为"解耦"的落地机制
- 按领域纵切的五个模块(`ingest` / `library` / `docs` / `ai` / `core`)及其解耦纪律
- 数据库选型(现在 SQLite,未来 Postgres 的触发条件)
- 现状代码与目标架构的差距,以及从现状到目标的演进路径

不覆盖的内容(见其他文档):
- 实体字段与状态机细节 → [02-domain-model.md](./02-domain-model.md)
- REST 端点的路径/入参/出参 → [06-api-contract.md](./06-api-contract.md)
- 前端技术栈与页面结构 → [04-navigation-ux.md](./04-navigation-ux.md)、[05-frontend.md](./05-frontend.md)

读者:后续接手这个项目的开发者(包括几个月后的自己),在加一个新数据源、加一张新表、或者决定要不要换数据库时,先看这篇。

## 1. 整体心智模型

架构是一张"横切分层 × 纵切模块"的网格:**横着看是层,竖着看是领域模块**。每个模块内部都完整包含四层的一个纵切片,模块之间只在"领域模型/契约层"这一层共享东西。

```
                  ingest              library             docs               ai            core
             ┌────────────────┬───────────────────┬──────────────────┬──────────────┐
API/路由层    │ ingest/router  │  library/router    │  docs/router     │  (无独立路由)  │
             ├────────────────┼───────────────────┼──────────────────┼──────────────┤
服务/用例层   │ ingest/service │  library/service   │  docs/service    │  ai/service   │
             ├────────────────┼───────────────────┼──────────────────┼──────────────┤
仓储层        │ ingest/repo    │  library/repo      │  docs/repo       │  (无仓储,     │
             │ (batch/        │  (repo 表)         │  (doc 表)        │   不持久化)   │
             │  candidate 表) │                    │                  │              │
             └────────────────┴───────────────────┴──────────────────┴──────────────┘
领域模型/契约层  ─────────────────────  core(实体契约:batch/candidate/repo/doc)  ─────────────────────
```

要点:
- **横向(层):** 依赖方向自上而下,箭头不可反向 —— API 依赖服务,服务依赖仓储和领域模型,仓储依赖领域模型,领域模型不依赖任何人。
- **纵向(模块):** `ingest`、`library`、`docs` 各自拥有一条完整的"路由 → 服务 → 仓储"纵切片,互不越界;`ai` 是纯计算服务,没有自己的表也没有自己的路由,被别的模块调用;`core` 不是一个"业务模块",而是被②③④层共享的实体契约,画在最底层是因为所有纵切片都立在它上面。
- 这张图里横向的"层边界"防止"路由里直接写 SQL"这种坍塌;纵向的"模块边界"防止"library 直接 join batch 表"这种越界。两条纪律配合,才能让单人项目在长期堆功能时保持可维护。

## 2. 四层架构

| 层 | 职责 | 厚/薄 | 依赖谁 |
|---|---|---|---|
| ① API / 路由层 | FastAPI 路由:收请求、做输入校验(Pydantic Body/Query)、调用对应模块的服务层方法、把返回的领域模型序列化成响应。 | **薄**:不写业务规则,不直接碰数据库。 | 服务/用例层 |
| ② 服务 / 用例层 | 业务编排与规则本体:收藏晋升流程(candidate → repo)、状态机流转、软删除(归档/硬删除)语义、AI 触发时机的判断("现在该不该调 ai 模块")。 | **厚**:所有"为什么这么做"的逻辑都在这里。 | 仓储层、领域模型、其他模块的服务/API(仅限被允许调用的方向,见 §4) |
| ③ 仓储层(Repository) | 唯一认识数据库的层。对外:接收/返回领域模型(Pydantic 对象);对内:写 SQL / 调 SQLAlchemy。 | 薄且专一:只做数据存取,不做业务判断。 | 领域模型、SQLAlchemy 引擎 |
| ④ 领域模型 / 契约层 | 实体定义(Pydantic 模型:`CrawlBatch`、`Candidate`、`Repo`、`Doc` 及其枚举),是②③④三层之间传递数据时唯一认可的"通用语"。 | 最薄,只是数据结构定义,不含行为。 | 无(最底层) |

字段与枚举取值以 [02-domain-model.md](./02-domain-model.md) 为准,这里不重复定义。

### 务实边界:为什么不搞更"标准"的分层

- **领域模型直接用 Pydantic 贯穿②③④层,不另造 DTO / ORM Model / API Schema 三套对象来回 `.from_orm()` / `.to_dict()`。** 单人本地应用没有"内部表示要对外部隐藏字段"这种强诉求,多一层 Mapper 只是徒增样板代码和心智负担。分层的价值在"依赖方向清晰",不在"类的数量多"。
- **不上事件总线、插件系统、微服务。** 这些机制是为"多团队并行开发"或"运行时动态扩展"服务的,当前是单进程单人应用,模块间的方法调用(Python 函数调用)已经足够表达依赖关系,引入这些机制只会增加理解成本和运行时故障面。
- 换句话说:分层是为了**约束依赖方向**,不是为了**堆砌抽象层数**。

## 3. 仓储层:解耦的落地机制

仓储层不是"为了分层而分层",它同时是两条硬约束的**执行点**:

### 3.1 强制"不跨模块读表"

规则本身("模块间只认对方的 API 和实体契约")只是一句话,真正让它可执行的是:**数据库表只能被拥有它的那个模块的仓储代码访问**。

- `library/repository.py` 是全项目里唯一出现 `... FROM repos ...` SQL 的地方。
- 如果 `ingest` 模块想知道某个 candidate 对应的 URL 是不是已经收藏过,它**不能**自己写一句 `SELECT id FROM repos WHERE url = ?`——那样等于绕过仓储层直接摸别人的表,一旦 `library` 未来给 `repos` 表加字段、拆表、换存储引擎,`ingest` 里那句手写 SQL 立刻变成隐藏的定时炸弹。
- 正确做法:`ingest/service.py` 调用 `library` 暴露的查询方法(例如 `library.service.find_by_url(url) -> Repo | None`,或更收敛的 `library.service.is_saved(url) -> bool`)。`library` 内部无论用什么 SQL、加了什么索引、甚至换了数据库,只要这个方法的输入输出契约不变,`ingest` 一行代码都不用改。

这就是"仓储层强制不跨模块读表"的真实含义:**它把"谁能碰这张表"从一句君子协定,变成了物理上只有一个模块的代码路径能写出访问这张表的 SQL**。

### 3.2 让"换数据库"变成低成本

因为服务层永远只通过仓储层的方法签名(输入/输出都是领域模型)跟数据打交道,从不直接接触连接串、SQL 方言、驱动库,所以换数据库这件事被压缩到仓储层内部:

- 服务层代码里没有一行 `sqlite3.connect(...)` 或 `psycopg.connect(...)`,只有 `await repo_repository.get_by_id(repo_id)` 这样的调用。
- 换 Postgres 时,改动范围是:SQLAlchemy 的连接串(`sqlite+aiosqlite:///...` → `postgresql+asyncpg://...`)、方言相关的极少数 SQL 写法(如有)、以及部署配置。**服务层、API 层、领域模型一行代码不用动**。
- 具体触发条件见 §6。

## 4. 领域模块纵切

按领域(而不是按技术层)横切代码目录,是为了让"加一个新数据源"这种常见变更只碰一个模块:

| 模块 | 负责什么 | 对外暴露什么 | 依赖谁 |
|---|---|---|---|
| `ingest` | 抓取与候选池:Trending / Search / 手动贴的 fetcher,`crawl_batch` 与 `candidate` 的生命周期(pending/saved/dismissed)。 | 批次列表、候选列表、"收藏晋升"/"忽略"用例 | `library`(判断是否已收藏、执行收藏晋升写入)、`core` |
| `library` | 收藏、分类、标签、生命周期状态(`watching`/`to-learn`/`learning`/`using`)、软删除(归档/取消归档/硬删除)。 | `repo` 的增删改查、按 URL 查重、状态流转用例 | `ai`(触发分析)、`core` |
| `docs` | 详情文档的 CRUD、Markdown 渲染、多篇排序。 | `doc` 的增删改查、AI 起草文档用例 | `library`(校验 `repo_id` 存在)、`ai`(起草内容)、`core` |
| `ai` | LLM 分析:GitHub 元数据 → 摘要/分类/标签;起草文档草稿。纯计算服务,不持久化任何表,因此没有独立的仓储和路由。 | 分析用例、起草用例 | `core`(输入输出用领域模型描述) |
| `core` | 共享的实体契约:`CrawlBatch`、`Candidate`、`Repo`、`Doc` 及枚举类型的 Pydantic 定义。 | 实体本身 | 无 |

模块内部的"纵切片"结构(以 `ingest` 为例):
```
ingest/
├── router.py       # ① API 层:GET /api/batches、POST /api/ingest/run 等
├── service.py       # ② 服务层:批次抓取编排、收藏晋升/忽略用例
└── repository.py    # ③ 仓储层:crawl_batch、candidate 两张表的 SQL
```
`docs`、`library` 结构同理;`ai` 只有 `service.py`(和调用第三方 LLM API 的客户端代码),没有 `router.py` 和 `repository.py`。

### 解耦纪律

**模块间只认对方的 API(服务层暴露的方法)和 `core` 里的实体契约,不直接读对方的表、不直接调对方仓储层或内部私有函数。**

典型例子(§3.1 已展开):`ingest` 要判断一个 candidate 对应的仓库"是否已收藏",必须调用 `library` 暴露的查询方法,不能自己 `JOIN`/`SELECT` `repos` 表。同理:
- `docs` 起草文档前需要仓库的摘要和标签,调用 `library.service.get_repo(repo_id)` 拿到 `Repo` 领域模型,不直接读 `repos` 表。
- `ai` 分析仓库信息时,输入是 `library` 或 `ingest` 传进来的领域模型字段(如 `description`、`readme` 摘录),`ai` 自己不知道、也不需要知道这些数据来自哪张表。

这条纪律的好处和 §3.1 一致:任何一个模块的内部存储结构变化,只要它对外暴露的方法签名不变,调用方零感知。

> AI 具体在哪个用户动作触发(收藏晋升那一刻 / 手动贴 URL 时 / 点按钮手动触发),属于产品决策,已定稿见 [01-product-model.md](./01-product-model.md) §AI 触发时机;本篇只描述"谁调用谁"的依赖关系。

## 5. 数据库选型

### 现在:SQLite + WAL

- **SQLite + WAL(Write-Ahead Logging)模式**:契合"本地零配置、单人使用"的产品定位,不需要额外起数据库进程,单文件即整个数据库,WAL 模式下读写并发也足够单人量级使用。
- **ORM:SQLAlchemy 2.0(async)**,配合 FastAPI 的 async 路由使用 `aiosqlite` 驱动。选它的直接理由是:**把"未来换库"这件事压缩成改一行连接串**——只要业务代码(服务层、仓储层方法体内的查询构造)使用 SQLAlchemy Core/ORM 的查询构造器而不是手写方言相关的 SQL,底层换成 Postgres 时改动被限制在连接配置和极少数方言相关细节上。

### 未来:换 Postgres 的三个触发条件

命中任一条,才考虑从 SQLite 换到 Postgres,不提前引入:

1. **要部署成多人 / 云端使用**(不再是单人本地场景)。
2. **抓取并发写频繁冲突**(定时任务并发写候选池,SQLite 单写者模型开始成为瓶颈)。
3. **要上向量检索(`pgvector`)做"语义找相似项目"**(SQLite 没有生产可用的向量索引扩展)。

### 为什么切换是低成本的

因为仓储层是唯一接触数据库的地方(§3.2),换库这件事的影响面被严格限制:

- **零改动**:API 层、服务/用例层、领域模型(Pydantic 实体)。
- **改动集中在仓储层内部**:SQLAlchemy 连接串从 `sqlite+aiosqlite:///./gallery.db` 换成 `postgresql+asyncpg://...`;个别用到 SQLite 特有语法的地方(如有)改写成标准 SQL 或 Postgres 方言。
- **触发条件③(`pgvector`)是新增能力,不是重构**:会在对应模块(未来可能是新的 `discovery` 模块或 `library` 扩展)新增一个"按向量找相似"的仓储方法,是加法,不推翻已有接口。

## 6. 现状代码与目标架构的差距

现状(`main.py` / `db.py` / `github_fetch.py` / `llm.py`):

| 现状 | 目标架构 |
|---|---|
| `main.py` 单文件承载所有路由,路由函数里直接调用 `db.py` 的模块级函数、直接编排"抓取 → 调 LLM → 写库"的业务顺序。 | 路由(①)、编排逻辑(②)按模块拆分到 `ingest` / `library` / `docs` / `ai` 各自的 `router.py` / `service.py`。 |
| `db.py` 是一张扁平单表 `repos`,用同步 `sqlite3` 直连,函数即"仓储",但和业务逻辑(如判重、软删除)混在调用方(`main.py`)里。 | 按 §2 领域模型拆成 `crawl_batch` / `candidate` / `repo` / `doc` 四张表,SQLAlchemy 2.0 async 仓储对外只认领域模型;判重、软删除等规则上移到服务层,仓储层只做纯粹的数据存取。 |
| 只有硬删除(`DELETE /api/repos/{id}`),没有归档(软删除)语义。 | `repo.archived_at` 软删除维度,归档为默认"移除"动作,硬删除作为次级操作,规则落在 `library` 服务层(见 [02-domain-model.md](./02-domain-model.md) §软删除语义)。 |
| 没有"流"(candidate/batch)概念,贴 URL 即直接进正式收藏表,AI 分析在入库时同步触发。 | 三层内容模型(流/库/知识)分离存储,`ingest` 只存 GitHub 原始信息不调 LLM,AI 分析延后到收藏晋升那一刻按需触发。 |
| 没有详情文档(`doc`)概念。 | `docs` 模块承载 `repo` 1─N `doc`,Markdown 存储渲染展示。 |

**这是扩展,不是推倒重来**:

- `github_fetch.py` 的抓取逻辑(解析 URL、调 GitHub API、截取 README)可以原样下沉为 `ingest` / `library` 模块里 fetcher 的实现细节,接口不需要重新设计。
- `llm.py` 的分析逻辑(调用兼容 OpenAI 协议的接口、未配置时优雅降级为"GitHub 描述 + 未分类")可以原样下沉为 `ai` 模块的 `service.py` 实现,对外行为不变。
- `db.py` 现有的 CRUD 函数集合,是"仓储层雏形但缺少模块边界和领域模型分表"——重构路径是把 `repos` 表的字段按 §2 拆到四张表,把模块级函数改写成按模块归属的 SQLAlchemy async 仓储类,而不是重写一套全新逻辑。
- 换句话说:现有代码里"抓取"和"AI 分析"两块基础设施是可复用资产,真正要新建的是**表结构拆分**、**模块边界**、**软删除与状态机的服务层规则**这三块。

> **已定稿(数据迁移)**:这是新项目、不考虑兼容,**不写数据迁移脚本**。Phase 1 直接按 §2 的四表 schema 重建本地库(丢弃现有 `gallery.db` 里的示例数据,重新 `init_db`)。省去迁移工具的复杂度;真正有价值的历史数据尚未产生,没有迁移的必要。
