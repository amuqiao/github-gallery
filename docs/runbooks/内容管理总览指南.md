# 内容管理总览指南

本文用来建立 GitHub Gallery 内容维护的整体心智模型：展馆如何组织内容，项目、笔记、专题如何增删改查，以及发布前应该如何检查。

本文面向日常内容维护者。字段合同以 [`../contract/content-bundle-config.md`](../contract/content-bundle-config.md) 为准，批量导入细节见 [`content-import-workflow.md`](./content-import-workflow.md)，发布命令细节见 [`content-publishing-workflow.md`](./content-publishing-workflow.md)。

## 先理解整体模型

平台首页是展馆入口，展馆负责承载自己的项目和专题。专题不是全站独立内容，当前版本里专题从属于某一个展馆。

```text
平台首页 /
├─ GitHub 展馆 /halls/github/
│  ├─ item: GitHub 项目
│  │  ├─ index.md       项目正文
│  │  └─ notes/*        项目笔记
│  └─ collection: GitHub 专题
│     └─ 只能引用 GitHub 展馆内的项目
│
├─ Models 展馆 /halls/models/
│  ├─ item: AI 模型
│  │  ├─ index.md       模型正文
│  │  └─ notes/*        模型笔记
│  └─ collection: 模型专题
│     └─ 只能引用 Models 展馆内的模型
│
├─ Music 展馆 /halls/music/
│  └─ 规划中：当前只展示入口，不承载 content bundle
│
└─ Movies 展馆 /halls/movies/
   └─ 规划中：当前只展示入口，不承载 content bundle
```

核心关系可以压缩成一条线：

```text
hall 展馆
  -> item 项目或模型
     -> note 笔记
  -> collection 专题
     -> 引用同展馆 item
```

## 内容状态

内容通过目录表达状态。页面只从 `published` 生成，`drafts` 和 `archived` 不出现在公开页面里。

```text
catalog/content/
├─ drafts/       草稿：可以编辑，尚未公开
├─ published/    已发布：会生成页面
└─ archived/     已归档：保留内容，但不展示
```

状态流转如下：

```text
新建
  -> drafts
     -> publish
        -> published
           -> archive
              -> archived
                 -> restore
                    -> drafts
```

日常维护只需要记住两个入口：

```sh
./scripts/content.sh
./scripts/verify.sh release
```

`content.sh` 负责创建骨架、查询状态和流转内容；`verify.sh release` 是发布前门禁，负责发现引用错误、字段错误和构建错误。

## 常用操作总览

| 目标 | 命令入口 | 主要修改文件 | 是否生成页面 |
| --- | --- | --- | --- |
| 新增 GitHub 项目 | `content.sh item new github github_project` | `item.yaml`、`index.md` | 发布后生成 |
| 新增模型项目 | `content.sh item new models ai_model` | `item.yaml`、`index.md` | 发布后生成 |
| 新增 Apple app | `content.sh item new app-store apple_app` | `item.yaml`、`index.md` | 发布后生成 |
| 新增笔记骨架 | `content.sh item note add` | `item.yaml`、`notes/*` | item 发布后生成 |
| 导入或替换笔记文件 | `content.sh item note import/replace` | `item.yaml`、`notes/*` | published item 立即生成 |
| 新增专题 | `content.sh collection new` | `collection.yaml`、`index.md` | 发布后生成 |
| 查询内容 | `content.sh list/status/show` | 不修改文件 | 不影响 |
| 发布内容 | `content.sh publish` | 自动移动目录 | 生成页面 |
| 下线内容 | `content.sh archive` | 自动移动目录 | 不再生成 |
| 恢复内容 | `content.sh restore` | 自动移动目录 | 回到草稿 |
| 发布前检查 | `verify.sh release` | 不修改文件 | 检查构建 |

## 新增 GitHub 项目

GitHub 项目属于 `github` 展馆，item kind 使用 `github_project`。

```sh
./scripts/content.sh item new github github_project gpt-sovits \
  --title "GPT-SoVITS" \
  --summary "支持少样本音色克隆、语音转换和文本转语音实验的 WebUI。" \
  --repo "https://github.com/RVC-Boss/GPT-SoVITS" \
  --category ai \
  --tag audio \
  --maintenance-status unknown
```

创建后会得到草稿目录：

```text
catalog/content/drafts/github/items/gpt-sovits/
├─ item.yaml     结构化配置
└─ index.md      项目正文
```

维护方式：

```text
1. 用命令创建草稿
2. 编辑 index.md 写项目介绍、使用方式、观察笔记
3. 必要时编辑 item.yaml 补充分类、标签、来源等结构化字段
4. 运行 publish
5. 运行 release 检查
```

发布：

```sh
./scripts/content.sh publish github item gpt-sovits
./scripts/verify.sh release
```

## 新增模型项目

模型项目属于 `models` 展馆，item kind 使用 `ai_model`。

```sh
./scripts/content.sh item new models ai_model htdemucs-ft-onnx \
  --title "HT-Demucs FT ONNX" \
  --summary "面向音乐四轨分离的 HT-Demucs FT ONNX 模型包。" \
  --source-type huggingface \
  --source-url "https://huggingface.co/StemSplitio/htdemucs-ft-onnx" \
  --provider StemSplitio \
  --input audio \
  --output audio \
  --task source-separation \
  --access download \
  --format onnx \
  --runtime onnxruntime
```

创建后会得到草稿目录：

```text
catalog/content/drafts/models/items/htdemucs-ft-onnx/
├─ item.yaml     模型结构化配置
└─ index.md      模型正文
```

模型字段的维护重点：

```text
provider     提供方
modalities   输入/输出模态
tasks        适用任务
access       访问方式
formats      模型格式
runtimes     运行时
source.url   来源链接
```

发布：

```sh
./scripts/content.sh publish models item htdemucs-ft-onnx
./scripts/verify.sh release
```

## 新增笔记

笔记从属于 item，不是独立内容。适合放试用记录、架构分析、实验日志、HTML 说明页等。

```text
item
├─ index.md
└─ notes/
   ├─ quick-start.md
   └─ architecture-note.html
```

新增 Markdown 笔记：

```sh
./scripts/content.sh item note add models htdemucs-ft-onnx quick-start \
  --title "快速试用" \
  --summary "记录模型定位、运行入口、输入输出和适用边界。" \
  --format markdown
```

新增 HTML 笔记：

```sh
./scripts/content.sh item note add github gpt-sovits architecture-note \
  --title "架构笔记" \
  --summary "记录架构观察。" \
  --format html \
  --display site
```

从已有 Markdown 或 HTML 文件导入笔记：

```sh
./scripts/content.sh item note import models htdemucs-ft-onnx deployment-guide \
  --state published \
  --file .data/htdemucs-ft-onnx-指南.html \
  --title "HTDemucs-FT ONNX 模型讲解与阿里云部署指南" \
  --summary "讲解 HTDemucs-FT ONNX 模型原理、运行方式和阿里云部署路径。" \
  --display standalone
```

替换已有笔记正文：

```sh
./scripts/content.sh item note replace models htdemucs-ft-onnx deployment-guide \
  --state published \
  --file .data/htdemucs-ft-onnx-指南.html
```

注意事项：

- `item note add` 主要用于草稿 item。
- `item note import` 支持把外部 `.md` 或 `.html` 文件导入到 `drafts` 或 `published` item；HTML 导入必须显式声明 `--display site` 或 `--display standalone`。
- `item note replace` 只替换已有笔记正文，不修改 note 元数据。
- 已发布 item 的笔记文件更新也应通过 `content.sh` 完成，让脚本负责写锁、校验和失败回滚。

## 新增专题

专题用于把同一展馆内的 item 组织成一个策展页面。

```sh
./scripts/content.sh collection new github voice-cloning \
  --title "声音克隆项目" \
  --summary "GitHub 展馆内的声音克隆项目策展。" \
  --item gpt-sovits
```

创建后会得到草稿目录：

```text
catalog/content/drafts/github/collections/voice-cloning/
├─ collection.yaml    专题配置和 item 引用
└─ index.md           专题正文
```

专题引用关系写在 `collection.yaml`：

```yaml
items:
  - item: gpt-sovits
  - item: cosyvoice
```

专题规则：

- GitHub 专题只能引用 GitHub item。
- Models 专题只能引用 Models item。
- 已发布专题只能引用同展馆内已发布的 item。
- 如果专题引用了未发布、已归档或不存在的 item，`./scripts/verify.sh release` 会失败。

发布：

```sh
./scripts/content.sh publish github collection voice-cloning
./scripts/verify.sh release
```

## 查询内容

查询命令不修改文件，也不会触发构建。

查看某个展馆全部内容：

```sh
./scripts/content.sh list github
./scripts/content.sh list models
```

只看已发布内容：

```sh
./scripts/content.sh list published github
./scripts/content.sh list published models
```

查看单个内容当前状态和路径：

```sh
./scripts/content.sh status models item htdemucs-ft-onnx
./scripts/content.sh status github collection voice-cloning
```

查看单个内容配置：

```sh
./scripts/content.sh show models item htdemucs-ft-onnx
./scripts/content.sh show github collection voice-cloning
```

查询时的判断路径：

```text
不知道内容在哪
  -> list <hall>
     -> 找到 id
        -> status <hall> <item|collection> <id>
           -> 得到 state 和 path
              -> 按路径编辑或检查
```

## 更新内容

更新分两类：正文更新和结构更新。

```text
正文更新
  -> 改 index.md 或 notes/*
  -> verify.sh release

结构更新
  -> 改 item.yaml 或 collection.yaml
  -> 检查引用关系
  -> verify.sh release
```

内容文件更新应优先通过 `content.sh` 完成。当前脚本已经覆盖 item/collection 骨架、笔记骨架、外部笔记文件导入/替换、发布、归档、恢复和只读查询；如果某类静态内容缺少脚本入口，应先补受控命令，再写入 catalog。

已发布内容的推荐策略：

| 更新类型 | 推荐做法 |
| --- | --- |
| 更新已有笔记正文 | 使用 `content.sh item note replace --state published` |
| 从外部 Markdown/HTML 新增笔记 | 使用 `content.sh item note import --state published` |
| 改字段结构、调整专题引用 | 优先回到草稿后修改，再重新发布 |
| 下线某个项目或专题 | 使用 `archive`，不要直接删除目录 |
| 批量替换内容 | 使用 import batch，并先执行 `validate`、`plan`、`diff` |

结构性更新的安全路径：

```text
查询内容位置
  -> 判断它是否被 published collection 引用
     -> 如果被引用，先更新或归档相关 collection
        -> archive / restore 到 drafts
           -> 修改文件
              -> publish
                 -> verify.sh release
```

## 归档和恢复

归档表示下线但保留内容。

```sh
./scripts/content.sh archive models item htdemucs-ft-onnx
./scripts/content.sh archive github collection voice-cloning
```

恢复表示从归档回到草稿，恢复后不会直接发布。

```sh
./scripts/content.sh restore models item htdemucs-ft-onnx
./scripts/content.sh restore github collection voice-cloning
```

归档顺序要注意引用关系：

```text
collection 引用 item
  -> 不能先归档 item
  -> 应先更新或归档 collection
  -> 再归档 item
```

这样可以避免线上专题指向已经下线的项目。

## 删除内容

日常维护不推荐硬删除，优先使用 `archive`。

```text
下线内容
  -> archive

误操作恢复
  -> restore

彻底删除草稿
  -> import batch delete
  -> 必须显式传入 --allow-delete
```

删除只应处理确认不需要保留的草稿内容。已经发布过的内容通常应该归档，而不是删除。

## 批量导入

批量导入适合 AI 整理结果、批量迁移或一次性创建多个草稿。

```text
人工或 AI 整理内容
  -> .tmp/import-batches/<batch-id>/
  -> content.sh import validate
  -> content.sh import plan
  -> content.sh import diff
  -> content.sh import apply
  -> catalog/content/drafts/
  -> 人工检查和编辑
  -> content.sh publish
```

常用命令：

```sh
./scripts/content.sh import validate .tmp/import-batches/example-content-batch
./scripts/content.sh import plan .tmp/import-batches/example-content-batch
./scripts/content.sh import diff .tmp/import-batches/example-content-batch
./scripts/content.sh import apply .tmp/import-batches/example-content-batch
```

导入不会直接发布内容。导入成功后，正式内容来源变成 `catalog/content/drafts/`。

## 发布前检查清单

每次准备上线前，按这个顺序检查：

```text
1. list/status/show 确认内容状态和路径
2. 检查 index.md、notes/* 是否是要发布的内容
3. 检查 item.yaml 或 collection.yaml 的引用是否正确
4. 对 drafts 内容执行 publish
5. 运行 ./scripts/verify.sh release
6. 本地打开关键页面检查视觉和链接
7. 再提交 git 或部署
```

最低命令集：

```sh
./scripts/content.sh list published github
./scripts/content.sh list published models
./scripts/verify.sh release
```

如果本地开发服务正在运行，可以检查这些页面：

```text
/
/halls/github/
/halls/models/
/halls/github/items/<id>/
/halls/models/items/<id>/
/halls/<hall>/collections/<id>/
```

## 常见边界

- `music` 和 `movies` 当前是规划中展馆，只展示入口，不承载 content bundle。
- 专题当前从属于展馆，不做跨展馆专题。
- `published` 是公开页面来源，`drafts` 和 `archived` 不生成公开内容页。
- `content.sh` 负责创建骨架、导入/替换笔记文件、状态流转和查询；正文静态文件缺少受控入口时，应先优化脚本再写入 catalog。
- `verify.sh release` 是上线前门禁，不应该跳过。
- 字段新增、删除或重命名不在本文处理范围内，应先改 schema，再同步 loader、脚本和合同文档。

```text
用 content.sh 创建和流转内容，用生成的文件写正文，用 verify.sh release 拦截上线前错误。
```
