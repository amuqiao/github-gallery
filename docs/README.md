# GitHub Gallery 设计文档集

这里是 GitHub Gallery 的**设计文档集索引**。它本身不讲产品细节,只回答一个问题:
**这套文档是什么、给谁看、按什么顺序读、各篇负责什么、彼此怎么衔接。** 具体内容在各分册里。

---

## 这套文档是什么

GitHub Gallery 是一个本地部署、单人使用的「GitHub 项目个人知识库 + 学习追踪系统」。
这套文档记录它的**产品设计与技术架构决策**:内容模型、领域实体、后端分层、前端技术栈、
导航与 UX、REST API 契约、分期路线。

它是**设计蓝图**,不是使用手册,也不是 API 参考的自动生成物——是给"要理解或续建这个系统的人"看的。

## 面向谁

- 独立开发者本人(边设计边实现,需要一处稳定的事实源)。
- 后续接手或协作的开发者(需要快速建立心智模型,再落到某一层细节)。
- 为本项目写代码的 AI agent(需要术语、实体名、字段名、路由的唯一权威来源)。

## 怎么读(建议阅读顺序)

主线自上而下,从"为什么/是什么"逐步落到"怎么实现":

```
00 概览        → 先建立心智模型:愿景、目标、术语表
01 产品模型    → 三层内容 + 状态机 + 软删除 + AI 触发
02 领域模型    → 实体、字段、枚举(01 的落地形态)
03 架构        → 后端四层 + 模块解耦 + DB 选型
04 导航 UX     → 页面层级、路由、各页职责
05 前端        → 前后端分离、技术栈、视觉体系
06 API 契约    → REST 端点(连接前端与后端的合同)
07 路线        → 分期落地顺序
08 决策记录    → 已拍板的关键决策及理由(可追溯)
```

- **只想了解产品在做什么**:读 [00](./00-overview.md) → [01](./01-product-model.md) 即可。
- **要动后端**:[02](./02-domain-model.md) → [03](./03-architecture.md) → [06](./06-api-contract.md)。
- **要动前端**:[04](./04-navigation-ux.md) → [05](./05-frontend.md) → [06](./06-api-contract.md)。
- **想知道现在做到哪、下一步做什么**:[07](./07-roadmap.md)。

## 文档间关系

- **00 是入口**,先读它建立全局认知,其余各篇是它的展开。
- **01 → 02**:产品模型(概念)决定领域模型(实体字段/枚举),02 是 01 的数据落地。
- **03 承 02**:领域实体是后端四层共享的契约层;03 讲这些实体如何在分层中流转。
- **04 → 05**:导航/路由(信息架构)先定,05 讲用什么技术栈把它实现出来。
- **06 是接缝**:前端(04/05)与后端(02/03)通过 REST 契约对接,双方都以它为准。
- **07 横跨全部**:说明上述各层按什么顺序分期落地。
- **08 是决策台账**:各篇里"已定稿"的关键决策集中登记在 08,附理由,供日后追溯"当初为什么这么定"。
- **note.md 独立于主线**:它是历史初衷,只读不改,供追溯设计动机。

## 维护规则

- **唯一事实源优先**:术语、实体名、字段名、状态取值、模块名、路由、技术栈,以设计 brief 为准,
  各篇不得自行发明或改名。改概念先改源头,再同步各篇。
- **不重复**:同一事实只在其归属的分册里详述,别处引用而非复制。索引页(本文件)不搬运正文内容。
- **仓库内引用一律用相对路径**(如 `./01-product-model.md`),便于随目录移动。
- **发现缺口用 `> TODO(待定)` 标注**,不要编造填充。
- **note.md 保留不覆盖**:新增设计另开文件,不改写历史初衷记录。
- **决策留痕**:关键产品/技术决策拍板后,在相关篇章以 `> 已定稿` 就地标注,并在 [08-decisions.md](./08-decisions.md) 登记一条(含理由),便于日后追溯。
