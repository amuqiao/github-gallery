一文读懂 PySceneDetect
把视频按镜头切开

贯穿全文的任务只有一个:手里有一条 58 秒的产品评测粗剪 demo.mp4(1080p / 25fps),想按镜头拆成独立片段,交给剪辑挑素材、给数据标注建 clip 数据集。看 PySceneDetect 如何把帧间像素差异变成时间码清单,再变成一组 .mp4 和一张 CSV。

▸ demo.mp4 58s · 1080p · 25fps → scenedetect -i demo.mp4 detect-adaptive list-scenes split-video → ✓ demo-Scene-001…006.mp4 ✓ demo-Scenes.csv

上面是可以拖的:这条曲线就是 PySceneDetect 逐帧算出的 content_val(相邻帧的内容差异),越过阈值线就切一刀。为什么有的切点会漏、有的会误切,CH03 的完整调参台里对着答案讲。

CH 01// CAPABILITY · 能力契约

它负责一件窄而硬的事:找到镜头切换的那一帧

PySceneDetect 是一个开源 Python 工具(BSD 协议,pip install scenedetect),名字里的 "scene" 其实是剪辑意义上的镜头(shot):一次连续拍摄。它不理解剧情,只回答一个问题——这条视频在哪些时间点从一个镜头切到了另一个镜头,然后把答案落成清单、缩略图或切好的片段。

✓ 交给它的事

  • 输入:一个本地视频文件——mp4 / mkv / mov / avi 等,凡是本机 FFmpeg / OpenCV 解不开的它也解不开。输入只读,不会被修改。
  • 处理:逐帧计算相邻帧差异(色相/亮度/饱和度/边缘的加权变化,或亮度均值),按检测器规则判定切点;硬切(hard cut)是它的主场。
  • 输出:① 场景时间码清单(stdout 表格 + *-Scenes.csv);② 每场景抽帧 JPEG(save-images);③ 调 ffmpeg 切出的独立视频(split-video);④ 每帧指标 stats.csv 供复盘。
  • 典型使用者:剪辑/后期拆素材;ML 数据工程把长视频切成训练 clip;媒资系统给视频建镜头索引;自动化集锦/二创流水线。

✗ 不该指望它的事

  • 语义"场景":它不知道"咖啡馆这场戏"由 12 个镜头组成。同一地点聚类、剧情分段属于下游任务。
  • 复杂渐变转场的高召回:长 dissolve、划像、花字转场靠帧差很难稳定抓到,这是深度模型(如 TransNetV2)的领域,见 CH07。
  • 转码与画质:它切片时只是调用 ffmpeg,裁剪、缩放、修复变帧率都应该在上游用 ffmpeg 自己做。
  • 音频、字幕、内容理解:完全不看声音,不打语义标签。
  • 流媒体 URL:先把文件下载/录制到本地。
一句话契约:视频文件进,时间码(以及按时间码派生的片段/缩略图)出。所有下游价值都建立在"切点找得准"这一件事上——所以这篇文章一半篇幅在讲怎么让它切得准、以及怎么验证它切准了。
先别追求"单工具完美":PySceneDetect 更准确的定位是可解释、可脚本化的候选切点生成器,不是理解剧情和摄影意图的最终裁判。闪光灯、频闪、快速甩镜和真实硬切在帧差曲线上可能长得几乎一样;dissolve 又会把一次切换摊薄到几十帧里。真实业务里要先决定"宁可多切一点"还是"宁可少切一点",再用验证、过滤、人工审核或深度模型升级把结果接住。

from scenedetect import detect, AdaptiveDetector, split_video_ffmpeg

# detect() 一步到位:打开视频 → 逐帧检测 → 返回 [(start, end), ...] 时间码对
scenes = detect("demo.mp4", AdaptiveDetector(), stats_file_path="stats.csv")

for i, (start, end) in enumerate(scenes, 1):
    print(f"Scene {i}: {start.get_timecode()} → {end.get_timecode()}  "
          f"({(end - start).get_seconds():.1f}s)")

split_video_ffmpeg("demo.mp4", scenes, show_progress=True)

返回值是 FrameTimecode 对象对,能直接换算帧号(.get_frames())、秒(.get_seconds())、时间码字符串——这就是嵌进自己脚本时的数据结构,不用解析任何文本。要更细的控制(多检测器叠加、逐帧回调、复用 StatsManager)再下探 SceneManager 这一层 API。

CH 03// PARAMETERS · 参数心智模型

三个旋钮决定 90% 的结果:检测器、阈值、最短场景

PySceneDetect 的参数不少,但真正改变行为的只有一小撮。下面这台调参台里埋了四个"考点"——一处画面变化很小的弱切、一次闪光灯、一段 dissolve 渐变、一个片尾 fade。切换检测器、拖动阈值,底部"检测结果 vs 真实镜头"两条带子会立刻告诉你代价是什么。

从上面能拧出来的几条经验

detect-content:绝对差越线就切

默认阈值 -t 27 抓硬切又稳又快。但它是"一刀切"的绝对标准:想抓到 00:30.2 那次弱切(帧差仅 24)得降到 20 附近,顺便就把闪光(帧差 30)放了进来;再往下探到能抓渐变的 16,离手持噪声的洪水(12 以下)只剩一步——灵敏度和误切是同一个旋钮。

detect-adaptive:看的是相对邻域的倍数

把帧差除以前后几帧的滚动均值,安静画面里的小变化会被放大,晃动画面里的大数值会被稀释。所以它在默认 -t 3 就抓到了弱切,而闪光那一帧身处嘈杂的手持邻域,比值反被稀释到线下——同一份素材,五处硬切全中、零误切。运动多、灯光乱的实拍素材,默认选它。

detect-threshold:只管黑场

它比较的不是帧差,而是整帧平均亮度是否穿过阈值——专门切 fade to/from black。硬切在它眼里不存在。素材靠黑场分段(录播、老式转场)才用它,或与其他检测器叠加补片尾。

五种检测器横评:效果、场景、优缺点

上面调参台可切换的是前三个;hash / hist 原理更简单,列在这里做选型对照。五个都是"三(五)选一"的关系,一条命令只挂一个。

检测器看什么信号擅长(效果)盲区与坑什么场景用它
detect-content相邻帧 HSV 内容差的绝对值干净硬切,又稳又快;配 -s stats.csv 曲线最好复盘,是教程与调参的基准灵敏度和误切是同一个旋钮:降阈值抓弱切必然引进闪光/抖动;dissolve、黑场一律看不见演播室、成片、切换干净的素材;想要"可解释的默认起点"
detect-adaptive帧差 ÷ 前后邻域滚动均值的比值运动/手持画面里的硬切、安静段里的弱切都抓得住;闪光被嘈杂邻域稀释,天然抗瞬变dissolve 依旧看不见;画面持续高频晃动会抬高分母,极端情况下埋掉真切;阈值量纲是"倍数",与 content 不通用vlog、纪实、运镜多的实拍——大多数真实素材的首选
detect-threshold整帧平均亮度是否穿越阈值fade to/from black 一抓一个准,还能顺便给出黑场中点做精确分割点除黑场外一切都不存在:硬切、渐变、白闪全部无视;素材整体偏暗时阈值要跟着降录播/课程按黑场分章节、老式黑场转场、补片尾 fade
detect-hash相邻帧感知哈希距离计算量小,速度是帧差法的数倍,海量素材粗扫利器精度换来的:弱切、构图相近的切换容易漏;不适合做最终精切媒资库第一遍粗分、量大于质的批处理,之后对可疑段精扫
detect-hist相邻帧 YUV 直方图差异只看颜色分布、不看像素位置,对镜头运动天然不敏感,抗抖动误切反过来:两个镜头颜色分布接近(同场景反打)就漏;对灯光渐变也会迟钝手持/运动误切太多、而镜头之间颜色区分明显的素材
选型口诀:不知道选什么就 adaptive 起步;有黑场章节再跑一遍 threshold 补边界;素材以万计先用 hash 粗扫;要精调阈值就换回 content + stats.csv 看曲线。CLI 一条命令只能挂一个检测器,"两样都要"见 CH06 的候选切点流水线。

自动调优为什么仍然不能完美

它优化的是评分,不是语义

调参台里的"全局最优"只是把几个检测器、阈值和 -m 组合扫一遍,按命中数、误切数和默认值距离排序。它不会知道 00:19.6 是闪光灯,也不会知道 36s 的 dissolve 是剪辑意图。

弱切和闪光会抢同一个旋钮

为了抓弱切或渐变,阈值通常要降低;阈值一低,闪光、频闪、甩镜和手持抖动也更容易过线。这不是某个参数没找到,而是召回率和精确率共用一组视觉信号。

单检测器有物理天花板

content / adaptive 主要看帧差,天然偏硬切;threshold 只看黑场;hash / hist 又会用精度换速度或抗运动。业务要全都要,就要进入候选切点融合和审核流程。

关键参数速览(不是手册,是会改变结果的那几个)

参数默认改变什么什么时候动它
detect-content / adaptive / threshold / hashdetect-content(教程惯例)"什么算一次切换"的定义本身实拍/运镜多 → adaptive;只按黑场分段 → threshold;海量视频粗扫 → hash(感知哈希,快)
-t, --thresholdcontent: 27 / adaptive: 3.0灵敏度:低了碎、高了漏先跑一遍带 -s stats.csv,看曲线定值,别盲试
-m, --min-scene-len0.6s场景最短时长,合并碎片场景快闪混剪降到 0.3s;访谈/课程升到 2s 抗噪
-d, --downscale / -fs, --frame-skip自动缩放 / 0速度 ⇄ 精度:检测在缩小画面/隔帧上进行4K 长片粗扫加 -fs 2;注意 frame-skip 会让切点精度变粗、且不能配合 stats 复用
time -s / -e全片只处理一个时间区间调参时抽两分钟试跑:time -s 1m -e 3m,快一个量级
split-video --copy不加(重编码 libx264)切片速度 ⇄ 切点精度:--copy 不重编码但切点吸附到关键帧片段只为人工浏览用 --copy;进训练集/成片必须帧级精确就用默认
--luma-only(detect-content)关忽略色彩,只比亮度灯光变色、调色跳变频繁的素材,减少颜色引起的误切
心智模型一句话:检测器决定"用什么尺子量帧差",阈值决定"多大算一刀",min-scene-len 决定"多碎算噪声"。其余参数几乎都在换取速度或输出形式。
CH 04// VERIFY · 结果怎么算对

三层验证:数字合理 → 抽样看图 → 曲线复盘

"命令跑完没报错"离"切对了"还差三步。更重要的是,不同业务对"切对"的定义并不一样:剪辑拆素材、训练集入库和媒资粗索引用的质量门槛不该相同。

先定义业务目标,再调检测器

业务目标更怕什么推荐策略质量门槛
剪辑拆素材误切太碎,剪辑浏览成本上升adaptive 起步,适当提高 -m;用 save-images export-html 快速人工过一遍相邻场景缩略图明显不同;允许少量漏切由剪辑手工补
ML 训练集片段混入两个镜头,污染标签高精度优先:阈值保守、短片段过滤、疑似边界进人工审核;切片用默认重编码保证帧级精度抽样片段首/中/尾必须同一镜头;高风险类别提高复核比例
媒资粗索引成本太高、吞吐不够hash 或低清代理粗扫,只对可疑长段/低置信段再用 adaptive 精扫场景数和平均时长落在合理区间;允许后续检索时再精修
课程/录播章节边界漏掉若靠黑场/静帧分段,优先 threshold;硬切只是辅助信号黑场前后时间码准确;不要为了抓非章节硬切制造碎片
综艺/预告/短视频dissolve、花字、频闪转场漏检PySceneDetect 做 baseline;召回是硬指标时升级到 TransNetV2 等深度模型按人工真值算 precision / recall,不要只看场景数量
决策顺序:先定"宁可漏切还是宁可误切",再选检测器和阈值。没有这个业务目标,自动调优只能给出数学上最优的一组参数,无法保证业务上最可用。

三层验证按成本从低到高

① 数字合理性 · 5 秒

看 stdout 摘要和 demo-Scenes.csv:58 秒的评测粗剪切出 4–8 个场景是正常的;切出 40 个说明阈值太低,切出 1 个说明太高或检测器选错。再扫一眼时长列:不该有 <0.5s 的碎片,所有场景时长之和应等于原片时长。

② 抽样看图 · 1 分钟

save-images 给每个场景存 3 张图(首/中/尾)。抽查标准很机械:同一场景的 3 张图必须是同一个镜头;相邻场景的交界两张图必须明显不同。前者不满足 = 漏切,后者不满足 = 误切。要看全量就 export-html 生成一张带缩略图的审核网页。

③ 曲线复盘 · 出问题才做

怀疑某处漏切时打开 stats.csv,找到那个时间点的 content_val:值确实低 → 是弱切/渐变,该换 detect-adaptive 或降阈值;值明明很高 → 检查是不是被 min-scene-len 合并了。CH03 的调参台就是这张曲线的交互版。

把 ① 写成代码,流水线里自动跑

import pandas as pd

df = pd.read_csv("demo-Scenes.csv", skiprows=1)          # 第一行是 Timecode List 汇总
assert len(df) >= 2,                          "只有 1 个场景:阈值过高或检测器不适配"
assert df["Length (seconds)"].min() > 0.5,   "存在碎片场景:调高 -m / -t"
assert abs(df["Length (seconds)"].sum() - 58.0) < 0.1, "场景没有铺满全片"

这三条断言便宜到可以挂在每一次批处理后面;真正的质量抽查(②)按比例采样人工看即可。

CH 05// AUTOMATION · 脚本与流水线契约

exit code 只说"流程没崩",成功要数产物

把它放进 cron / CI / 任务队列之前,先弄清它对机器的承诺:

契约点行为对策
exit code0 = 流程正常结束——包括"检出 0 个场景";非 0 = 参数错误 / 文件打不开 / 解码失败判成功用双保险:exit code 为 0 且 产物计数 > 0
stdout / stderr场景表走 stdout,日志与进度条走 stderr机器解析别抓 stdout,读 *-Scenes.csv 或直接用 Python API 拿 scene_list
覆盖行为输出文件名由输入名派生(demo-Scene-001.mp4),重跑直接覆盖,不追加、不去重天然幂等;但不同视频若重名会互相覆盖,用 -o 目录 按任务隔离
部分产物split-video 逐段写盘,中途被杀会留下残缺片段写进临时目录,全部成功后原子 mv 到正式位置
可复用中间态-s stats.csv 存每帧指标,同一视频换阈值重跑可跳过大部分解码批量调参时固定带上,省的是最贵的解码时间

一个能直接抄的批处理骨架

#!/usr/bin/env bash
# 用法: ./split_one.sh input.mp4 —— 成功后片段在 clips/<视频名>/ 下
set -euo pipefail
in="$1"; name="$(basename "${in%.*}")"
tmp="$(mktemp -d)"; trap 'rm -rf "$tmp"' EXIT

scenedetect -i "$in" -o "$tmp" -s "$tmp/stats.csv" \
            detect-adaptive list-scenes split-video

n="$(ls "$tmp"/*-Scene-*.mp4 2>/dev/null | wc -l)"
(( n > 0 )) || { echo "[FAIL] $in: 0 scenes produced" >&2; exit 1; }

mkdir -p "clips/$name" && mv "$tmp"/* "clips/$name/"
echo "[OK] $in → $n clips"

要在 Python 服务里做同样的事,直接用 CH02 的 detect():异常即失败,len(scene_list)==0 即空结果,不需要解析任何输出。

CH 06// PIPELINE · 嵌进工作流

它站在解码之后、一切理解之前

分镜几乎总是视频流水线的第一道结构化工序:上游只负责把素材喂成它能稳定解码的样子,下游拿着时间码各取所需。

Upstream · 准备采集 / 下载素材

相机、手机、录屏、平台下载。手机与录屏常是变帧率(VFR),是后面最大的坑。

→

Upstream · 预处理ffmpeg 规整

统一成恒定帧率、必要时出低清代理加速调参:
ffmpeg -i cam.mov -vsync cfr -r 25 demo.mp4

→

本文主角PySceneDetect

检测切点,产出三类物:时间码 CSV(数据契约)、片段 mp4(直接可用)、缩略图 / stats(供审核复盘)。

→

Downstream · 消费三条去向

① 片段 → 标注平台 / 训练集 / 剪辑工程
② CSV → pandas 统计、生成 EDL/OTIO 进 NLE
③ export-html 审核页 → 人工抽查后放行

链路示例 A:ML 训练集

yt 下载 → ffmpeg 转 CFR → scenedetect 切片 + CSV → 断言校验(CH04) → 片段重命名入库 → 标注/训练。切点帧级精确很重要,split-video 用默认重编码而不是 --copy。

链路示例 B:剪辑拆素材

素材 → scenedetect list-scenes save-images → export-html 快速过一遍 → 只把需要的场景 split 出来,或把 CSV 转成标记导进 Resolve/Premiere。这里速度优先,--copy 足够。

生产里不是"检测完就结束",而是处理候选切点

Candidate · 候选多路生成切点

adaptive 抓硬切,threshold 补黑场;转场密集素材再加深度模型。多路结果先都当候选,不要急着切片。

→

Filter · 过滤吃掉明显噪声

合并距离过近的切点,过滤短于业务下限的碎片,把 00:19.6 这类闪光误切标为低置信候选。

→

Review · 审核只看高风险段

生成 export-html 或自建审核页,优先复核短片段、连续密集切点、dissolve 区和模型/规则分歧的位置。

→

Commit · 落库产出稳定契约

人工或规则确认后再输出最终 CSV / EDL / OTIO / clips。下游只消费"已确认切点",不直接消费原始检测结果。

关键区别:PySceneDetect 的输出是很好的候选时间码,但生产系统最好把"原始候选"和"确认后的最终切点"分开保存。这样误切/漏切可以回溯,调参或模型升级也不会污染历史结果。
CH 07// FAILURE MODES · 常见失败边界

它会在哪里骗你,以及怎么接住

漏切 · 渐变转场

dissolve / 划像抓不到

渐变把一次切换摊薄成几十帧,每帧差异都不过线(调参台里那段紫色斜纹就是)。这是帧差法的原理性盲区,不是 bug。

对策:fade to black 用 detect-threshold 叠加补;真正的 dissolve 多、且召回要求高时,换深度模型(TransNetV2)做检测、PySceneDetect 只做切片执行。

误切 · 瞬时闪变

闪光灯 / 频闪 / 快速甩镜

一帧的剧烈变化和真切点在帧差上长得一模一样(调参台 00:19.6 的 ⚡)。

对策:换 detect-adaptive——瞬变的帧差会被嘈杂邻域的均值稀释,多数闪光过不了比值线;残余碎片交给 -m 合并;拿到 CSV 后按最短时长再过滤一道也很便宜。

时间码漂移 · VFR

手机/录屏素材切点对不上

变帧率视频在 OpenCV 后端下时间换算会漂,表现为"CSV 里的时间码和播放器里看到的差半秒"。

对策:上游一律 ffmpeg -vsync cfr 转恒定帧率(CH06 预处理位);或改用 PyAV 后端(pip install scenedetect[pyav])。

环境 · 依赖缺失

split-video 报 ffmpeg not found

检测本身只要 OpenCV,但切片是外包给 ffmpeg 的;Windows 上最常见的翻车点就是 ffmpeg 不在 PATH。

对策:装好后用 ffmpeg -version 自检;只有 mkvtoolnix 时可用 split-video --mkvmerge(仅流拷贝模式)。

性能 · 长片高清

4K 两小时素材跑得久

检测速度大致与"分辨率 × 帧数"成正比。默认会自动 downscale,但解码本身省不掉。

对策:调参阶段用 time -s/-e 抽片段 + 低清代理;定参后全片只跑一次并落 stats.csv;极端量级用 -fs 1/2 隔帧,接受切点变粗。

输入 · 路径与解码

打不开文件 / 切出 0 场景

路径带空格没加引号、容器损坏、罕见编码 OpenCV 解不动;或素材真的一镜到底。

对策:先 ffprobe 确认能解;0 场景时 exit code 仍是 0,所以流水线必须数产物(CH05);确认是长镜头素材就别硬调低阈值制造假切点。

误切和漏切出现后怎么处理

现象先判断处理方式什么时候升级
闪光灯误切 @00:19.6切出来的碎片是否短于业务最小时长;前后缩略图是否仍是同一镜头提高 -m 或在 CSV 后处理里合并短片段;若闪光很多,给"单帧峰值但前后画面相似"的候选降置信频闪舞台、演唱会、闪切广告里误切密集时,引入模型或人工审核队列
弱切漏检stats.csv 里该点是低峰还是被 -m 合并优先试 adaptive;再降阈值;降阈值带来的误切用短片段过滤接住同场景反打、构图接近的切换大量漏掉时,单纯帧差不够
dissolve 漏检转场是否被摊成长缓坡,没有单帧越线黑场 fade 用 threshold 补;非黑场 dissolve 标成高风险段进入审核dissolve 是核心边界时,直接上深度模型,不要继续拧帧差阈值
切点时间对不上素材是否 VFR;切片是否用了 --copy上游转 CFR;要求帧级精度时不用 --copy多来源手机/录屏批处理必须把 CFR 预处理固化进流水线
CH 08// TRADE-OFFS · 对比与取舍

什么时候用它,什么时候不用

"检测镜头边界"这件事至少有五种做法,差别在可脚本化程度、转场召回和成本:

方案强项短板选它当
PySceneDetect本地、免费、CLI+API 双入口,清单/切片/缩略图一条龙,参数可解释渐变转场召回有限,纯 CPU 帧差法默认之选:批量、可复现、硬切为主的素材
ffmpeg select='gt(scene,0.4)'零新依赖,一行命令单一指标、无 min-scene-len、输出要从日志里抠,没有清单产物机器上只有 ffmpeg、临时看一眼切点
手写 OpenCV 帧差指标完全自定义阈值策略、时间码、切片、边界情况全部重造研究自定义检测指标本身,而不是想拆视频
深度模型(TransNetV2 / AutoShot)渐变、花式转场召回显著更高要模型权重与 GPU,集成/维护成本高成片、预告片、综艺这类转场密集素材,且召回是硬指标
云 API(视频智能类服务)免环境、附带其他分析按分钟计费、数据出域、离线不可用量大且素材本就在云上、合规允许
NLE 内置场景检测(Resolve / Premiere)图形界面,切完直接进时间线无法脚本化、无法批量、结果导不成数据剪辑师单次手工任务,后续就在 NLE 里干活
取舍口诀:要"能进流水线的时间码",用 PySceneDetect;要"渐变也不许漏",上深度模型;只是"顺手看看",ffmpeg 或 NLE 就够。三者并不互斥——不少流水线用深度模型出切点、仍用 PySceneDetect 的 split_video_ffmpeg 执行切片。

后续升级路线:从工具使用到业务闭环

阶段 1:可解释 baseline

统一预处理为 CFR,默认 adaptive,固定输出 Scenes.csv、stats.csv、缩略图和审核页。目标是先让每次切分可复现、可检查。

阶段 2:规则后处理

保存原始候选与最终切点两份结果。加入最短时长、近邻合并、黑场补边界、异常场景数报警和按业务抽样审核。

阶段 3:多路融合

adaptive、threshold、必要时 hist/hash 各自生成候选,按来源和局部证据打分。分歧点进审核,一致点自动放行。

阶段 4:深度模型

当业务明确要求 dissolve、花式转场或高召回,引入 TransNetV2 / AutoShot 等模型。PySceneDetect 仍可负责切片、时间码格式和下游契约。

阶段 5:标注闭环

把人工修正的误切/漏切沉淀成真值集,定期计算 precision / recall / F1。后续调参、换模型、改规则都用同一套素材回归。

阶段 6:按业务分流

剪辑、训练集、媒资索引用不同 profile,不要共用一套阈值。profile 里记录检测器、阈值、-m、预处理和审核比例。

CH 09// CHEAT SHEET · 速查

带走这七行

# 安装(检测) + ffmpeg(切片)
pip install "scenedetect[opencv]"

# 最常用:检测 + 清单 + 缩略图 + 切片,一条龙
scenedetect -i in.mp4 -s stats.csv detect-adaptive list-scenes save-images split-video

# 只要时间码清单(交给下游脚本)
scenedetect -i in.mp4 -o out/ detect-adaptive list-scenes

# 抽 2 分钟调参,便宜地找阈值
scenedetect -i in.mp4 time -s 1m -e 3m detect-content -t 21 list-scenes -n

# 快速粗切(不重编码,切点吸附关键帧,仅供浏览)
scenedetect -i in.mp4 detect-adaptive split-video --copy

# 人工审核页:每个场景的缩略图排成网页
scenedetect -i in.mp4 detect-adaptive save-images export-html

参数三句话:运动多用 detect-adaptive;阈值别猜,看 stats.csv;碎片交给 min-scene-len。成功判定两件套:exit code 0 + 产物数 > 0。官方文档与源码见 scenedetect.com 与 GitHub Breakthrough/PySceneDetect(本文基于 v0.6.x 行为,细节以你安装版本的 scenedetect help 为准)。
