能力契约：它负责什么，不负责什么

FFmpeg 是一个媒体格式与编码的转换引擎。它的契约很朴素：给它一个或多个媒体输入（文件、URL、设备、管道）， 它按你的参数完成解封装、解码、滤镜、编码、封装，产出新的媒体文件或流。输入输出都是「字节层面的媒体」， 它不理解内容，也不替你做创作决策。典型使用者是后端/脚本工程师、视频网站与转码服务的开发者、数据/ML 工程师（抽帧、抽音频）、以及需要批量处理素材的创作者。

交给 ffmpeg

  • 转码 / 转封装HEVC→H.264、MOV→MP4、任意格式互转，本文主线任务
  • 压缩与缩放用 CRF 控制质量，用 scale 改分辨率
  • 无损剪切、拼接、抽取音轨-c copy 不重新编码，秒级完成
  • 抽帧、截图、生成缩略图 / GIFML 数据准备和预览图的标准做法
  • 批量、无人值守处理纯 CLI，exit code 明确，天生适合脚本和流水线

别交给 ffmpeg

  • 创意剪辑多轨时间线、转场、调色请用剪映 / Premiere / DaVinci
  • 理解内容识别人脸、生成字幕文本是 ML 模型的事，ffmpeg 只能烧录现成字幕
  • 绕过 DRM加密流不解、也不该解
  • 修复严重损坏的文件能容错读取，但不是修复工具
  • 「一个参数都不想学」的一次性转换偶尔转一个文件，HandBrake 这类 GUI 更省心
一句话心智模型：ffmpeg 不是「视频编辑器」，而是一条你用参数配置的装配线。 输入进厂 → 五个工位 → 成品出厂。所有参数都只是在回答一个问题：哪个工位、做什么。
三个默认行为不要误会：① 没写 -map 时，ffmpeg 会按默认规则挑流，不保证保留全部音轨、字幕和附件； ② 只要进了滤镜（如 -vf scale），视频就必须重新编码，不能再 -c:v copy； ③ 容器、编码、像素格式、时间戳是四层问题，文件扩展名只决定封装层，不能代表兼容性已经满足。

调用面：同一个引擎，四种用法

FFmpeg 项目其实提供了多层入口，但它们共享同一套引擎。对绝大多数场景，CLI 就是最佳 API—— 稳定、文档最全、行为可预期。其余入口只在特定条件下才值得。

入口形态适合不适合
ffmpeg CLI 命令行 / 脚本 subprocess 调用 本文所有场景：转码、剪切、抽帧、批处理、CI 流水线 需要逐帧编程处理像素时绕远
ffprobe CLI 只读的元数据检查器 转码前探测输入、转码后验证产物、输出 JSON 给脚本消费 任何写操作（它不改文件）
语言封装库 如 Python 的 ffmpeg-python、Node 的 fluent-ffmpeg 在应用代码里动态拼装复杂 filter 图 本质仍是拼 CLI 参数；简单任务直接 subprocess 更透明
libav* C API 链接 libavcodec / libavformat 等库 播放器、实时处理、需要帧级控制的产品（OBS、Chrome 都在用） 脚本化任务——开发成本高一个数量级
建议：脚本里优先用「参数数组」而不是拼接字符串来调用 CLI，例如 Python 的 subprocess.run(["ffmpeg","-i",path,...])——天然规避文件名带空格和注入问题。

参数心智模型：真正改变结果的只有八组

ffmpeg 有上千个参数，但决定「质量、体积、速度、剪切精度、播放兼容性、保留哪些流、时间轴是否稳定」的核心只有下面几组。 规则也只有一条：写在 -i 之前的作用于输入，写在 -i 之后的作用于输出。

-crf 0–51质量与体积的总闸门

CRF（恒定质量因子）是 libx264/x265 最重要的参数：数值越小质量越高、文件越大； 经验法则是 ±6 ≈ 体积翻倍 / 减半。它替代了「猜码率」——你声明想要的质量，编码器自己分配码率。拖动滑块感受取舍：

画质示意（非真实编码）
-crf 23 通用分发档
16 更清晰·更大34 更小·更糊
预估产物体积
≈180 MB
相对 2.1GB 源
8.4%

23 是 libx264 的默认值，网页/社交分发的安全起点。

-preset用时间换压缩率（不是换画质）

从 ultrafast 到 veryslow 共 9 档。常见误解是「preset 越慢画质越好」—— 其实在同一 CRF 下画质基本一致，更慢的 preset 只是用更多 CPU 时间把同等画质压得更小。 交互式用 medium（默认）；夜间批量任务可用 slow 省 10–20% 体积； ultrafast 留给「只要快、不在乎体积」的临时预览。

-c copy重新编码 vs 流复制：两种完全不同的操作

-c:v libx264 是重新编码；-c copy 是流复制—— 压缩数据原样搬进新容器，不解码不编码。想「只换个容器」或「无损剪一段」时，它快上两个数量级。切换看差异：

重新编码：改编码、改分辨率、控体积
$ ffmpeg -i IMG_4032.MOV -vf "scale=-2:1080" -c:v libx264 -crf 23 -c:a aac -b:a 128k output.mp4
耗时 ≈ 2 分钟 有损（受 CRF 控制） 可改分辨率 / 编码 / 体积 可任意帧精确剪切
-ss / -t / -to时间轴：剪哪一段，从哪里数

-ss 指定起点，-t 指定时长，-to 指定终点。 关键在 -ss 相对 -i 的位置——它决定 ffmpeg 是「按索引跳过去」还是「从头解码丢弃到起点」：

截取第 1:00 起的 20 秒
$ ffmpeg -ss 00:01:00 -i IMG_4032.MOV -t 20 -c:v libx264 -c:a aac clip.mp4

输入侧 seek：先按关键帧索引跳到 1:00 附近再开始解码，快；配合重新编码时，现代版本会精确到帧。 这是默认该用的写法。

唯一的坑：-ss + -c copy 组合时无法精确剪切——流复制不能从任意帧开始， 剪切点会落在最近的关键帧上，开头可能多几秒或短暂黑屏。要精确到帧，就重新编码。
-vf scale / -movflags两个「不显眼但必写」的分发参数

-vf "scale=-2:1080"：高度定为 1080，宽度按比例自动计算；用 -2 而不是 -1 是为了保证宽度是偶数——libx264 遇到奇数尺寸会直接报错（见下文失败案例）。

-movflags +faststart：转码结束后把 MP4 的索引（moov atom）搬到文件头。 没有它，浏览器要下载完整个文件才能开始播放；加上它，秒开。凡是产物要放到网页或流媒体分发，都写上。

-map / -sn / -map_metadata明确保留哪些流，而不是相信默认选择

一个媒体文件里可能有多条视频、多个音轨、字幕、封面、章节和元数据。没写 -map 时，ffmpeg 会按默认规则选择「每类最合适的一条」， 这对普通转码够用，但对多语言、多字幕、带封面或监控多路流很危险：命令成功了，产物却少了一条音轨。

$ ffmpeg -i in.mkv -map 0:v:0 -map 0:a? \ -c:v libx264 -crf 23 -c:a aac out.mp4

-map 0:v:0 只取第一个视频流；-map 0:a? 取所有音频，问号表示「没有音频也不报错」； -sn 丢字幕，-map_metadata 0 明确保留输入元数据。做归档或多语言分发时，先用 ffprobe 看清流，再写 -map。

-vf / -filter_complex简单滤镜和复杂滤镜不是一回事

单输入、单输出的视频变换用 -vf：缩放、裁剪、旋转、抽帧都在这里。只要出现多输入、多输出、画中画、水印叠加、音视频分别处理， 就该换 -filter_complex，并给中间结果命名。

$ ffmpeg -i main.mp4 -i logo.png \ -filter_complex "[0:v][1:v]overlay=W-w-24:24[v]" \ -map "[v]" -map 0:a? -c:v libx264 -c:a copy out.mp4

记住边界：滤镜处理的是解码后的原始帧，所以被滤镜碰过的那条流必须重新编码；没进滤镜的音频流可以继续 -c:a copy。

-r / fps / -fps_mode帧率和时间戳：别把 VFR 当 CFR

手机、录屏、直播切片常见变帧率（VFR）：平均看是 59.94fps，但每帧间隔不完全一致。分发通常没问题； 但要进剪辑工程、逐帧标注、抽帧训练或和外部时间码对齐，就要决定是否规整成恒定帧率（CFR）。

$ ffmpeg -i phone.mov \ -vf "fps=30,scale=-2:1080" \ -fps_mode cfr -c:v libx264 -crf 23 -c:a aac out.mp4

-r 30 写在输入前是「按 30fps 解释输入」，写在输出后是「输出 30fps」；多数转码不要随手写。 真正想抽帧或规整帧率时，用 fps 滤镜把意图写清楚，再用 ffprobe 验证 avg_frame_rate、r_frame_rate 和时长。

验证产物：别用「文件存在」当成功

ffmpeg 失败时经常留下一个半截的输出文件，所以「output.mp4 存在」不能证明任何事。 可靠的验证是让 ffprobe 读回产物的元数据，和预期做对比：

ffprobe — 机器可读的产物体检
$ ffprobe -v error -show_entries format=duration,size:stream=codec_name,width,height \ -of json output.mp4 { "streams": [ { "codec_name": "h264", "width": 1920, "height": 1080 }, { "codec_name": "aac" } ], "format": { "duration": "182.415000", "size": "188743680" } }
  1. exit code 为 0

    第一道也是最硬的一道。非 0 时其它一切不必再看。

  2. 时长与源一致

    ffprobe 读出 duration，与输入相差应在 0.1 秒内；差很多 = 转码中途断了。

  3. 编码 / 分辨率符合预期

    codec_name 是 h264、宽高是 1920×1080——确认参数真的生效了。

  4. 流没有丢错

    检查视频、音频、字幕数量是否符合业务预期。多音轨和字幕文件尤其要看 streams[].codec_type 与 tags.language。

  5. 像素格式与播放端兼容

    网页/手机分发优先确认视频是 yuv420p。如果源是 10-bit、HDR 或 4:4:4，转 H.264 时可能需要显式写 -pix_fmt yuv420p。

  6. 抽一帧人眼看看

    ffmpeg -ss 90 -i output.mp4 -frames:v 1 check.jpg，从中段抽一帧确认画面正常、没有花屏。

  7. 全量解码体检（重要产物才做）

    ffmpeg -v error -i output.mp4 -f null - 把整个文件解码一遍，stderr 无输出即无坏帧——最严格但最慢。

验证不是越多越好，而是按风险选：个人压缩看时长、编码、抽帧即可；上线分发要加像素格式、faststart、全量解码； 归档和多语言内容要额外检查 -map 后的流数量、语言标签、章节和元数据。

自动化契约：脚本如何和 ffmpeg 打交道

写进脚本或流水线之前，需要和它约定清楚五件事：

契约点行为脚本里怎么处理
成功 / 失败exit code 0 = 成功，非 0 = 失败唯一可信信号；bash 里 set -e，Python 里 check=True
日志通道全部日志走 stderr；stdout 保留给管道媒体数据加 -hide_banner -v error，让 stderr 只剩真正的问题
覆盖行为输出文件已存在时交互式询问，会把无人值守脚本挂死必写 -y（覆盖）或 -n（跳过），二选一
部分输出失败时可能残留半截文件，且它不幂等——重跑会直接覆盖先写临时名，exit code 为 0 后再 mv 到最终名（mv 原子性 = 近似幂等）
进度进度行也在 stderr，格式不稳定需要程序化进度就加 -progress pipe:1，会向 stdout 输出 key=value 行
资源占用转码会吃满 CPU / GPU / 磁盘 IO；并发过高比单条命令慢，还可能拖垮机器在队列层限制并发；固定 -threads 或 worker 数；给任务设置超时和最大输入时长
版本漂移不同构建的编码器、硬件加速、默认行为可能不同容器化固定版本；启动时记录 ffmpeg -version、-encoders 和关键参数 profile

可直接抄的最小批处理脚本

transcode.sh — 覆盖关键自动化契约
#!/usr/bin/env bash set -euo pipefail # 任何一步失败立刻退出 in="$1" out="${in%.*}_1080p.mp4" tmp="${out}.part" # 先写临时名 ffmpeg -hide_banner -v error -y \ -i "$in" \ -vf "scale=-2:1080" \ -c:v libx264 -crf 23 -preset medium \ -c:a aac -b:a 128k \ -movflags +faststart \ -f mp4 "$tmp" # 临时名不叫 .mp4，显式指定容器 # 走到这里 exit code 必为 0，产物才可信 → 原子落盘 mv "$tmp" "$out" dur=$(ffprobe -v error -show_entries format=duration -of csv=p=0 "$out") echo "OK $out (${dur}s)"

批量跑一个目录：for f in *.MOV; do ./transcode.sh "$f"; done。 注意 "$f" 的引号——文件名带空格是脚本里最常见的翻车点。

失败边界：八个最常撞上的错误

每一个都给出真实报错片段和修法。点开对照——大部分 ffmpeg 报错都比看起来友好，关键信息就在最后几行。

尺寸height not divisible by 2 —— 奇数分辨率›
[libx264] height not divisible by 2 (1280x719) Error while opening encoder for output stream #0:0

libx264 要求宽高都是偶数。当你写 scale=1280:-1 让 ffmpeg 按比例算另一边时，就可能算出奇数。

修法：自动算的那一边永远写 -2：scale=1280:-2 或 scale=-2:1080，强制取整到偶数。

构建Unknown encoder 'libx264' —— 环境里的 ffmpeg 不是你以为的 ffmpeg›
Unknown encoder 'libx264'

ffmpeg 是按编译选项裁剪功能的：发行版仓库、Docker 精简镜像里的构建可能没编入 libx264（GPL 许可）或其它编码器。 同一条命令在你机器上能跑、在 CI 里报错，多半是这个原因。

修法：用 ffmpeg -encoders | grep 264 确认当前构建能力；换用官方静态构建或功能完整的镜像。 流水线里最好在启动时校验一次 ffmpeg -version 并固定版本。

容器codec not currently supported in container —— 编码和容器不匹配›
[mp4 @ 0x...] Could not find tag for codec pcm_s16le in stream #1, codec not currently supported in container

容器（MP4/MKV/WebM）和编码（H.264/VP9/PCM）是两层概念，且有兼容矩阵：MP4 装不了 PCM 音频，WebM 只收 VP8/VP9/AV1。 -c copy 换容器时最容易撞上。

修法：不匹配的那条流单独重编码，如 -c:v copy -c:a aac；或换个来者不拒的容器（MKV 几乎什么都能装）。

时间轴-c copy 剪切后开头黑屏 / 时长不准 —— 关键帧边界›
$ ffmpeg -ss 00:01:00 -i in.mp4 -t 20 -c copy clip.mp4 # 无报错，但 clip.mp4 开头卡帧 2 秒，实际时长 22.3s

这是最阴险的一类问题：命令成功、exit code 为 0，但产物不对。 流复制只能从关键帧开始，1:00 不在关键帧上时，剪切点就会漂移。

修法：需要精确剪切就去掉 -c copy 重新编码；能接受几秒误差（比如粗剪素材）才用流复制换速度。 这也是「验证要查时长」的直接理由。

输入moov atom not found —— 输入本身就是半截文件›
[mov,mp4,m4a,3gp,3g2,mj2 @ 0x...] moov atom not found IMG_4032.MOV: Invalid data found when processing input

MP4/MOV 的索引默认写在文件末尾，录制中断、上传不完整、或把上一次失败的半截产物当输入，都会缺 moov。 ffmpeg 无法修复它，只能拒绝。

修法：在源头解决——上传服务校验完整性；自己的产物用「临时名 + mv」避免半截文件混入； 这也是为什么自己生成 MP4 要加 +faststart 把索引前置。

流选择命令成功但少了音轨 / 字幕 —— 默认 stream selection 不是保留全部›
$ ffmpeg -i movie.mkv -c:v libx264 -c:a aac out.mp4 # out.mp4 只有一条默认音轨，第二语言音轨和字幕没了

ffmpeg 默认会为每种类型挑一条流，并不等于「输入有什么就都保留」。多语言、内嵌字幕、章节、封面图最容易在这里丢。

修法：先 ffprobe -show_streams -of json in.mkv 看清流，再显式写 -map。 归档用 -map 0 -c copy 起步；分发用 -map 0:v:0 -map 0:a?，字幕按播放端能力决定保留、转码或丢弃。

播放兼容电脑能播，手机/浏览器黑屏 —— 像素格式或色彩规格不兼容›
Video: h264, yuv444p10le, 1920x1080 # 某些移动端硬解不支持 10-bit 或 4:4:4 H.264

编码是 H.264 不代表所有设备都能播。网页和手机最稳的是 8-bit yuv420p；HDR、10-bit、4:4:4 源在转分发版时要主动降到兼容档。

修法：分发版加 -pix_fmt yuv420p，必要时把 HDR→SDR 色彩转换列为单独流程；不要把归档母版和网页分发版混成同一个 profile。

时间戳音画逐渐不同步 / 抽帧数量不稳定 —— VFR 输入没被当回事›
$ ffprobe -v error -select_streams v:0 -show_entries stream=r_frame_rate,avg_frame_rate in.mov r_frame_rate=60000/1001 avg_frame_rate=143827/2399

手机和录屏文件常是 VFR。普通播放能靠时间戳对齐；但抽帧、训练集、逐帧标注或和外部字幕对齐时，VFR 会让「第 N 帧」和「第 N 秒」的关系变复杂。

修法：需要帧级稳定时，先决定输出 CFR：用 -vf fps=30 -fps_mode cfr 明确重采样； 如果业务必须保留原时间戳，就不要用帧号当真相源，后续一律按时间戳对齐。

取舍：什么时候用它，什么时候别用

候选它赢在ffmpeg 赢在选择建议
HandBrake（GUI） 零学习成本，预设完善，适合偶尔转几个文件 可脚本化、参数全开、能进服务器 一次性人工任务用 GUI；要重复第二次就写 ffmpeg 命令
剪映 / Premiere / DaVinci 创意剪辑：多轨、转场、调色、字幕设计 确定性的机械变换、批量、无人值守 「人做决定」用编辑器，「规则做决定」用 ffmpeg；两者常串联——编辑器出成片，ffmpeg 出各分辨率分发版本
云转码（MediaConvert / 阿里云 MPS 等） 弹性并发、托管运维、DRM/自适应码流开箱即用 零成本起步、数据不出本地、完全可控 日均几百个文件以内自建 ffmpeg worker 足够；量级上万或要 DRM 再上云——云服务底层多半也是 ffmpeg
moviepy 等编程库 用 Python 对象逐帧合成、叠加动画 性能（moviepy 底层就是调 ffmpeg，多绕一层慢很多） 需要程序化生成画面内容才用库；纯转换/剪切直接 ffmpeg

判断标准可以收敛成一句话：任务能不能写成「对每个输入，执行同一套确定的变换」。 能——ffmpeg 几乎总是那个成本最低、最可控的答案；不能（需要审美判断、逐个决策）——去用带时间线的编辑器。

速查：八条覆盖日常 90% 的命令

主线任务：压成网页可播的 1080p MP4
ffmpeg -i in.mov -vf "scale=-2:1080" \ -c:v libx264 -crf 23 -preset medium \ -c:a aac -b:a 128k \ -movflags +faststart out.mp4
无损换容器（秒级）
ffmpeg -i in.mkv -c copy out.mp4
精确剪切 1:00 起 20 秒
ffmpeg -ss 00:01:00 -i in.mp4 -t 20 \ -c:v libx264 -c:a aac clip.mp4
抽取音频为 MP3
ffmpeg -i in.mp4 -vn -c:a libmp3lame -q:a 2 out.mp3
每 5 秒抽一帧图（喂 ML / 做预览）
ffmpeg -i in.mp4 -vf fps=1/5 frames/f_%04d.jpg
体检任意媒体文件（只读）
ffprobe -v error -show_format \ -show_streams -of json in.mp4
保留所有流无损归档（容器兼容时）
ffmpeg -i in.mkv -map 0 -c copy archive.mkv
网页最稳分发版：强制兼容像素格式
ffmpeg -i in.mov -vf "scale=-2:1080" \ -c:v libx264 -crf 23 -preset medium \ -pix_fmt yuv420p -c:a aac -b:a 128k \ -movflags +faststart out.mp4
