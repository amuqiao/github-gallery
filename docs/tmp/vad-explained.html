一文读懂 · 语音信号处理

机器怎么听出"现在有人在说话"？ VAD — Voice Activity Detection 语音活动检测

你对智能音箱说完一句话，它怎么知道你说完了、该去执行了？通话静默时，系统怎么知道可以不传数据省带宽？这些问题的答案都是同一个东西：VAD。下面这条波形就是它每天面对的世界——试着自己当一回 VAD。

你刚刚体验到的两个困境，就是 VAD 全部技术演进的起点：① 阈值往下调，误报变多；往上调，漏检变多——鱼与熊掌。② 噪声一大，能量这个特征本身就失效了——语音和噪声在能量上重叠，阈值放哪儿都不对。记住这两点，后面的一切都是在解决它们。

缘起它为什么出现，解决什么问题

VAD 的任务定义非常克制：给每一小段音频打一个二分类标签——"有人声"或"没人声"。它不关心说的是什么（那是 ASR 的事），不关心是谁在说（那是说话人识别的事），只回答"有没有"。这个看似简单的问题之所以重要，是因为它站在几乎所有语音系统的大门口：

  • 省带宽 / 省算力：这是 VAD 的出身。电话通话中约一半时间是听对方说，自己这端是静音。GSM、VoIP 编码器（如 G.729 Annex B）用 VAD 触发 DTX（不连续传输），静音期只发极小的舒适噪声参数，带宽省一半。今天同样的逻辑用在 ASR 前端：语音识别模型很贵，静音段根本不该送进去。
  • 端点检测（endpointing）：语音助手判断"你说完了"，本质是 VAD 检测到语音结束后持续了几百毫秒静音。切早了截断你的话，切晚了响应迟钝——这个体验差异用户感知极强。
  • 唤醒与功耗：耳机、音箱上常驻一个微瓦级的小 VAD，检测到人声才唤醒后面的大模型，否则电池撑不住。
  • 数据流水线：训练语音模型前，用 VAD 把几万小时录音里的有效语音切出来，是最基础的预处理。

边界也要说清：VAD 只做"有/无"判断。它不负责把你的声音和电视里的人声区分开（两者都是人声，VAD 都会报"有"），也不负责判断这句话是不是对设备说的。这些是它常被误解能做、实际做不了的事，后面"常见误区"一节展开。

为什么特征一路从"能量"进化到"神经网络"

回看首屏实验：噪声一大，能量就失效。VAD 五十年的历史就是不断寻找"人声有、噪声没有"的特征：

时代特征 / 方法核心假设被什么打败
朴素短时能量 + 过零率（ZCR）语音比背景响；清音过零率高任何非平稳噪声：关门声、键盘声都比语音响
经典频谱特征 + 统计模型（如 WebRTC VAD 的 GMM）语音和噪声在各子带上的分布不同，可用高斯混合建模，并在线更新噪声估计babble noise（一群人说话的背景音）——噪声本身就是语音，分布假设崩溃
现代神经网络直接学（Silero VAD、各家端到端模型）不做人工假设，从海量"带噪语音 + 标签"里学出人声的判别性表示（谐波结构、共振峰轨迹、时序模式）训练分布外的场景仍会退化；且模型更大、有延迟成本

注意这不是"新的淘汰旧的"：手表里的常驻 VAD 至今仍是能量法（因为只有几微瓦的功耗预算），会议软件里则是神经网络 VAD。选哪个是工程取舍，不是先进程度排名。

动手Hangover：为什么逐帧判决不能直接用

就算逐帧判决准确率高达 95%，直接使用仍是灾难。语音里天然有停顿（"今天……呃……天气不错"）、弱音尾巴（句尾的轻声、摩擦音能量很低），逐帧看全是"静音"，一刀切下去，句子就被剁碎了。下面每个方块是一帧，点按钮看平滑前后的差别：

Hangover 的实现通常是一个小状态机：判到语音后进入"语音态"，之后即使连续若干帧判为静音，也再等 N 帧才真正切换到静音态；反向也常要求"连续 M 帧语音才进入语音态"（防止一声咳嗽触发）。两个参数直接决定体验：

  • N 太小 → 句子被停顿切碎，ASR 收到残句，识别结果支离破碎；
  • N 太大 → 语音助手在你说完后傻等半天才响应，通话软件把你静音后的杂音继续外放。
这是 VAD 最反直觉的一课：产品体验的好坏往往不取决于逐帧准确率，而取决于这个不起眼的平滑逻辑。调 VAD 的大部分时间是在调 hangover 和 endpointing 超时，而不是换模型。

最小例子20 行代码跑通一个真 VAD

用 Google 开源的 webrtcvad（GMM 方案，几乎零依赖、CPU 上快到可以忽略）切一个 WAV 文件。这是可以直接验证前文所有概念的最小实验：

# pip install webrtcvad
import webrtcvad, wave

vad = webrtcvad.Vad(2)   # aggressiveness 0~3：越大越激进，误报少但漏检多
                          # —— 这就是首屏那根"阈值线"的工程化版本

wf = wave.open("speech.wav", "rb")   # 要求：16kHz、16bit、单声道
rate = wf.getframerate()
frame_ms = 20                        # 每帧 20ms（仅支持 10/20/30ms）
frame_bytes = int(rate * frame_ms / 1000) * 2

t = 0.0
while True:
    frame = wf.readframes(frame_bytes // 2)
    if len(frame) < frame_bytes: break
    is_speech = vad.is_speech(frame, rate)      # 逐帧判决：True / False
    print(f"{t:6.2f}s  {'SPEECH' if is_speech else '  --  '}")
    t += frame_ms / 1000
# 注意：输出会在词间隙"闪烁"——webrtcvad 不带 hangover，需要你自己加，
# 这正是上一节状态机存在的意义。

三个可动手验证的实验：① 把 aggressiveness 从 0 调到 3，观察漏检/误报此消彼长；② 给音频叠加白噪声，看 GMM 什么时候撑不住；③ 换 Silero VAD（PyTorch，输出的是 0~1 概率而非硬判决）跑同一段带噪音频，直观感受神经网络方案的差距。

落地工程实现：真实项目里它长什么样

先划清边界：输入、输出、前置条件

维度约定
输入PCM 音频。绝大多数 VAD 实现（webrtcvad、Silero）要求 16kHz / 单声道 / 16-bit；离线文件是 MP3/双声道/44.1kHz 是常态，重采样和转声道是你的前置责任，不是 VAD 的。流式场景则是固定长度的帧（chunk）序列。
输出两种形态：① 逐帧布尔值/概率（流式场景，供下游状态机消费）；② 时间戳段列表 [{start, end}, ...]（离线场景，最常用的交付物）。团队协作时，把输出定成"秒为单位的段列表 JSON"能省很多沟通成本。
前置条件音量不能过低（数字增益过小的录音会让一切 VAD 漏检，先做归一化/AGC）；如果环境噪声极端，考虑在 VAD 前挂一级降噪——但注意降噪会改变波形，评测要在降噪后的信号上做。
不该由它解决区分目标说话人和电视人声（personal VAD / 说话人验证的事）；判断"这句话是不是对我说的"（语义层）；音乐中的人声检测（歌声和语音分布差异大，需要专门模型）；把噪声去掉（那是降噪）。把这些需求塞给 VAD，方案一定失败。

最小实现路径：一条数据流走通

离线批处理（最常见的落地形态）的主链路只有四步：输入规整 → 逐帧打分 → 段整形 → 输出时间戳。下面用 Silero VAD 走通全程——它输出概率而非硬判决，正好把"阈值"和"平滑"两个决策点显式地留在你手里：

# pip install silero-vad soundfile   (Python 3.8+，CPU 即可)
from silero_vad import load_silero_vad, read_audio, get_speech_timestamps

model = load_silero_vad()

# ① 输入规整：read_audio 内部完成重采样到 16kHz + 转单声道
wav = read_audio("meeting.mp3", sampling_rate=16000)

# ② 逐帧打分 + ③ 段整形：库把状态机封装成了四个关键参数
segments = get_speech_timestamps(
    wav, model,
    threshold=0.5,                 # 语音概率阈值：首屏那根线
    min_speech_duration_ms=250,    # 短于此的"语音"当误触发丢弃（防咳嗽）
    min_silence_duration_ms=300,   # 静音超过此值才切段：即 hangover
    speech_pad_ms=30,              # 段两端外扩，保住弱音头尾
    return_seconds=True,
)

# ④ 输出交付：段列表就是下游（切音频/送 ASR/存库）的通用接口
for seg in segments:
    print(f"{seg['start']:8.2f}s → {seg['end']:8.2f}s")

注意这段代码里没有 try/except、没有默认值兜底：输入文件坏了就该抛错让上游知道，静默降级只会把问题埋到下游 ASR 的离奇结果里。工程上真正值得写的健壮性是：入口处断言采样率和声道数，出口处对"零段输出"打日志报警（大概率是音量问题，不是真的全程静音）。

流式场景（实时通话、语音助手）的差别只在数据形态：输入变成 30ms 一帧的循环，你自己维护那个 hangover 状态机（上一节演示的逻辑，约 20 行代码），逐帧吐出 speech_start / speech_end 事件。主链路思想完全相同，不再重复。

三个典型场景的推荐路径

场景一：离线批处理（切播客、清洗训练数据、给录音打时间戳）
→ Silero VAD，别犹豫。离线意味着延迟和算力都不是约束，此时唯一重要的是噪声下的准确率，神经网络方案全面占优。调参重点：数据要送 ASR 就调大 speech_pad_ms（漏字比多切一点噪声更伤），做统计分析则收紧 threshold 减少误报。

场景二：实时语音助手 / 通话端点检测
→ Silero 流式模式为主，CPU 预算极紧才退回 webrtcvad。这个场景的胜负手不在模型而在状态机参数：endpointing 超时 500–800ms 起步，然后用真人试用来调，指标是"被截断次数"和"响应等待感"，不是帧准确率。若用云 ASR，优先用它内置的端点检测，本地 VAD 只做粗筛省流量。

场景三：高并发服务端网关（几百路音频同时进来，先滤掉静音再分发）
→ 级联：webrtcvad 粗筛 + Silero 精判。第一级用 aggressiveness=1（宁可误报不可漏检）把明显静音挡掉，通常能滤掉一半以上流量；第二级只对存活的段跑 Silero。这样单路成本接近 webrtcvad，精度接近 Silero——工业上省钱的标准做法。

选型的判断顺序可以压缩成一句话：先看延迟/算力预算划掉不可行的，再看噪声场景在剩下的里选最准的，最后把调参精力全部投给平滑与端点参数——这与前文的主线完全一致：模型决定下限，状态机决定体验。

辨析相近概念与常见误区

概念回答的问题和 VAD 的关系
VAD这一帧有没有人声？—
端点检测 Endpointing这句话什么时候开始、什么时候结束？建立在 VAD 之上，加上"静音持续多久算说完"的策略层
唤醒词检测 KWS刚才说的是不是"Hey Siri"？关心内容，比 VAD 重得多；常由 VAD 先把关再触发
说话人分离 Diarization谁在什么时候说话？第一步往往就是跑 VAD，再对语音段聚类分人
降噪 / 语音增强怎么把噪声去掉？互补：降噪改善音频本身，VAD 只打标签不改音频；实践中常降噪后再 VAD
误区一："VAD 能过滤掉电视里的说话声"

不能。电视人声也是人声，VAD 的定义就是检测人声，它会如实报告"有语音"。区分"目标说话人 vs 其他人声"是 personal VAD / 目标说话人提取的课题，需要注册说话人特征，是另一套系统。

误区二："准确率 98% 的 VAD 一定比 95% 的好用"

不一定。第一，帧准确率会被"静音占大头"的数据灌水——一段 90% 是静音的录音，全判静音就有 90% 准确率。看 VAD 要看 miss rate 和 false alarm rate 两条曲线（或 ROC/DET 曲线），并且在你的目标噪声场景下测。第二，如上一节所说，产品体验还取决于平滑策略和延迟，单看逐帧指标会选错模型。

误区三："上神经网络 VAD 总是更好"

要看约束。神经网络 VAD 在低信噪比、babble noise 下碾压传统方法，但它有模型体积、算力、以及前瞻上下文带来的固有延迟。在耳机常驻监听（功耗预算以微瓦计）或对延迟极敏感的场合，能量法/GMM 仍是正确答案。工程上常见做法是级联：小 VAD 常驻粗筛，大 VAD 精判。

误区四："VAD 阈值调一次就完了"

环境是会变的。安静办公室调好的阈值，到了地铁上就是灾难。稍好的系统都会做噪声底自适应（跟踪最近的最低能量作为噪声估计，阈值随之浮动），WebRTC VAD 的 GMM 也在线更新噪声模型。你在首屏实验里手动干的事（噪声变大→被迫抬高阈值），真实系统必须自动完成。

迁移拿去就能用的决策清单

  1. 先问场景：功耗/延迟预算多少？噪声环境是什么（安静房间 / 车载 / 街头 / 多人环境）？误报和漏检哪个更致命？（通话省带宽宁可误报，ASR 端点宁可漏检慢一点。）
  2. 选方案：极限功耗 → 能量法；CPU 实时、中等噪声 → webrtcvad；离线处理或高噪声 → Silero VAD 等神经网络方案；已在用 ASR 大模型 → 很多 ASR（如 Whisper 的第三方 pipeline）内置 VAD，别重复造。
  3. 定帧长：10–30ms 是行业惯例；实时交互取短（延迟低），离线处理取长（更稳）。
  4. 调平滑，而不是死磕模型：speech→silence 的 hangover 通常 200–500ms 起步；endpointing 超时按产品体验调（语音助手常见 500–800ms）。
  5. 用真实噪声评测：拿目标场景的录音，画 miss / false-alarm 曲线，别只看总准确率。

最后收束回那条主线：VAD 是一个被"特征在噪声下是否仍可分" + "误报漏检如何取舍" + "时序如何平滑"三个问题完全定义的小而美的领域。理解了首屏那条阈值线为什么不够用，你就理解了它的全部演进逻辑——之后无论遇到哪个具体实现，都只是在这三个问题上给出了不同答案而已。
