一文读懂 YOLO
You Only Look Once

一张图片进去,一串「框 + 类别 + 置信度」出来——只看一次,整图一次前向就完成检测。这篇文章讲清 YOLO 解决什么任务、数据如何在网络里流动、十年间的版本演进,以及你该不该用它。

输入 H×W×3 图像 输出 [x, y, w, h, conf, class] × N 一次前向 ≈ 几毫秒
input: image 480×320×3output: 3 detections
section · 它解决什么任务0.98

目标检测:不仅要认出「是什么」,还要框出「在哪里」

图像分类回答一个问题:这张图是什么。目标检测回答两个:图里有哪些东西,每个东西的位置在哪。输出从「一个类别标签」变成「一组带坐标的框」——这个变化让问题难了一个量级。

图像分类 Classification

输入一张图 → 输出一个类别。
"dog" 0.95
不知道狗在哪,也不知道有几只。

目标检测 Detection ← YOLO

输入一张图 → 输出 N 个「框+类别+置信度」。
[x,y,w,h, 0.92, "dog"]
知道每个目标是什么、在哪、有多确定。

实例分割 Segmentation

比检测更进一步,精确到每个像素的轮廓。计算更贵。新版 YOLO(v8 起)也顺带支持。

为什么会出现 YOLO

2015 年之前,主流检测器是 两阶段 的 R-CNN 家族:第一步先生成上千个「可能有物体」的候选区域(region proposals),第二步逐个区域做分类和位置修正。准确,但慢——早期 R-CNN 处理一张图要几十秒,即使优化后的 Faster R-CNN 也难以满足实时需求。

YOLO 的提议非常激进:把检测当作一个回归问题,整张图只过一次网络,直接从像素回归出所有框的坐标和类别——"You Only Look Once"。第一版就做到了 45 FPS,比同期两阶段方法快一个数量级,代价是精度略低、小目标较弱。此后十年的版本演进,本质上就是在「快」的基础上一路把「准」补回来。

输入、输出与边界

项目内容
输入一张 RGB 图像,推理前会被缩放/填充到固定尺寸(常见 640×640×3),像素值归一化到 0~1
输出检测框列表,每个框是 [x, y, w, h, confidence, class_id];框数量不定,取决于图中内容和阈值设置
能做检测训练时见过的类别(如 COCO 数据集的 80 类);新版还支持分割、姿态估计、旋转框、跟踪等任务头
不能做检测没训练过的类别(需要重新训练或用 YOLO-World 这类开放词汇模型);理解图像语义、回答问题、生成描述——那是多模态模型的事
一句话定位:YOLO 是一类「单阶段、实时优先」的目标检测卷积网络。当你的需求是「在视频流或大批图像里快速找到已知类别的物体」,它几乎是默认选项。
section · 核心思想0.97

把图切成网格,每个格子负责「落在我这里的物体」

YOLO 的原始洞察:把图像划分为 S×S 网格,物体中心点落在哪个格子,就由哪个格子负责预测这个物体。每个格子输出固定长度的向量——几个候选框的坐标、有没有物体的置信度、以及类别概率。整张图的所有格子并行计算,一次前向全部完成。

interactive · 把鼠标移到(或点按)任意网格上,看这个格子在预测什么
# 移入网格查看该格子的预测向量

每个格子输出:
[ x, y, w, h,
  objectness,
  p(person), p(car), p(dog), … ]
图中 彩色圆点 是三个物体的中心。只有中心点所在的格子「负责」输出高置信度预测,其余格子学会输出「这里是背景」。

简化演示:真实模型中每个格子会预测多个候选框,且在多个尺度的网格上同时进行(见下一节)。

这个设计带来两个直接后果,理解它们就理解了 YOLO 一半的演进史:

① 快 —— 不需要「先猜哪里可能有物体、再逐个看」,所有位置的预测在一次卷积前向里并行完成,天然适合 GPU。
② 输出是冗余的 —— 成千上万个格子各自报告,同一个物体会被多个相邻预测重复命中,所以必须有一步 NMS(非极大值抑制) 去重:按置信度排序,保留最高分的框,删掉与它重叠过大(IoU 超阈值)的其余框。直到 YOLOv10 才通过训练策略把这一步从推理中去掉。

section · 核心数据流0.96

一张图在网络里的五站旅程

现代 YOLO(v5 之后)的结构高度模块化:Backbone 提特征 → Neck 融合多尺度 → Head 出预测 → 后处理筛选。点击下方每个阶段,看数据的形状如何一路变化。

关键直觉:多尺度是为了大小通吃。深层特征图(20×20)每个格子看到的原图范围大、语义强,负责大物体;浅层特征图(80×80)分辨率高、细节多,负责小物体。Neck 的作用就是让深层的语义流向浅层、浅层的细节流向深层,三个尺度互通有无——这是 v3 引入多尺度、v4/v5 引入 PANet 之后精度大涨的核心原因。
section · 训练与推理0.95

训练时学什么,推理时算什么

同一个网络,两种模式。训练是「拿标注答案反复纠错」,推理是「一次前向 + 一次筛选」。分清两者,你才知道哪些因素在哪个环节影响结果。

学习目标:让每个格子的输出逼近标注

训练数据是「图片 + 标注框」。YOLO 的标注格式极简,每张图对应一个 .txt,每行一个物体:

# class_id  x_center  y_center  width  height(全部归一化到 0~1)
0  0.245 0.573 0.128 0.539   # person
16 0.427 0.727 0.204 0.231   # dog
2  0.733 0.667 0.375 0.348   # car

每一步训练:前向得到全部格子的预测 → 标签分配(决定哪些预测应负责哪个真实框,这是各版本差异最大的隐藏环节)→ 计算损失 → 反向传播更新权重。损失由三部分构成:

Box Loss 框回归

预测框与真实框的重叠度差距。从早期 MSE 演进为 IoU / GIoU / CIoU 系列,直接优化「框得准不准」本身。

Objectness Loss 有无物体

让「负责物体的格子」输出高置信度,让海量背景格子输出低置信度。正负样本极不平衡,是训练稳定性的关键。

Class Loss 类别

负责格子的类别概率逼近真实类别,通常是 BCE(每类独立二分类,允许多标签)。

哪些因素决定训练效果

因素影响
数据集决定模型「认识什么」。类别分布、标注质量、场景覆盖度的影响远大于换模型版本
数据增强v4/v5 引入的 Mosaic(四图拼一图)大幅提升小目标与多尺度鲁棒性,是「免费涨点」的代表
输入尺寸 imgsz越大越利于小目标,但显存与耗时平方级增长;训练和推理尺寸应保持一致
预训练权重几乎总是从 COCO 预训练权重微调(fine-tune),而不是从零训练;小数据集下差距悬殊
模型规格 n/s/m/l/x同一版本按宽度/深度缩放出多个体量,精度与速度的第一道取舍

推理:确定性的四步流水线

① 预处理:保持长宽比缩放 + 灰边填充(letterbox)到 640×640,归一化,HWC→CHW。
② 前向:一次网络计算,得到约 8400 个候选预测(权重固定,无随机性)。
③ 解码 + 置信度过滤:把网络输出还原为像素坐标,丢弃 conf < conf_thres 的框。
④ NMS 去重:同一物体的重复框只留最高分(YOLOv10 起可免去这步)。最后把坐标映射回原图尺寸。

推理时真正影响结果的旋钮

参数作用
conf_thres置信度门槛。调低→查全率高但误检多;调高→干净但漏检多。默认约 0.25
iou_thresNMS 的重叠判定阈值。调低→去重狠,密集物体易被误删;调高→重复框残留。默认约 0.45~0.7
imgsz推理分辨率。小目标多就调大(如 1280),延迟随之上升
half / int8FP16 半精度或 INT8 量化,速度翻倍级提升,精度损失通常 <1 个点
硬件与格式同一模型在 PyTorch / ONNX Runtime / TensorRT 上延迟可差数倍;部署格式是工程性能的主要变量
常见误区:推理结果「不准」时,先检查 conf/iou 阈值和输入尺寸是否与场景匹配,再怀疑模型本身——大量「模型不行」的结论其实是后处理参数不合适。

section · 最小可运行示例0.93

三行代码跑通推理

以生态最成熟的 Ultralytics 为例(YOLOv8 / YOLO11 同一套 API)。以下示例可直接在本地验证。

① 安装(Python ≥ 3.8)
pip install ultralytics
② 最小推理脚本 predict.py
from ultralytics import YOLO

model = YOLO("yolo11n.pt")          # 首次运行自动下载,nano 版仅约 5.4 MB
results = model("street.jpg", conf=0.25, iou=0.45)   # 一次前向 + 后处理

for box in results[0].boxes:
    cls  = results[0].names[int(box.cls)]   # 类别名
    conf = float(box.conf)                  # 置信度
    x1, y1, x2, y2 = box.xyxy[0].tolist()   # 像素坐标
    print(f"{cls:8s} {conf:.2f}  [{x1:.0f},{y1:.0f},{x2:.0f},{y2:.0f}]")

results[0].save("out.jpg")               # 保存画好框的可视化结果

section · 选型与边界0.92

该不该用 YOLO?一份判断清单

适合

视频流实时检测(监控、驾驶辅助、机器人)/ 边缘与移动端部署 / 类别固定的工业质检、农业计数 / 需要快速微调落地的中小数据集项目 / 检测+分割+姿态的一站式需求。

不适合 / 需谨慎

极小目标或超高分辨率遥感(考虑切片推理 SAHI)/ 极度密集且相互遮挡的场景(NMS 会误删)/ 类别开放、无法预先枚举(用 YOLO-World / Grounding DINO)/ 需要理解语义与关系(用多模态大模型)。

常见误区

「版本号越大越好」v8 之后各代 COCO 精度差距常在 1 个点以内;数据质量、输入尺寸、阈值调优的收益通常更大。选生态(文档、导出链路、社区)往往比追新更划算
「YOLO 能认出任何东西」预训练权重只认训练集类别(COCO 80 类)。「安全帽」「缺陷」都需要自己标注训练
「demo 里很准,上线就拉胯」训练分布 ≠ 部署分布:光照、角度、摄像头差异都会掉点。上线前用真实场景数据微调和评估
「许可证无所谓」Ultralytics 系(v5/v8/11)为 AGPL-3.0:闭源商用需购买商业授权。对许可敏感可考虑 Apache-2.0 的 YOLOX、PP-YOLOE、RT-DETR 等

与两阶段 / Transformer 检测器的取舍

vs Faster R-CNN(两阶段):YOLO 快数倍,部署链路成熟;两阶段在某些高精度、小目标学术基准上仍有优势,但工程界已大面积转向单阶段。
vs DETR 系(Transformer):DETR 端到端免 NMS、结构优雅,RT-DETR 已能同台竞速;YOLO 胜在轻量规格更全、边缘端优化生态(TensorRT/NCNN/RKNN)更深。实时 + 资源受限,YOLO 仍是默认答案;服务器端高精度,两者都值得一测。
