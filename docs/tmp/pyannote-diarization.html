speaker-diarization-3.1
Speaker Diarization · 说话人分割

把一段多人录音,
切成 "谁在何时说话" 的时间轴

pyannote.audio 是一个基于 PyTorch 的开源说话人分割库。给它一段混着几个人声音的音频,它输出每一句话的起止时间和说话人标签——不做转写,只回答 "who spoke when"。

conference.wav · 16kHz mono ──▶ Pipeline("speaker-diarization-3.1") ──▶ conference.rttm · 谁在何时说话
DIARIZATION OUTPUT · conference.wav
00:00 / 00:24

▲ 这条时间轴就是本文的主线:一个 Annotation 对象——每个色块 = 一个 speaker turn(start / duration / label)。悬停任一色块看它的取值。

01

能力契约:它负责什么,不负责什么

先划清边界。pyannote 只解决 "分割 + 聚类 说话人" 这一件事。它不认识说话人是谁(不做声纹身份识别),不转写文字(那是 ASR 的活)。分不清 "SPEAKER_00 是张三" 是正常的——它只保证同一个色块内是同一个人。

▸ INPUT

  • 一段音频文件(.wav/.flac/.mp3),内部统一重采样到 16kHz 单声道
  • 可选:说话人数量约束 num_speakers 或 min/max_speakers
  • 一个 Hugging Face access token(模型是 gated 的)

▸ OUTPUT

  • 一个 pyannote.core.Annotation:有序的 (start, end, speaker) 三元组集合
  • 可 write_rttm() 落成标准 RTTM 文件
  • 标签是匿名的 SPEAKER_00 / 01 …,同一段音频内稳定

▸ 谁在用它

  • 做会议 / 播客 / 客服录音转写的工程师(diarization + ASR)
  • 语音研究者:需要离线、可复现、可用 DER 评测的 baseline
  • 需要私有部署、数据不能出内网的团队
不该交给它

说话人身份识别

它给不出"这是谁",只给匿名标签。要识别具体人需另配 speaker verification / enrollment。

不该交给它

语音转文字

输出里没有一个字。文字要接 Whisper 等 ASR,再与 RTTM 时间轴对齐。

不该交给它

实时低延迟流式

默认 pipeline 是离线整段处理。实时场景需另做流式方案,精度会打折。

不该交给它

脏音频救场

远场、强噪声、重叠严重时精度骤降。它不做降噪,前置清洗是你的活。

03

调用面:该从哪个入口用它

和 ffmpeg 那种命令行工具不同,pyannote 的主入口是 Python 对象。理解这一点决定了你怎么把它接进流水线。

主入口 · 推荐

Python SDK:Pipeline

唯一的一等公民。Pipeline.from_pretrained(...) 拿到对象后当函数调用。批处理、复用模型、精细控制参数都在这里。99% 的用法从这里开始。

你自己封的

CLI:包一层脚本

没有官方 diarization CLI。要命令行用法,自己写个 diarize.py 用 argparse 收 --audio --num-speakers --out,内部调 SDK,末尾 write_rttm。自动化契约由你定。

进阶

低阶模型 + 自组 pipeline

想只做 VAD、或换 embedding 模型、或改聚类——可以单独加载 Model.from_pretrained("pyannote/segmentation-3.0") 等积木自己拼。研究向,不做产品别碰。

配置 / 复现

超参 instantiate

聚类阈值、min_cluster_size 等通过 pipeline.instantiate({...}) 或 YAML 注入。要在自己数据上调优、并锁定复现结果时用。

04

参数心智模型:少数几个真正改变结果的旋钮

pyannote 参数不多,但说话人数量这一个旋钮几乎决定成败。下面直接调它,看同一段音频的分割结果如何被"重新聚类"。

最该管的

num_speakers

确切人数。知道就传——把"猜几个人"这个最容易错的环节直接消掉,精度显著上升。

min/max_speakers

只知道范围时用。比如访谈 min=2, max=2、圆桌 max=6。给个上界能挡住过度分裂。

clustering threshold

藏在超参里的合并/分裂尺度。同一人被拆成两个标签→调高;两人被并成一个→调低。需评测集配合调。

05

怎么确认它真的做对了

别只看它没报错。真正的验收有两层:看 RTTM / 时间轴做抽样目检,以及用 DER 指标对着参考答案量化。悬停左边任意一行,看它落在时间轴哪里。

RTTM 一行怎么读

        
SPEAKER file 1 3.918 1.680 <NA> <NA> SPEAKER_01 <NA> <NA>

        
关键就三列:起始 3.918s、时长 1.680s、说话人 SPEAKER_01。其余 <NA> 是格式占位。

Diarization Error Rate = (漏检 + 误检 + 混淆) ÷ 总语音时长。用 pyannote.metrics 拿 hypothesis 对 reference 算。

06
自动化调用契约:流水线怎么判成败

  
因为它是库不是命令,成败信号要你在包装脚本里自己制造。核心一句话:推理失败会抛异常,你把它翻译成 exit code 和产物存在性。

  

    
信号约定为什么关键

    
      
exit code包装脚本捕获异常 → 非 0;正常写完 RTTM → 0pipeline 本身不给退出码,是你的脚本给。别吞异常。

      
stdout只打产物路径 / 关键统计(段数、speaker 数),便于上游解析把日志噪声(下载进度、warning)留给 stderr。

      
stderr + 日志ProgressHook 进度、模型下载、torch warning 都走这里长音频看这里判断是卡住还是在跑。

      
输出产物RTTM 是唯一真凭。脚本必须自己检查文件非空推理"成功"但零段落也可能发生(全判静音)。段数=0 应视为可疑。

      
覆盖 / 幂等write_rttm 以 "w" 打开会覆盖同名文件同输入同参数结果基本可复现;想严格幂等就先写临时文件再原子改名。

      
部分输出中途崩溃可能留下半截 RTTM因此推荐"先写 .tmp 成功后 rename",避免下游读到残缺文件。

    
  







  
07
它在流水线里的位置

  
最典型的落点是"带说话人的转写"。pyannote 站在音频清洗之后、ASR 对齐之前——它先划好时间轴,ASR 再往里填字。

  

    
① 取音频
ffmpeg 转 16kHz 单声道 wav,去掉容器/编码差异

    
▶

    
② pyannote
diarization → RTTM
谁在何时说话

    
▶

    
③ ASR
Whisper 等转写,得到带词级时间戳的文本

    
▶

    
④ 对齐合并
按时间戳把每句文本挂到对应 speaker

    
▶

    
⑤ 下游
分角色摘要 / 检索 / 人工校对

  

  

    
前置准备
把输入喂"干净"
务必先 ffmpeg -ac 1 -ar 16000 统一成单声道 16kHz wav。能拿到人数就一并传 num/min/max_speakers。前置降噪对脏音频回报很高。

    
产物交接
RTTM 怎么往下传
下游要么直接吃 RTTM,要么你把 Annotation 转成 JSON 段列表再与 ASR 词表按重叠时长匹配。合并逻辑是"每个词归给覆盖它最多的 speaker 段"。

  







  
08
常见失败边界

  
按出现频率排。第一个几乎每个新手都撞——展开看症状与解法。


  

    token / gated 模型没接受协议401 · 最常见＋
    

      加载时报未授权或提示需接受 user conditions。原因:没建 HF token、或没在模型页点 Accept、或 token 没读写权限。
      
FIX 逐个打开 speaker-diarization-3.1 与它依赖的 segmentation-3.0 页面点 Accept,再传有效 token;CI 里用环境变量 HF_TOKEN。

    

  

  

    版本 / 依赖不匹配ImportError · 加载报错＋
    

      拿旧代码跑 3.x,或 torch/torchaudio 版本对不上,pipeline 加载即崩,或行为和文档不一致。2.x 与 3.x 的模型名、API 都变了。
      
FIX 锁版本:明确用 pyannote.audio>=3.1 配套模型 speaker-diarization-3.1,别混用 2.x 教程。

    

  

  

    音频格式 / 后端读不了mp3 · backend＋
    

      直接喂 mp3 或异常采样率时,底层 torchaudio/soundfile 可能读不出或静默错采样。
      
FIX 上游一律 ffmpeg -i in.mp3 -ac 1 -ar 16000 out.wav,把格式问题挡在 pyannote 之外。

    

  

  

    人数没约束 → 过分裂 / 过合并精度 · 隐性＋
    

      不给 num/min/max 时,聚类靠阈值猜人数:两人被拆成三、或三人并成两,是最隐蔽的"没报错但结果错"。
      
FIX 尽量传确切或范围;拿不到就抽样目检段数与 speaker 数是否合理,必要时调 clustering threshold。

    

  

  

    长音频显存 / 耗时OOM · 性能＋
    

      几小时的录音一次性喂进去,CPU 上极慢,GPU 上可能显存吃紧。
      
FIX 上 GPU 并用 ProgressHook 看进度;超长文件按静音点切段处理再拼时间轴,或降低批大小。

    

  

  

    重叠语音 / 远场噪声DER 飙高＋
    

      多人抢话、混响、远场麦克风会让 confusion 和漏检大幅上升——这是模型能力边界,不是 bug。
      
FIX 前置降噪 / 回声消除;接受重叠段精度天花板;必要时换更贴合场景的 fine-tuned 模型。

    

  







  
09
和相近方案怎么选

  
pyannote 强在开源、离线、可评测、SOTA baseline;弱在要你自己搭 GPU、管 HF token、写胶水。对照下表看它什么时候是对的选择。

  

    
方案它是什么什么时候选它什么时候别选

    
      

        pyannote.audio
        纯 diarization 库,只做分割聚类
        要离线/私有部署、可控可调、要 DER 评测 baseline
        只想快速拿到"带说话人的转写"、不想写胶水
      

      

        WhisperX
        Whisper ASR + pyannote(内部就用它)+ 词级对齐,打包好
        目标是转写带说话人,想开箱即用少写代码
        只要 diarization、或要对分割环节做深度定制
      

      

        NVIDIA NeMo
        大型语音工具箱,含 MSDD 等 diarizer
        研究向、要流式/多模块、已在 NeMo 生态里
        只需一个稳定 baseline,嫌它重、上手陡
      

      

        云 API
        AWS Transcribe / Deepgram / AssemblyAI 内置 diarization
        不想搭 GPU、量小、能接受按分钟付费与数据出网
        数据敏感必须内网、量大成本敏感、要离线
      

      

        手写脚本
        自己拼 VAD + 声纹 + 聚类
        几乎没有——除非做研究复现
        生产场景:精度和维护成本都打不过 pyannote
      

    
  







  
10
工程落地:最小实现路径与方案选型

  
理解了原理,再看在真实项目里怎么落地。先说边界,再给一条按数据流走的最小主链路,最后按场景给推荐。


  

    
接收什么
输入前置条件
16kHz 单声道 wav;一个可用 HF token;有 GPU 更好。尽量已知说话人数或范围。

    
产出什么
交付物
RTTM + 结构化 JSON 段列表(start/end/speaker),供 ASR 对齐或前端渲染时间轴。

    
不由它解决
边界外
身份识别、转写、降噪、实时流式——都在 pyannote 之外,由前后置模块负责。

  


  
最小实现路径(主链路)

  
按数据流:准备 → 复用 pipeline → 逐文件推理 → 转 JSON 交付。刻意不写 silent fallback / 吞错默认值——失败就抛,由调用方决定。

  

    
diarizer.py · 主链路load once → reuse

    
import json, torch
from pyannote.audio import Pipeline
from pyannote.audio.pipelines.utils.hook import ProgressHook

# 1) 加载一次,进程内复用(加载昂贵)
pipeline = Pipeline.from_pretrained(
    "pyannote/speaker-diarization-3.1",
    use_auth_token=os.environ["HF_TOKEN"])
pipeline.to(torch.device("cuda"))

def diarize(wav_path, out_json, num_speakers=None):
    # 2) 推理:已知人数就传,消掉最易错环节
    with ProgressHook() as hook:
        ann = pipeline(wav_path, num_speakers=num_speakers, hook=hook)

    # 3) Annotation -> 结构化段列表(交付契约)
    segs = [{"start": round(t.start, 3),
             "end": round(t.end, 3),
             "speaker": spk}
            for t, _, spk in ann.itertracks(yield_label=True)]

    # 4) 先写临时文件再原子改名,保证下游不读残缺
    tmp = out_json + ".tmp"
    with open(tmp, "w") as f:
        json.dump({"segments": segs}, f, ensure_ascii=False)
    os.replace(tmp, out_json)
    return len(segs)          # 段数=0 由调用方判为可疑

  


  
推荐路径(按场景)

  

    

      
场景 A · 会议转写带说话人

      
直接上 WhisperX

      
→ WhisperX(内含 pyannote)

      
你的目标其实是"分角色的文字"。WhisperX 把 diarization + ASR + 对齐都打包了,底层还是 pyannote,少写大量胶水。除非要深度定制分割,不必自己拼。

    

    

      
场景 B · 私有部署 + 可控可评测

      
直接用 pyannote

      
→ pyannote.audio + 包装脚本

      
数据不能出网、要能用 DER 在自己数据上调优和验收。用上面的主链路封成脚本/服务,复用 pipeline,产 RTTM+JSON,配 pyannote.metrics 建评测集。

    

    

      
场景 C · 量小 · 不想搭 GPU

      
走云 API

      
→ Deepgram / AssemblyAI / AWS

      
偶尔处理几个文件、没有 GPU 也不想维护模型。云服务内置 diarization,按分钟付费即用即走。前提是能接受数据出网与单价。
