核心动机

一个 HTTP 请求不应该做所有事

用户点击"注册"按钮，你的服务器同步发了欢迎邮件——邮件服务器慢的时候，用户要等 3 秒才能看到"注册成功"。这不是邮件慢的问题，是架构错了。

❌ 同步阻塞（问题所在）

HTTP 请求被迫等待所有操作完成才能返回

接受请求
写数据库 (200ms)
发欢迎邮件（等 SMTP 服务器…2500ms）
压缩头像 (800ms)
返回响应 ← 3.5s后
⚠ 用户等待 3.5 秒。SMTP 超时时直接报 500。
✓ Celery 异步（正确姿势）

任务入队即返回，worker 在后台并发处理

接受请求
写数据库 (200ms)
.delay() 入队 (<5ms)
返回响应 ← 205ms
（后台 worker）发邮件 + 压图像（并发）
✓ 用户 205ms 后看到成功页面
核心思路：把"需要时间"和"必须等待"这两件事分开。数据库写入必须等，但发邮件不需要用户等——Celery 让你明确表达这个区别。

Producer — 你的应用

  • 调用 task.delay(args) 或 task.apply_async(args, kwargs, countdown=5)
  • 不执行任务，只把「任务名 + 参数 + 元数据」序列化成消息推入 Broker
  • 立即拿到一个 AsyncResult 对象，可以用它来轮询结果
  • 可以是 Django/Flask/FastAPI 里的 View，也可以是定时脚本

最小可运行示例

五行代码跑起来

先看能跑的最小例子，再理解每一行为什么这样写。

from celery import Celery

# 1. 创建 Celery 实例，指定 broker
app = Celery('myapp', broker='redis://localhost:6379/0',
             backend='redis://localhost:6379/1')

# 2. 用 @app.task 装饰器注册任务
@app.task
def add(x, y):
    return x + y

@app.task
def send_email(user_id, subject="Hello"):
    # 实际发邮件逻辑...
    return f"email sent to user {user_id}"
📌 backend 是可选的，只有需要拿回 task 返回值时才要配置
from tasks import add, send_email, on_success, on_failure
from datetime import datetime, timedelta, timezone

# .delay() 是最简单的发送方式
result = add.delay(4, 6)
print(result.id)  # 'a3f2c1b0-...' 立即返回

# apply_async() 提供完整控制
send_email.apply_async(
    args=[42],
    kwargs={'subject': 'Welcome!'},
    countdown=10,            # N 秒后执行（相对时间）
    eta=datetime.now(timezone.utc) + timedelta(hours=1),
                             # 指定绝对时间执行（与 countdown 互斥）
    expires=3600,            # N 秒内未执行则丢弃
    queue='email',           # 发到指定队列
    priority=5,              # 优先级 0-9（RabbitMQ: 9最高；Redis: 0最高!）
    time_limit=60,           # 硬超时：60s 强制 SIGKILL
    soft_time_limit=50,      # 软超时：50s 抛 SoftTimeLimitExceeded
    link=on_success.s(),      # 成功后自动调用的回调
    link_error=on_failure.s(), # 失败后自动调用的回调
    ignore_result=True,       # fire-and-forget：不存结果，省 backend 开销
)
📌 countdown 和 eta 互斥，不能同时用。priority 方向因 broker 不同而相反：RabbitMQ 9=最高，Redis 0=最高。

定时任务

Celery Beat：周期性任务调度

Beat 是一个独立的调度进程，按设定的时间表把任务发进队列，由 worker 执行。它和 cron 的区别是：配置是代码，任务执行是分布式的。

from celery import Celery
from celery.schedules import crontab

app = Celery('tasks', broker='redis://localhost:6379/0')

app.conf.beat_schedule = {
    # 每 30 秒执行一次
    'add-every-30-seconds': {
        'task': 'tasks.add',
        'schedule': 30.0,
        'args': (16, 16),
    },
    # 每天 8 点生成报告
    'daily-report': {
        'task': 'tasks.generate_report',
        'schedule': crontab(hour=8, minute=0),
    },
    # 每周一 9:30 发周报
    'weekly-digest': {
        'task': 'tasks.send_digest',
        'schedule': crontab(hour=9, minute=30, day_of_week=1),
    },
}
app.conf.timezone = 'Asia/Shanghai'
📌 配置 timezone 很重要，否则 crontab 按 UTC 算

⚠️ Beat 只能有一个实例

为什么不能多开？

Beat 是中心化调度器，它维护一个调度状态文件（celerybeat-schedule）来记录上次执行时间。多个 Beat 实例各自独立，会重复触发任务。

高可用方案：用 Kubernetes 的单副本 Deployment + 快速重启，或者用 redbeat（把调度状态存进 Redis，支持 leader election）。

Beat vs Worker

职责分工

Beat 只发消息，不执行任务。到点了它就 .delay() 一下，然后忘记这件事。实际执行在 worker 里。

# 开发时：可以用 --beat 嵌入 worker（不推荐生产）
$ celery -A tasks worker --beat

# 生产时：独立进程
$ celery -A tasks beat &
$ celery -A tasks worker -c 4
Canvas 工作流编排

当一个任务不够用：Canvas

现实场景往往需要多个任务协作——先做 A，再拿 A 的结果做 B；或者 A、B、C 并行，全部完成后做 D。Canvas 就是 Celery 给这类需求提供的"积木系统"。

Canvas 解决什么

如果你写出了这样的代码，你需要 Canvas：

# ❌ 这样写是同步阻塞的，失去了异步的意义
r1 = fetch_data.delay(url)
data = r1.get()       # 阻塞等待
r2 = process.delay(data)
result = r2.get()   # 再次阻塞

Canvas 的解法

# ✓ 声明式地描述依赖关系，Celery 自动编排
from celery import chain

workflow = chain(fetch_data.s(url), process.s())
result = workflow.delay()
# 全程异步，不阻塞任何东西

六个核心原语

点击任意原语查看详解与执行示意

⛓
chain
串行管道：A → B → C
顺序

前一个任务的返回值自动成为下一个任务的第一个参数。适合有数据依赖的流水线。

⊞
group
并行扇出：同时执行多个任务
并行

多个任务同时发送到 broker，各自独立执行。返回 GroupResult，可整体等待或逐一查询。

⊕
chord
并行 + 汇聚：group 完成后执行 callback
聚合

= group + 汇聚任务。并行任务全部完成后，将所有结果作为列表传给 callback。需要 result backend。

⊟
chunks
批量分片：大任务自动切片
批量

把一个大列表自动均分成 N 批，每批作为一个 group task 执行。适合批量处理场景。

⟶
map
顺序 map：单参数，一条消息
顺序

只发一条消息，在同一个 worker 进程内 for 循环顺序执行。不是并行。适合轻量批量操作，避免大量消息 overhead。

✳
starmap
顺序 map：多参数解包，一条消息
解包

和 map 相同，但迭代的是元组列表，每个元组用 *args 解包传入任务。等价于 Python 的 itertools.starmap。

理解 .s() — Signature（签名）

  

    

      
核心概念

      
Signature 是"任务的配方"

      
在 Canvas 里，你不能直接传函数，要传它的"签名"——记录了函数名和参数的可序列化对象，可以跨网络传递、延迟执行。

      
# task.s() 创建 Signature（不执行）
add.s(2, 3)         # add(2, 3)
add.s(2)            # add(2, ?)  偏函数
add.si(2, 3)        # immutable：忽略上一步结果

    

    

      
s() vs si() vs delay()

      
三种调用方式的区别

      
# .delay() — 立刻发送，立刻执行
add.delay(2, 3)

# .s() — 创建 Signature，链式时接收前一步结果
chain(double.s(10), add.s(5))
# double(10)=20 → add(20, 5)=25

# .si() — immutable Signature，不接收结果
chain(fetch.s(), notify.si("done"))
# notify 总是收到 "done"，不管 fetch 返回什么

    

  


  
  
最容易混淆：map / starmap / group 的选择

  

    一句话区别：map 和 starmap 是顺序的，只发 1 条消息，整个列表在单个 worker 里 for 循环跑完。group 是真正并行的，发 N 条消息，可以在 N 个 worker 上同时跑。
  

  

    

    

      
        

          原语
          参数形式
          消息数
          执行方式
          适合场景
        

      
      
        

          map
          task.map([x, x, x])
每项是单个参数		
          1 条
          单 worker 顺序
          轻量批量、无需并行
        

        

          starmap
          task.starmap([(a,b), ...])
每项是元组，* 解包		
          1 条
          单 worker 顺序
          多参数批量、无需并行
        

        

          chunks
          task.chunks(it, n)
自动均分成 n 组		
          n 条
          n 个 worker 并行（每组内顺序）
          大批量，折中并行度
        

        

          group
          group(task.s(x) for x in it)
每项一个独立 Signature		
          N 条
          最多 N 个 worker 真并行
          重任务、需要最大并行度

重试机制

  
# default_retry_delay 默认是 180 秒（3 分钟），max_retries 默认是 3
@app.task(bind=True, max_retries=3, default_retry_delay=30)
def send_email(self, user_id):
    try:
        email_service.send(user_id)
    except TemporaryError as exc:
        # 30s 后重试，最多 3 次
        raise self.retry(exc=exc, countdown=30)
    except PermanentError:
        # 永久错误不重试，直接变成 FAILURE
        raise

# 指数退避：30s, 60s, 120s, 240s, 480s
@app.task(bind=True)
def flaky_task(self):
    try:
        do_work()
    except Exception as exc:
        countdown = 2 ** self.request.retries * 30
        raise self.retry(exc=exc, countdown=countdown, max_retries=5)

# 软/硬超时：区分"超时可清理"和"超时必须杀死"
from celery.exceptions import SoftTimeLimitExceeded

@app.task(time_limit=120, soft_time_limit=100)
def long_task():
    try:
        do_long_work()
    except SoftTimeLimitExceeded:
        # 100s 到了：还有 20s 可以做清理/保存进度
        save_progress()
        raise
    # 120s 到了：强制 SIGKILL，无法捕获

# link / link_error：任务完成/失败后自动触发回调
@app.task

@app.task

process_order.apply_async(
    args=[order_id],
    link=on_done.s(),
    link_error=on_fail.s(),

避坑指南

  
这些坑踩过才知道

  
Celery 的问题往往在上线后才暴露。这里是最常见的几个，展开看原因和解法。


  

    

      
        !
        任务里调用 .get() 导致死锁
      
      ▶
    

    

      
原因：如果 worker 在执行一个任务时，调用另一个任务的 .get()，而那个任务要在同一个 worker 上执行，就会产生死锁——worker 在等结果，但结果要由正在等待的 worker 来计算。

      
解法：用 Canvas 替代。在任务内组合 Signature，不要阻塞等待。

      
# ❌ 在任务里调 .get()
@app.task
def pipeline():
    r = step1.delay()
    data = r.get()   # ⚠️ 可能死锁！
    step2.delay(data)

# ✓ 用 chain 替代
@app.task
def pipeline():
    chain(step1.s(), step2.s()).delay()

    

  


  

    

      
        !
        任务参数传了不可序列化的对象
      
      ▶
    

    

      
原因：任务参数要经过 Broker 传输，必须可以 JSON 序列化。传入 Django Model 实例、文件对象、数据库连接等会直接报错，或者序列化成空对象。

      
解法：只传 ID，在任务内部重新查询。

      
# ❌ 传 Model 实例
user = User.objects.get(id=42)
send_email.delay(user)  # ⚠️ 序列化失败或数据过期

# ✓ 只传 ID
send_email.delay(user_id=42)  # 任务内部再查

    

  


  

    

      
        !
        chord 里一个任务失败，callback 仍然执行
      
      ▶
    

    

      
原因：chord 的 header（并行任务）中如果有任务失败，callback 仍然会被调用，失败的那个位置结果是异常对象而非预期返回值。chord_propagates 这个配置并不存在，网上很多文章写错了。

      
正确解法：用 link_error 捕获 header 里的单个失败，或在 callback 里检查每个结果的类型。

      
# ✓ 在 callback 里检查每个结果
@app.task
def aggregate(results):
    for r in results:
        if isinstance(r, Exception):
            logger.error(f"subtask failed: {r}")
            continue
        process(r)

# ✓ 用 link_error 捕获整个 chord 的失败
@app.task
def handle_chord_error(task_id, exc, tb):
    logger.error(f"chord {task_id} failed: {exc}")

chord(header, callback).apply_async(link_error=handle_chord_error.s())

    

  


  

    

      
        !
        任务在模块导入时生成（热路径里创建 Signature）
      
      ▶
    

    

      
原因：Signature 对象在创建时就固定了参数。如果把一个带参数的 Signature 存为模块级变量，参数不会更新，永远用创建时的值。

      
# ❌ 模块级 Signature（参数被固化）
WORKFLOW = chain(fetch.s(config.URL), process.s())
# config.URL 改变后，WORKFLOW 里的 URL 不变

# ✓ 在函数里创建 Signature
def get_workflow():
    return chain(fetch.s(config.URL), process.s())

    

  


  

    

      
        !
        忘记配置 result backend，调用 .get() 一直超时
      
      ▶
    

    

      
原因：不配置 result_backend 时，任务执行结果无处存储，AsyncResult.get() 会永远等待（或超时），状态也永远是 PENDING。这不是 bug，是正常行为——fire-and-forget 场景就不需要 backend。

      
解法：需要结果时配置 Redis 或 Django DB 作为 backend；chord 必须配置 backend。不关心结果时，显式设置 ignore_result=True 跳过 backend 写入。

      
# fire-and-forget 正确姿势：显式声明
@app.task(ignore_result=True)
def send_notification(user_id): ...

# 或者发送时临时忽略
send_notification.apply_async([user_id], ignore_result=True)

    

  


  

    

      
        !
        priority 优先级：RabbitMQ 和 Redis 方向相反
      
      ▶
    

    

      
原因：Celery 的 priority 参数范围是 0-9，但两个主流 broker 的优先级语义是相反的，完全是历史遗留问题。

      
# RabbitMQ：9 = 最高优先级，0 = 最低
task.apply_async(priority=9)  # RabbitMQ: 优先执行
task.apply_async(priority=9)  # Redis:     最后执行！

# Redis：0 = 最高优先级，9 = 最低
task.apply_async(priority=0)  # Redis:     优先执行
task.apply_async(priority=0)  # RabbitMQ:  最后执行！

# 最安全的跨 broker 做法：
# 用不同队列模拟优先级，而不依赖 priority 参数
task.apply_async(queue='high')
task.apply_async(queue='low')
# worker 优先消费 high 队列
# $ celery -A app worker -Q high,low

    

  


  

    

      
        !
        测试时任务实际不执行，或者需要真实 broker
      
      ▶
    

    

      
问题：单元测试里 .delay() 真的会往 broker 发消息，如果测试环境没有 Redis/RabbitMQ 就会报连接错误。

      
解法一：用 task_always_eager=True，让所有任务在调用进程里同步执行，不走 broker。

      
解法二：用 .apply() 直接同步调用，不发消息，适合测试单个任务逻辑。

      
# 方法一：全局 eager 模式（conftest.py）
@pytest.fixture(autouse=True)
def celery_eager(settings):
    settings.CELERY_TASK_ALWAYS_EAGER = True
    # Celery 5+ 新配置名
    app.conf.task_always_eager = True

# 方法二：直接 .apply() 同步执行（推荐）
result = add.apply(args=[4, 6])  # 同步，不走 broker
assert result.result == 10

# 方法三：mock 掉 delay
with patch('tasks.send_email.delay') as mock_task:
    view_register(request)
    mock_task.assert_called_once_with(user_id=42)

# 方法四：pytest-celery（官方测试工具）
# pip install pytest-celery
# 提供真实 broker/backend 的 pytest fixtures

Flower：可视化监控面板

  

    

      
# 安装并启动
$ pip install flower
$ celery -A tasks flower --port=5555
# 访问 http://localhost:5555

# 带认证启动
$ celery -A tasks flower \
    --basic_auth=admin:password \
    --url_prefix=flower

# 查看 API（Flower 提供 REST API）
GET /api/tasks          # 任务列表
GET /api/workers        # worker 状态
POST /api/task/revoke/{task_id}  # 撤销任务

    

    

      

        
Flower 能看到什么

        
    
          
  • →所有 worker 的实时状态、并发数、处理速率
    • 
          
  • →每个任务的执行历史、耗时、状态、参数
    • 
          
  • →失败任务的完整 traceback
    • 
          
  • →任务队列积压情况
    • 
          
  • →手动重试或撤销任务
    • 
        

        
生产环境建议加认证，Flower 本身没有内置权限控制。
