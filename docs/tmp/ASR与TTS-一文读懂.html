ASR 与 TTS
声音与文字之间的一对镜像

你对手机说一句话,它听懂了,再念一段话回你——中间发生了两次跨越。 声音是连续、密集的气压波,文字是离散、稀疏的符号。 ASR 把波压成符号,TTS 把符号还原成波。 两者方向相反,却共用同一座桥:声学特征(频谱图)。看懂这层镜像关系,整件事就通了。

01
从一个真实场景说起

为什么这件事不简单:两个世界之间隔着鸿沟

你说「明天天气」。麦克风收到的,只是一段随时间起伏的电压—— 每秒采样 16000 个数字,一句话就是几万个点。 它没有「字」的边界,没有标点,还混着风扇声和回声。

而你要的输出,只有 4 个汉字。从几万个数到 4 个字,信息被极度压缩了。

反过来,TTS 拿到「明天天气」4 个字,要生成一段听起来像人说的声音—— 可文字里没写该用什么语速、哪里停顿、句尾升调还是降调。

同样 4 个字,可以念得平淡、惊讶、或不耐烦。信息又被极度放大了。

两道坎,其实是同一道坎的正反面:

ASR 要把密集、连续、带噪的信号,压成稀疏、离散、干净的符号; TTS 要把稀疏符号,还原成密集信号,还得补上文字里缺失的所有细节。 接下来两节先讲清它们共用的桥,再讲清那把打开镜像的钥匙——对齐。

02
两条路的交汇点

那座共用的桥:从波形到频谱图

没人直接拿几万个采样点去识别或生成。第一步都是把波形切成一小段一小段的帧(frame)—— 通常每 25ms 一帧、每 10ms 滑一步,再对每帧做傅里叶变换,得到「这一瞬间各个频率有多强」。 把所有帧排起来,就是频谱图:横轴时间、纵轴频率、颜色代表能量。语音里那几道亮带就是元音的共振峰(formant)。

01 · 分帧

切成短帧

连续波形按 25ms 窗、10ms 步长切片。1 秒语音 ≈ 100 帧。

02 · 变换

看频率成分

每帧做 FFT,得到该瞬间的频谱;取对数、压到 mel 刻度更贴近人耳。

03 · 拼接

时间×频率的图

帧首尾相接,得到 mel-spectrogram(或 MFCC/Fbank 特征)。

记住这个数字:1 秒 ≈ 100 帧。

频谱图对 ASR 是输入端(要从它读出文字),对 TTS 是输出端(要生成它再变回声音)。 同一种表示,两头各用一次——这正是「镜像」的物理基础。而「100 帧对几个字」这个悬殊的比例,直接引出了下一节的核心问题。

03
理解一切的钥匙

对齐:坍缩与扩展,是同一件事的两个方向

100 帧,「你好」只有 2 个字。谁负责把这 100 : 2 对上号? ASR 要把很多帧坍缩(collapse)成一个字——这是 CTC 的活; TTS 要把一个字扩展(expand)成很多帧——这是 duration predictor 的活。 两个操作互为逆运算。下面两个面板,亲手推一遍就懂了。

ASR · CTC 坍缩 多帧 → 字

帧标签 → 文字

模型给每帧打个标签,允许留空(_,blank)。规则:先合并连续相同,再删掉所有 _。

8 帧原始标签。点「合并」开始坍缩。
TTS · Duration 扩展 字 → 多帧

文字 → 帧序列

duration predictor 预测每个字/音该占几帧,再把它复制这么多份,铺满时间轴。

2 个字,各自带一个时长。点「扩展」铺开。
blank(_) 到底干嘛用的?

它是「分隔符」。碰到「呱呱」这种真·叠字,标签像 呱 呱 会被合并成一个; 中间插个 blank 变 呱 _ 呱,合并后仍是两个。 没有 blank,CTC 就分不清「该合并的重复」和「本就成对的字」。这正是对齐设计里最精妙的一笔。

04
波 → 符号

ASR 全流程:从级联到端到端

经典 ASR 是一条级联流水线,每个模块单独训练。点开每一站看它在干嘛—— 注意最后你会发现:很多环节到了端到端时代被合并进了一个网络,但它们背后的问题并没有消失。

端到端时代 · 三种对齐方式

端到端把「声学 + 词典 + (部分)语言」塞进一个网络,输入频谱、直接吐文字。区别主要在怎么处理对齐——各有取舍。

CTC · 每帧独立打标 + 坍缩

对齐
第 03 节那套 blank + 坍缩,无需帧级标注。
优点
结构简单、天然可流式、推理快。
代价
假设各帧输出条件独立,不建模字与字的依赖,通常要外挂一个 LM 来补语言常识。
用在
轻量/实时场景,常作为大模型里的一个分支(如 Conformer-CTC)。

RNN-T · 加一个「已输出文本」预测网络

对齐
encoder 看声音、prediction network 看已经吐出的字,联合决定下一步。
优点
建模了输出间依赖,又天然流式——工业界串流(手机语音输入、实时字幕)的主力。
代价
训练显存/工程复杂度更高。
用在
Google、各家输入法的 on-device 实时识别。

Attention 编解码 · 让解码器「回看」整段声音

对齐
attention 权重软对齐:每生成一个字,自动去声音里找该看哪几帧。
优点
精度高,能利用全句上下文,长音频、多语言表现强(如 Whisper)。
代价
要看到较完整的输入才好解码,难以低延迟流式;可能「跳读/重复」。
用在
离线转写、字幕生成、多语种翻译。
05
符号 → 波

TTS 全流程:把 ASR 反过来跑一遍

把上一节的箭头掉个头,就是 TTS 的骨架:前端把文字整理成音,声学模型把音变成频谱图, 声码器把频谱图变回波形。有意思的是,大家常以为难点在后半段的「拟人音色」, 其实一半的坑在前端——文字远比它看起来更「欠说明」。

A 前端 Frontend

把「能读」的文字变成「能念」的音串。

2024 → 二〇二四;3:30 → 三点半

韵律预测
哪里停顿、哪个字重读、句尾升降调

mel-spectrogram → 最终波形。

FastSpeech2 里的 duration predictor,做的正是第 03 节右边那个扩展; 而 mel-spectrogram,正是第 02 节那座桥。TTS 不是新东西——它是 ASR 沿着同一条路,反向走了一遍。

07
别踩的坑 · 怎么取舍

常见误区与工程取舍

ASR 就是「听音查字典」

同音字声学模型根本分不清。你说 shì,是「是/事/市/室/试」? 靠的是语言模型结合上下文:「天气很shì好」不通,「天气很适好」也不对,「明天天气不错」才对。声学负责听,语言负责懂。

TTS 就是「逐字念拼音」

前端一半的功夫在消歧与韵律。念错「重(chóng/zhòng)庆」「银行(háng)」, 或者把 $5.5 念成「美元五点五」,比机械音更让人出戏。文字没写全的东西,得靠前端补齐。

流式(实时)是「免费」的

这是最核心的工程取舍:延迟 vs 精度。越想边说边出字,能看到的未来上下文越少, 纠错空间越小,精度越低。所以实时字幕偏爱 RNN-T,离线高精度转写偏爱 Whisper 这类全局 attention。

端到端 ≠ 不再需要文本资源与规则

工业系统里,ASR 仍常融合外部 LM(领域词、专有名词),TTS 仍离不开 TN 规则和发音词典。 端到端简化了结构,没消灭这些问题——它们只是换了个地方存在。

选型速记

要实时、上设备 → 流式(RNN-T / streaming Conformer);要最高精度、能离线 → 全局 attention(Whisper 类)。 TTS 要低延迟并发 → 非自回归声学(FastSpeech2)+ 并行声码器(HiFi-GAN); 要极致自然/情感 → 自回归或更大的生成式模型,牺牲一点速度。

把它接进真实项目

前七节讲清了「是什么、为什么」。接下来四节讲「怎么用」:先划清它该管什么、不该管什么, 再按数据流走一遍最小实现,然后对比方案、给出选型建议。示例以 Python 为主,只展示主链路。

08
先划清责任边界

落地边界:接什么、产出什么、别让它管什么

ASR 的边界

接收
一段音频(理想是 16kHz 单声道 PCM)
产出
文字,可附带时间戳、置信度、分段
前置
解码 + 重采样到 16k 单声道;必要时 VAD 切静音、长音频分段
不归它管
说话人分离(diarization)、标点顺滑、意图理解(NLU)、修复烂录音

TTS 的边界

接收
干净的文本(可带 SSML 控制韵律)
产出
波形(WAV / MP3 / opus,可流式)
前置
文本归一化 TN、按句切分、选音色与采样率
不归它管
从 PDF/网页抽正文、决定「说什么」、直接吃原始标记(HTML/Markdown)
一条铁律:garbage in, garbage out。

ASR 修不了本就听不清的录音,TTS 也决定不了内容对不对。把音频质量、文本清洗、业务逻辑这些 不属于模型的问题留在模型外面解决,系统才好维护。边界画错,后面全是坑。

09
按数据流走一遍

最小实现路径:输入准备 → 核心处理 → 后处理 → 交付

ASR 主链路
输入准备

规整音频

解码 → 重采样 16k 单声道 → VAD 切掉静音、长音频切段。

核心处理

模型推理

喂给 ASR 模型,得到带时间的分段文本。

后处理

让文本可用

标点恢复 / ITN(数字→阿拉伯) / 时间戳对齐 / 热词纠偏。

交付

结构化输出

transcript + segments(JSON),给下游 NLU 或字幕。

TTS 主链路
输入准备

整理文本

TN 归一化(数字/符号/多音字) → 分句 →(可选 SSML)。

核心处理

合成音频

声学模型出 mel,声码器出波形。

后处理

拼接与整形

分句拼接 + 句间静音 → 响度归一 → 编码目标格式。

交付

音频输出

流式返回或落地成文件。

落到代码,主链路可以很短。下面三段各只做一件事——前置整音、ASR 推理、TTS 合成:

prep_audio.py  ·  通用前置
import subprocess

# 几乎所有 ASR 的前置：任意格式 → 16kHz 单声道 WAV
subprocess.run(
    ["ffmpeg", "-i", "raw.m4a", "-ar", "16000", "-ac", "1", "clean.wav"],
    check=True,   # 转码失败立即抛错，不静默兜底
)
asr.py  ·  自建 faster-whisper
from faster_whisper import WhisperModel

model = WhisperModel("large-v3", device="cuda", compute_type="float16")

segments, info = model.transcribe(
    "clean.wav",
    language="zh",
    vad_filter=True,                         # 内置 VAD，切掉静音段
    initial_prompt="热词：Claude、Anthropic",   # 领域词偏置
)
for seg in segments:
    print(f"[{seg.start:5.1f}s] {seg.text}")

换成云端只是把中间一步替成一次 API 调用,前置/后处理不变:client.audio.transcriptions.create(model="whisper-1", file=f, language="zh")。

tts.py  ·  云端合成(OpenAI)
from openai import OpenAI

client = OpenAI()
resp = client.audio.speech.create(
    model="tts-1",
    voice="alloy",
    input="明天多云转晴，最高气温二十六度。",   # 已做过 TN 的干净文本
)
resp.stream_to_file("weather.mp3")

三段都只走主链路:失败即抛,不吞错、不塞默认值。真实项目再往外包重试、限流、缓存——那是模型之外的工程,别混进核心链路。

三条路怎么比

方案选型:云 API / 自建开源 / 端侧离线

ASR 和 TTS 的落地方式高度一致,都在这三条路里选。取舍轴是同一根:省事 ↔ 可控、便宜 ↔ 精度、在线 ↔ 离线。

方式适用场景主要成本关键限制不推荐用于
云 API MVP、低量、想要「开箱最好效果」又不想运维 按时长 / 字数计费,量大后很贵 数据出域;网络往返延迟;可定制性低 高并发长期跑;隐私合规;需离线
自建开源
(GPU)		 中高量、隐私敏感、要领域定制/微调 一次性 GPU + 持续 MLOps 人力 要工程与 GPU;需自己调优、扛住峰值 小团队、极低量、没有 GPU 预算
端侧 / 离线 实时、隐私、弱网、嵌入式(手机/车机) 端上算力;精度受模型体积约束 模型小 → 精度 / 音质打折 追求最高精度或最自然音色

11
对号入座

三个典型场景,直接给建议

场景 A · 一周内验证想法

低量 MVP

→ 云 API

一个函数调用就有生产级效果,零运维、零 GPU。先跑通业务闭环再谈成本——这个阶段自建纯属给自己上强度。ASR 用 whisper-1,TTS 用 OpenAI / ElevenLabs。

场景 B · 每天几千小时批量转写

高量 / 数据不能出内网

→ 自建 faster-whisper(GPU)

到这个量级,按量付费的账单会爆炸;自建把边际成本压到接近电费,数据也留在内网。用 VAD 分段 + 批处理喂 GPU,吞吐拉满。TTS 同理走 XTTS 类自建。

场景 C · App 实时字幕 / 车机语音

实时 / 弱网 / 离线

→ 端侧流式

延迟和离线是硬需求,云的往返和断网直接出局。ASR 用 sherpa-onnx 流式(或 RNN-T 类),TTS 用 Piper。接受精度/音质的折中,换来即时与隐私。

一句话选型

先云 API 验证,量或合规压上来了再自建,延迟或离线是硬指标才上端侧。 别一上来就自训模型——大多数项目卡住的地方是音频质量、TN 规则和后处理,不是模型本身。
