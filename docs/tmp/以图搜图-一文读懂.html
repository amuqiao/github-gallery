01

先看端到端链路

以图搜图的本质是一次“离线把图变成向量并建索引，在线把查询图变成同一个空间里的向量再找最近邻”的过程。真正决定成败的不是模型，而是离线和在线用的是不是同一段预处理与编码代码。

位置数据形态
原始输入① 图库：一个目录或对象存储前缀下的 N 张图 list[image_path]；② 查询：单张图 bytes | image_path | url，可带过滤条件 dict（类目、上架状态、时间范围）
最终输出Top-K 相似图及分数，JSON：{"query_id":str,"took_ms":int,"results":[{"image_id":str,"score":float,"thumb_url":str,"meta":{...}}]}，其中 score 是余弦相似度 ∈ [-1,1]

八个关键节点与它们之间的交接物

整条链路只有一条铁律：N2（预处理）+ N3（编码）必须封装成一个函数，离线建库和在线查询都调用它。90% 的“搜出来的结果莫名其妙”都是因为建库时做了 EXIF 旋转 / L2 归一化，而线上查询那条路径漏了其中一步。
02

每个节点怎么落地

每个节点固定 12 个字段。“是否建议手写”这一栏请认真看：以图搜图里值得手写的只有胶水逻辑和业务规则，模型、索引结构、特征匹配全都有成熟依赖，手写只会拿到更差的召回。

解决什么
把散落在磁盘/对象存储里的图片变成可寻址、可复现、有稳定主键的清单。没有这一步，后面向量和图片就对不上号。
默认落地方式
一个脚本遍历目录 → 校验可解码 → 算 sha256 去重 → 写 manifest.csv 和 SQLite 表。image_id 用 sha256 前 16 位，天然幂等，重跑不会产生重复行。
推荐依赖
pathlib hashlib sqlite3（标准库）+ Pillow 读尺寸与探测损坏。不需要任何框架。
是否建议手写
建议手写 就是 50 行遍历逻辑，引入 ETL 框架反而增加心智负担。
输入
image_dir: str 或 list[str]
处理逻辑
后缀白名单过滤 → 跳过 <2KB 文件 → Image.open().verify() 探测损坏 → sha256 全文件哈希 → 同哈希只保留第一条 → 批量写库
输出
SQLite 表 images(image_id TEXT PK, path TEXT, sha256 TEXT, width INT, height INT, bytes INT, phash TEXT, status TEXT, created_at TEXT)
中间产物
manifest.csv（人肉可读、可 diff）、skipped.log（损坏/过小/重复的原因，排查必备）
伪代码
for p in Path(root).rglob("*"):
    if p.suffix.lower() not in EXT or p.stat().st_size < 2048: skip(p, "tiny"); continue
    try: w, h = Image.open(p).size
    except Exception as e: skip(p, "decode"); continue
    sha = sha256(p.read_bytes()).hexdigest()
    if sha in seen: skip(p, "dup"); continue
    rows.append((sha[:16], str(p), sha, w, h, p.stat().st_size))
conn.executemany("INSERT OR IGNORE INTO images VALUES (?,?,?,?,?,?)", rows)
平替方案
只做 POC 时可以退化成一个 ids.json: list[str] + 同名 paths.json，连 SQLite 都不用。
升级方案
目录遍历 → 对象存储 list_objects_v2 分页；全量重建 → 消息队列驱动的增量入库（上传即入库）；SQLite → Postgres，加 status 软删除位和 updated_at 支持增量重编码。
常见坑
  • 拿文件路径当主键：图片一挪目录，整个索引全废。
  • 图库里本来就有大量完全相同的图，不去重的话搜索结果第一页会被同一张图刷屏。
  • 忘记记录 width/height，后面想按分辨率过滤只能重新扫一遍全库。
解决什么
把任意格式、任意尺寸、任意色彩空间、可能带 EXIF 旋转的图，统一成模型要的张量；顺手产出感知哈希（pHash）供后面做近重复合并。
默认落地方式
直接用模型自带的 preprocess（open_clip.create_model_and_transforms 返回的第三个值，或 HF 的 CLIPImageProcessor），不要自己写 resize/normalize。自己写的归一化均值方差错一位，召回直接崩。
推荐依赖
Pillow（ImageOps.exif_transpose）、pillow-heif（iPhone HEIC）、imagehash（pHash/dHash）、模型自带 processor。CPU 密集时换 Pillow-SIMD。
是否建议手写
不建议手写 resize / normalize / 哈希算法。建议手写 的只有“损坏图怎么兜底”的业务分支。
输入
image_path: str 或 raw: bytes
处理逻辑
Image.open → exif_transpose（纠正手机竖拍）→ RGBA/CMYK/P 统一 convert("RGB")（透明通道贴白底）→ processor 变换 → 堆成 batch；同时算 pHash 与 256px 缩略图。
输出
torch.Tensor[b, 3, 224, 224] float32、phash: str（16 位十六进制）
中间产物
thumbs/{image_id}.jpg（256px，前端展示 + 人工评估看图用，别到线上再从原图缩）
伪代码
ImageFile.LOAD_TRUNCATED_IMAGES = True
def load_rgb(path):
    im = Image.open(path)
    im = ImageOps.exif_transpose(im)          # 关键：修正旋转
    if im.mode in ("RGBA", "LA", "P"):
        bg = Image.new("RGB", im.size, (255,255,255))
        bg.paste(im.convert("RGBA"), mask=im.convert("RGBA").split()[-1])
        im = bg
    return im.convert("RGB")

def to_tensor(path):  # 离线在线共用这一个函数
    im = load_rgb(path)
    return preprocess(im), str(imagehash.phash(im))
平替方案
纯近重复检索（找盗图/找重复上传）可以完全不用模型：只留 pHash + 汉明距离，零 GPU、毫秒级、几行代码。
升级方案
DataLoader(num_workers=8) 并行解码 → 图片预转 WebP 降 IO → NVIDIA DALI 把解码搬到 GPU → 大图先 draft() 快速下采样再精修。
常见坑
  • 漏了 exif_transpose：同一张图正着传和倒着传，向量差很远。
  • PNG 透明背景直接 convert("RGB")，透明区变黑，整张图语义都变了。
  • 截断的 JPEG 会抛异常打断整个 batch，要提前设 LOAD_TRUNCATED_IMAGES 并逐张 try。
  • GIF/多帧 TIFF 默认只取第一帧，商品动图可能第一帧是白屏。
解决什么
把图片映射成定长向量，使“视觉/语义相似”等价于“向量夹角小”。这是整条链路的效果天花板。
默认落地方式
直接加载预训练模型跑推理，不要训练、不要微调。选型看目标：
· 找“同一件实物/同款商品/近重复” → DINOv2 ViT-B/14（dim 768），自监督特征对实例级检索更强；
· 找“语义相似/风格相似”，并且未来还想用文字搜图 → CLIP ViT-B/32（dim 512），图文同空间；
· 只判重复 → 见平替。
推荐依赖
torch + open_clip_torch（CLIP 生态最全）或 transformers（AutoModel.from_pretrained("facebook/dinov2-base")）。最省事的一行版：sentence-transformers 的 SentenceTransformer("clip-ViT-B-32")，.encode() 直接给 numpy。
是否建议手写
绝不手写 模型结构；POC 阶段也不要微调。要手写 的只有 batch 循环、归一化和落盘时的顺序对齐。
输入
ids: list[str] + tensor[b,3,224,224]（来自 N2，顺序必须与 ids 严格一致）
处理逻辑
batch=32~128 → torch.inference_mode() → encode_image → L2 归一化（归一化后内积就等于余弦相似度，faiss 用 IndexFlatIP 即可）→ .cpu().numpy().astype("float32") → 按 batch 顺序 vstack。
输出
ndarray[n, 512] float32（每行 L2 范数 = 1.0）
中间产物
embeddings.npy、ids.json: list[str]、meta.json: {"model":"ViT-B-32","pretrained":"laion2b_s34b_b79k","dim":512,"normalized":true,"built_at":"..."} —— meta.json 是防止“换了模型忘了重建索引”的唯一保险。
伪代码
model, _, preprocess = open_clip.create_model_and_transforms(
    "ViT-B-32", pretrained="laion2b_s34b_b79k")
model.eval().to(dev)

vecs = []
for batch_paths in chunks(paths, 64):
    x = torch.stack([to_tensor(p)[0] for p in batch_paths]).to(dev)
    with torch.inference_mode():
        v = model.encode_image(x)
        v = v / v.norm(dim=-1, keepdim=True)   # L2 归一化，务必
    vecs.append(v.cpu().numpy().astype("float32"))

emb = np.vstack(vecs)                 # [n, 512]
np.save("embeddings.npy", emb)
json.dump(ids, open("ids.json","w"))   # 行号 i ↔ ids[i]
平替方案
· 只做去重/找盗图：pHash + 汉明距离，无需深度模型；
· 无 GPU 又要语义：timm 的 ResNet50 全局池化层（dim 2048），效果弱于 CLIP 但 CPU 可跑；
· 完全不想装 torch：调用云端多模态向量 API，按张计费，POC 阶段几块钱搞定。
升级方案
fp16 / torch.compile → 导出 ONNX 用 ONNX Runtime（CPU 提速 2~3 倍）→ TensorRT + 动态 batch；效果上：用自己业务的正样本对做对比学习微调（通常是最大的单点收益）；多向量策略（全图 + 主体检测 crop 各存一条，检索时取 max）。
常见坑
  • 建库归一化了、查询没归一化（或反之），分数全乱且不报错。
  • 换了模型/权重却复用旧索引：向量空间根本不同，结果是随机的。用 meta.json 做启动校验。
  • dtype 不是 float32，faiss 会直接拒绝或静默出错。
  • 多进程并行编码后按完成顺序拼接，导致 ids[i] 和 emb[i] 错位——务必按输入顺序 vstack。
  • 用 ImageNet 分类模型的 logits 层当特征，那是类别分布不是视觉特征。
解决什么
把“查询向量和全库 N 个向量逐一比对”变成可接受的延迟。注意：N 不大的时候这个节点根本不需要。
默认落地方式
按数据量分档，不要越级：
· n < 5 万：numpy 一行矩阵乘就够（5 万×512 float32 只占 100MB，单次检索 ~10ms）；
· n < 200 万：faiss.IndexFlatIP 精确检索，零参数、零调优、召回 100%；
· n > 500 万 才考虑 HNSW / IVF-PQ 近似索引。
推荐依赖
faiss-cpu（uv add faiss-cpu，无需 GPU）；轻量平替 hnswlib；再往上是 Qdrant / Milvus，但那是服务不是库。
是否建议手写
绝不手写 HNSW / IVF / PQ。可以手写 的只有 n 极小时的 emb @ q + argpartition。
输入
emb: ndarray[n, 512] float32（已 L2 归一化）+ ids: list[str]
处理逻辑
建 IndexFlatIP(dim) → 套 IndexIDMap2 以便用自己的整数 id → add_with_ids → write_index。字符串 image_id 与 faiss 的 int64 id 之间用 idx2id.json 做映射（或直接用行号，行号即 ids 下标）。
输出
index.faiss（二进制）+ idx2id.json: list[str]，二者与 meta.json 必须同批产出、同批发布。
中间产物
build_log.json: {"n":48213,"dim":512,"build_sec":6.2,"index_mb":94.2,"type":"IndexFlatIP"} —— 后面做容量规划全靠它。
伪代码
emb = np.load("embeddings.npy")           # [n, 512] float32, 已归一化
index = faiss.IndexFlatIP(emb.shape[1])   # 内积 = 余弦
index = faiss.IndexIDMap2(index)
index.add_with_ids(emb, np.arange(len(emb)).astype("int64"))
faiss.write_index(index, "index.faiss")

# 百万级以上再换：
# index = faiss.index_factory(512, "HNSW32", faiss.METRIC_INNER_PRODUCT)
# index.hnsw.efConstruction = 200; index.add(emb)
# 查询时 index.hnsw.efSearch = 128  ← 不调这个召回会很难看
平替方案
纯 numpy：scores = emb @ q; top = np.argpartition(-scores, k)[:k]。POC 阶段这就是正确答案，别急着上 faiss。
升级方案
Flat → HNSW（内存换速度，百万级 p95 几毫秒）→ IVF-PQ（内存压缩 8~32 倍，代价是召回下降，必须重新评估）→ 换成 Qdrant / Milvus 服务（需要带条件过滤、实时增删、多副本、快照恢复时）→ 数据本来就在 Postgres 且 <100 万条，用 pgvector + HNSW 索引最省事。
常见坑
  • IVF 系索引忘记 train()，或 nprobe 用默认值 1，召回率断崖式下跌还以为是模型不行。
  • 没套 IndexIDMap，删一条数据后所有行号错位。
  • index.faiss 和 embeddings.npy 版本漂移：重编码了向量但索引是旧的。发布时应把 index.faiss + idx2id.json + meta.json 打成一个带时间戳的目录整体切换。
  • 过早上 ANN：几万张图用 HNSW 换来的是调参痛苦和召回损失，收益为零。
解决什么
把一张查询图变成候选集。这里没有新技术，只有一个要求：和建库走同一段代码。
默认落地方式
进程启动时一次性加载 model + index + idx2id，之后每次请求只做「预处理 → 编码 → search → 映射 id → 查元数据」。召回数量取 k * 3，给 N6 重排留出空间。
推荐依赖
复用 N2/N3 的依赖 + faiss 的 read_index + sqlite3 批量取元数据。别为查询单独引任何东西。
是否建议手写
建议手写 —— 这一层就是胶水，30 行以内，手写最清楚。
输入
query: bytes | image_path、top_k: int、filters: dict | None
处理逻辑
to_tensor(query) → encode_image → 归一化 → q: ndarray[1,512] float32 → D, I = index.search(q, k*3) → ids[i] 还原 image_id → SELECT ... WHERE image_id IN (...) 取路径与业务字段 → 剔除与查询图 sha256 相同的那条（否则用户上传库里已有的图，第一条永远是自己）。
输出
list[(image_id: str, score: float, meta: dict)]，长度 k*3，score 降序，∈ [-1, 1]
中间产物
query_log.jsonl：每行 {"query_id","sha256","top_ids":[...],"scores":[...],"took_ms":{"pre":8,"encode":21,"search":3}}。分段计时是后面做性能优化的唯一依据。
伪代码
# 启动时加载一次，绝不要放在请求函数里
INDEX = faiss.read_index("index.faiss")
IDS   = json.load(open("ids.json"))
assert json.load(open("meta.json"))["model"] == MODEL_NAME   # 版本校验

def search(img_bytes, k=10):
    x, _ = to_tensor(io.BytesIO(img_bytes))        # 与建库同一函数
    with torch.inference_mode():
        q = model.encode_image(x[None].to(dev))
        q = (q / q.norm(dim=-1, keepdim=True)).cpu().numpy().astype("float32")
    D, I = INDEX.search(q, k * 3)                  # 多召回，留给重排
    return [(IDS[i], float(s)) for i, s in zip(I[0], D[0]) if i != -1]
平替方案
没有 faiss 时：scores = EMB @ q.T，np.argpartition 取 top-k，行为完全等价。
升级方案
模型推理与向量检索拆成两个服务（GPU 与内存资源分开扩容）→ 查询向量按图片 sha256 做 Redis 缓存（同一张图反复搜是高频场景）→ 索引热更新用双 buffer：新索引加载完成后原子切换指针，不停服。
常见坑
  • 每次请求都 read_index / from_pretrained：延迟从 30ms 变成 3 秒。
  • 忘记排除查询图自身，评估指标虚高、用户体验莫名其妙。
  • faiss 默认吃满所有 CPU 核，和 web worker 抢资源导致 p99 抖动，用 faiss.omp_set_num_threads(4) 限制。
  • 把 torch 推理放在 async 路由里同步执行，阻塞事件循环——丢到线程池跑。
解决什么
把“向量空间里近”翻译成“业务上真的该展示”。向量召回只负责别漏，这一层负责别错。用户抱怨的绝大多数 badcase 都在这里解决，而不是换模型。
默认落地方式
POC 阶段只做三件事，顺序固定：
① 近重复合并：pHash 汉明距离 ≤ 5 的归为一组，只留组内最高分；
② 阈值截断：余弦 < 阈值直接丢弃（宁可返回 3 条也别返回 10 条垃圾）；
③ 业务过滤：下架、同店铺、同一上传者、时间范围。
推荐依赖
①③ 用标准库即可；判断“是不是同一件实物”要更硬的证据时用 opencv-python 的 ORB/SIFT 特征匹配 + findHomography(RANSAC)，看内点数；或用更强的模型（DINOv2、SigLIP）对 Top-50 重新打分。
是否建议手写
阈值与过滤规则手写（这是业务逻辑，只有你知道）；特征匹配与几何校验不要手写，OpenCV 现成。
输入
list[(image_id, score, meta)]，长度 k*3
处理逻辑
分组去重 → 阈值过滤 → 业务规则过滤 → （可选）几何校验加权 → 截断到 top_k → 给每条附上被保留/被丢弃的 reason
输出
list[(image_id, final_score: float, reason: str)]，长度 ≤ top_k
中间产物
rerank_debug.json：记录每条候选在哪一步被丢掉。没有它，调阈值就是盲调。
伪代码
def rerank(cands, thr=0.78, k=10):
    kept, seen_hash = [], []
    for cid, score, meta in cands:                 # 已按 score 降序
        if score < thr:                    continue   # ② 阈值
        if meta["status"] != "online":      continue   # ③ 业务
        h = int(meta["phash"], 16)
        if any(bin(h ^ s).count("1") <= 5 for s in seen_hash):
            continue                                # ① 近重复合并
        seen_hash.append(h); kept.append((cid, score, "ok"))
        if len(kept) == k: break
    return kept
平替方案
只保留阈值截断一条规则。哪怕只有这一条，用户满意度也会明显好于“无脑返回 Top-10”。
升级方案
多路召回融合（向量 + pHash + 标签/OCR 文本 BM25），用 RRF 倒数排名融合，无需训练即可上线 → 训练轻量 LTR 模型，用点击日志做标签 → 交叉编码器对 Top-20 精排。
常见坑
  • 全局一个阈值：纯色图、白底商品图、风景图的相似度分布完全不同，白底图之间余弦轻松 0.9+。至少按类目分别定阈值。
  • 去重太激进，把“同款不同颜色”当重复删掉了。
  • 重排耗时超过召回耗时（比如对 Top-100 全跑 SIFT），得不偿失，控制在 Top-20 以内。
解决什么
把 Top-K 变成前端能直接渲染的响应，并顺手把可观测数据留下来。
默认落地方式
POC 阶段先用 gradio：30 行代码就有一个能上传图、并排看结果缩略图的网页，这对人工评估的价值远高于写 API。确认效果之后再换 FastAPI 单进程，全局加载模型与索引。
推荐依赖
gradio（POC）→ fastapi + uvicorn + python-multipart（服务）。缩略图直接由静态目录或对象存储返回，不要走 Python。
是否建议手写
不要手写 HTTP 层；要手写 的是入参校验（大小上限、格式白名单、超时）。
输入
HTTP multipart/form-data: file=@query.jpg, top_k=10
处理逻辑
校验（≤10MB、jpg/png/webp/heic）→ N2 → N3 → N5 → N6 → 拼 thumb_url → 记日志 → 返回
输出
{"query_id": "q_8f3a...", "took_ms": 41,
 "results": [
   {"image_id":"a1b2c3d4e5f60718", "score":0.912,
    "thumb_url":"/thumbs/a1b2c3d4e5f60718.jpg",
    "meta":{"category":"shoes", "width":1200, "height":1200}}
 ]}
中间产物
requests.jsonl（含分段耗时、返回条数、是否命中阈值为空），以及被查询图片的落盘副本（用于事后复现 badcase，注意合规）。
伪代码
app = FastAPI()
MODEL, INDEX, IDS = load_all()     # 模块级，启动加载一次

@app.post("/search")
async def api(file: UploadFile, top_k: int = 10):
    raw = await file.read()
    if len(raw) > 10 * 1024 * 1024: raise HTTPException(413)
    t0 = time.perf_counter()
    cands = await run_in_threadpool(search, raw, top_k)   # 别阻塞事件循环
    hits  = rerank(cands, k=top_k)
    return {"query_id": uuid4().hex, "took_ms": int((time.perf_counter()-t0)*1000),
            "results": [to_dict(h) for h in hits]}
平替方案
连服务都不要：04_search.py query.jpg 直接打印 JSON 到 stdout。POC 验证链路，这就够了。
升级方案
API 与推理 worker 拆分 → GPU 侧做动态 batching（多个请求攒一批推理，吞吐提升数倍）→ 索引双 buffer 热切换 → 网关限流、鉴权、按租户隔离索引。
常见坑
  • uvicorn --workers 4 会把模型和索引在内存里复制 4 份，一台机器直接 OOM。先算内存再定 worker 数。
  • 没做上传大小限制，一张 8000×6000 的图能把预处理耗时拉到几秒。
  • 返回原图 URL 而非缩略图，前端一页加载几十 MB。
解决什么
让“换个模型 / 调个阈值 / 换个索引”这件事有客观依据，而不是靠翻几页结果凭感觉。这个节点必须在 POC 阶段就建好，它的成本只有半天。
默认落地方式
手工标一份 20~50 条的 golden set：每条 query 图对应一组“应该被搜到”的 image_id。跑一个脚本算 Recall@K / mAP，结果写 metrics.json，每次改动前后对比。
推荐依赖
numpy 足够，指标公式十几行。要省事可用 ranx 或 pytrec_eval，一行算出 Recall/MRR/NDCG/mAP。
是否建议手写
建议手写 Recall@K 与 mAP（十几行，看得见才信得过）；标注集必须人工标，别用模型自己生成标签，那是自证。
输入
eval.csv: query_image_path, positive_ids(以 | 分隔)
处理逻辑
对每条 query 跑完整链路取 Top-K → 与 positive 集合求交 → 累加 Recall@1/5/10、mAP、以及分段延迟的 p50/p95
输出
metrics.json: {"model":"ViT-B-32","n_query":30,"recall@1":0.83,"recall@5":0.94,"map":0.79,"p50_ms":38,"p95_ms":71,"index_build_sec":6.2}
中间产物
per_query.csv（每条 query 的命中情况），用来快速定位是哪一类图片翻车了。
伪代码
def evaluate(queries, K=(1,5,10)):
    rec = {k: [] for k in K}; aps = []
    for qpath, positives in queries:
        ranked = [cid for cid, _ in search_full(qpath, k=max(K))]
        for k in K:
            rec[k].append(len(set(ranked[:k]) & positives) / len(positives))
        hit = 0; ap = 0.0
        for i, cid in enumerate(ranked, 1):
            if cid in positives:
                hit += 1; ap += hit / i
        aps.append(ap / len(positives))
    return {f"recall@{k}": mean(v) for k, v in rec.items()} | {"map": mean(aps)}
平替方案
连标注都还没有时，用“自查自”冒烟测试代替：拿库内图当 query，Top-1 必须是它自己且 score > 0.99。这条能挡掉 80% 的链路 bug。
升级方案
golden set 进 CI，指标下降超过阈值就阻断发布 → 从线上点击/加购日志自动挖掘正样本，扩充评估集 → A/B 实验框架，用线上指标（点击率、转化）而非离线指标做最终裁决。
常见坑
  • 评估集里的图就在索引库里，且没排除自身，Recall 虚高到 1.0。
  • 只看 Recall@1。以图搜图是给人看一整屏的，Recall@10 和人工相关性更贴近体感。
  • 标注只标了“明显正确”的，漏标的正样本被算成错误，指标被系统性低估。
03

POC 怎么跑通

目标：一个下午，五个脚本，一个目录的产物。不写服务、不建数据库集群、不上向量库。

最小样例数据

  • 200~1000 张图，覆盖 5~10 个类目。太少看不出问题，太多拖慢迭代。
  • 每个类目里至少放 3 张“应该互相搜到”的图：同一物体的不同角度、不同光线、不同背景。这是评估集的来源。
  • 刻意混入 3 类噪声：纯白/纯色图、手机截图、一个故意截断的损坏 JPEG。它们专门用来验证 N1/N2 的兜底分支。
  • 再复制 5 张图做变体：缩放到 50%、加水印、转成 PNG、旋转 90° 并写入 EXIF。这些是“必须仍然搜到原图”的硬性用例。
  • eval.csv 手工写 20 行：query_image_path,positive_ids。

五条验证：确认链路真的通了

#用例通过标准
1自查自：拿库内一张图当 queryTop-1 必须是它自己，score > 0.99。不通过 = 预处理或 id 映射错了，别往下走。
2缩放 50% / 加水印后的变体图当 query原图仍在 Top-1。不通过 = 特征太脆弱，检查是否漏了归一化。
3旋转 90° 并写 EXIF 的图当 query原图仍在 Top-5。不通过 = exif_transpose 没加。
4完全无关的图（风景图搜鞋库）Top-1 分数明显低于同类查询（通常 < 0.6）。不通过 = 分数没有区分度，阈值无从谈起。
5连跑两次 02_embed.pynp.allclose(a, b) 为 True，且 ids.json 完全一致。不通过 = 有非确定性来源（多进程乱序、随机裁剪），后面所有实验结论都不可信。
第 1 条和第 5 条最值钱。「自查自」挡掉 id 错位、归一化不一致、预处理不一致三类 bug；「可复现」保证你后面做的每次对比实验都是有效的。这两条写成脚本，每次改完代码跑一遍。
04

存储怎么选

四类存储各管一件事，职责不要混。POC 阶段其中三类都可以用文件代替。

存储类型负责保存什么POC 用什么规模上来后换成
文件 / 对象存储 原图、缩略图、embeddings.npy、index.faiss、模型权重、评估集快照 本地目录。不要上 S3。 S3 / MinIO / OSS。原图和索引文件按版本目录存放，索引发布 = 换一个目录指针。
关系数据库 image_id、路径或对象 key、sha256、phash、宽高、类目、上下架状态、上传者、时间；查询日志 SQLite 单文件，一张表。 PostgreSQL。数据量大再加分区表；查询日志量大时单独走 ClickHouse 或日志系统。
向量索引 向量本体 + 行号↔image_id 映射（+ 进阶：可过滤的 payload） embeddings.npy + index.faiss 两个文件。 <100 万且数据已在 PG → pgvector（省一套系统，事务一致）；千万级 / 要实时增删和条件过滤 → Qdrant（部署最轻）或 Milvus（生态最全、分布式）。
全文索引 图片标题、标签、OCR 文本、商品属性——只有做多路召回时才需要 不用。真要试就 SQLite FTS5。 Elasticsearch / OpenSearch。它们也支持向量字段，如果团队已经在用 ES，可以直接做图文混合检索，省一套向量库。
图数据库 只有当“相似关系本身要被多跳遍历”时才需要：盗图传播链路溯源、同款商品聚簇后的团伙识别、以图连接的知识图谱 不用，且中团队之前通常都不用。 Neo4j / NebulaGraph。判断标准很简单：你的需求是不是“从 A 出发找 3 跳以内的关联图片”。只是“找最像的 10 张”永远不需要图数据库。
POC 阶段可以一个都不装的：向量数据库、Elasticsearch、Redis、消息队列、对象存储、Kubernetes。这些东西每一个都会在你还没验证效果之前，先消耗掉你三天。真实的顺序是：先证明「搜出来的图是对的」，再考虑「怎么扛住流量」。

算一下你到底需不需要向量数据库

向量占用 = n × dim × 4 字节  (float32)

    10 万张 × 512 维 =  205 MB   → numpy / faiss Flat，笔记本随便跑
   100 万张 × 512 维 =  2.0 GB   → faiss Flat 常驻内存仍然可以
 1,000 万张 × 512 维 = 20.5 GB   → 该上 HNSW 或 Qdrant/Milvus 了
 1,000 万张 × 768 维 = 30.7 GB   → 或者用 PQ 压缩到 1/8，代价是召回下降

05

评估指标怎么定

以图搜图属于检索任务，效果指标看排序质量，工程指标看延迟与成本。每个指标都给了「POC 怎么低成本验」和「上线后怎么持续看」。

效果指标

Recall@K
|Top-K ∩ 正样本| / |正样本|
衡量该被搜到的图，有多少进了前 K。以图搜图最核心的指标，K 一般取 1 / 5 / 10。
POC20~50 条手标 query，05_eval.py 跑一遍，几秒出结果。
上线golden set 固定不动，接入 CI；每次换模型/改阈值必跑，掉超过 2 个点就阻断发布。
mAP
mean(平均精度)，考虑正样本的具体排位
衡量排序质量。一条 query 有多个正样本时比 Recall 灵敏：正样本排第 1 和排第 9，Recall@10 一样，mAP 差很多。
POC和 Recall 同一个脚本一起算，成本为零。
上线作为模型选型的主指标（Recall 用来做发布卡口，mAP 用来选模型）。
Top-K 人工相关性
抽样 50 条 query × Top-10 打 0/1/2 分
衡量最贴近真实体感，能发现标注集完全覆盖不到的 badcase（比如全是白底图互搜）。
POC用 gradio 页面并排看图，两个人各标一遍，半天完成。
上线每周固定抽 50 条真实 query 人工回看；有点击数据后逐步用 CTR 代替。
去重准确率
近重复判定的 Precision / Recall
衡量N6 的合并规则有没有误伤。误删「同款不同色」是高频投诉来源。
POC造 30 对：15 对真重复（缩放/水印/裁边）+ 15 对易混淆（同款不同色/同系列），看阈值能否分开。
上线监控每日被合并的条数占比，突然飙升说明阈值或数据分布出问题了。

工程指标

端到端延迟
p50 / p95，拆成 预处理 / 编码 / 检索 / 重排
衡量用户等多久。必须分段统计——CPU 环境下瓶颈几乎总在编码（占 60~80%），而不是检索。
POCtime.perf_counter() 分段打点，跑 100 次取分位数。
上线每段耗时打成独立指标，p95 设告警。CPU 上 CLIP ViT-B/32 单张约 20~40ms，可作为基线参照。
吞吐与索引构建耗时
QPS；n 张图全量重建需要多久
衡量构建耗时决定你能多久更新一次库。如果全量重建要 8 小时，就必须改增量方案。
POC记 build_log.json 里的 build_sec，按线性外推到目标规模。
上线构建任务耗时进监控；超过窗口期就告警。编码阶段可水平扩展，索引构建通常不能。
存储与 API 成本
n × dim × 4B；调用云 API 时按张计费
衡量规模化的真实门槛。1000 万 × 512 维 = 20GB 内存，这是要不要上 PQ 压缩的判断依据。
POC直接算，一行公式。用云端向量 API 的话先算 100 万张要多少钱。
上线按月看索引内存、对象存储容量、GPU 卡时；冷门数据下沉到低频存储。
失败率
解码失败 / 超时 / 空结果 占比
衡量「空结果率」尤其重要：阈值调太高会让大量查询返回 0 条，指标上看不出来，用户直接流失。
POC看 skipped.log 里解码失败的比例，以及 20 条 query 里有几条被阈值清空。
上线分类打点：解码失败、超时、阈值清空。空结果率是调阈值最直接的反馈信号。
06

升级路线

四个阶段各自独立，不要混着看。每一层只回答三个问题：现在不上什么、什么时候换、换完解决什么、代价是什么。

规模 812 ~ 5 万张 · 目标：证明「搜出来的图是对的」 · 全部产物是一个目录里的几个文件

技术栈

  • 本地目录存图 + SQLite 存元数据
  • open_clip ViT-B/32 或 DINOv2 离线编码
  • embeddings.npy + numpy 矩阵乘（或 faiss Flat）
  • gradio 页面看结果 + 5 个脚本
  • 20~50 条 golden set + 05_eval.py

坚决不要上

  • 向量数据库（Qdrant / Milvus）
  • 对象存储、Elasticsearch、Redis、消息队列
  • Docker / K8s / 微服务拆分
  • 模型微调、ANN 索引调参
  • HTTP 服务（stdout JSON 就够）

代价

  • 单机内存受限，不能扩容
  • 更新库要全量重跑，几分钟
  • 没有并发能力
  • ——这些在这个阶段都不是问题
规模 5 万 ~ 100 万张 · 目标：有一个别人能调的接口，元数据能过滤 · 1~3 人维护

换什么

  • SQLite → PostgreSQL（多进程并发写、字段索引）
  • 本地目录 → S3 / MinIO（原图与索引文件按版本目录发布）
  • numpy → faiss IndexFlatIP 常驻内存，随服务启动加载
  • 脚本 → FastAPI 单进程，模型与索引模块级加载
  • 加增量入库脚本 + 夜间全量重建索引

解决什么问题

  • 别的服务能调了，不用手动跑脚本
  • 能按类目/上下架/时间过滤（先召回再用 PG 过滤）
  • 图片不再绑死在一台机器的磁盘上
  • 索引可回滚：切目录指针即可

仍然不要上

  • 向量数据库——100 万 × 512 维才 2GB，Flat 完全扛得住
  • ANN 近似索引——精确检索的召回是 100%，何必
  • 模型微调、多路召回、重排模型

代价

  • 一台 16~32GB 内存的机器（含模型常驻）
  • 要维护 PG 备份和索引发布流程
  • 索引更新有延迟（夜间重建 = T+1）
规模 100 万 ~ 1000 万张 · 目标：实时增删、带条件过滤、效果可持续迭代 · 3~10 人

换什么

  • faiss 文件 → Qdrant 或 Milvus（payload 过滤、实时 upsert/delete、快照、多副本）
  • 单进程 → API 与 embedding worker 拆分，GPU 侧动态 batching
  • Flat → HNSW（内存换延迟）
  • 单路召回 → 多路召回 + RRF 融合（向量 + pHash + 标签/OCR 走 ES）
  • 手工评估 → 离线评估流水线 + CI 卡口，golden set 扩到 500+
  • 开始做领域微调：用业务正样本对做对比学习

解决什么问题

  • 新图上传后秒级可搜，下架图立刻消失
  • 过滤条件在向量库里就完成，不用超召回再过滤
  • GPU 利用率从 20% 提到 70%+
  • 效果迭代有客观依据，不再靠拍脑袋

暂时不要上

  • 分布式多分片（千万级单机 Qdrant 仍能扛）
  • 在线学习 / 实时特征更新
  • 自研向量引擎

代价

  • 多一套有状态服务要运维、备份、扩容
  • PG 与向量库之间的双写一致性问题（需要对账任务）
  • 模型版本与索引版本的兼容管理复杂度上升
  • GPU 成本进入账单
规模 1000 万 ~ 亿级 · 目标：稳定性、成本、效果三条线同时可控 · 专职团队

换什么

  • 单机向量库 → 分片 + 多副本集群，按业务线或时间分片
  • float32 → PQ / 标量量化 + 冷热分层，内存降到 1/8~1/32
  • 零散脚本 → 特征平台：统一管理 embedding 版本、回填、灰度双写
  • 规则重排 → LTR / 交叉编码器精排，训练数据来自线上点击回流
  • 离线指标 → A/B 实验平台，用业务指标最终裁决
  • ES / OpenSearch 承接图文混合检索与标签召回

解决什么问题

  • 单点故障不再影响全站；可按分片灰度
  • 存储成本从不可承受降到可预算
  • 换模型不再是一次性大爆炸，可以双索引灰度切流
  • 效果提升从「换模型」变成「持续的数据飞轮」

这一层的真实难点

  • 不是选型，而是embedding 版本治理：亿级数据重编码一次的时间与成本
  • 召回率与成本的持续权衡（PQ 压缩多少算够）
  • 合规：用户上传图的留存、删除与可追溯

代价

  • 专职的检索/平台团队
  • GPU 集群与向量集群的常态化成本
  • 任何一次模型升级都是一个跨季度的项目
跨越层级的唯一判断标准是数字，不是感觉。先算 n × dim × 4，再看 p95 延迟和索引重建耗时。这三个数没有超出当前方案的能力之前，任何"升级"都只是在增加你的运维面积。
