一文读懂 · Image-to-Image Search

以图搜图 给一张图，找出"看起来像"的其他图 —— 从可行性验证到企业级检索系统

这篇文章不讲某个框架怎么分层，也不堆一串工具名。它想解决一个更具体的问题：你已经决定要做"以图搜图"这件事，但不知道从哪儿下手 —— 该先跑一个脚本，还是先选模型，还是先想清楚"相似"到底是什么。读完之后，你应该能判断：demo 怎么在一天内跑通、POC 要验证什么、小团队怎么上线、中团队怎么扩展、企业级要治理什么。

F.01 概念对齐

这个能力到底是什么Input / Output / 成功标准 / 不解决什么

在选模型、选架构之前，先把这几件事说清楚 —— 否则 demo 做出来了，也不知道算不算"成"。

输入 / 输出

输入是一张图片：用户上传的照片、系统内部产生的一帧截图、一张商品图。输出是一个有序列表：[(图片ID, 相似度分数), ...]，通常还带缩略图和跳转链接，按分数从高到低排列，取 Top-K。

它不是一个"是/否"的判断，而是一个排序问题 —— 这一点决定了后面所有的技术选型。

用户怎么用

典型场景：上传一张图找同款商品、找同一个人/同一个场景的其他照片、给素材库查重、在历史截图里找相似的记录、给一段视频找相似的参考画面。

共同点：用户心里已经有一个"像"的标准，系统要做的是逼近这个标准，而不是发明一个标准。

"相似"是业务定义的，不是模型给的。模型只会告诉你两张图的向量距离有多近；多近算"相似"、按什么维度相似（外观？语义？构图？同一实体？），这是业务问题，需要在做 demo 之前就有一个粗略答案，否则连验收标准都定不下来。

成功标准怎么定

不要用"分数越高越好"这种模糊说法。可落地的成功标准通常是：挑一批有已知答案的查询图，看 Top-K 里有没有业务认为"对"的结果 —— 用 Recall@K（该出现的有没有出现）、Precision@K（出现的里有多少是真的对）配合人工抽检满意度来衡量。这几个概念在下文"验证与风险"一节会展开。

哪些事情不由它解决

  • 它不做 OCR（读图里的文字）、不做目标检测出框（框出图里有几个物体）——如果业务需要这些，是额外的模块，不要指望"以图搜图"顺带解决。
  • 它不保证语义理解：模型给出的是视觉特征上的接近，不是"看懂了图里在讲什么故事"。
  • 它不做版权 / 真伪鉴定：找到视觉相似不等于法律意义上的侵权判定。
  • 它不解决"相似"定义本身的业务分歧：多相似算相似，需要业务提前定阈值和验收标准，模型和索引解决不了这个分歧。
F.02 最小链路

30 分钟内跑通的最小链路先验证"方向对不对"，不追求效果和工程完整度

这一步的目标只有一个：验证"拿一批图，能不能把相似的图挑出来"这件事本身是不是可行的。不建索引服务，不加权限，不做任何"以后可能需要"的设计。

  1. 准备样例数据：一个文件夹 data/images/，放 100～300 张图，尽量覆盖典型场景（同款不同角度、不同光照、局部遮挡），不需要很多。
  2. 选一个模型：直接用开源 CLIP（如 ViT-B-32），本地 CPU 就能跑，慢一点但能跑通，不需要一开始就上 GPU 或云 API。
  3. 写脚本提取 embedding：把每张图变成一个向量，存成一个 numpy 数组 + 一份路径列表。
  4. 建索引：先不用向量数据库，直接用 numpy 做暴力余弦相似度，几百张图完全够用。
  5. 发起一次查询：取一张图算 embedding，和索引里所有向量算相似度，排序取 Top-K。
  6. 人工验证：把 Top-K 图打印/展示出来，肉眼看是不是真的像。
01A 离线：批量提取 embedding，建一个"内存索引"build_index.py
# 离线执行一次；数据/模型变了就重跑
import open_clip, torch
from PIL import Image
import numpy as np, os, pickle

model, _, preprocess = open_clip.create_model_and_transforms(
    "ViT-B-32", pretrained="openai"
)
model.eval()

image_dir = "data/images"
paths = [os.path.join(image_dir, f) for f in os.listdir(image_dir)]

embeddings = []
for p in paths:
    # 图片损坏就应该直接报错退出，不要 try/except 悄悄跳过
    img = preprocess(Image.open(p).convert("RGB")).unsqueeze(0)
    with torch.no_grad():
        feat = model.encode_image(img)
        feat = feat / feat.norm(dim=-1, keepdim=True)  # 归一化，内积即余弦相似度
    embeddings.append(feat.numpy()[0])

embeddings = np.stack(embeddings)  # shape: (N, 512)
with open("index.pkl", "wb") as f:
    pickle.dump({"paths": paths, "embeddings": embeddings}, f)
01B 线上：一次查询search.py
def search(query_path, top_k=5):
    with open("index.pkl", "rb") as f:
        store = pickle.load(f)

    img = preprocess(Image.open(query_path).convert("RGB")).unsqueeze(0)
    with torch.no_grad():
        q = model.encode_image(img)
        q = q / q.norm(dim=-1, keepdim=True)
    q = q.numpy()[0]

    scores = store["embeddings"] @ q  # 都归一化过，内积=余弦相似度
    top_idx = np.argsort(-scores)[:top_k]

    return [(store["paths"][i], float(scores[i])) for i in top_idx]

for path, score in search("data/query.jpg"):
    print(f"{score:.3f}  {path}")
这两个脚本就是完整的"demo"。它没有服务、没有数据库、没有权限，但它已经能回答最关键的问题：这条技术路线，在你的数据上，能不能把相似的图挑出来。如果这一步都验证不了，后面的架构讨论都没有意义。
F.03 线下 / 线上

完整链路拆解哪些步骤离线做，哪些步骤线上做

demo 只有两个脚本，但真正上线的系统里，同样的逻辑要分成"离线维护索引"和"线上响应查询"两条线 —— 混在一起是很多项目变慢、变不可控的起点。

离线链路
线上链路
离线：不在用户等待的请求路径里，可以慢，可以批处理 线上：用户在等，越简单越好，能不加的组件先不加

离线链路：为什么需要 · 什么时候可以先不做

步骤为什么需要什么时候可以先不做
导入数据总要有个来源：本地目录、对象存储、业务系统同步、爬虫抓取。demo 阶段直接放一个本地文件夹即可，不需要写"导入系统"。
清洗脏数据会直接污染向量空间：损坏图、重复图会让"相似"结果失真。demo 阶段可以先不做；进入 POC 起至少要做"去损坏、去重"这两件事。
切分一张图里有多个目标时，不切分会让 embedding 变成"整体氛围相似"而非"目标相似"。单目标场景（比如整图就是一件商品）可以先跳过，不需要先接检测模型。
Embedding核心中的核心，没有它就没有可比较的向量表示。——（这一步不能跳过）
索引构建数据量大之后，暴力比对的延迟会明显上升，需要 ANN 索引加速。几千张以内，直接 numpy 矩阵乘法或 faiss.IndexFlatIP 就够，不需要专门的索引服务。
批处理评测没有它就没法判断"这批数据 / 这个模型到底行不行"，全凭肉眼感觉是危险的。demo 阶段可以先靠人工看几个 case；进入 POC 必须要有。

线上链路：为什么需要 · 什么时候可以先不做

步骤为什么需要什么时候可以先不做
接收查询用户上传图片或传图片 URL，是整条链路的入口。——（这一步不能跳过）
召回用 embedding + ANN 检索拿到候选集（比如 Top 100），是"相似"这件事真正发生的地方。——（这一步不能跳过）
重排召回结果"看起来差不多但排序不够准"时，用更贵但更准的模型/特征重新排序。大多数场景可以先不做；只有排序质量明显不够、且召回已经排除主要问题时才加，因为它会增加延迟和成本。
过滤业务规则：权限、库存状态、审核状态、黑名单——只要涉及真实业务就必须做，且要显式失败（比如权限查询失败不能默认放行）。纯个人验证 / 无业务约束的 demo 可以先不做。
返回结果把排序后的 Top-K、分数、元数据整理成结构化响应。——（这一步不能跳过）
混合检索、聚类、分类这些模块放在哪一段？混合检索（向量分数 + 关键词分数融合）发生在"召回"之后、"重排"之前；聚类通常是离线做的，用于去重和构建"同款分组"；分类可能出现在召回前（限定检索范围）也可能出现在过滤阶段（排除误检类别）；人工审核通常不在实时链路里，而是离线抽检 + 针对高风险结果的复核队列。这些细节会在下一节"技术路线怎么选"里展开。
F.04 技术路线

技术路线怎么选六条常见路线，没有绝对的"最优解"

下面这张表不是用来找"哪个最好"，而是用来对照你的约束条件——数据规模、隐私要求、团队能力——排除掉明显不合适的路线。选一个你最看重的因素，看看表格会亮哪几列。

维度 本地开源模型 云 API 厂商一体化方案 开源项目二次开发 自研 pipeline 传统算法增强
(pHash / 局部特征)

成本结构一次性硬件/GPU + 运维，长期边际成本低按调用量付费，量大后可能反超自建订阅/托管费用，通常比自建贵但省人力中，省模型训练但仍需工程投入最高，人力成本主导极低，CPU 就能跑

隐私 / 数据出境图片不出本地/内网，最可控图片需发给第三方，需评估合规同上，需评估合规取决于部署方式最可控本地计算，可控
团队能力要求需要会调 PyTorch / 推理框架几乎零门槛，调 API 即可中，需理解平台概念需要读懂并改造别人的代码需要完整算法 + 工程团队门槛最低
一个常见的实际路径：demo/POC 阶段用本地开源模型或云 API 快速验证方向；确认方向可行、数据量和调用量涨起来之后，再根据"云 API 成本是否反超自建"“数据是否有出境限制”这两个信号，决定要不要转向自建或私有化部署。不必一开始就纠结"终极方案"。

模型怎么选

  • 通用模型（CLIP / OpenCLIP）：广泛物体、场景相似度检索的默认起点，先用它验证方向。
  • 领域模型：细分场景效果远好于通用模型——比如同款商品检索、人脸检索，都需要专门训练/微调的 embedding 模型，直接拿通用 CLIP 当人脸特征用，效果通常会明显打折。
  • 多模态模型：需要"文搜图"或"图搜图 + 文本联合过滤"时用，CLIP 本身就是图文双塔结构，可以直接复用它的文本侧。
  • Embedding 模型 vs Reranker：embedding 模型负责快速召回（双塔结构，向量可预先算好存起来），reranker 负责精排（通常是更贵的交叉编码结构，只对候选集现算，不能预计算）——两者不是二选一，是分工。
  • 分类模型 / 检测模型：用于前置过滤（先判断类目再限定检索范围）或后置过滤（排除误检类别），不是核心检索逻辑的一部分，是辅助模块。

算法和工程模块，分别放在链路的哪一段

模块放在哪一段作用
相似度检索（向量召回）召回核心动作，把候选集从全量数据里捞出来。
关键词检索召回（并行）如果图片有标题/标签等文本元数据，可以和向量召回并行做文本检索。
混合检索召回之后、重排之前把向量分数和关键词分数融合（加权或 RRF 之类的排序融合方法）。
重排重排用更贵但更准的模型对候选集做精排。
聚类离线去重、发现同款簇，构建"同款分组"索引。
分类召回前或过滤阶段前置限定检索范围，或后置过滤误检类别。
规则过滤 / 阈值判定过滤业务规则 + 分数阈值，决定哪些候选真正返回给用户。
后处理（去重/打散）过滤之后、返回结果之前避免 Top-K 全是同一张图的近似重复，保证结果多样性。
人工审核离线 / 旁路队列不在实时链路里，是定期抽检 + 高风险结果复核队列。

依赖和成熟模块：按职责选，而不是按名气选

职责解决什么问题常见选择
模型推理运行时让模型跑起来，并尽量快PyTorch, ONNX Runtime, TensorRT

开源方案怎么借鉴：不是"用不用"，是"借哪一层"

把开源项目当成一个整体"要不要用"，是一种懒惰的二分法。更常见也更实用的做法是拆开看，只借你真正缺的那一层：

① 直接使用整个项目

适合"业务不追求差异化，只要能跑起来"的场景。代价是被项目的设计假设绑定，改起来别扭。

② 只借模型权重

比如只用 CLIP / OpenCLIP 的预训练权重，自己写检索逻辑。最常见的方式——模型是最难自己训练的部分，复用价值最高。

③ 只借索引/检索模块

比如只用 FAISS 这个库本身，不用某个项目整套检索服务代码。适合已经有自己的数据管道，只缺高效向量检索能力。

④ 只借 UI / 管理后台

用某个开源项目的标注/检索管理界面，后端换成自己的。适合需要快速出一个可用的管理界面，又不想从零写前端。

⑤ 只借评测方法

参考别人怎么构造评测集、怎么算指标，不用其代码。适合已经有自己的实现，但不知道怎么系统评估效果。

厂商方案怎么判断：减少了什么负担，又带来什么代价

方案减少了什么工程负担带来什么成本 / 锁定 / 隐私问题
云模型 API不用训练/维护模型按量计费，量大后可能比自建贵；效果和 pipeline 强绑定，换厂商要重新调阈值、重新评测；图片要出网络发给第三方。
托管向量库不用运维分布式向量检索服务订阅费通常比自建集群贵但省运维人力；数据迁移和 API 差异带来锁定；部署在自己云账号内通常隐私可控，但仍是第三方服务。
对象存储不用自己搭文件服务器、备份、CDN成本可控且成熟，S3 协议相对通用、锁定较低；隐私取决于是否满足数据留存地合规要求。
Serverless不用运维服务器、处理扩缩容对突发流量友好，但长期高负载可能比常驻实例贵；各厂商运行时/触发器不通用，锁定较强；对 GPU 推理支持有限，不一定适合 embedding 这类重计算任务。
AI 平台 / 企业知识库 / 搜索平台整条链路（embedding + 索引 + 管理后台）都内置好了成本通常最高，锁定最强——数据结构和检索逻辑都在平台内部；适合"不追求技术自主可控，只要业务结果"的团队。

本地方案怎么判断

适合
  • 离线验证阶段——不想为了验证可行性就先签厂商合同
  • 隐私敏感数据——人脸、医疗影像、内部资料
  • 成本可控——调用量大到云 API 成本不划算
  • 内网部署要求——企业数据不能出内网
限制
  • 需要 GPU 才能跑得快，CPU 能跑但通常只适合小规模验证
  • 索引文件需要自己管理版本和备份
  • 数据更新需要自己写增量流程，不像托管服务开箱即有
  • 部署运维需要自己承担——模型服务挂了、索引损坏了都要自己排查

向量索引 / 向量数据库相似度检索FAISS / Chroma 本地文件索引数据量大到内存放不下、需要高频增删改、需要多机分布式检索时
图数据库多跳关系、实体网络、关系推理通常 demo 阶段就不需要核心能力本身变成"关系推理"而不是"相似度检索"时——这种情况已经不是纯粹的以图搜图了
demo 阶段的轻量替代能撑多久？本地目录 + JSON/SQLite + FAISS/Chroma，几百到几千张样例文件完全没问题。瓶颈信号：查询延迟明显变高、内存放不下全部向量、多进程同时读写索引文件发生冲突、需要支持增量更新但现有方案只能整体重建——出现任意一个，就该考虑升级对应的存储组件了。

POC / 生产阶段：数据怎么进、怎么更新、怎么回滚

  • 导入：写增量导入脚本，而不是每次全量重跑——全量重跑在数据量变大后会拖垮上线节奏。
  • 增量更新：新图片进来时只算新图片的 embedding、只更新索引里新增的部分，而不是重建整个索引。
  • 索引重建：定期（比如每周/每天）全量重建，修复增量更新积累的漂移或碎片化；重建期间要考虑"旧索引是否还能服务"——双索引切换，而不是重建时直接下线。
  • 版本管理：索引文件需要版本号，方便回滚——新模型上线后效果变差，能快速切回旧索引/旧模型。
  • 离线评测集：一批"查询图 - 预期相似图"的标注对，每次模型/索引变更前跑一遍，防止"改了却不知道变好还是变差"。
  • 回滚：保留上一版本索引和模型的能力，出问题能迅速切回，而不是只能往前修。

线上请求链路要保持简单

用户输入 → FastAPI/脚本入口 → 调用模型/索引/业务规则 → 返回结构化结果。只有任务耗时、文件大、并发高，或者需要批处理（比如夜间批量导入）时，才引入队列、worker 和任务状态——不要一开始就假设需要一整套异步架构。

F.06 分阶段路线

demo → poc → 小团队 → 中团队 → 企业级每个阶段：新增了什么、解决什么问题、带来什么成本、什么时候不值得上

这是整篇文章的核心主线。点开每一格，看这一阶段具体要做什么——也看清楚"什么时候不该急着进入下一阶段"。

目标

用最少组件验证"这个能力是否可行"——不是验证效果多好，是验证方向对不对。

新增组件

  • Python 脚本 / Notebook
  • 一个开源模型（本地）或云 API（二选一即可）
  • numpy / FAISS 内存索引
  • 几百张样例图

解决的问题

回答"这条技术路线能不能把相似的图挑出来"这个最基本的问题。

带来的成本

几乎为零，一到两天工作量。

什么时候不值得上

如果业务上连"什么算相似"都还没想清楚，做 demo 也验证不了什么——应该先把业务定义谈清楚，再动手写代码。

目标

验证真实数据下的效果、延迟、成本，以及失败样本长什么样。

新增组件

  • 真实业务数据（不是精选样例）
  • 简单的 FastAPI 封装
  • 基础存储（SQLite + 本地目录，或云对象存储）
  • 小规模离线评测集（几十到上百个标注 query）

解决的问题

回答"这个方案在真实数据上，指标能不能达到业务能接受的下限"。

带来的成本

需要拉通真实数据授权、花时间标注评测集，也可能发现模型不适配，需要换模型。

什么时候不值得上

如果 demo 阶段就已经发现方向明显不对（比如模型对这类图片完全不敏感），不要急着上 POC 去"碰运气"，先换路线。

目标

让真实用户能用起来，同时保持架构简单。

新增组件

  • 持久化（向量索引落盘 + 定期备份）
  • 任务状态记录
  • 基础权限校验（至少区分"谁能查询"“谁能看到哪些结果"）
  • 日志、区分环境的配置文件
  • 部署脚本（哪怕只是一个 Dockerfile + docker-compose）
  • 人工抽检机制（定期抽查结果质量）

解决的问题

从"能在我电脑上跑"到"能稳定给别人用"。

带来的成本

需要有人负责基础运维——重启服务、看日志、处理坏 case。

什么时候不值得上

用户量本身就很小、很低频（比如内部工具偶尔用一下），这时候过度补齐权限/监控反而是浪费——够用就好，不用往企业级看齐。

目标

支撑增长的数据量和访问量，同时保证效果不随规模变大而变差。

新增组件

  • 更稳定的数据管线（增量导入 + 索引重建 + 版本管理）
  • 任务队列/worker（处理批量导入、大文件、高峰期请求）
  • 独立对象存储
  • 专门的向量库/支持向量检索的搜索引擎（替换内存索引）
  • 监控（延迟/成功率/成本）
  • 评测回归（每次上线前自动跑评测集）
  • 灰度发布（新模型/新索引先给一小部分流量）
  • 成本观测（尤其用云 API 时，量大后成本可能失控）

解决的问题

从"能用"到"规模变大也不会垮、也不会不知不觉变差"。

带来的成本

需要专门的工程投入维护这些组件，团队分工开始出现——有人管数据管线，有人管服务。

什么时候不值得上

数据量和访问量还没真的涨到内存索引/单机撑不住的地步，提前上这些组件只是增加维护负担而没有实际收益。

目标

在合规、安全、可持续运营的前提下，支撑多业务方/多租户使用。

新增组件

  • 多租户隔离（不同业务线的数据和检索不能互相看到）
  • 细粒度权限体系
  • 审计（谁在什么时候查了什么、结果是什么）
  • 合规（数据出境、留存期限、内容审核）
  • 私有化部署能力
  • 容量规划（提前预估未来半年到一年的增长）
  • 分片重建等索引重建策略
  • 灾备（索引/模型/数据的多副本和恢复演练）
  • 严格的模型版本管理和上线前评测/回滚流程
  • 人工审核队列和处理 SLA
  • 供应商替换策略（评估"换厂商需要多大代价"，避免被单一厂商锁死）

解决的问题

让系统在组织级别可信、可审计、可持续，而不只是"能跑"。

带来的成本

最高，需要专门的平台团队、合规团队配合。

什么时候不值得上

团队/业务规模没有到多租户、多业务线共享的程度，过早引入这些治理成本会拖慢所有人。

F.07 FastAPI 的位置

FastAPI 只在需要服务化时出现不是架构教程，只是一层薄薄的暴露方式

如果脚本能跑通，先展示脚本链路；只有需要暴露成 API 给别的系统/前端调用时，才把它包成 FastAPI 服务。它负责接收请求、上传文件、触发任务、查询状态、返回结果——仅此而已。

02A 同步接口：直接返回检索结果main.py
from fastapi import FastAPI, UploadFile
from pydantic import BaseModel

app = FastAPI()

class SearchResult(BaseModel):
    path: str
    score: float

@app.post("/search", response_model=list[SearchResult])
async def search_image(file: UploadFile, top_k: int = 5):
    image_bytes = await file.read()
    # 复用前面脚本里的 search 逻辑，不需要重写一遍
    results = run_search(image_bytes, top_k=top_k)
    return [SearchResult(path=p, score=s) for p, s in results]
02B 异步接口：耗时任务放后台，不阻塞请求main.py
from fastapi import BackgroundTasks, HTTPException

@app.post("/reindex")
async def trigger_reindex(background_tasks: BackgroundTasks):
    task_id = create_task_record()
    background_tasks.add_task(rebuild_index, task_id)
    return {"task_id": task_id}

@app.get("/tasks/{task_id}")
async def get_task_status(task_id: str):
    status = get_task_record(task_id)
    # 查不到就显式抛错，不要返回默认的"processing"掩盖问题
    if status is None:
        raise HTTPException(status_code=404, detail="task not found")
    return status
什么时候从 BackgroundTasks 升级到独立队列/worker？当重建任务需要处理大量并发请求、失败后需要重试机制、需要跨进程/跨机器分发任务，或者需要任务优先级和限流时——这时候才引入 Celery/RQ 等独立队列。不要默认所有 demo 一上来就搭一整套异步架构，大多数 demo 和 POC 阶段，BackgroundTasks 已经够用。
F.08 验证与风险

怎么判断做得好不好，出问题先看哪里验证方法 · 常见失败模式 · 排查顺序

怎么判断方案可用

  • 小样本人工验证：挑 10-20 个典型 query，人工看排序是否合理，适合 demo 阶段。
  • 离线评测集：标注"查询图-预期相似图集合"，跑 Recall@K（该出现的有没有出现）、Precision@K（出现的里有多少是真的相似）。
  • 排序指标：如果相似度有分级（非常像/比较像/不像），用更细的排序指标；大多数场景 Recall@K / Precision@K 已经够用。
  • 延迟：端到端（用户点查询到看到结果），而不只是模型推理时间。
  • 成本：单次查询成本 + 离线建索引成本 + 存储成本，要按预期 QPS/数据量估算，不能只看 demo 阶段小数据的成本。
  • 失败样本分析：定期把 Precision 低的 query 拉出来人工看，分类失败原因——是数据问题、模型问题，还是阈值问题。
  • 用户验收：指标达标不代表用户满意，最终还是要看真实用户觉得"这个好用"。

常见失败模式（点开看排查建议）

01数据质量差+

模糊、过曝、遮挡严重、缩略图分辨率太低导致细节丢失。排查建议：先看能不能过滤/提高数据质量，而不是急着换模型。

02模型不适配+

通用模型在细分领域效果差，比如人脸/商标/工业零件这类需要专门模型的场景。排查建议：换领域模型，或至少考虑微调。

03向量召回不准+

embedding 本身没问题，但检索没找到该有的候选，通常是 ANN 索引参数设置不当，比如召回数太小、索引类型选错。排查建议：检查 ANN 索引配置，而不是先怀疑模型本身。

04阈值难设+

不同 query 的"合理相似度分数"分布差异很大，固定阈值要么漏检要么误检。排查建议：考虑相对排序而不是绝对阈值，或者按类目/场景分别设阈值。

05索引过期+

新图片进来了但没有出现在检索结果里，因为索引没有增量更新。排查建议：检查增量更新链路是否正常运行，而不是怀疑模型突然变差。

06权限过滤缺失+

检索返回了用户本不该看到的图片。排查建议：这是安全问题，必须显式加权限过滤，不能假设向量检索结果天然是"安全"的。

07云 API 成本过高+

量上来后按次计费的成本超出预算。排查建议：重新评估是否要自建/换成本地模型，或者引入缓存（常见 query 缓存结果）。

08本地模型太慢+

CPU 推理跟不上 QPS。排查建议：考虑 GPU、模型量化、批处理（batching），或者降级到更小的模型。

09企业数据不能出内网+

合规要求。排查建议：这是路线选择问题，不是优化问题——应该在选型阶段就排除云 API，而不是上线后才发现。

排查顺序：先看数据，最后才看架构

① 数据 → ② 模型 → ③ 索引/检索 → ④ 后处理/业务规则 → ⑤ 服务架构

反过来"一出问题先怀疑框架/数据库"是最没有效率的排查顺序——架构问题通常是最后才需要考虑的，也是最容易被过度怀疑的。

哪些能力不该过度工程化：数据量很少（几百张以内）、使用频率很低（一天几次甚至更少）、质量要求不高（内部工具/个人验证）、只是想快速看看这个方向靠不靠谱——这些场景下，优先用脚本 + 本地文件 + 轻量索引，不要因为"将来可能要扩展"就提前引入向量数据库/消息队列/多租户设计。这些"面向未来的设计"往往会拖慢真正要解决的问题的验证速度。
以图搜图 · 一文读懂 —— 从最小可跑链路，到企业级治理。技术路线会变，但"先验证方向、再谈架构"这条主线不会变。
