KNOWLEDGE · IMAGE EMBEDDING

把图片变成一串数字

人眼一眼就能看出两张图片像不像，计算机却不能直接比较像素。Image Embedding 做的事情， 是把一张图片压缩成一个定长向量——语义越相似的图片，向量在空间里离得越近。 从此，「像不像」变成了一个可以计算的距离。

为什么需要它

先看一个真实场景

你在做一个电商系统，用户上传一张照片，想在库里找出长得像的商品。 直觉的做法是逐像素比较两张图——这在真实场景里几乎立刻失效。

同一款衣服，模特换了个姿势、光线变了、裁剪角度不同，两张图的像素值可能天差地别， 即使肉眼一眼就能认出「这是同一款」。逐像素比较（比如算欧式距离）对这种变化毫无免疫力。

Image Embedding 解决的是「给一张图片一个语义指纹」的问题：用来做检索、去重、聚类、 给下游模型提供特征。它不负责判断图里有什么类别、物体在哪、写了什么字——这些边界会在后面专门讲清楚。

核心机制

图片如何一步步变成向量

从文件到向量要经过 6 个确定性步骤，其中只有第 4 步是「学出来的」， 其余都是工程上的规范化处理——但每一步都会实实在在影响最终向量的质量。

(H, W, 3) uint8

读取（Load）

用 PIL 或 OpenCV 把文件解码成像素数组。不同图片的 H、W 各不相同——这正是下一步必须 resize 的原因。

Image.open(path).convert("RGB")

尺寸各不相同：一批图片的 H、W 很可能完全不一致。
(H,W,3) → (224,224,3) uint8

Resize

视觉 encoder 的输入尺寸是固定的（常见 224×224 或 336×336），所有图片必须统一到同一尺寸，模型才能用同一组权重处理整批数据。

插值方式、是否居中裁剪会带来微小差异，但通常不是决定性因素。
uint8 [0,255] → float32 分布

归一化（Normalize）

先把像素值从 [0,255] 缩放到 [0,1]，再按颜色通道减均值、除以标准差，把数值调整到模型训练时见过的分布。

x = (pixel/255 − mean) / std

不同模型的 mean/std 不同（比如 CLIP 官方用的是 mean=(0.4815, 0.4578, 0.4082)， 而不是常见的 ImageNet 统计值）——用错归一化参数，向量质量会明显下降。
(224,224,3) → (D,)　D 常见 512 / 768 / 2048

视觉 Encoder（唯一「学出来」的一步）

图片被送进预训练好的神经网络（CNN 如 ResNet，或 Vision Transformer 如 ViT），逐层提取从边缘、纹理到物体、场景的特征，最后输出一个定长向量。

这一步的权重决定了「语义相近」具体指什么——用什么模型、什么数据、什么损失函数训练出来的 encoder，直接决定向量质量。
(D,) → (D,)，长度变为 1

向量归一化（L2 Normalize）

把向量压缩到单位球面上，只保留方向、丢掉长度信息。归一化之后，余弦相似度等于向量点积，检索时可以直接用更快的点积运算。

v_norm = v / ‖v‖

(A, B) → 一个标量，[-1, 1]

相似度计算

用余弦相似度衡量两个向量的接近程度。归一化之后，公式简化为点积。检索时取 top-k 相似度最高的结果作为「以图搜图」的答案。

cosine(A, B) = A·B / (‖A‖‖B‖)

直接用像素级欧式距离做这件事效果很差——这正是文章开头那个场景要解决的问题。

    划清边界

    它不是分类、不是检测、也不是 OCR

    很多「都在处理图片」的技术，其实解决的是完全不同的问题。混着用，要么用力过猛，要么文不对题。

    维度 Image Embedding 图像分类 目标检测 OCR 图文多模态

    输入 一张图片（或裁剪区域） 一张图片 一张图片 一张图片 图片 +（可选）文本
    输出 定长向量 离散类别标签 多个 bounding box + 类别 文字字符串 CLIP：图文共享向量；VLM：自然语言
    核心问题 这张图和哪些图语义相近？ 这张图属于哪个类？ 图里有什么、在哪？ 图里写的是什么字？ 图文能否对应上 / 描述图片
    类别是否固定 不需要预定义类别 需要固定类别表 需要固定类别表（或开放词汇变体） 不适用 CLIP zero-shot 不需固定类别
    典型模型 / 工具 ResNet / ViT 骨干、CLIP image encoder ResNet / EfficientNet + softmax head YOLO / Faster R-CNN / DETR Tesseract / PaddleOCR / TrOCR CLIP / ALIGN；GPT-4V / Claude 等 VLM
    分类模型 ≠ 通用 embedding

    分类模型的倒数第二层其实也是一种 embedding，只是它被交叉熵损失塑造过， 更贴近「分类边界」，不一定是最好的通用相似度表示。CLIP 类模型专门用对比学习训练， 让语义相似的图文都靠近，这正是它更适合做检索的原因。

    CLIP ≠ 生成式 VLM

    CLIP 是「图像 embedding + 文本 embedding 共享同一向量空间」的模型，本质仍是输出向量。 GPT-4V / Claude 这类 VLM 是生成式的，输入图像后能输出自然语言描述、回答问题—— 这已经超出「输出一个向量」的范畴，是不同的能力层级。

    写入向量库，或返回 top-k 检索结果

    // 批量编码 · 写入向量库 · 以图搜图
    from PIL import Image
import numpy as np

IMG_SIZE = 224
MEAN = np.array([0.485, 0.456, 0.406])
STD  = np.array([0.229, 0.224, 0.225])

def preprocess(path: str) -> np.ndarray:
    img = Image.open(path).convert("RGB").resize((IMG_SIZE, IMG_SIZE))
    x = np.asarray(img, dtype=np.float32) / 255.0
    x = (x - MEAN) / STD
    return x.transpose(2, 0, 1)          # HWC -> CHW

def embed_batch(paths: list[str], model) -> np.ndarray:
    batch = np.stack([preprocess(p) for p in paths])   # (N, 3, 224, 224)
    vectors = model(batch)                              # (N, D)
    norms = np.linalg.norm(vectors, axis=1, keepdims=True)
    return vectors / norms                              # L2 normalize

# 1) 批量编码 + 写入向量库
vectors = embed_batch(image_paths, model)
vector_db.upsert(ids=image_paths, vectors=vectors)

# 2) 以图搜图
query_vector = embed_batch([query_path], model)[0]
matches = vector_db.search(query_vector, top_k=5, metric="cosine")

# 3) 图文匹配（仅 CLIP 类模型可用：文本编码器输出同一向量空间）
text_vector = text_model(["a red running shoe"])[0]
text_vector = text_vector / np.linalg.norm(text_vector)
matches = vector_db.search(text_vector, top_k=5, metric="cosine")

    常见向量库选择：本地库如 FAISS，服务化的有 Qdrant、Milvus、Weaviate，或直接用 Postgres 的 pgvector 扩展。

    怎么选

    四种落地方式，各自适合什么场景

    没有「最好」的方案，只有和场景匹配的方案。

    方案 适合场景 主要成本 关键限制 不推荐
    通用视觉模型
    ResNet / ViT 分类骨干    		 图像 domain 单一（如同类商品）、已有分类模型可复用、不需要跨模态检索 本地部署免费；需自行维护推理代码 向量空间为分类边界优化，语义相似度不够直观；无法图文匹配 需要以文搜图、类别高度开放的场景
    CLIP 类多模态模型
    open_clip / OpenAI CLIP    		 以图搜图 + 以文搜图都要、开放类别（zero-shot）、图像多样 模型较大（几百 MB～几 GB），依赖 GPU 推理 细粒度差异不够敏感；分辨率有限，会丢失细节 工业质检级别的微小瑕疵比对
    云 API
    embedding / 多模态 API    		 不想自建 GPU 服务、快速验证商业场景、调用量不大 按调用量计费，规模化后成本累积；有网络与合规依赖 无法自定义 / fine-tune 向量空间；依赖第三方可用性 图片涉及隐私不能出域、超大规模离线批处理
    轻量验证方案
    小模型 / pHash + 暴力搜索    		 概念验证、数据量小（几千张以内）、先验证思路能不能 work 几乎为零，几行代码即可跑通 语义理解弱（pHash 仅能应对近似重复），规模上不去 生产环境、需要真正语义级相似度的场景
    直接抄作业

    三个典型场景，这样选就对

    场景 A

    电商同款商品检索（图搜图）

    CLIP 类开源模型起步

    domain 相对聚焦，CLIP 通用权重通常已经够用；精度不够再考虑用对比学习在自己的商品图上 fine-tune，不需要一开始就依赖云 API。

    场景 B

    内容平台图文关联 / 审核

    CLIP 类多模态模型，几乎没有替代选项

    需求本身就是「图文能不能对应上」，只有让图片和文本共享同一向量空间的模型能直接做到——通用视觉模型或纯 OCR 都做不到这件事。

    场景 C

    快速验证内部工具原型

    云 API，或小模型 + numpy 暴力搜索

    数据量小、时间优先，不需要向量数据库和 ANN 索引；先用最简单的方式跑通逻辑，验证有效后再考虑规模化。

    一句话记住它

    心智模型回顾

    Image Embedding = 用一个预训练好的视觉网络，把图片压缩成一个方向（单位向量）—— 语义越像的图片，方向越接近。

    适合用它

    • 以图搜图 / 相似图检索
    • 图片去重、聚类
    • 给下游模型提供图像特征
    • 配合 CLIP 做图文跨模态检索

    不适合用它

    • 需要知道物体在图里的位置 → 用检测
    • 需要读出图里的文字 → 用 OCR
    • 需要一个固定的类别标签 → 用分类
    • 需要模型「说话」描述图片 → 用生成式 VLM
