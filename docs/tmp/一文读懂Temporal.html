01 ProblemStatement

先理解：Temporal 到底解决什么问题

从一个再普通不过的业务流程说起——用户下单之后发生的事：

PlaceOrder → ReserveInventory → ChargePayment → WaitForShipmentSignal → ShipOrder → SendReceipt

预订库存要调库存服务，扣款要调支付网关，发货要等仓库系统回调（可能几小时后才来），最后还要发收据邮件。类似的还有用户 onboarding、退款审批、数据处理管道——它们的共同点是：

  • 跨多个服务和外部系统：库存、支付、仓库、邮件，每一个都可能抽风；
  • 持续时间长：几秒、几小时、几天，甚至「等用户 30 天后续费」这种量级；
  • 中间步骤会失败：超时、网络抖动、下游 503、重复投递，还可能需要人工或外部事件介入；
  • 必须可恢复、可查询、可审计、可重试：客服要能查到「这单卡在哪一步」，事故后要能从断点继续，而不是从头重跑或者干脆丢单。

为什么普通做法会越写越复杂

大多数团队的演化路径是：先写同步代码 → 加消息队列解耦 → 加 cron 扫表补偿 → 在数据库里加 status 字段记录进度。每一步都合理，最终却拼出一个难以维护的系统：

  • 状态散落在多处——一部分在 DB 的 status 字段，一部分在队列里的消息，一部分在某个进程的内存中；
  • 重试和幂等逻辑到处都是——每个消费者都要自己写退避重试、去重、死信处理；
  • 失败恢复路径几乎无法测试——「进程在扣款成功但没记账之间崩了怎么办」这类分支很少被覆盖；
  • 流程进度难以可靠重建——排障时只能靠捞日志、拼消息、猜状态机走到了哪。

本质问题是：「流程走到哪一步了」这个状态没有一个单一、可靠、可恢复的事实来源。

Temporal 的一句话心智模型：用普通代码描述业务流程，由 Temporal 负责持久化进度、调度任务、失败恢复和长时间运行。你写「流程长什么样」，它保证「流程一定按这个样子走完或明确失败」。

02 DurableExecution

Durable Execution：Temporal 的核心抽象

Durable execution（持久化执行）的意思是：你可以像写普通函数一样写一个长流程——顺序调用、if/else、循环、await sleep(30天) ——而这个函数的执行进度本身被持久化了。进程崩溃、机器重启、网络断掉，函数都能「接着上次的位置」继续，而不是从头再来或永远丢失。

它不是内存快照

一个常见的想当然：「Temporal 大概是把进程内存 dump 下来，崩了再载入」。不是。Temporal 从不保存你的进程内存、栈或变量本身。它保存的是一份 Event History ——「这个流程发生过什么」的事件序列：Workflow 启动了、某个 Activity 被安排并返回了结果 X、某个 Timer 到期了、某个 Signal 到达了。

恢复时，新的 Worker 把你的 Workflow 代码重新从第一行跑一遍；每当代码走到「调用 Activity」「等 Timer」这类点位，SDK 发现 History 里已经有对应结果，就直接回放结果、不再真正执行外部操作。代码沿着同样的路径快速「重演」到崩溃前的位置，内部变量因此被重建——然后从那里真正继续。这就是 replay，第 5、6 章会展开它的机制和它对代码的约束。

这如何改变后端心智模型

  • 你写的是流程代码：业务顺序、分支、等待，直接用编程语言表达，不再翻译成状态机表或 DAG 配置；
  • Temporal 维护流程状态和执行历史：进度不在你的内存里，也不在你手写的 status 字段里；
  • Worker 可以挂掉再回来：Worker 是无状态的执行器，它的死活不影响流程的存亡，只影响流程推进的快慢。

把这条链路读顺，你就理解了 Temporal 的运行时形态：

  1. Client 发起 Workflow Execution，Temporal Service 写下第一个事件并安排一个 Workflow Task；
  2. Worker 从 Task Queue poll 到 Workflow Task，运行你的 Workflow 代码，直到代码做出下一个「决定」——安排 Activity、开 Timer、启动 Child Workflow，或停下来等 Signal；
  3. 这个决定交回 Service，落成事件；如果是 Activity，Service 再生成 Activity Task 放进 Task Queue；
  4. Worker poll 到 Activity Task，真正执行外部操作（HTTP、DB、支付网关），结果写回 Event History；
  5. Service 据此安排新的 Workflow Task，Workflow 依据历史继续推进；循环往复，直到完成、失败、取消，或继续长期等待。

注意「等待发货 Signal」那一步：Workflow 停在 await 上时，没有任何进程在为它空转——没有线程阻塞、没有轮询。它只是 Service 里的一条持久化状态，等几天都不消耗 Worker 资源。

05 HistoryReplayed

Event History 与 Replay：为什么能恢复

Event History 是一份 append-only 的事实记录：只追加、不修改，按顺序记下这个 Workflow Execution 发生过的一切。它不是「顺便打的日志」，而是 Temporal 恢复执行的唯一依据。

Replay 到底在做什么

当 Worker 崩溃、重启，或 Workflow 长时间等待后被再次唤醒时，接手的 Worker 手里只有两样东西：你的 Workflow 代码 和这份 Event History。它做的事叫 replay：

  • 重新运行代码：从 Workflow 函数第一行开始执行；
  • 已发生的结果从 History 回放：代码走到 await reserveInventory()，SDK 在 History 里找到 ActivityTaskCompleted，直接把当时的返回值塞回去，不会再调一次库存服务；Timer、Signal、随机数、时间取值同理；
  • 走到 History 尽头，才开始真正执行新东西：代码越过最后一个已记录事件后，接下来的 Activity 才会被真正安排。

replay 的目的只有一个：重建 Workflow 的内部状态（局部变量、走到哪个分支、等在哪个 await 上），从而让 Worker 崩溃后能继续、让进程重启和代码部署不打断流程、让「跑几个月的 Workflow」成为可能。

普通进程崩溃

  1. 变量、调用栈、进度全在内存里
  2. 进程死亡 → 内存清零
  3. 「扣款成功但没发货」这种中间态永久丢失
  4. 只能靠捞日志 + 人工修数据恢复

Temporal Workflow 恢复

  1. 每个决定和结果已作为事件落盘
  2. Worker 死亡 → History 完好无损
  3. 新 Worker replay History，重建到崩溃前的确切状态
  4. 从断点继续，外部副作用不重复执行
06 DeterminismRequired

Determinism：为什么 Workflow 代码不能随便写

Replay 有一个前提：同一份 Event History 回放时，代码必须做出一模一样的决策序列。如果第一次运行时代码安排了 Activity A，replay 时却因为「现在是周末」走了另一个分支去安排 Activity B，SDK 就无法把历史对上号——Workflow 会报 non-determinism 错误，无法正确恢复。

所以 Workflow 代码必须是 deterministic（确定性）的。这意味着不要在 Workflow 函数里直接做这些事：

  • 读当前时间（Date.now()、time.Now()）——每次 replay 都不一样；
  • 取随机数、生成随机 UUID；
  • 发网络请求、直接调数据库——这是副作用，replay 时会重复执行；
  • 读外部可变状态：环境变量、全局单例、文件、共享内存；
  • 依赖语言层面的非确定行为（比如无序 map 的遍历顺序、真实线程并发）。

这些事情不是不能做，而是要么放进 Activity（结果会被记录并回放），要么用 SDK 提供的 replay-safe 版本：Workflow 专用的当前时间（如 workflow.now()）、durable 的 sleep/Timer、sideEffect/确定性随机数，以及升级代码用的 versioning / patching API。

Determinism 检测卡 · 逐行判断：留在 Workflow，还是移到 Activity / 换 replay-safe API？

判定标准：这一行在两次 replay 中会不会产生不同的值或副作用？会 → 它不属于 Workflow 本体。

07 ActivityTaskScheduled

Workflow vs Activity：编排与副作用的边界

Workflow 负责「编排」

  • 决定步骤顺序、分支、循环
  • 保存业务流程状态（局部变量即状态）
  • 等待：Signal、Timer、条件
  • 安排 Activity、Timer、Child Workflow
  • 根据结果决定下一步（含补偿逻辑）

Activity 负责「干活」

  • 执行外部 I/O：HTTP、DB、message broker、payment API
  • 做一切可能失败、超时、需要重试的副作用
  • 可配置 retry policy 与各类 timeout
  • 长任务可以 heartbeat 汇报进度
  • 应设计为 idempotent（幂等）——因为它可能被重试

一个粗暴但好用的判断口径：「如果这行代码执行两次会出问题（重复扣款）或产生不同结果（当前时间），它就该是 Activity。」

08 TaskDispatched

Worker、Task Queue 与调度路径

Worker 是你部署和运行的进程——一个普通的服务，里面注册了 Workflow 和 Activity 代码。它不对外提供接口，只做一件事：长轮询（poll）Task Queue，拿到任务、执行、上报结果。Temporal Service 从不主动连接你的 Worker，这让 Worker 可以跑在任何能出网的环境里（内网、K8s、笔记本）。

任务分发路径是固定的四步：Service 产生 Task →放进 Task Queue → Worker poll 到 → 执行并回报。Task 分两种：

  • Workflow Task：「把这个 Workflow 的代码推进到下一个决策点」——执行的是编排逻辑；
  • Activity Task：「真正去执行这个外部副作用」——调 HTTP、写 DB 的就是它。
Worker 扩缩容模拟 · 拖动滑块，观察 backlog 与吞吐
TASK QUEUE BACKLOG

三个工程要点：

  • 扩容 = 加 Worker：每个 Worker 处理能力有限（这里假设 2 tasks/s），到达速率超过总能力时 backlog 增长，加 Worker 即可消化；
  • Task Queue 可以用来路由：GPU 任务一个队列、普通任务一个队列，不同 Worker 组各 poll 各的；
  • Worker 挂掉 ≠ Workflow 丢失：上面按「杀掉一个 Worker」试试——流程状态在 Service 的 Event History 里，任务只是暂时没人领，等 Worker 回来（或超时后重新入队）就继续。Worker 是牛，流程是账本；牛病了换一头，账本还在。
09 ActivityTaskFailed → Retrying

Retry、Timeout、Heartbeat：失败如何被建模

Temporal 不只是「自动重试」，而是把失败处理变成可配置、可观察的执行语义——你声明策略，Service 负责计时、调度和记账。核心配置有四个：

  • Retry Policy：失败后如何重试——初始间隔、退避倍数、最大间隔、最大尝试次数（Activity 默认无限重试，直到超时上限或被取消）；
  • Start-To-Close Timeout：单次尝试从开始执行到必须结束的最长时间，几乎总是应该设置；
  • Schedule-To-Start Timeout：任务从入队到被某个 Worker 领走的最长等待——用于检测「没有 Worker 在干活」；
  • Schedule-To-Close Timeout：整个 Activity Execution（含所有重试）的总耗时上限。

Heartbeat 是给长 Activity 用的：执行中定期向 Service 汇报「我还活着，进度到 X」。配合 heartbeat timeout，可以在几秒内发现卡死的 Worker 并触发重试，而不用等漫长的 Start-To-Close；重试的新尝试还能读到上次的 heartbeat details，从进度 X 继续而不是从零开始。

Retry / Timeout 时间线 · 调参数，看这个 Activity Execution 的命运

试试：① 把「实际耗时」拖到超过 startToCloseTimeout，看每次尝试都变成 timeout；② 把「注定失败次数」调到 ≥ maximumAttempts，看重试耗尽后 Workflow 收到最终失败。

幂等是你的责任。Activity「至少执行一次」而不是「恰好一次」——网络分区时，副作用可能已发生但结果没能上报，重试就会再来一遍。扣款、发货、发邮件这类操作必须用幂等键、去重表或对账机制兜住，否则「自动重试」会变成「自动重复扣款」。

11 TimerStarted

Timer、Schedule、Child Workflow：长流程如何组合

  • Timer——在 Workflow 里 await sleep("30 days")。这不是线程 sleep：Timer 是 Service 里的持久化事件，不依赖任何 Worker 进程活着；30 天里 Worker 可以升级、重启一百次，到点后 Service 照样触发 TimerFired，Workflow 继续。与普通 sleep 的区别：普通 sleep 占着线程且进程一死就没了。
  • Schedule——按计划定期启动新的 Workflow Execution（每天凌晨跑对账流程）。与 cron 的区别：cron 只负责「到点执行一条命令」，错过就错过、跑挂了不知道；Schedule 启动的是完整 Workflow，带重试、可查历史、可配置错过后的补跑与重叠策略。
  • Child Workflow——从一个 Workflow 里启动另一个 Workflow。与普通函数调用的区别：Child 有自己独立的 Event History、超时与重试语义和失败边界。适合拆分复杂流程（每个包裹一个配送子流程）、隔离失败（子流程失败不必拖垮父流程）、绕开单个 History 过长的问题。

12 NotAQueueNotACron

Temporal 与常见替代方案的区别

Temporal 经常被错认成某个单一组件。边界如下——注意每一行里两者解决的层次不同，很多时候是互补而非二选一：

对比它负责什么Temporal 的差别
Message queue
Kafka / RabbitMQ / SQS		可靠地传递任务和消息队列不知道「流程」的存在：多步状态、重试编排、超时、恢复、查询进度都要消费者自己写。Temporal 持久化流程状态、调度任务、内建 retry/恢复，并保留可查询的执行历史。Temporal 内部的 Task Queue 只是它的分发机制之一。
Cron定时触发一次执行cron 触发之后就不管了：跑挂、跑重、跑丢都无感知。Temporal 的 Schedule 触发的是带状态、可重试、可审计的长流程；且 Temporal 的主战场是「长流程本身」，定时只是入口之一。
Airflow数据工作流的 DAG 调度：批处理、ETL、按天分区的任务图Airflow 面向数据管道，DAG 结构静态、以调度周期为中心。Temporal 面向业务应用的 durable execution：流程即代码，支持任意分支/循环/等待外部事件、毫秒级启动、百万级并发实例（每个订单一个 execution）。
BPMN / Camunda图形化流程建模与执行BPMN 用图描述流程，适合业务人员参与建模；表达复杂逻辑要在图和代码间来回映射。Temporal 直接用通用语言写流程：版本控制、测试、code review 走软件工程的老路。
手写 saga / 状态机
DB status 字段 + 补偿		灵活，无新依赖手写方案要自己解决：状态持久化与一致性、崩溃恢复、重试退避、超时扫描、幂等去重、可观测——每个流程都重造一遍。Temporal 把这些收进统一运行时 + Event History；代价是引入新组件和 determinism 约束（第 15 章）。

14 VisibilityRecordUpserted

可观测性与运维入口

Event History 带来一个副产品：可观测性几乎是免费的。Temporal Web UI 开箱即可查看每个 Workflow Execution 的：当前状态（Running / Completed / Failed / …）、完整 Event History 时间线、每个 Activity 的 attempts 次数与失败原因堆栈、输入输出 payload、pending 中的 Activity 和 Timer。排障时不再拼日志——直接打开这条 execution，看它卡在哪个事件上。

Visibility / Search Attributes 解决另一个问题：几百万条 execution 里怎么找到目标？你可以给 Workflow 打上自定义可检索属性（如 customerId、orderAmount、region），然后用类 SQL 语法筛选：「所有金额大于 1 万、状态为 Running、卡了超过 1 天的订单流程」。运营巡检、客服排查、审计取证都走这个入口。

生产采用清单（入门先知道有这些事）

  • Namespace 隔离：按团队 / 环境 / 业务域划分 Workflow、Task Queue、配置与可见性边界；
  • Retention：已结束的 execution 的 History 保留多久，影响存储与审计；
  • Worker 部署与扩缩容：Worker 是你的服务，容量规划、灰度、监控（poll 成功率、task 延迟）都归你；
  • SDK 版本与 Workflow 代码演进：跑了一半的老 execution 还要按老逻辑 replay，改代码要用 versioning / patching 或 Worker Versioning 策略；
  • 数据加密与 payload converter：业务数据会存进 Event History，敏感字段应通过自定义 payload codec 加密后再落盘；
  • Temporal Cloud vs self-host：自托管要运维 Service 集群和数据库；Cloud 把平台层外包，Worker 仍然跑在你自己的环境里。
15 AdoptionDecision

工程实践：什么时候适合用 Temporal

适合

  • 长时间业务流程（分钟 → 数月）
  • 多步骤、跨服务、有外部副作用
  • 需要可靠重试、可恢复、可查询、可审计
  • 人工审批、等待外部事件、补偿（saga）逻辑
  • 典型场景：订单履约、支付与退款、用户 onboarding、订阅计费、基础设施编排

不适合或未必需要

  • 极简单的 fire-and-forget 异步任务（发个通知就完）
  • 纯 CPU 短任务、无流程状态需求
  • 只需要低延迟同步 RPC 的调用路径
  • 团队暂时无法接受新的运行时与编程约束

采用成本要说清楚：需要理解并遵守 determinism 约束（第 6 章）、为每个 Activity 设计幂等（第 9 章）、部署和运维 Worker 舰队、处理 Workflow 代码的版本演进，以及搭建或购买 Temporal Service 本身。这些都不难，但都不是零。

16 MisconceptionDetected

常见误区与反例

「Temporal 就是一个（高级）消息队列」
队列传递任务，不理解流程。Temporal 的核心资产是每个流程的状态与 Event History：多步编排、durable timer、replay 恢复、按属性检索 execution，这些都在队列的能力之外。Task Queue 只是它内部的分发部件。
「Temporal 就是 cron」
Schedule 确实能定时启动流程，但那只是入口。cron 触发后不负责执行的可靠性；Temporal 负责的恰恰是触发之后那段又长又容易失败的路。
「Workflow 里可以随便调用外部 API」
不行。Workflow 代码会被 replay 反复执行，直接调外部 API 会重复产生副作用、并破坏 determinism。所有外部 I/O 放进 Activity，由 History 记录结果、replay 时回放。
「Worker 挂了，Workflow 就丢了」
正相反。流程状态在 Temporal Service 的 Event History 里，Worker 只是无状态执行器。Worker 全挂只会让流程暂停推进，Worker 回来后 replay 继续。
「Event History 就是日志而已，和恢复关系不大」
History 不是给人看的副产品，而是恢复机制的核心输入：replay 靠它回放每个已完成步骤的结果，重建 Workflow 内部状态。删掉日志系统照常跑；删掉 History，流程无法恢复。
「Activity 会自动重试，所以不需要幂等」
恰恰因为会自动重试，才必须幂等。「执行成功但结果没上报」时重试会重复执行副作用。扣款要幂等键，发货要去重，邮件要防重发。
「用了 Temporal，所有失败都会自动消失」
Temporal 消化的是基础设施层面的失败（崩溃、超时、网络抖动）。业务层面的失败——支付被拒、库存不足、审批驳回——仍然需要你在 Workflow 里显式建模：分支、补偿（退款、释放库存）、人工介入。
「Temporal 只能跑短任务」
相反，长流程才是主场：Timer 可以等几个月，execution 可以跑一年，等待期间不占用任何 Worker 资源；超长流程还可用 Continue-As-New 滚动开新 History。
「用了 Temporal 就不需要数据库 / 业务状态了」
Temporal 管的是流程状态（这单走到哪一步）。订单金额、库存数量、用户资料这些领域数据仍然属于你的业务数据库；Activity 负责读写它们。两者是分工，不是替代。
17 MinimalExample

最小代码示例（TypeScript SDK）

四段代码对应四个角色。目标是服务理解，不是生产项目——省略了错误分类、测试和部署细节。

① Workflow —— 编排逻辑，只能写确定性代码

// workflows.ts —— 运行在 Worker 里，会被 replay 反复执行
import { proxyActivities, defineSignal, defineQuery,
         setHandler, condition } from '@temporalio/workflow';
import type * as acts from './activities';

// 通过 proxy 调 Activity，并在这里声明 timeout / retry 策略
const { reserveInventory, chargePayment, shipOrder, sendReceipt } =
  proxyActivities<typeof acts>({
    startToCloseTimeout: '30 seconds',
    retry: { initialInterval: '1s', backoffCoefficient: 2, maximumAttempts: 5 },
  });

export const shipmentSignal = defineSignal('shipmentReady');
export const statusQuery   = defineQuery<string>('status');

export async function orderWorkflow(orderId: string) {
  let status = 'PLACED';                 // 局部变量就是流程状态，replay 时自动重建
  let shipped = false;
  setHandler(statusQuery, () => status);  // Query：只读，不写 History
  setHandler(shipmentSignal, () => { shipped = true; });

  // ✗ 这里不能：Date.now() / Math.random() / fetch() / 直接查 DB
  // ✓ 不确定操作与外部 I/O 一律进 Activity
  await reserveInventory(orderId);  status = 'RESERVED';
  await chargePayment(orderId);     status = 'PAID';
  await condition(() => shipped);   // durable 等待 Signal，可等数天，不占线程
  await shipOrder(orderId);         status = 'SHIPPED';
  await sendReceipt(orderId);
  return (status = 'DONE');
}

③ Worker —— 你部署的进程，poll Task Queue

// worker.ts —— 部署几份都行；挂掉不影响流程存亡
import { Worker } from '@temporalio/worker';
import * as activities from './activities';

const worker = await Worker.create({
  workflowsPath: require.resolve('./workflows'),
  activities,
  taskQueue: 'orders',   // 只处理这条 Task Queue 上的任务
});
await worker.run();        // 开始长轮询

④ Client —— 启动、Signal、Query

// client.ts —— 在任何服务里（如 API 网关）调用
import { Client } from '@temporalio/client';
import { orderWorkflow, shipmentSignal, statusQuery } from './workflows';

const client = new Client();
const handle = await client.workflow.start(orderWorkflow, {
  taskQueue: 'orders',
  workflowId: 'order-1001',       // 业务 ID 即 Workflow ID，天然去重
  args: ['order-1001'],
});

console.log(await handle.query(statusQuery));  // → "PAID"（同步读状态）
await handle.signal(shipmentSignal);            // 仓库回调 → 流程继续

18 CheatSheet

Temporal 概念与职责速查表

概念一句话职责它不负责 / 最易混淆点
Durable Execution代码执行进度被持久化，崩溃后按历史恢复继续不是内存快照；靠 Event History + replay
Temporal Service持久化 History、维护状态、生成与调度 Task、执行 timer/retry 计时不运行你的业务代码
Temporal Clientstart / signal / query / update / cancel / terminate Workflow不执行流程本身
Workflow Definition你写的流程代码（编排、状态、等待）必须 deterministic，不做外部 I/O
Workflow Execution某次实际运行的流程实例，有唯一 Workflow ID≠ Definition；一份代码百万实例
Activity执行外部副作用与不确定操作，可配 retry/timeout/heartbeat至少一次执行 → 必须设计幂等
Worker你部署的进程：poll Task Queue，执行 Workflow/Activity 代码无状态；挂掉 ≠ 流程丢失
Task Queue分发 Workflow Task / Activity Task 给 Worker 的逻辑队列不存流程状态；不是「Temporal 就是队列」的证据
Event Historyappend-only 事实来源；replay 的输入；审计与排障的依据不是普通日志，删了就无法恢复
Replay / Determinism重跑代码 + 回放历史结果，重建内部状态不重复执行已记录的副作用；要求代码确定性
Retry Policy / Timeout声明式失败语义：间隔、退避、次数、四类超时不消化业务失败；补偿要自己建模
Signal / Query / Update写事件（异步）/ 读状态（不入史）/ 校验式变更（有返回）Query 不得有副作用；Signal 无返回值
Timer / Schedule / Child WFdurable 等待 / 定期启动流程 / 子流程隔离与组合≠ sleep / cron / 函数调用
Namespace隔离 Workflow、Task Queue、配置与可见性—
Visibility / Search Attributes按自定义属性检索、筛选 execution用于找到流程，不是流程状态本身

收束回主线：Temporal 让长时间、易失败、多步骤的业务流程可靠运行，方式是——你用普通代码写流程（Workflow），把副作用装进可重试的 Activity，由你部署的 Worker 执行；Temporal Service 把每一步写进 append-only 的 Event History，任何组件崩溃后都能 replay 历史、恢复到正确状态继续。排队只是手段，历史才是核心。
