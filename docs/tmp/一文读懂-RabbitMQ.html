核心模型

三件套之前，还有三层连接抽象

RabbitMQ 用 AMQP 0-9-1 协议。你和它打交道时，会经过 Virtual Host → Connection → Channel 三层，理解这三层才能理解为什么代码要那样写。点击各行查看详情。

📮
Virtual Host (vhost)
完全隔离的命名空间，等于一个独立的 RabbitMQ 实例
🔌
Connection
一条 TCP 长连接，建立开销大，应复用
📡
Channel
Connection 内的虚拟轻量通道，实际操作都在 Channel 上
Virtual Host 是 RabbitMQ 里的多租户单元。不同应用（如 staging/production）部署在同一个 RabbitMQ 实例时，各自使用不同 vhost，Exchange/Queue/Binding 互不可见，权限独立管理。默认 vhost 是 /。

类比：一栋邮政大楼（RabbitMQ 实例）里有多个独立的营业厅（vhost），每个厅有自己的前台、分拣系统和信箱墙，互不干扰。

Producer → Exchange → Queue → Consumer：核心数据流

最重要的一句话：Producer 从不直接向 Queue 发消息。它只跟 Exchange 说话，由 Exchange 根据路由规则决定消息去哪里。Queue 对 Producer 不可见。 
import pika

# 1. 建立连接（TCP，开销大，生产中应复用）
connection = pika.BlockingConnection(
    pika.ConnectionParameters(
        host='localhost',
        port=5672,
        virtual_host='/',
        credentials=pika.PlainCredentials('guest', 'guest'),
        heartbeat=60,            # 心跳（秒），防断连
        blocked_connection_timeout=300
    )
)

# 2. 开 Channel（轻量，同一 Connection 可开多个）
channel = connection.channel()

# 3. 发消息到 exchange，带 routing_key
channel.basic_publish(
    exchange='order_events',    # 目标 exchange
    routing_key='order.created', # 路由键
    body=b'{"order_id": 42}',
    properties=pika.BasicProperties(
        delivery_mode=2,        # 2=持久化，1=不持久
        content_type='application/json',
        message_id='msg-uuid-001',
    )
)
connection.close()
📌 delivery_mode=2 只是消息层的持久化声明，还需要 exchange 和 queue 都是 durable 才真正不丢
import pika

connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()

# 设置预取数量（QoS）：每次最多给我 1 条，处理完再要下一条
channel.basic_qos(prefetch_count=1)

# 回调函数：每收到一条消息就调用一次
def on_message(channel, method, properties, body):
    print(f"收到: {body}")
    print(f"routing_key: {method.routing_key}")
    print(f"delivery_tag: {method.delivery_tag}")

    # 手动 ack：告诉 broker 这条消息处理完了，可以删除
    channel.basic_ack(delivery_tag=method.delivery_tag)

    # 如果处理失败，nack 并重新入队
    # channel.basic_nack(delivery_tag=method.delivery_tag, requeue=True)

# 注册消费，auto_ack=False = 手动确认模式
channel.basic_consume(
    queue='order_queue',
    on_message_callback=on_message,
    auto_ack=False          # ⚠️ 生产中务必 False
)

print('等待消息...')
channel.start_consuming()  # 阻塞，持续消费
📌 auto_ack=True 时消息从 broker 推出去的瞬间就被删除，consumer 崩溃则消息丢失
# 声明 Exchange、Queue、Binding（幂等，不存在则创建，存在则验证）
channel.exchange_declare(
    exchange='order_events',
    exchange_type='topic',
    durable=True,          # broker 重启后保留
    auto_delete=False,      # 没有绑定时不自动删除
)

channel.queue_declare(
    queue='order_queue',
    durable=True,          # 持久化队列
    exclusive=False,        # True=仅当前 connection 可用，断连后删除
    auto_delete=False,
    arguments={
        'x-message-ttl': 86400000,         # 消息 24h 过期（毫秒）
        'x-dead-letter-exchange': 'dlx',    # 死信转发到 dlx
        'x-max-length': 10000,              # 队列最多 1 万条
    }
)

# 绑定：让 order.# 路由到 order_queue
channel.queue_bind(
    queue='order_queue',
    exchange='order_events',
    routing_key='order.#'   # topic 模式：# 匹配零或多个词
)
📌 声明是幂等的。Consumer 和 Producer 都应该在启动时声明，谁先启动都不会出错
路由核心

Exchange 是邮局的分拣规则

Exchange 本身不存储消息，它只负责路由——按规则把消息转发到一个或多个 Queue。不同 Exchange 类型，就是不同的分拣规则。

精确匹配路由键

消息只投递到 binding_key 与 routing_key 完全相同的队列。最常用，也最好理解。

精确匹配
1对1 或 N对1

一个 queue 可以绑多个 routing key；多个 queue 也可以绑同一个 key（广播效果）。

使用场景
任务分发、明确类型的事件路由、RPC 回调队列
# Direct exchange 示例
channel.exchange_declare('logs', 'direct', durable=True)

# 两个队列绑定不同的 routing_key
channel.queue_bind('error_queue', 'logs', 'error')
channel.queue_bind('info_queue',  'logs', 'info')
channel.queue_bind('info_queue',  'logs', 'warning')

# 发送 routing_key='error' → 只去 error_queue
channel.basic_publish('logs', 'error', b'disk full')

# 发送 routing_key='info' → 只去 info_queue
channel.basic_publish('logs', 'info', b'server started')

# 发送 routing_key='debug' → 没有队列绑定，消息丢弃！
# （除非设置了 mandatory=True 或有 alternate exchange）
⚠️ 如果 routing_key 没有任何 binding 匹配，消息会被 broker 丢弃（或 mandatory=True 时返回给 producer）

广播：无视 routing_key

消息投递到所有绑定的队列，完全忽略 routing_key（写什么都一样）。

广播
1 → N
常见误区：fanout 并非"发多少份"——它只发一条消息，但路由到多个队列。每个队列里各有一份副本。
使用场景：实时通知推送、缓存失效广播、日志多点存储 
# Fanout exchange：routing_key 无效
channel.exchange_declare('notifications', 'fanout', durable=True)

# 三个不同的服务各自绑一个队列
channel.queue_bind('push_queue',   'notifications', routing_key='')
channel.queue_bind('email_queue',  'notifications', routing_key='')
channel.queue_bind('audit_queue',  'notifications', routing_key='')

# 发一条，三个队列都收到
channel.basic_publish(
    exchange='notifications',
    routing_key='',  # fanout 下写什么都无效
    body=b'user_login:user_42'
)
# → push_queue, email_queue, audit_queue 各得一份
如果此刻没有任何队列绑定 fanout exchange，消息被静默丢弃

通配符模式匹配

routing_key 是用 . 分隔的词组，binding_key 可以含通配符：

* 匹配 恰好一个词
# 匹配 零个或多个词
通配符
灵活分层
使用场景：日志分级路由（logs.*.error）、多维度事件过滤 
# Topic exchange：通配符路由
channel.exchange_declare('events', 'topic', durable=True)

channel.queue_bind('all_logs',    'events', 'logs.#')
channel.queue_bind('error_logs',  'events', 'logs.*.error')
channel.queue_bind('app_events',  'events', 'app.*')

# 消息路由结果：
# routing_key='logs.app.error' → all_logs, error_logs
# routing_key='logs.db.error'  → all_logs, error_logs
# routing_key='logs.app.info'  → all_logs（不匹配 *.error）
# routing_key='app.login'      → app_events
# routing_key='logs'           → all_logs（# 匹配零个词）
# routing_key='payment.done'   → 无匹配，消息丢弃

channel.basic_publish('events', 'logs.app.error', b'NullPointerException')
topic exchange 可以模拟 direct（不用通配符）和 fanout（binding_key="#"）的行为

按消息头属性路由

忽略 routing_key，改为匹配消息的 headers 字典。binding 时用 x-match: all（AND）或 x-match: any（OR）控制匹配逻辑。

按属性
AND / OR
实际中较少使用。headers exchange 功能强大但性能较差（需要解析消息头），大多数场景用 topic 就够了。适合：需要多维度条件路由，且维度多于一两个时。 
# Headers exchange：按消息属性路由
channel.exchange_declare('file_events', 'headers', durable=True)

# x-match: all = 必须 format=pdf AND action=upload 都满足
channel.queue_bind(
    queue='pdf_uploads',
    exchange='file_events',
    routing_key='',  # 忽略
    arguments={
        'x-match': 'all',
        'format': 'pdf',
        'action': 'upload',
    }
)

# 发消息时在 headers 里带属性
channel.basic_publish(
    exchange='file_events',
    routing_key='',
    body=b'file data...',
    properties=pika.BasicProperties(
        headers={'format': 'pdf', 'action': 'upload'}
    )
)  # → 命中 pdf_uploads
headers exchange 的 binding_key 参数写什么都没用，关键在 arguments 字典里的 x-match

隐藏的 direct exchange

每个 RabbitMQ 都有一个名为 ""（空字符串） 的 default exchange，类型是 direct。每个 queue 声明后，自动绑定到 default exchange，binding key = queue 名。

名称=""
自动绑定
为什么你一开始觉得 RabbitMQ 很简单？因为初学例子直接向 exchange="" 发消息，routing_key=队列名，消息就到了队列——这绕开了整套路由系统，让人误以为消息是"直接发给队列"的。 
# 初学例子常用写法（via default exchange）
channel.queue_declare(queue='hello')

channel.basic_publish(
    exchange='',         # 空字符串 = default exchange
    routing_key='hello', # routing_key = 队列名时，消息到该队列
    body=b'Hello World!'
)

# 这背后发生了什么：
# 1. queue_declare('hello') 自动创建了:
#    default_exchange --[binding: "hello"]--> queue "hello"
# 2. basic_publish 到 default exchange + rk='hello'
#    → 匹配到 binding "hello" → 消息进入 queue "hello"

# ⚠️ 不能手动向 default exchange 添加 binding
# ⚠️ 不能删除 default exchange
生产代码里请避免使用 default exchange，明确声明你的 exchange 和 binding，代码意图更清晰
队列深入

Queue 不只是个列表

Queue 的属性决定了它的行为边界。这里有几个参数的组合，弄错了会在生产环境里留下隐患。

声明参数

参数含义默认
durablebroker 重启后队列是否保留False
exclusive仅限当前 connection，断连后删除False
auto_delete最后一个 consumer 断开后删除False
passive仅检查是否存在，不创建False

x-arguments（扩展行为）

参数含义
x-message-ttl队列里消息的过期时间（毫秒）
x-expires队列本身的空闲过期时间（毫秒）
x-max-length最大消息条数，超出按策略处理

持久化的三层陷阱：要实现消息不丢失，需要同时满足 ① exchange durable=True ② queue durable=True ③ 消息 delivery_mode=2。三个条件缺一不可。很多人只设了队列持久化，忘了消息本身。

Dead Letter Exchange（DLX）——消息的最终归宿

消息在以下情况变成"死信"：被 nack/reject 且 requeue=False、TTL 过期、队列达到最大长度。死信不会消失，而是被转发到配置的 DLX，从而可以被监控、重试或人工处理。

# 1. 声明死信处理 exchange 和队列
channel.exchange_declare('dlx', 'direct', durable=True)
channel.queue_declare('dead_letter_queue', durable=True)
channel.queue_bind('dead_letter_queue', 'dlx', routing_key='failed')

# 2. 业务队列：配置 DLX 和 TTL
channel.queue_declare(
    queue='order_queue', durable=True,
    arguments={
        'x-dead-letter-exchange': 'dlx',
        'x-dead-letter-routing-key': 'failed', # 可选
        'x-message-ttl': 30000,  # 30s 未消费 → 死信
        'x-max-length': 5000,    # 超出则最老消息 → 死信
    }
)

# 3. consumer 处理失败时主动 nack 并不重入队
def on_message(ch, method, props, body):
    try:
        process(body)
        ch.basic_ack(method.delivery_tag)
    except PermanentError:
        # requeue=False → 触发死信流转
        ch.basic_nack(method.delivery_tag, requeue=False)
死信队列最好有独立的监控和告警，它是生产问题的"最后一道防线"
# 延迟重试模式：利用 TTL + DLX 实现"30s 后重试"

# 1. 等待队列：消息在这里等待 TTL 到期
channel.queue_declare(
    queue='order_wait_queue', durable=True,
    arguments={
        'x-message-ttl': 30000,          # 30s 后过期
        'x-dead-letter-exchange': 'orders', # 过期后→业务 exchange
        'x-dead-letter-routing-key': 'order.retry',
        # ⚠️ 等待队列不要绑 consumer！
    }
)

# 2. 业务失败时，把消息发到等待队列
def on_message(ch, method, props, body):
    retry_count = props.headers.get('x-retry-count', 0)
    try:
        process(body)
        ch.basic_ack(method.delivery_tag)
    except TemporaryError:
        ch.basic_ack(method.delivery_tag)  # ack 原消息
        if retry_count < 3:
            # 发到等待队列，30s 后重新进入业务队列
            ch.basic_publish(
                exchange='', routing_key='order_wait_queue',
                body=body,
                properties=pika.BasicProperties(
                    headers={'x-retry-count': retry_count + 1},
                    delivery_mode=2
                )
            )
        else:
            # 超过重试次数，发到死信队列
            ch.basic_publish('dlx', 'failed', body)
这是在 RabbitMQ 里实现延迟重试的经典方法，不依赖 rabbitmq-delayed-message-exchange 插件
可靠性基础

消息确认：谁保证消息不丢

RabbitMQ 的"至少一次"投递保证，依赖两个方向的确认：Consumer 告诉 broker 消息处理完了（consumer ack），Producer 确认 broker 收到了消息（publisher confirm）。两个方向都有坑。

Unacked
Acked
Nacked
Rejected
Dead Letter
Unacked（已投递未确认）
Broker 已将消息推送给 consumer，但还没收到 ack。消息此时同时存在于 broker 和 consumer（逻辑上的"飞行中"状态）。如果 consumer 断连，broker 会把这条消息重新入队，投递给其他 consumer。
channel.basic_consume(queue, callback, auto_ack=False) # 手动 ack 模式

QoS / prefetch_count：流量控制的关键

prefetch_count

限制未 ack 消息数量

告诉 broker "每次最多给我 N 条"，处理并 ack 完一条后，才能收到下一条。

# 每次最多拿 1 条（最保守，适合重任务）
channel.basic_qos(prefetch_count=1)

# 允许预取 10 条（吞吐量更高）
channel.basic_qos(prefetch_count=10)
⚠ prefetch_count=0（默认）

无限预取——危险！

broker 会把队列里所有消息都推给第一个连上的 consumer，后来的 consumer 收不到任何消息。

多个 worker 时，务必设置 prefetch_count，否则负载完全不均衡。

Publisher Confirms：发布端的保证

默认情况下，basic_publish 是"fire and forget"——broker 收没收到，你不知道。开启 Publisher Confirms 后，broker 会对每条消息回一个 ack/nack。

# 开启 Publisher Confirms
channel.confirm_delivery()

try:
    channel.basic_publish(
        exchange='orders',
        routing_key='order.created',
        body=b'{"id":42}',
        properties=pika.BasicProperties(delivery_mode=2),
        mandatory=True  # 无匹配路由时返回给 producer 而非丢弃
    )
    print('Broker 已确认接收')
except pika.exceptions.UnroutableError:
    print('消息无法路由！')
except pika.exceptions.NackError:
    print('Broker 拒绝了消息（内部错误？）')
同步确认会阻塞，吞吐量低但代码简单。生产高吞吐场景用异步确认
import threading

# 开启异步确认
channel.confirm_delivery(
    ack_nack_callback=lambda method: print(f'Broker 回复: {method}')
)

# 用字典跟踪未确认的消息
unconfirmed = {}
delivery_tag = 1

def publish(body):
    global delivery_tag
    unconfirmed[delivery_tag] = body
    channel.basic_publish('orders', 'order.created', body,
        properties=pika.BasicProperties(delivery_mode=2))
    delivery_tag += 1

def on_ack(method):
    if method.NAME == 'Basic.Ack':
        unconfirmed.pop(method.delivery_tag, None)
    elif method.NAME == 'Basic.Nack':
        body = unconfirmed.pop(method.delivery_tag, None)
        if body: republish(body)  # 重发
异步确认适合高吞吐批量发送，需要自己跟踪未确认的消息

上生产前的可靠性检查

点击每一项确认你已经处理。所有项都勾选，才算做了基本的可靠性保证。

✓
Exchange 声明了 durable=True broker 重启后 exchange 依然存在，否则消息无法投递
✓
Queue 声明了 durable=True broker 重启后队列和其中消息依然存在
✓
消息发布时设置 delivery_mode=2（持久化） exchange + queue durable 还不够，消息本身也要持久化
✓
Consumer 使用 auto_ack=False（手动确认） 任务处理完成后再 ack；处理失败时 nack(requeue=True/False)
✓

✓
配置了 Dead Letter Exchange（DLX） 失败/过期消息有地方收，而不是静默丢弃
✓
开启了 Publisher Confirms（高可靠场景） 确认 broker 真的收到了消息，而不是 fire and forget
✓
Consumer 幂等（允许重复投递） broker 在网络抖动后可能重发同一条消息，consumer 必须能处理重复
✓
Connection 配置了心跳和重连逻辑 heartbeat 防止 broker 或中间件超时断连；应用层需要自动重连
✓
使用 Quorum Queue（RabbitMQ 3.8+）代替 Classic Mirrored Queue Quorum Queue 基于 Raft，数据安全性更强，是新项目的推荐选择
常用模式

三个你会反复用到的消息模式

⚡ Work Queue（任务分发）多个 worker 竞争消费，负载均衡 ▶

同一队列绑多个 consumer，broker 轮流分发（round-robin）。配合 prefetch_count=1 实现能者多劳（处理快的 worker 拿更多消息）。

# Consumer（多个实例并行运行）
channel.basic_qos(prefetch_count=1)

def do_work(ch, method, props, body):
    import time
    time.sleep(body.count(b'.'))  # 模拟耗时
    ch.basic_ack(method.delivery_tag)

channel.basic_consume('task_queue', do_work, auto_ack=False)
channel.start_consuming()
# Producer
channel.queue_declare('task_queue', durable=True)

for i in range(10):
    channel.basic_publish(
        exchange='', routing_key='task_queue',
        body=f'task {i}...'.encode(),
        properties=pika.BasicProperties(delivery_mode=2)
    )
# 启动多个 consumer 进程，消息被均衡分发
prefetch_count=1 让慢 worker 不会被撑死，快 worker 能做更多工作——这是 Work Queue 的灵魂设置。
📢 Pub/Sub（发布订阅）一条消息广播给所有订阅者 ▶

每个 subscriber 声明一个独占的、临时的队列，绑到 fanout exchange。消息发到 exchange，所有在线 subscriber 各得一份。

# Subscriber（每个实例独立的临时队列）
channel.exchange_declare('news', 'fanout')

# 独占队列：不指定名字，broker 自动生成；断连后自动删除
result = channel.queue_declare(queue='', exclusive=True)
queue_name = result.method.queue  # 形如 'amq.gen-xyz123'

channel.queue_bind(queue_name, 'news')
channel.basic_consume(queue_name, lambda ch,m,p,b: print(b), auto_ack=True)
channel.start_consuming()

# Publisher
channel.basic_publish('news', routing_key='', body=b'Breaking news!')
# → 所有在线 subscriber 各收一份。离线的 subscriber 收不到历史消息
Pub/Sub 中的临时队列不持久化——subscriber 离线期间的消息会丢失。如果需要"离线也能补发"，要用持久队列，并用不同消费者组区分。
🔁 RPC（请求-响应）通过消息实现同步调用语义 ▶

RPC 的关键是两个字段：reply_to（回调队列名）和 correlation_id（请求 ID，用于匹配响应和请求）。

# RPC Client
import uuid

# 独占回调队列
cb = channel.queue_declare('', exclusive=True)
callback_queue = cb.method.queue

corr_id = str(uuid.uuid4())
response = None

def on_response(ch, m, props, body):
    global response
    if props.correlation_id == corr_id:
        response = body

channel.basic_consume(callback_queue, on_response, auto_ack=True)

channel.basic_publish(
    exchange='', routing_key='rpc_queue',
    body=b'30',  # 参数
    properties=pika.BasicProperties(
        reply_to=callback_queue,
        correlation_id=corr_id,
    )
)
while response is None:
    connection.process_data_events()
print(f'结果: {response}')
# RPC Server
channel.queue_declare('rpc_queue')

def fibonacci(n):
    if n == 0: return 0
    if n == 1: return 1
    return fibonacci(n-2) + fibonacci(n-1)

def on_request(ch, m, props, body):
    result = fibonacci(int(body))
    # 把结果发回 reply_to 队列
    ch.basic_publish(
        exchange='', routing_key=props.reply_to,
        body=str(result).encode(),
        properties=pika.BasicProperties(
            correlation_id=props.correlation_id
        )
    )
    ch.basic_ack(m.delivery_tag)

channel.basic_qos(prefetch_count=1)
channel.basic_consume('rpc_queue', on_request)
channel.start_consuming()
对比与选型

为什么不用 Redis List 做消息队列

Redis List（LPUSH/BRPOP）可以做简单队列，Kafka 适合流处理，RabbitMQ 在中间——它适合的是"需要复杂路由和可靠投递的任务分发"。

能力 RabbitMQ Redis List/Streams Kafka
消息路由 ✓ Exchange 4 种路由规则 ✗ 只能点对点 △ Topic/Partition
消息确认（ack） ✓ 内置 ack/nack △ Streams 支持 ✓ offset commit
消息持久化 ✓ 三层持久化 △ RDB/AOF，非专为队列 ✓ 磁盘存储，可回放
消息回放 ✗ 消费即删除 △ Streams 支持 ✓ 核心能力
复杂 workflow ✓ DLX、延迟、优先级 ✗ 需自建 ✗ 需自建
吞吐量 △ 万级/s（带 ack） ✓ 十万级/s ✓ 百万级/s
运维复杂度 △ 中等（需管理 vhost/exchange/binding） ✓ 低（已有 Redis） ✗ 高（ZK/KRaft + 集群）
适合场景 任务分发、事件路由、RPC、工作流 简单任务队列、缓存辅助队列 日志采集、事件溯源、大数据管道
选 RabbitMQ 的理由
  • ✓消息需要按类型路由到不同处理器
  • ✓需要可靠的"至少一次"投递保证
  • ✓需要 DLX、延迟重试、优先级队列
  • ✓已有团队，熟悉 AMQP 生态
  • ✓Celery/Dramatiq 的默认 broker
考虑其他方案的情况
  • ✗需要消息回放/事件溯源 → Kafka
  • ✗已有 Redis，任务很简单 → Redis Streams
  • ✗吞吐量 > 几十万/s → Kafka/Pulsar
  • ✗不想管理额外基础设施 → 云原生 SQS/Pub-Sub

常见误区汇总

!Exchange 存储消息 （错误）▶

Exchange 只做路由，不存储任何消息。如果消息无法匹配任何绑定，会被丢弃（或 mandatory=True 时退回给 producer）。只有 Queue 存储消息。

!durable queue 就能保证消息不丢 （不够）▶

durable 只保证队列结构在重启后存在。消息本身必须也设置 delivery_mode=2 才会持久化到磁盘。另外，消息在内存缓冲区到磁盘之间有一个短暂的窗口期，极端情况下仍可能丢失——Quorum Queue 通过多副本 Raft 日志解决这个问题。

!auto_ack=True 更高效，应该用 （危险权衡）▶

auto_ack=True 时消息在 broker 推给 consumer 的瞬间就被删除，consumer 崩溃会导致消息丢失。吞吐量确实略高，但只适用于"允许丢消息"的场景（如实时日志）。任何需要保证处理的场景都应用手动 ack。

!fanout exchange 会"复制"消息，增加 N 倍存储 （部分正确）▶

fanout 确实会在每个绑定的 queue 里放一份消息，但 RabbitMQ 内部会尽量共享消息体（reference counting），不一定是 N 份物理拷贝。不过从应用层角度，每个 queue 各自独立持有一份，管理上确实是 N 份。

!一个 Connection 开很多 Channel，Channel 数量无所谓 （有上限）▶

Channel 虽然轻量，但每个 Channel 都占用服务器内存，且 AMQP 协议层有 channel-max 限制（默认 65535）。更重要的是，Channel 不是线程安全的，多线程应用中每个线程应独立持有一个 Channel（但可以共享 Connection）。
