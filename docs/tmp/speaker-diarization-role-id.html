给一段视频，
切出「谁在什么时候说话」，
再判定「他是什么角色」

Speaker Diarization 回答 who spoke when，输出的是匿名标签 SPEAKER_00；Speaker Role Identification 把匿名标签映射到业务角色——面试官/候选人、医生/患者、坐席/客户。这是两个任务，用的是两套方法、两套指标，也在两个不同的阶段失败。

把指针移到色块上，或用 Tab 键聚焦，看这一段的结构化输出。
SPEAKER_00 SPEAKER_01 SPEAKER_02 overlap（重叠语音）

全文以「线上面试录像 → 结构化面试纪要」为主线例子。医患问诊、客服质检、庭审记录、课堂分析的链路几乎一致，差别只在角色定义、隐私约束和验收口径，文中会分别标出。

00:00

先把能力边界钉死

这个能力最容易翻车的地方不在模型，而在一开始没说清它到底交付什么。

IN输入

一个视频文件（mp4/mov），可能带多路音轨。真正被用到的通常只有一条 16kHz 单声道 PCM。画面在基础方案里完全不参与，只有在做视听融合时才有用。

OUT输出

一个分段列表：[{start, end, speaker, role, text}]。speaker 是聚类出的匿名标签，role 是映射后的业务角色，text 来自 ASR，是可选的第三方能力。

它解决什么

  • 分段与聚类：把连续音频切成语音片段，并把属于同一个人的片段聚到同一个标签下。片段数、说话人数都可能是未知的。
  • 角色映射：把 SPEAKER_01 判定为「候选人」，让下游能按角色统计——候选人说话占比、面试官提问数量、患者主诉片段。

它明确不解决

  • 不是 speaker identification（声纹身份认证）。diarization 不知道这个人是张三，它只知道「这几段是同一个人」。要认到具体的人，需要事先注册的声纹库，那是另一个任务，也是另一套合规要求。
  • 不是 ASR。它不产出文字。文字要么不需要，要么由 Whisper/云 ASR 提供，再和分段对齐。
  • 不做语义理解。「这场面试通过与否」是下游 LLM 的事，diarization 只提供带角色的结构化文本。
  • 不保证跨文件一致。同一个人在两个视频里会拿到不同的 SPEAKER_00。跨会议追同一个人需要额外的声纹检索层。

成功标准长什么样

不要用「跑通了」当验收。这个能力的验收至少三条同时成立：分段边界和说话人归属的错误率（DER）在可接受区间；角色映射在真实数据上的准确率达标；单位时长的处理成本和延迟在预算内。三条中任意一条塌了，下游的纪要、质检、统计全部不可信。

动手前先问一句：这段音频真的需要 diarization 吗？

如果录制源本身就分轨——客服系统的双声道录音（坐席一路、客户一路）、会议平台导出的每人独立音轨（多数云会议录制支持按参会者分文件）、多人各戴一支麦克风——那么说话人归属是已知的，直接按 channel 或按文件切分即可，DER 恒等于 0，角色也直接来自平台元数据。花力气去 diarize 一段本来就分好轨的音频，是这个领域里最常见的浪费。先去查录制源。

01:00

最小可跑链路：一个下午，一个脚本

第一版不要服务、不要数据库、不要队列。目标只有一个：拿 3~5 段真实视频，跑出一份带角色的 JSON，然后人眼看它错在哪。下面五步就是全部。

MINIMAL PIPELINE · run_once.py
# 1) 抽音频。所有 diarization 模型的通用输入都是 16kHz 单声道 PCM。
#    直接喂 mp4 多数库也能跑，但显式抽一次，失败点才清楚。
import subprocess, pathlib

def extract_audio(video: str, wav: str) -> str:
    cmd = ["ffmpeg", "-y", "-i", video,
           "-vn",                 # 丢掉视频流
           "-ac", "1",             # 单声道（先确认源不是分轨的！）
           "-ar", "16000",         # 16kHz，模型的训练采样率
           "-c:a", "pcm_s16le", wav]
    subprocess.run(cmd, check=True)   # 解码失败直接抛，不要吞
    return wav

wav = extract_audio("interview_001.mp4", "work/interview_001.wav")

先确认原始视频是不是多音轨。ffprobe 一行就能看：如果每个参会者一条轨，后面四步全都不用做。

# 2) diarization。这一步只回答 who spoke when，不产生任何文字。
from pyannote.audio import Pipeline
import torch

pipeline = Pipeline.from_pretrained(
    "pyannote/speaker-diarization-3.1",
    use_auth_token=HF_TOKEN,      # 需先在模型页面接受使用条款
)
pipeline.to(torch.device("cuda"))    # CPU 也能跑，RTF 差一个数量级

# 已知人数就传进去。这一个参数带来的提升常常超过换模型。
diar = pipeline(wav, num_speakers=2)
# 人数不确定时用区间：min_speakers=2, max_speakers=4

with open("work/interview_001.rttm", "w") as f:
    diar.write_rttm(f)          # RTTM 是评测工具的标准输入格式

turns = [
    {"start": seg.start, "end": seg.end, "speaker": spk}
    for seg, _, spk in diar.itertracks(yield_label=True)
]
print(len(turns), len({t["speaker"] for t in turns}))   # 段数、人数

跑完先看两个数：段数和人数。人数离谱（面试跑出 6 个人）说明这条路线在你的音频上要调，先别往下走。

# 3) ASR + 对齐。注意必须要词级时间戳——句子会跨说话人。
from faster_whisper import WhisperModel

asr = WhisperModel("large-v3", device="cuda", compute_type="float16")
segments, info = asr.transcribe(wav, language="zh", word_timestamps=True)
words = [w for s in segments for w in s.words]

def speaker_of(t: float) -> str:
    """词中点落在哪个 turn 内就归谁；落在空隙里归最近的 turn。"""
    for tn in turns:
        if tn["start"] <= t <= tn["end"]:
            return tn["speaker"]
    return min(turns, key=lambda tn: min(abs(tn["start"]-t),
                                          abs(tn["end"]-t)))["speaker"]

# 把连续同说话人的词合并成 utterance
utts, cur = [], None
for w in words:
    spk = speaker_of((w.start + w.end) / 2)
    if cur is None or cur["speaker"] != spk:
        cur = {"speaker": spk, "start": w.start, "end": w.end, "text": w.word}
        utts.append(cur)
    else:
        cur["end"] = w.end
        cur["text"] += w.word

这段胶水逻辑就是 WhisperX 帮你做的事。自己写一遍的价值是：出错时你知道该看时间戳还是看分段。

# 4) 角色识别。输入不是音频，是「每个 speaker 的画像」。
#    粒度是 speaker 级：一个 SPEAKER_xx 一个角色，不要逐段判。
import json, collections

profile = collections.defaultdict(lambda: {"sec": 0.0, "turns": 0, "samples": []})
for u in utts:
    p = profile[u["speaker"]]
    p["sec"] += u["end"] - u["start"]
    p["turns"] += 1
    if len(p["samples"]) < 8:            # 采样，别塞整篇
        p["samples"].append(u["text"][:80])

prompt = f"""这是一场线上面试的转写，说话人已被匿名聚类。
可选角色（封闭集合）：interviewer / candidate / observer / unknown
判定线索：提问密度、单段长度、发言时长占比、是否介绍流程。
规则：不确定输出 unknown；interviewer 可以有多人；不要臆造角色。
只输出 JSON，形如 {{"SPEAKER_00": {{"role": "...", "confidence": 0.0, "reason": "..."}}}}

数据：
{json.dumps(profile, ensure_ascii=False, indent=2)}"""

mapping = json.loads(call_llm(prompt))   # 解析失败就让它抛
for u in utts:
    u["role"] = mapping[u["speaker"]]["role"]

在写这段之前，先花十分钟确认规则能不能直接判出来：会议元数据里有没有面试官账号？画面上有没有姓名条？能规则解决的，不要给 LLM。

# 5) 输出 + 立即自查。这份结构就是后面 API 的响应结构，早点定死。
import json, pathlib

result = {
    "job_id": "interview_001",
    "speakers": mapping,
    "segments": [
        {"start": round(u["start"], 2), "end": round(u["end"], 2),
         "speaker": u["speaker"], "role": u["role"], "text": u["text"]}
        for u in utts
    ],
}
pathlib.Path("out/interview_001.json").write_text(
    json.dumps(result, ensure_ascii=False, indent=2), encoding="utf-8")

# --- 三条自查，不通过就别继续做工程 ---
n_spk = len(mapping)
speech = sum(u["end"]-u["start"] for u in utts) / info.duration
assert 2 <= n_spk <= 4, f"说话人数异常: {n_spk}"
assert speech > 0.3, f"语音占比过低: {speech:.2f}，检查音轨与 VAD"
print({r: round(sum(u["end"]-u["start"] for u in utts if u["role"]==r), 1)
       for r in {u["role"] for u in utts}})
# 面试官时长应显著少于候选人；反了就是角色整体对调，最危险的失败。

最后那行 print 是最有价值的一行：角色整体对调时，JSON 看起来完全正常，只有时长分布会露馅。

这一版为什么够用

  • 它验证了三件最贵的事：你的音频质量能不能被切开、说话人数能不能估对、角色信号是否存在于文本里。这三件事中任何一件失败，后面所有工程都白做。
  • 它产出的 JSON 就是最终 API 的响应结构。数据形状定早了，后面换模型、换厂商都不用改下游。
  • 它天然产出第一批失败样本。跑完立刻人工看 3 段，把「切碎了」「两个人被合成一个」「角色反了」分别记下来，这就是 POC 评测集的种子。

什么时候可以先不做

先不做 ASR

如果只要「谁说了多久」的统计（发言占比、打断次数），diarization 单独就够。ASR 是链路里最贵的一段，能省则省。

先不做视频画面

画面能显著提升准确率，但也让链路复杂度翻倍。先用纯音频摸清基线 DER，再判断值不值得引入。

先不做微调

预训练 diarization 模型在通用场景已经可用。微调只有在你有标注数据、且基线明显不够时才谈。

02:00

哪些步骤离线做，哪些在请求里做

这个能力和 RAG 那类「离线建索引、线上查」的结构不一样：它的重活几乎全在离线（或异步）侧，线上请求只是在读已经算好的结果。想清楚这一点，架构就不会跑偏。

OFFLINE · 一次处理，多次读取
  1. 01 · INGEST
    接收视频，落对象存储，登记任务

    为什么需要：原始文件必须可回溯，重跑、复现指标、追责都靠它。可省：demo 阶段就是本地目录。

  2. 02 · DECODE
    ffmpeg 抽 16k 单声道 wav

    为什么需要：统一采样率和声道，隔离掉容器格式的坑。这里也是判断「是否本来就分轨」的地方。可省：永远不能省。

  3. 03 · DIARIZE
    VAD → 分段 → embedding → 聚类 → 重叠处理

    为什么需要：这是能力本体，也是整条链路里最耗 GPU 的一段。可省：录制源分轨时整段跳过。

  4. 04 · ASR
    转写，要词级时间戳

    为什么需要：只有词级时间戳才能把文字正确切给说话人。可省：只做时长统计、不要文本时省掉，能省一大笔。

  5. 05 · ALIGN
    把词分配给 turn，合并成 utterance

    为什么需要：这是把两条并行结果缝在一起的地方，也是最容易出「文字归错人」的地方。可省：不做 ASR 时不存在。

  6. 06 · ROLE
    规则先验 → LLM / 分类器 → 落 speaker→role 映射

    为什么需要：把匿名标签变成业务可消费的角色。可省：下游只需要「有几个人分别说了多久」时不需要。

  7. 07 · PERSIST
    写分段表、写派生产物、更新任务状态

    为什么需要：线上请求只读这里。状态必须能区分成功、失败和失败原因。可省：单机脚本写一个 JSON 就够。

  8. 08 · EVAL
    对评测集批量跑分，写入指标表

    为什么需要：模型、参数、厂商任何一次变更，都要能对比。没有这一步，你无法证明新版本更好。可省：demo 阶段用人眼看 3 段代替。

  1. 01 · REQUEST
    用户提交视频，或查询已有结果

    提交类请求只做三件事：校验、落存储、入队，然后立刻返回 job_id。绝不在请求里等处理完成。

  2. 02 · AUTH & SCOPE
    鉴权，确定这个人能看哪些 job

    为什么需要：面试、问诊、通话录音全是强隐私数据，权限过滤缺失是最常见的严重事故。可省：只有本地单人使用时。

  3. 03 · READ
    按 job_id 读分段，可按 role / 时间区间过滤

    为什么需要：这是线上侧唯一的「计算」，本质是一次带索引的数据库查询，毫秒级。

  4. 04 · RENDER
    拼装成转写视图、纪要输入或下载链接

    为什么需要：前端要的是可读结构（按角色分栏、可点击跳转时间点）。可省：直接返回原始 JSON 由调用方处理。

线上链路应该短到无聊。如果你发现自己在请求里调模型，多半是需求被误解成了「实时字幕」——那是另一个能力（流式 diarization，用 diart 或厂商的实时接口），架构完全不同：它要处理增量聚类和标签回溯修正，而不是批处理。

判断依据只有一条：这一步的结果对同一个视频是否只算一次。

抽音频、VAD、embedding、聚类、ASR、角色判定，对同一个视频算一次就够，全部离线。查询、按角色过滤、按时间跳转、拼接展示，每次请求都不一样，放线上。一段 60 分钟的视频，即便在 GPU 上，整条链路也常是分钟级——它不可能放在一次 HTTP 请求里同步完成。

03:00

技术路线：四条，各自的适用边界

先选路线，再选模型。选错路线的代价是重做，选错模型的代价只是换个权重。用下面的约束筛一遍，看哪几条会被淘汰。

按约束筛选：
路线典型选择适合代价
本地开源模型 pyannote.audio 3.x（segmentation + wespeaker embedding + 聚类）
NVIDIA NeMo（MSDD / Sortformer，端到端）
3D-Speaker（CAM++ / ERes2Net，中文场景友好）		 隐私敏感、内网部署、量大到云 API 成本不可接受、需要改中间结果（自定义聚类阈值、注入先验说话人数） 要自己扛 GPU、模型版本、显存和推理运行时；首次接入 pyannote 需要在 Hugging Face 上接受模型使用条款并配置 token；效果调优要人。
云 ASR API 附带 diarization AssemblyAI、Deepgram、Azure AI Speech、AWS Transcribe、Google STT，以及国内的阿里云/腾讯云/讯飞语音 ASR 和 diarization 一起要、量不大、团队没有算法人力、要最快出第一版；多数厂商一个参数就开（如 diarize=true / ShowSpeakerLabels） 数据出网；说话人数上限和聚类策略基本不可调；按分钟计费，量大后成本曲线陡；厂商换模型时你的指标会无声漂移。
会议平台 / 一体化方案 会议软件自带的转写与发言人区分、企业会议纪要平台、CCaaS 质检模块 场景刚好就是「会议纪要」「客服质检」这类标准需求，且不需要把结果深度接进自家系统 能力边界由厂商定，角色体系通常固定；深度定制基本不可能；数据留在厂商侧。但它常常直接给你分轨音频和参会者姓名，这本身是巨大的捷径。
开源项目二次开发 WhisperX（ASR + 强制对齐 + 说话人分配一条龙）
diart（流式 / 在线 diarization）
ASD 项目如 TalkNet-ASD、Light-ASD		 已经确定要本地化，但不想从零拼 VAD、对齐、分配这些胶水逻辑；或需要流式而非离线 项目维护活跃度参差，依赖冲突常见（torch/torchaudio/onnxruntime 版本地狱）；要有人能读源码并锁死环境。
自研 pipeline 自己串 VAD → 分段 → speaker embedding → 聚类 → 重叠检测 → 后处理 场景高度特殊（固定 2 人、固定麦位、极短音频、特定噪声），通用模型明显不适配，且有算法人力 最贵。只有当你能证明通用方案在你的数据上确实不行时才启动，且要先有评测集才能证明。
规则与结构先验（加在任意路线之上） 按声道分离、按会议元数据、按发言时长占比、按开场顺序、按屏幕姓名条 OCR 几乎所有场景都该先做这一层。尤其是角色识别——很多场景里角色根本不需要模型来判。 规则会随业务变化失效，必须有回归测试；不要把规则藏在代码深处，要能被看见、被改。

筛选只是提示哪些路线会先被淘汰，真正的决定要拿你自己的 20 段真实数据跑一遍再下。

模型怎么选

模型类型在链路里的位置选型要点
VAD / 分段模型最前端，切出语音区间决定 miss 和 false alarm 的下限。silero-vad 轻量够用；pyannote 的 segmentation 模型自带重叠语音的多标签输出，比传统单标签 VAD 更适合多人场景。
Speaker embedding把每个片段编码成向量直接决定聚类质量。wespeaker ResNet 系、NeMo TitaNet、3D-Speaker 的 CAM++/ERes2Net 都是常见选择。中文/远场场景优先试国产权重，跨语种差异是真实存在的。
端到端 diarization一步出分段+标签EEND 系（含 NeMo Sortformer）天生处理重叠语音，且延迟结构更适合流式；代价是支持的说话人上限通常固定（常见 4 人），超过就退化。人数多、且未知，倾向传统 pipeline。
ASR并行分支，产出词级时间戳要角色化文本就必须有词级时间戳，句级不够——句子会跨说话人。faster-whisper（CTranslate2 推理）性价比高；WhisperX 用 wav2vec2 做强制对齐把时间戳打准。
LLM最后一段，做角色判定用于零样本角色分类和纪要生成。它不参与分段，不要指望它修正 diarization 的边界错误。
视觉模型可选分支，见下一节人脸检测/跟踪、主动说话人检测（ASD）、姓名条 OCR。只在音频方案触到天花板、且画面确实有信息时引入。

依赖清单：按职责，不按流行度

服务与存储

注意这里没有向量数据库。原因见「存储决策」一节——大多数 diarization 系统压根不需要它。

开源方案怎么借

  • 直接用整个项目：只在场景和项目假设高度吻合时（比如就是要「音频转带说话人的字幕」，WhisperX 直接用）。
  • 只借模型权重：最常见也最稳。把 embedding 模型或 segmentation 模型抠出来，聚类和后处理自己写，你就能控制阈值和说话人数先验。
  • 只借评测方法：DIHARD、AMI、VoxConverse 这些基准的评测脚本和 collar 口径，是你自建评测集时最值得抄的东西。抄口径比抄代码有价值。
  • 只借前端：人工校正说话人标签的界面（波形 + 泳道 + 拖拽边界）不必自研，找现成的转写校对界面改。
04:00

它是视频，画面里藏着最便宜的答案

纯音频方案在会议室远场、麦克风共用、多人抢话时会明显退化。而视频里往往有音频给不了的强信号。按「投入产出比从高到低」排，画面能提供三样东西：

最划算屏幕上的姓名

线上会议录像的画面里通常直接印着参会者姓名条。用 PaddleOCR/RapidOCR 每隔几秒抽帧识别一次，配合「当前高亮/说话中」的边框，你几乎白拿了说话人身份和角色。这条线索经常比任何声学模型都准，却最常被忽略。

中等主动说话人检测

ASD（TalkNet-ASD、Light-ASD 等）判断画面中哪张脸此刻在说话：人脸检测跟踪 → 唇动与音频的时序相关性 → 逐帧「说/不说」。把 ASD 的人脸轨迹当作聚类约束，能大幅压低说话人混淆，尤其在重叠语音段。

辅助位置与人脸聚类

固定机位下，座位位置本身就是角色先验（主位=面试官/法官/主诊医生）。人脸 embedding 聚类还能提供一个独立于声音的说话人数估计，用来校验音频聚类估出的 K。

什么时候不要碰画面。

画面里没有人脸（共享屏幕全程占满）、分辨率太低、只录了一个大远景、或者摄像头根本没开——这些情况下视觉分支只会白烧 GPU。另外人脸是比声纹更敏感的生物识别信息，一旦引入，合规评估的范围立刻扩大。先用纯音频拿到基线 DER，再拿一批「音频失败样本」验证画面是否真的能救回来，再决定。

05:00

角色识别：先穷尽规则，再考虑模型

Role identification 的输入不是音频，而是已经聚好类的说话人。它的粒度是 speaker 级——一个 SPEAKER_00 对应一个角色，而不是逐段判定（逐段判定既慢又不稳，还会自相矛盾）。四层方法，从上往下试，能在上层解决就别往下走。

ROLE RESOLUTION · 四层，按顺序尝试
L1结构先验与元数据：零成本，先榨干

录制源的 channel（坐席/客户）、会议邀请里的参会者身份、面试系统里已知的面试官账号、屏幕姓名条 OCR 的结果、诊室固定麦位。这些是确定性信息，不是预测。

还有一类弱先验很好用：说话总时长占比、首个发言人、提问句占比、平均语段长度。在面试场景里，「提问密度高、单段短」几乎就等于面试官。这类规则的价值不在于单独准，而在于它给 LLM 提供了可核对的特征。

L2LLM 零样本分类：POC 阶段的默认解

把每个 speaker 的若干条代表性发言采样出来（不要塞整篇，长会议会爆预算也会稀释信号），连同角色定义和判定线索一起给 LLM，要求输出 speaker → role 的 JSON 映射，并强制要求给出理由和置信度。理由不是为了好看，是为了让人工复核时能一眼看出它是不是抓错了线索。

关键约束要写进 prompt：角色集合是封闭的、允许输出 unknown、同一角色是否允许多人（两个面试官）、是否必须每个角色都被分配到。这四条不写清，输出就会漂。

L3微调文本分类器：量大且角色固定时更划算

把一个 speaker 的所有发言拼成一篇文档，做文档级分类。中文场景用 bert-base-chinese 一类的编码器就够，几千条标注样本可以打平甚至超过 LLM，推理成本低两三个数量级，延迟稳定。

触发条件很明确：角色体系半年不变、日处理量到了让 LLM 费用变显眼的程度、且你已经在 L2 阶段积累了可直接当训练集的人工修正记录。

L4声纹注册匹配：当「角色」其实等于「特定的人」

坐席工号、固定主诊医生、公司内固定面试官——这类场景里角色是绑定到人的。做法是维护一个声纹注册库，把 diarization 出来的每个 speaker 的 embedding 与注册库比对，超过阈值就认。

这是全文唯一需要向量检索的地方，也是合规压力最大的地方：声纹属于生物识别信息，在国内《个人信息保护法》下属敏感个人信息，需要单独同意和更严格的存储、留存、删除策略。没有法务确认之前不要建这个库。

角色识别的失败长什么样

  • 整体对调：两个角色被完整互换。这是最危险的失败——下游统计全反，但输出看上去完全正常。必须有专门的检测规则（比如「面试官提问数应显著多于候选人」这类不变量）。
  • 上游污染：diarization 把两个人合并成一个 speaker，角色识别再准也只能给出一个角色。角色错误里有相当一部分根本不是角色模型的问题，排查时先看 diarization。
  • 角色不在集合内：突然进来一个 HR、一个家属、一段背景电视声。必须允许 unknown，强行分配比留空危害更大。

存储：先问需要什么，再决定用什么

这个能力经常被默认套上「AI 应用 = 向量数据库」的模板，但它的数据其实是时间区间，不是语义向量。逐个判断：

STORAGE DECISION · 点选你的情况
存储负责什么demo 阶段替代什么时候撑不住
关系数据库 任务状态、视频元数据、分段表（start/end/speaker/role/text）、人工修正记录、评测结果、权限与配额、审计 SQLite 或直接一个 JSON 文件 并发写任务状态、需要多人同时校对、需要按角色跨视频聚合统计时
对象存储 原始视频、抽取的 wav、RTTM、转写 JSON、抽帧图片等派生产物 本地目录 data/raw + data/derived 单机磁盘放不下、worker 要横向扩、需要给前端发临时下载链接时
向量索引 只有一个用途：跨文件的说话人声纹检索与注册匹配（L4） 一个 numpy 数组 + 余弦相似度，几千人以内完全够 注册人数到十万级、需要在线增删、需要多副本时才考虑专门的向量库
图数据库 基本不需要 — 除非核心需求是「谁和谁在多少场会议里共同出现、经由谁认识谁」这类多跳关系推理，否则关系库两张表就够。

一个容易忽略的表：人工修正记录。

从第一天就把「人改了什么」存下来——哪个 speaker 被合并、哪个角色被改、边界被拖到哪。它同时是你的评测集来源、微调数据来源和质量趋势指标来源。等到需要时再补，历史就没了。

07:00

五个阶段：每一步新增了什么，代价是什么

不要跳级。每一级解决的是上一级已经暴露出来的具体痛点，没痛就别加。

时间盒：一天。3~5 段真实视频，一个 Python 脚本，本地目录，本地模型或直接云 API。

组件

ffmpeg + 一个 diarization 方案 + 可选 ASR + 一次 LLM 调用 + 本地 JSON。没有服务、没有数据库、没有队列。

解决什么

回答「我的音频能不能被切开、人数能不能估对、角色信号在不在文本里」。

代价

几乎没有。最大的成本是环境——torch/onnxruntime/CUDA 版本冲突能耗掉半天，用容器锁死。

不要做

不要在这一步搭 FastAPI、上向量库、写 Dockerfile、设计多租户。也不要用最干净的样例来验证——那会给你一个假的信心。

时间盒：两到三周。目标不是「跑得更好」，是拿到能写进结论的数字。

新增组件

30~50 段人工标注的评测集（RTTM + 角色标签）、批量跑分脚本、pyannote.metrics/dscore、失败样本目录、一个最小 FastAPI（提交/查状态/取结果）、SQLite 或 PostgreSQL 存任务。

解决什么

给出 DER 及其三项分解、角色 macro-F1、RTF、单位时长成本、失败率。同时验证 2~3 条候选路线到底差多少——这是决定要不要自建的唯一依据。

代价

标注是主要开销，也是唯一不能外包给直觉的部分。先标 20 段做一致性检查再规模化。

什么时候不值得上

如果处理量一年也就几百个视频，POC 的结论大概率是「用云 API + 人工校对」，不必再往下走。

目标：每天稳定跑，出问题能查。架构保持简单，补的是持久化和可运维性，不是抽象层。

新增组件

PostgreSQL（任务、分段、人工修正）、对象存储或挂载盘、结构化日志（带 job_id）、配置文件化（模型版本、阈值、num_speakers 策略）、部署脚本或容器、一个人工校对页面、每周抽检流程。

解决什么

结果不再丢；失败可追溯到具体 job 和具体阶段；有人在持续看质量而不是等用户投诉。

代价

一台带 GPU 的机器（或稳定的 API 预算）、一个人的部分精力做运维和抽检。

什么时候不值得上

别在这一步引入 Kubernetes、服务网格、特征平台或统一 AI 中台。这个阶段的瓶颈是质量和人工校对效率，不是架构。

目标：扛住量，并且看得见质量在往哪走。

新增组件

Celery/RQ + Redis 队列与独立 GPU worker（关键是限制 GPU 并发）、任务优先级与重试策略、监控看板（RTF、队列深度、失败类型分布、成本/小时）、离线回归评测接进 CI、模型与阈值版本化、灰度发布（新旧版本双跑对比 DER）。

解决什么

高峰期不再堆积或 OOM；换模型、换厂商、改阈值有了可对比的证据；质量下滑能在用户之前被发现。

代价

GPU 资源池的调度与成本；回归评测本身也要跑 GPU；灰度双跑意味着一段时间内算力翻倍。

什么时候不值得上

日处理量还在几十个视频、且没有并发峰值时，队列只是增加了一层调试难度。

目标：可审计、可隔离、可替换。到这一步，工程难点已经不在模型上了。

新增组件

多租户与数据隔离（存储、索引、日志三层都要隔）、细粒度权限与访问审计、数据留存与删除策略（含声纹与人脸的单独同意与删除路径）、私有化部署与离线模型分发、容量规划与灾备、模型版本与评测结果的完整追溯、人工审核闭环、供应商替换预案。

解决什么

让这套能力可以合法地处理面试录像、问诊录音、通话记录这类高敏数据，并在合规审查中说得清每一条数据的来路和去处。

代价

合规评审周期通常比开发周期长。私有化部署意味着你要为每个客户维护一套模型版本和硬件基线。

最容易被低估的一条

「供应商替换」不是备用方案文档，而是要求你的分段结构、评测集和接口层从一开始就不绑定任何单一厂商的输出格式。这个决定要在 POC 阶段就做，不是企业级阶段才补。

08:00

评测：跑通不等于能用

这是全文最该多花时间的一节。diarization 有一个非常成熟的标准指标体系，不用自创；角色识别则要自己定，但也别只写「准确率」。

DER 是什么，以及它怎么骗你

Diarization Error Rate 是三类错误时长之和除以总语音时长：false alarm（把非语音判成语音）、missed detection（漏掉了真实语音）、speaker confusion（说话人归属错了）。注意它可以超过 100%，因为重叠语音会被重复计数。

DER CALCULATOR · 拖动看三类错误各自的权重

报 DER 必须同时报口径，否则数字没有意义。

同一份结果，用 0.25s 的 collar（宽容边界）和不用 collar，DER 能差出一倍；跳过重叠语音段（skip overlap）和不跳，又是另一个量级。学术论文里的漂亮数字大多带 collar。你自建评测时，把口径写进配置文件并固定下来，之后所有版本对比都用同一套。用 pyannote.metrics、dscore 或 meeteval 算，不要自己写。

按任务类型选指标

任务核心指标为什么
DiarizationDER（拆开看 FA / Miss / Confusion 三项）、JER、说话人数估计准确率只看总 DER 会掩盖问题：FA 高是 VAD 阈值问题，Confusion 高是 embedding/聚类问题，两者的修法完全不同。说话人数估错是最致命的单点故障。
Diarization + ASR 端到端cpWER、WDER业务真正消费的是「带说话人的文本」。cpWER 把说话人排列和识别错误一起算，最贴近用户感受；WDER 单看词级说话人归属错误率。
Role identificationspeaker 级 accuracy、macro-F1、per-role recall、confusion matrix、unknown 判出率角色分布通常极不均衡（面试官 1 人、候选人 1 人、旁听 3 人）。只看 accuracy 会被多数类带跑，必须看每个角色单独的 recall，尤其是业务上最贵的那个角色。
下游纪要 / 质检关键字段抽取准确率、引用片段命中率、人工修正率它反映的是整条链路的复合质量，是给业务方看的口径。

工程与业务指标

  • RTF（real-time factor）：处理时长 / 音频时长。这是这个能力最重要的成本指标——它直接决定单位时长成本和 GPU 需求量。GPU 与 CPU 的 RTF 常差一个数量级，必须在你自己的硬件和典型时长上实测，别信别人的数。
  • 端到端时延：从上传到结果可读，包含排队时间。用户感知的是这个，不是模型推理时间。
  • 失败率与失败类型：解码失败、无语音、超时、显存溢出要分开统计，混在一起看等于没看。
  • 业务侧：人工校对每小时音频所花的分钟数（这是最能打动业务方的数字）、纪要采纳率、质检误判带来的申诉量。

评测集怎么造

随手挑几段清晰录音验证是自欺。一个能用的评测集需要分层：

  • 常规样本（约六成）：覆盖典型时长、典型人数、典型录制设备。
  • 难例（约三成）：重叠说话、抢话打断、远场回声、背景音乐或电视、口音、中英夹杂、超短应答（「嗯」「对」——它们极难切且极常见）、单人独白（会诱发模型硬切出第二个人）。
  • 高风险样本（约一成）：角色对调会造成业务事故的场景、涉及敏感内容的场景。这部分的验收标准要单独定，通常要求接近零错。
  • 标注规则：静音多长算段落切分、语气词算不算语音、重叠段怎么标、说话人数以什么为准。规则不统一，两个标注员的一致性会低到让指标失去意义——先标 20 段做一致性检查，再大规模标。
  • 版本管理：评测集和模型版本要一起打 tag。指标变化时，你必须能区分「模型变了」和「评测集变了」。

指标不达标时的排查顺序

  1. 数据与标注：采样率被重采样错了吗？多声道被错误混音了吗？标注规则一致吗？大量「模型问题」最后查出来是 ffmpeg 参数错了。
  2. 分解 DER：FA 高 → 调 VAD 阈值、查背景噪声；Miss 高 → 查短语音段和低音量段；Confusion 高 → 换 embedding 模型、查聚类。
  3. 说话人数与聚类阈值：如果业务上人数已知（面试就是 2~3 人），把 num_speakers 或 min/max_speakers 传进去。这一个参数带来的提升，常常超过换模型。
  4. ASR 对齐：角色化文本错了，先确认是 diarization 错还是词级时间戳偏移。
  5. 角色层的 prompt / 规则：到这一步再改 prompt 和分类器。
  6. 最后才是服务架构。排队慢、超时不会让 DER 变差，别在这里找算法问题。
09:00

服务化：三个接口就够

脚本跑通之后再包服务。因为处理是分钟级的，接口必须是异步任务模式：提交、轮询、取结果。不要设计同步接口，那会在第一个长视频上超时。

FastAPI · 最小三接口
# app.py —— 只做三件事：收任务、报状态、给结果
from fastapi import FastAPI, UploadFile, HTTPException, BackgroundTasks
from pydantic import BaseModel

app = FastAPI()

class JobCreated(BaseModel):
    job_id: str
    status: str

@app.post("/jobs", response_model=JobCreated)
async def create_job(file: UploadFile, bg: BackgroundTasks,
                     num_speakers: int | None = None):
    """上传视频，落对象存储，入队。已知人数就传进来，它比换模型更有用。"""
    if file.content_type not in ALLOWED_TYPES:
        # 不接受的格式直接 400，不要静默转码成别的东西
        raise HTTPException(415, f"unsupported content_type: {file.content_type}")
    job_id = storage.put_and_register(file, num_speakers=num_speakers)
    bg.add_task(run_pipeline, job_id)   # 仅限 POC；见下方说明
    return JobCreated(job_id=job_id, status="queued")

@app.get("/jobs/{job_id}")
async def get_status(job_id: str):
    """queued / running / succeeded / failed。失败必须带原因，不要只回 failed。"""
    job = db.get_job(job_id)          # 不存在时直接抛 404,不返回空对象
    if job is None:
        raise HTTPException(404, f"job not found: {job_id}")
    return {"job_id": job.id, "status": job.status,
            "progress": job.progress, "error": job.error}

@app.get("/jobs/{job_id}/transcript")
async def get_transcript(job_id: str, role: str | None = None):
    """取结果，可按角色过滤。这是唯一在线上做的"计算"。"""
    job = db.get_job(job_id)
    if job is None:
        raise HTTPException(404, f"job not found: {job_id}")
    if job.status != "succeeded":
        # 没跑完就明确告诉调用方状态，不要返回半截结果
        raise HTTPException(409, f"job not ready: {job.status}")
    return db.get_segments(job_id, role=role)

什么时候从 BackgroundTasks 换成真队列

BackgroundTasks 跑在同一个进程里：进程重启任务就没了、没有重试、没有并发控制、GPU 会被多个请求同时抢。它只适合 POC。出现下面任意一条就该换成 Celery/RQ/arq + 独立 worker：

  • 任务会超过几分钟，或用户会在处理期间刷新页面。
  • 需要限制 GPU 并发（这是最常见的触发原因——两个任务同时抢显存会直接 OOM）。
  • 需要重试、需要区分「可重试的失败」和「不可重试的失败」（坏文件重试一万次也没用）。
  • API 进程需要独立于 GPU 机器扩缩容。

不要为了「更稳」吞掉错误。

这条链路上最该显式暴露的四类失败：ffmpeg 解码失败、音频中检测不到任何语音、模型权重加载/授权失败、GPU 显存不足。见过太多实现把它们兜成「返回空分段列表」，结果下游拿到一份空纪要，以为这场会真的没人说话。空结果和失败是两件事，状态里必须能分开。

10:00

失败模式、验收口径、以及别过度工程化

常见失败模式

高频说话人被合并或被拆散

两个音色相近的人（同性别、同年龄段）被聚成一个；或同一个人因为音量/位置变化被拆成 SPEAKER_00 和 SPEAKER_03。前者靠传入已知人数和更强的 embedding 模型缓解，后者常需要后处理合并（把时长极短、且与某个主标签高度相似的簇并回去）。

高频短应答被吃掉

「嗯」「对」「好的」这类 0.3 秒的回应，VAD 常常漏掉或归给正在说话的人。它在客服质检和问诊场景里恰恰重要（表示确认）。修法是调低 VAD 的最小语音时长，代价是 false alarm 上升——这是一个必须由业务决定的取舍。

高频重叠语音

抢话、附和、串音。传统 pipeline 在重叠段只能给一个标签，天然产生 miss。端到端模型（EEND/Sortformer 系）在这里更强。评测时把「含重叠段」的样本单独拉出来看，否则整体 DER 会掩盖它。

中频单人独白被切成多人

模型倾向于在不确定时多切一个说话人。一段一个人讲了 40 分钟的视频，可能被切出 3 个 speaker。如果场景里存在单人视频，一定要把它放进评测集，并考虑用 max_speakers 兜住。

中频成本与延迟失控

云 API 按分钟计费，一旦接入全量历史视频回溯，账单会以你没预期的方式增长——上线前先用真实时长分布估一遍。本地模型则是 RTF 失控：CPU 上跑一小时音频可能要几十分钟，队列越积越长。两者都要在 POC 阶段就实测，不要用「以后再优化」搪塞。

必须提前处理数据不能出内网 / 生物识别合规

面试录像、问诊录音、客服通话大多含个人信息，声纹和人脸更属于敏感的生物识别信息。这不是上线前补个说明就能过的——它直接否决整条「云 API」路线，并决定你是否能建声纹注册库。这个约束要在选路线的第一天问清楚，不要做到一半才发现。

验收口径

必须达标

评测集上的 DER 达到约定阈值（口径固定）；核心角色的 recall 达标；高风险样本集零角色对调；解码与超时失败率低于约定值；成本/小时在预算内。

观察项

整体 accuracy、次要角色的 F1、平均段长分布、说话人数估计偏差、P95 端到端时延。持续记录、看趋势，但不阻断上线。

必须阻断

角色整体对调；把失败静默返回成空结果；未授权用户能读到他人任务；含敏感个人信息的数据流出约定边界。这四条任意一条出现，不上线。

可以接受的失败

边界偏差在几百毫秒内、重叠段归属不完美、极端噪声样本失败、罕见角色被判为 unknown——这些应当被明确写成「接受」，并配套人工复核入口。把所有失败都当 bug 修，会让这个项目永远上不了线。

什么时候根本不该做这套工程。

视频只有几十个、一个月处理一次、结果只给自己看、准确率差一点无所谓——那就一个 Python 脚本、一个本地目录、一个 JSON 文件，跑完人工扫一眼。没有队列、没有数据库、没有服务。这个能力的价值来自「量」和「持续」，两者都不具备时，工程投入不会有回报。
