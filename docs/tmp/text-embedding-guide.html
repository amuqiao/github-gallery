一文读懂 · TEXT EMBEDDING

当文字变成坐标

Text Embedding 做的事情，一句话就能说清：把一段文字变成高维空间里的一个点，让「意思相近」变成「坐标相近」——这样"相似"就可以被计算，而不只是被感觉。

这是为了讲清原理手工摆出的示意坐标 —— 点击任意一个点，看看语义空间里"谁离它最近"。真实模型输出的向量通常有 384 ~ 4096 维，没法直接画在纸面上。

虚线圈 = 多义词，向量会随语境改变（第二部分会具体解释）

01 · 为什么需要它

字面不同，意思相同——这是关键词匹配的盲区

假设你在做一个电商客服知识库。用户输入：「手机壳裂了怎么办」。知识库里刚好有一篇文档，标题是「屏幕保护壳出现裂痕的处理流程」——说的是同一件事，但两句话没有一个共同的词。

关键词匹配和 全文检索（BM25） 的核心机制都是"字面重合度"——遇到这种情况，它们通常会判定为不相关，或者打出很低的分。而 Text Embedding 判断的是"意思"，能认出这两句话在说同一件事。下面用这个真实场景的示意打分，对比两种方式的差异：

查询：「手机壳裂了怎么办」—— 上面的分数是为了演示典型规律而设置的示意值，不是真实模型的输出。

不过 Text Embedding 也不是万能的。它擅长"意思相近但字面不同"的匹配，但不擅长精确匹配——订单号、型号、专有名词的唯一性这类场景，字面匹配反而更可靠、更可解释；它也不做逻辑推理，更不会生成新内容，这些是 LLM 生成阶段的工作。这条边界会在第三部分具体展开。

02 · 核心机制

从字符串到向量：六步拆解

那么，从「手机壳裂了怎么办」这句话，到一个可以拿来算相似度的向量，中间到底发生了什么？整条链路可以拆成六步——点击下面的按钮，跟着这句话一步步走一遍。

01清洗 · Cleaning

目的是去掉与语义无关的噪声——多余空白、重复标点、全 / 半角不统一、控制字符，让后续的切分和编码更稳定。但清洗不是"删语义"。

"  手机壳裂了怎么办!!!  "
→
"手机壳裂了怎么办"
常见误区：为了"干净"，把否定词、语气词甚至标点全部删掉——这些往往携带语义（比如"不"直接决定句子意思相反），过度清洗反而会损伤向量质量。
02切分 · Tokenization

把清洗后的字符串切成模型词表里认识的最小单元（token）。中文里常见的做法不是简单按"字"或"词"切，而是用 BPE / WordPiece / SentencePiece 等子词（subword）算法，由模型训练时固定下来的词表决定切分规则。

为了方便阅读，下面按词级展示；真正送入模型的其实是每个 token 对应的整数 id。

手机壳裂了怎么办
常见误区：把不同模型的 tokenizer 和 encoder 混着用——tokenizer 和 encoder 是训练时绑定的一对，词表对不上，编码出来的向量没有意义。
03Encoder · 模型编码

token 先查表变成初始向量，再经过多层 Transformer，让每个 token 的向量融合上下文信息。这一步的输出是"逐 token 的向量矩阵"，形状是 (token 数, 隐藏维度)，还不是整句话的向量。

token示意向量（简化为 4 维展示，真实通常是 384 ~ 4096 维）
手机[ 0.12, -0.44, 0.81, 0.09 ]
壳[ 0.30, -0.10, 0.55, -0.22 ]
裂[ -0.18, 0.62, 0.14, 0.40 ]
了 / 怎么 / 办… （省略）

回头看开头的星图：在讨论数码产品的语境里，"苹果"的向量会更靠近"手机""电脑"；在讨论水果的语境里，会更靠近"香蕉""橙子"。这正是 encoder 产出的向量是"上下文相关（contextual）"的体现——也是它和 word2vec 这类"每个词固定一个向量"的早期方法的关键区别。

04Pooling · 池化

把"多个 token 向量"压缩成"一个句子向量"。常见方式：mean pooling（对所有 token 向量取平均，最常用、效果稳健）、CLS 向量（取一个特殊标记位置的向量）、max pooling（逐维取最大值）。

[0.12, -0.44, 0.81, 0.09] 手机
[0.30, -0.10, 0.55, -0.22] 壳
[-0.18, 0.62, 0.14, 0.40] 裂
… 了 / 怎么 / 办
↓ 逐维取平均（mean pooling）
[0.24, -0.06, 0.63, 0.05] —— 整句话的向量
常见误区：拿一个没有专门为句子表示训练过的模型的 CLS 向量直接当句向量用——效果通常明显不如 mean pooling，或者选用专门训练过的 sentence embedding 模型（如 sentence-transformers 系列，用对比学习专门优化过句子级别的向量空间）。
05归一化 · L2 Normalize

把向量缩放成单位长度（模长为 1），只统一"尺度"，不改变"方向"（也就是不改变语义指向）。归一化后，余弦相似度可以直接用点积计算——很多向量库默认假设向量已归一化，以此加速检索。

常见误区：写入向量库前忘记归一化——结果检索排序被"向量长度"干扰，而不是单纯反映"方向（语义）有多接近"。
06相似度计算 · Cosine Similarity

用两个（已归一化）向量的余弦值衡量方向接近程度，值域通常在 [-1, 1] 之间，越接近 1 越相似。检索时对 query 向量和所有候选文档向量批量计算，取分数最高的 Top-K。

夹角越小，相似度越高——「手机壳裂了怎么办」与「屏幕保护壳出现裂痕的处理流程」（doc A）夹角小，与「蓝牙耳机连接不上怎么解决」（doc D）夹角大。

把六步串起来看：文字 → 数字序列 → 上下文向量矩阵 → 单点向量 → 单位向量 → 可比较的相似度。这就是 Text Embedding 全部的机制。

03 · 边界区别

它和谁不一样：关键词匹配 / 全文检索 / LLM 上下文 / RAG

Text Embedding 经常和另外几个词被放在一起说——关键词匹配、全文检索、LLM 上下文、RAG。它们分工完全不同，把同一个客服场景走一遍就清楚了：

用户提问
「手机壳裂了怎么办」
↓
关键词匹配
未命中
全文检索（BM25）
低分
向量检索（Embedding）
✓ 命中 doc A
↓
命中片段：
"屏幕保护壳出现裂痕的处理流程…"
↓
LLM 上下文窗口把问题 + 命中片段一起放进 prompt
↓
LLM 生成回答
"您可以在购买后 7 天内申请更换…"

这就是一次典型的 RAG 链路：Embedding 只负责"召回层"里的一种召回方式，LLM 上下文只是资料的容器，真正生成语言的是 LLM。

维度关键词匹配全文检索（BM25）Text EmbeddingLLM 上下文RAG（组合）
匹配依据字面完全一致词频 / 字面相关性统计向量方向的语义接近程度不做匹配，只是"容器"综合检索结果驱动生成
典型场景精确编号 / 型号查找传统搜索引擎、站内搜索同义改写、模糊语义搜索把资料塞进 prompt 供阅读知识库问答、客服助手

局限同义词 / 改写全部漏掉对同义改写仍不敏感对精确值 / 专有名词不够敏感窗口长度有限，塞太多会挤占空间效果取决于检索质量，检索错生成也会错
常见误区一：有了向量检索就不需要关键词匹配 / 全文检索了。生产系统里常见做法其实是混合检索（hybrid search）——因为向量检索对精确型号、编号、罕见词、否定词的区分力，通常弱于字面匹配。
常见误区二：把 RAG 简单理解成"把资料塞进 prompt"。RAG 的核心其实是"先检索限定范围，再让 LLM 在这个范围内生成"，用来缓解大模型的幻觉和知识过期问题；Embedding 只负责"找出哪些资料相关"，并不判断资料本身对不对、新不新。

04 · 最小工程实现

Python 主链路：从输入文本到检索结果

把 Text Embedding 放进一个真实项目里，先讲清它的输入输出、前置条件和不负责的事情，再讲怎么实现。

输入 / 输出

输入是一批文本（字符串列表）；输出是每条文本对应的定长向量（numpy array）+ 必要的元数据（id、原文、来源），供检索后还原展示内容。

前置条件

已经确定长文档的切分（chunking）策略，以及使用哪个 encoder（及其对应的向量维度）。

不负责

不做精确条件过滤（时间 / 权限 / 类目）——交给向量库的 metadata filter；不判断答案对错——交给 LLM 生成 + 人工评估；不做去重与增量更新检测——需要额外的数据流程。

数据流分两条链路，建库和查询共用同一个 encoder：

离线建库
文档 chunks
→
清洗
→
批量编码
→
归一化
→
写入向量库
在线查询

→

关键约束：写入和查询必须用同一个模型、同一套清洗规则——否则两边的向量不在同一个语义空间里，相似度计算没有意义。

下面是主链路的最小伪代码——只展示关键输入输出和决策，不是完整项目脚手架：

# 1) 批量编码 + 归一化：写入和查询都要走这同一个函数 def embed_texts(texts: list[str]) -> np.ndarray: texts = [clean(t) for t in texts] # 清洗 vectors = encoder.encode(texts, batch_size=32) # -> shape (n, dim) norms = np.linalg.norm(vectors, axis=1, keepdims=True) return vectors / norms # L2 归一化 # 2) 离线建库：写入向量库 doc_vectors = embed_texts(doc_chunks) vector_store.upsert(ids=doc_ids, vectors=doc_vectors, metadata=doc_meta) # 3) 在线查询：编码 query，做相似度检索 query_vector = embed_texts([user_query])[0] hits = vector_store.search(query_vector, top_k=5, filter={"lang": "zh"}) # 4) 返回结果：取回原文 + 相似度分数 results = [(h.metadata["text"], h.score) for h in hits]

05 · 方案怎么选

两个独立维度：怎么编码，存哪 / 怎么查

决定怎么落地，其实是两个独立的选择：用什么把文字变成向量（本地模型 / 云 API），以及把向量放哪里、怎么查（轻量验证 / 向量数据库）。

常见误区：把"本地模型 / 云 API"和"向量数据库"当成一个互斥的四选一——它们其实是两个维度，一个决定"怎么编码"，一个决定"编码后存哪里/怎么查"，要组合使用，不是二选一。

维度一：编码方式

主要成本关键限制适合场景不推荐场景
本地模型一次性算力 / GPU，长期大批量更省需自行维护环境，中文效果依赖模型选型（如 BGE / GTE 系列）数据敏感不能出域、调用量巨大、离线场景团队没有 ML / 运维能力、短期 MVP 验证
云 API按 token / 次数计费，随规模线性增长数据出境合规问题、网络依赖、有速率限制快速验证、中小规模生产、无 GPU 资源团队超大规模长期高频调用、强合规要求场景

维度二：存储与检索方式

主要成本关键限制适合场景不推荐场景
内存暴力搜索几乎为零无持久化、无元数据过滤，数据量大会变慢几百到几千条数据的验证 / demo生产环境、数据量大、要求低延迟
本地嵌入式向量库
如 FAISS / Chroma		免费，占用本地磁盘 / 内存单机扩展性有限，一般无原生分布式中等数据量、单机应用、原型到小型生产超大规模、需要多机分布式、强并发在线服务
生产级向量数据库
如 Milvus / Qdrant / pgvector		需部署运维或使用云托管服务引入额外基础设施复杂度大规模数据、高并发、需要 metadata 过滤 / 高可用简单 demo、数据量很小、无运维能力

推荐路径——点击一个场景，看看两个维度怎么组合：

编码 云 API（如通义 / OpenAI embedding 系列）
存储 内存暴力搜索（numpy 直接算余弦相似度）

为什么：验证阶段最贵的是时间而不是调用费。用最省心的组合几十行代码跑通看效果，效果验证后再决定是否往下走自建路线，不需要搭建任何基础设施。

编码 云 API 或本地开源模型（视数据敏感度 / 调用量决定）
存储 本地嵌入式向量库（如 Chroma / FAISS）

为什么：这个量级下单机嵌入式向量库完全撑得住，不需要额外运维分布式系统；是否用本地模型主要看数据能不能出域、以及长期调用量是否大到值得自建。

编码 本地部署的专用中文 / 多语言开源模型（或私有化云 API）
存储 生产级向量数据库集群（Milvus / Qdrant / pgvector）

为什么：这个规模下调用成本和延迟稳定性成为主要矛盾，自建模型 + 专业向量数据库的长期综合成本和可控性，优于云 API + 轻量库的组合。

心智模型回顾

Text Embedding 只做一件事：把文字变成可以计算距离的坐标。它解决"意思相近但字面不同"的匹配问题，不解决精确匹配、逻辑推理和内容生成——那些分别是关键词匹配、传统程序逻辑和 LLM 生成该做的事。

工程上，最小的实现路径就是：清洗 → 批量编码 → 归一化 → 写入向量库 → 查询时同样编码 → 相似度检索 → 返回结果。选型时先分清"编码"和"存储检索"两个维度，再按数据规模和敏感度组合，而不是纠结选哪一个"最好"的方案。

本文所有示例分数、坐标、向量数值均为手工设计的示意值，用于讲清原理，并非真实模型的输出。
