一文读懂张量

张量不是神秘的"n 维盒子"，而是一段平平无奇的一维内存，加上一副决定"怎么读它"的眼镜——shape 和 stride。换一副眼镜，同一段内存就长成另一个形状。

下面这 24 个数在内存里永远是一条直线。点击不同的 shape，看逻辑视图如何变化，而琥珀色的内存条纹丝不动；把鼠标悬停在任何一个蓝色格子上，可以看到它"住在"内存的哪个位置，以及这是怎么算出来的。理解了这一屏，视图与拷贝、reshape 与 transpose 的区别、广播为什么不费内存，全都是推论。

WHY / 它解决什么问题

为什么是张量：真实数据天生有"轴"

先看一个具体场景：你要把 32 张 224×224 的 RGB 图片喂给模型。这份数据有四个互相独立的"方向"——第几张图、哪个颜色通道、第几行、第几列。用 Python 嵌套列表存是 list[list[list[list[float]]]]，取一个像素要四层循环，做一次"所有图片整体调亮"要手写四重 for。这就是张量要解决的问题：给"有多个独立方向的数据"一个统一的容器，让整块数据可以一次性参与运算。

所以张量的定义可以很朴素：标量是 0 维张量，向量是 1 维，矩阵是 2 维，再往上就只是"轴更多"，没有新概念。每根轴（axis / dim）都有自己的语义和长度，把各轴长度排在一起就是 shape：

数据典型 shape每根轴的语义ndim
一个标量（loss 值）()没有轴0
一条词向量(768,)特征维1
一张灰度图(28, 28)高 H × 宽 W2
一批 RGB 图（PyTorch 习惯）(32, 3, 224, 224)batch N × 通道 C × 高 H × 宽 W4
一批文本的隐状态(16, 512, 768)batch × 序列长度 seq × 隐藏维 hidden3
一段批量视频(8, 16, 3, 224, 224)batch × 帧 T × C × H × W5

两个立刻可用的习惯：

  • 轴是有名字的。读任何 shape 时，先在心里给每根轴标注语义（"这是 batch 轴、这是通道轴"），而不是背数字。形状 bug 的根源几乎都是"轴的语义对不上"——比如 OpenCV 给你 (H, W, C)，PyTorch 卷积要 (C, H, W)，数字都是 224×224×3，语义顺序完全不同。
  • 一个张量 = 数据 + 四要素元数据：shape（各轴多长）、dtype（每个元素是什么类型，float32/int64/bool…，决定精度和显存）、device（数据躺在 CPU 还是 GPU 上）、以及本文的主角 stride（数据在内存里怎么排）。前三个大家都会看，第四个才是理解一切"形状操作"的钥匙。

边界也说清楚：物理和数学里的"张量"另有更严格的定义（随坐标变换的对象）。深度学习语境的 tensor 就是多维数组——NumPy 叫 ndarray，PyTorch 叫 Tensor，概念一致。本文讲的是后者。

MECHANISM / 核心机制

内存与 stride：张量的"读法"是怎么算的

计算机内存没有"二维"，只有一条编了号的直线。所以任何多维张量落到内存里都要先"拍扁"。默认的拍法叫行优先（row-major / C order）：最后一根轴先走完，再进位到前一根轴——就像数字"个位先转，转满进十位"。

拍扁之后，"第 i 行第 j 列在哪"就成了一道乘加算术题。每根轴配一个 stride（步长）：这根轴的下标 +1 时，内存下标要跳几格。寻址公式：

内存下标 = i₀ × stride₀ + i₁ × stride₁ + … + offset

对一个行优先的 (3, 4) 矩阵：列下标 +1 挪 1 格（stride₁ = 1），行下标 +1 要跨过整整一行 4 个元素（stride₀ = 4）。所以 stride 是 (4, 1)。

沿行走，指针每步 +1，内存访问连续；沿列走，每步 +4，跳着读。对 12 个元素无所谓，对 GPU 上的 (32, 3, 224, 224)，连续访问能吃满缓存和内存带宽，跳跃访问则慢得多——这就是"内存布局影响性能"的全部原理，也是 contiguous（连续）这个词后面反复出现的原因。

现在回看首屏的规律就一目了然了：行优先下，stride 可以从 shape 直接推出来——每根轴的 stride = 它右边所有轴长度的乘积。比如 (2, 3, 4) → stride (12, 4, 1)。而"改变形状"从此有了两种本质不同的做法：只换眼镜（改 shape/stride，数据不动），或者真的搬数据（按新顺序重新抄一份）。下一章把这条线讲透。

VIEW vs COPY / 视图与拷贝

视图 vs 拷贝：哪些操作只是"换眼镜"

有了 stride，很多"看起来在改数据"的操作其实一个字节都没动：

  • 转置 transpose/.T：把 shape 和 stride 一起交换。(4,6)+stride(6,1) 变成 (6,4)+stride(1,6)——按列读的眼镜。
  • 切片 a[1:3]：改 offset（起点后移）和 shape，stride 不变。
  • 隔步切片 a[::2]：stride 直接乘 2，跳着读。
  • squeeze / unsqueeze / expand：增删长度为 1 的轴、或把 1 长轴"虚拟拉伸"（stride 设成 0，第 5 章细讲）。

这类操作产出的叫视图（view）：新张量、新元数据、同一段内存。代价是 O(1)，但有个必须刻进脑子的副作用——改视图 = 改原张量，因为它们本来就是同一份数据。

而有些操作躲不开搬数据：转置后想按新顺序"重新拍扁"（view 会直接报错，reshape 会默默拷贝）、显式调用 .contiguous() / .clone()。拷贝之后才是真正独立的两份数据。判断标准只有一条：新读法能不能用"同一段内存 + 某组 stride"表达出来？能 → 视图；不能 → 拷贝。

工程上的两条推论：其一，见到"莫名其妙被改了"的张量，先怀疑某处拿到的是视图而不是副本（尤其切片后就地修改）；需要独立数据就 .clone()。其二，view 报 not contiguous 时，别机械地补 .contiguous() 完事——它是一次真实的整块拷贝，先想清楚是哪一步（通常是 transpose/permute）打乱了布局、能否换个操作顺序绕开。

CLASSIC PITFALL / 经典翻车点

reshape ≠ transpose：形状相同，数据两回事

这是张量世界的第一大坑：reshape(3, 2) 和 transpose 都能把 (2, 3) 变成 (3, 2)，但它们做的是完全不同的事——

  • reshape：保持内存阅读顺序，重新断行。像把一段文字从"每行 3 字"重排成"每行 2 字"，字的先后顺序一个没变，只是换行位置变了。它回答"我想把这串数据重新分组"。
  • transpose：交换轴的语义。原来的第 i 行第 j 列，现在住到第 j 行第 i 列。元素之间的邻接关系被改变。它回答"我想让行和列互换角色"。

真实世界的高频翻车现场：把 OpenCV 读进来的 (H, W, C) 图片喂给要 (C, H, W) 的 PyTorch 卷积。正确写法是 img.permute(2, 0, 1)（permute 就是多轴版 transpose）；写成 img.reshape(3, H, W) 不会报任何错——shape 完全合法——但每个"通道"里装的都是三色像素交错的碎条纹，模型对着一堆噪声也能训练，只是永远不收敛。形状对了、数据错了，是最难排查的一类 bug，因为它静默无声。

BROADCASTING / 广播

广播：形状不同的张量如何直接运算

需求无处不在：给 (32, 3, 224, 224) 的一批图片减去逐通道均值 (3, 1, 1)；给 (batch, seq, 768) 的激活加一个 (768,) 的 bias。逐元素运算要求形状一致，难道要先把小张量物理复制成大形状？广播（broadcasting）说：不用复制，我帮你"假装"它是大形状。

规则只有两条，从最右边的轴开始对齐，逐轴比较：

  1. 两边相等，或其中一边是 1 → 兼容；是 1 的那边被"拉伸"到另一边的长度；
  2. 某一边缺这根轴 → 当作 1 处理（等价于左侧补 1）。任何一轴不满足 → 直接报错。

而"拉伸"的实现正是第 2 章的 stride 魔法：把这根轴的 stride 设成 0——下标怎么加，内存指针都不动，所有虚拟位置读到的是同一个元素。零拷贝，零额外内存。

最后一个高价值边界——expand vs repeat，它们都能"把小张量变大"：

  • expand：手动广播。只把 1 长轴的 stride 置 0，零拷贝；代价是所有虚拟位置共享同一元素，对它写入会同时"改到所有副本"（PyTorch 干脆禁止对 expand 结果就地写）。
  • repeat：真实平铺，物理复制数据；各副本独立可写，但 (768,).repeat(16, 512, 1) 会实打实吃掉 16×512 倍内存。

选择法则：只读（参与运算）用 expand / 直接靠自动广播；需要独立修改副本才用 repeat。顺带一提：广播省的是输入的内存，输出 (3, 4) 该多大还是多大，别指望它压缩结果。

AXES & REDUCTION / 轴与归约

dim=0 到底沿着谁：归约的方向感

sum、mean、max、softmax、argmax……几乎所有聚合操作都带一个 dim（NumPy 叫 axis）参数，而"dim=0 是按行还是按列"大概是被问得最多的问题。别背"行/列"，记一条对所有维度都成立的法则：

dim=k 的意思是：把第 k 根轴"压扁消掉"，结果的 shape 就是原 shape 删去第 k 项。

比如 (3, 4).sum(dim=0)：消掉长度为 3 的第 0 轴 → 结果 (4,)。求和的方向自然是"沿着被消掉的那根轴"——3 个行向量叠在一起压成 1 个。

切到 dim=1 看颜色怎么"转向"；再开 keepdim——shape 从 (3,) 变成 (3, 1)，值一模一样，只是留了个长度 1 的轴。为什么要留？为了接下来能广播回去：均值归一化 x - x.mean(dim=1, keepdim=True) 里，(3,1) 能自动广播到 (3,4)，而 (3,) 右对齐后是 3 对 4，直接报错。keepdim 不是装饰，是给广播留的接口。

把这套方向感迁移到高维就是日常操作：(batch, seq, hidden) 上，mean(dim=1) 消掉 seq 轴 → 句向量 (batch, hidden)；softmax(dim=-1) 沿最后一根轴归一化（-1 是"最后一轴"的通用写法，与具体 ndim 解耦，值得优先使用）。写任何带 dim 的操作前，先自问：我想消掉（或沿着）哪根有名字的轴？

MISCONCEPTIONS / 常见误区

常见误区与反例

每张卡片的标题是一个流传很广的错误说法（✕），点开看正确版本（✓）和一个能当场戳破它的反例。

"维度越高，张量越难理解"

难的从来不是维数，是轴的语义。任何维数的张量都是同一个模型：一段一维内存 + 每根轴一个 (长度, stride)。读高维 shape 的正确姿势是逐轴标注名字，而不是想象四维立方体。

反例：(8, 16, 3, 224, 224) 看着吓人，念成"8 段视频 × 每段 16 帧 × RGB × 高 × 宽"之后，取第 3 段视频的第 5 帧就是 v[2, 4]，和二维取元素没有任何区别。

"reshape 和 transpose 都是改形状，随便用哪个"

reshape 保持内存阅读顺序、重新断行；transpose 交换轴的语义、改变元素邻接关系。目标 shape 相同，得到的数据完全不同。

反例：第 4 章的 F 字图——transpose 得到躺倒的 F，reshape 得到条纹碎片。HWC 转 CHW 必须 permute(2,0,1)，用 reshape 不报错但图像已绞碎，模型静默地训不动。

"切片 / 转置得到的是新张量，改它不影响原来的"

它们是视图：新的元数据，同一段内存。就地修改视图，原张量同步变化，反之亦然。需要独立数据必须 .clone()（NumPy 用 .copy()）。

反例：第 3 章实验台——b = a[1:3] 后执行 b[0,0] = 99，原内存对应位置立刻变成 99。这类"远程改动"是最常见的静默 bug 来源之一。

"广播会把小张量复制成大张量，很浪费内存"

广播是 stride=0 的虚拟拉伸，输入侧零拷贝。真正做物理复制的是 repeat。

反例：(768,) 的 bias 加到 (16, 512, 768) 上，bias 依然只占 768 个数的内存；用 repeat(16, 512, 1) 实现同样效果则要多占 8192 倍。可用 expand 后查 storage 大小验证。

"view 报错 not contiguous？加个 .contiguous() 就完了"

.contiguous() 是一次整块物理拷贝，不是免费咒语。报错本质是"transpose/permute 后的读法无法零拷贝地重新拍扁"——先想想能否调整操作顺序（例如先 reshape 再 transpose），避免不必要的大张量拷贝；确实需要再加。

反例：在 (32, 512, 768) 上，一个多余的 contiguous 就是一次约 50MB 的显存搬运，出现在训练热路径里会被放大百万倍。

"reshape 里的 -1 是随便占位的"

-1 的语义是"这一轴的长度由总元素数除出来"：只能出现一次，且其余轴的乘积必须整除总元素数，否则报错。

反例：24 个元素 reshape(-1, 5) 直接报错（24 不被 5 整除）；reshape(-1, -1) 也是非法的——两个未知数一道方程解不出来。

"dim=0 就是'对每一行操作'"

"行/列"话术只在二维勉强成立且极易记反。可靠法则：dim=k 消掉第 k 根轴，操作沿被消掉的轴进行；结果 shape = 原 shape 删去第 k 项（keepdim 则改成 1）。

反例：(3,4).sum(dim=0) 得 (4,)——是把 3 行"竖着"压在一起（每列内求和），恰恰不是"对每一行求和"。到了 (batch, seq, hidden)，"行列"话术彻底失效，"消轴"法则照常工作。

"dtype 差不多就行，反正都是数"

dtype 决定精度、取值范围、显存占用，还决定运算行为：整型除法会截断、int64 索引是硬性要求、float16 容易上溢/下溢、不同 dtype 混算要么报错要么按提升规则悄悄转型。

反例：像素张量是 uint8 时，img.mean() 在部分框架直接报错或先溢出；(a/b) 两个 int 张量在 NumPy 里得 float、在某些旧代码里被 // 截断成 0——同一行代码，dtype 不同结果天差地别。习惯：进模型前统一 float32（或明确的混合精度策略）。

# stride (6, 1)：行下标 +1 内存跳 6 格，列下标 +1 跳 1 格

print(a.reshape(2, 3, 4).stride())   # (12, 4, 1)：右边轴长度的连乘
print(a.T.stride())                  # (1, 6)：转置 = shape 和 stride 一起交换
# NumPy 对应：a.strides（单位是字节，要除以 itemsize）

9.2 视图是别名：改一个，动两个（对应第 3 章）

pytorch · 共享内存验证 + clone 解耦
a = torch.arange(24).reshape(4, 6)
b = a[1:3]                       # 切片 → 视图
print(b.data_ptr() == a[1].data_ptr())   # True：同一段内存，起点后移

b[0, 0] = 99                    # 改视图……
print(a[1, 0])                  # tensor(99) —— 原张量被"远程"改了

c = a[1:3].clone()              # 想要独立数据：clone（NumPy 用 .copy()）
c[0, 0] = -1
print(a[1, 0])                  # 还是 99，不受影响

9.3 那个著名的 RuntimeError（对应第 3 章）

pytorch · view 要求 contiguous；reshape 会默默拷贝
a = torch.arange(24).reshape(4, 6)
t = a.T                          # 视图，stride (1, 6)，不再连续
print(t.is_contiguous())         # False

t.view(2, 12)   # RuntimeError: view size is not compatible ...

r = t.reshape(2, 12)             # 能跑：但内部做了一次物理拷贝
print(r.data_ptr() == a.data_ptr())      # False：已不共享内存
tc = t.contiguous()              # 显式拷贝成连续布局，之后 view 随意
print(tc.view(2, 12).data_ptr() == tc.data_ptr())  # True

9.4 permute 对，reshape 错：静默绞碎一张图（对应第 4 章）

pytorch · HWC → CHW 的正误写法
img_hwc = torch.rand(224, 224, 3)          # OpenCV/PIL 常见布局

chw_ok  = img_hwc.permute(2, 0, 1)        # 正确：交换轴的语义
chw_bad = img_hwc.reshape(3, 224, 224)     # 不报错，但数据已绞碎！

print(chw_ok.shape == chw_bad.shape)        # True —— shape 完全一样
print(torch.equal(chw_ok, chw_bad))         # False —— 内容天差地别
print(chw_ok[0, 0, :3])                    # R 通道第一行：正常像素
print(chw_bad[0, 0, :3])                   # R/G/B 交错的碎条纹

9.5 广播零拷贝：expand vs repeat（对应第 5 章）

pytorch · 用 storage 大小验证"虚拟拉伸"
bias = torch.randn(768)

e = bias.expand(16, 512, 768)     # 手动广播
r = bias.repeat(16, 512, 1)       # 物理平铺

print(e.shape == r.shape)                    # True，都是 (16, 512, 768)
print(e.stride())                            # (0, 0, 1) —— 前两轴 stride=0！
print(e.untyped_storage().nbytes())          # ≈ 768×4 字节：没复制
print(r.untyped_storage().nbytes())          # ≈ 16×512×768×4：真复制，8192 倍

x = torch.randn(16, 512, 768)
print(torch.allclose(x + bias, x + e))       # True：自动广播 ≡ expand

9.6 keepdim 是给广播留的接口（对应第 6 章）

pytorch · 逐行标准化的正误对比
x = torch.randn(3, 4)

m1 = x.mean(dim=1)                # shape (3,)   —— 消掉第 1 轴
m2 = x.mean(dim=1, keepdim=True)  # shape (3, 1) —— 留下长度 1 的占位轴

print((x - m2).shape)             # (3, 4)：(3,1) 广播到 (3,4)，正确
x - m1   # RuntimeError：右对齐后是 4 vs 3，广播失败
# 若 shape 恰好凑巧（如方阵），x - m1 甚至不报错、只是悄悄算错——更危险

张量操作速查表

操作做什么视图还是拷贝典型用途易错点
索引/切片 a[1:3]改 offset 和 shape，取子区域视图取 batch 子集、裁剪改切片会改原张量；整数索引 a[0] 会消掉一根轴，a[:1] 才保轴
transpose / permute交换轴的语义（shape+stride 同步换）视图（变非连续）HWC↔CHW、矩阵乘对齐、注意力换轴之后 view 会报错；元素邻接关系已改变
reshape / view保持内存阅读顺序，重新断行/分组连续时视图；否则 view 报错、reshape 拷贝拉平接全连接、拆分 head、合并 batch 维不能代替 transpose；-1 只能一个且需整除
contiguous() / clone()按当前读法物理重排/复制一份拷贝transpose 后要 view；求独立副本有真实搬运成本，别当免费咒语
squeeze / unsqueeze删/加长度为 1 的轴视图补 batch 维、对齐广播无参 squeeze() 会把所有 1 长轴全删，batch=1 时误伤
expand把 1 长轴 stride 置 0，虚拟拉伸视图（零拷贝）手动广播、只读平铺共享元素，禁止就地写入
repeat（np.tile）物理平铺复制拷贝需要可独立修改的副本内存倍增；参数是"重复次数"不是目标 shape
cat / stackcat 沿已有轴拼接；stack 新建一根轴再叠拷贝拼 batch 用 cat(dim=0)；把 n 个样本叠成 batch 用 stackcat 不增加 ndim，stack 增加；混用 shape 直接对不上
sum/mean/max(dim=k)消掉第 k 根轴，沿它聚合新张量池化、句向量、softmax 方向用"消轴"法则而非"行列"话术；配广播时记 keepdim
广播（自动）右对齐，1 或缺失轴虚拟拉伸（stride=0）输入零拷贝加 bias、减均值、掩码只认"相等或 1"；(5,4)⊕(5,) 会炸，需 (5,1)

四条随身法则：

  1. 张量 = 一维内存 + shape/stride 眼镜——先问"数据动没动"，再谈一切形状操作。
  2. 合并/拆分轴用 reshape，交换轴语义用 permute——目标 shape 相同不代表数据相同，静默错误最致命。
  3. 视图是别名——切片、转置、expand 改的都是同一份数据；要独立就 clone。
  4. 读 shape 先给轴命名，写 dim 先想消哪根轴——形状 bug 的解药是语义，不是试错。
