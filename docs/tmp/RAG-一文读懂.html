为什么存在

模型的"记得"，和知识库的"记录"不是一回事

训练把海量文本压缩进了参数，那是一种统计意义上的记忆——大部分时候够用，但恰好不满足业务场景最在意的三件事：能不能随时更新、能不能说清出处、能不能按人分权限。RAG 的解法很直接：把"知识"从参数里搬出来，放进一个可以增删、能标来源、可加权限过滤的外部知识库，让模型先去查，再照着查到的内容作答。

只靠参数记忆

更新方式重新训练或微调，周期以周/月计，改一条事实要等一整轮迭代
可审计性说不清某句话具体来自哪份文档、哪一条，无法逐句核实
权限控制所有用户共享同一套"记忆"，做不到"这段内容只有 HR 能看到"
成本模式一次性沉没成本，训练完成后局部纠正很麻烦

外部知识库（RAG 思路）

更新方式增删一条文档、改一个字段，近乎实时生效，不用碰模型本身
可审计性每句回答都能对应到具体 chunk 和文档出处，可点开原文核实
权限控制检索阶段按 metadata / ACL 过滤，天然支持"谁能看什么"
成本模式按查询量增量付费，知识库本身可以持续独立维护
边界对比

RAG 不是唯一答案，也不是万能答案

同样是"让模型知道更多"，微调、长上下文、传统搜索都能部分做到，但各自解决的问题不一样，边界也不一样。搞清楚这几条边界，才知道什么时候该用 RAG、什么时候该用别的、或者几个一起用。

解决什么教模型"怎么说话、怎么做任务"——固定的输出格式、领域术语、特定的推理套路，这些是改权重能学会的行为模式。
不能替代快速变化的具体事实。改一条知识就要重新训练，无法在回答里指出"这句话来自哪份文档"，事后也很难单独撤回某条被学进去的内容。
判断标准：要改的是"行为习惯"还是"具体事实"——前者考虑微调，后者用 RAG。两者常常一起用：微调定风格和任务套路，RAG 提供作答依据。
解决什么把一批必须整体通读、互相关联的文档直接塞进 prompt，适合一次性、跨文档的综合分析或推理。
不能替代知识库天然会持续增长，长上下文做不到"只挑相关的看"——每次都要重新读一遍全部资料，token 成本和延迟随内容量线性上升；也没有权限过滤能力，也不解决"知识怎么增删改"的管理问题。
判断标准：资料范围是固定且必须整体读完，还是持续增长且每次只需要一小部分——前者用长上下文，后者用 RAG 精准检索。
解决什么基于关键词的精确匹配（如 BM25 / Elasticsearch），排序机制成熟、可控、运维经验丰富，对编号、专有名词、精确术语非常敏感。
不能替代理解不了语义相近但措辞不同的提问（"住宿封顶"≈"住宿报销上限"），而且只能返回一堆文档链接，用户还得自己点进去读——不会直接生成一句可用的答案并标注引用。
判断标准：这不是二选一——RAG 的召回阶段经常直接把关键词检索作为一路输入，和向量检索混合使用，取长补短。
解决什么Embedding 只是"把文本变成向量、支持语义相似度计算"这一项技术，可以单独用在推荐、聚类、去重、语义搜索 UI 等和"生成回答"完全无关的场景里。
不能替代RAG 是一整条业务链路——采集、清洗、切分、写入、召回、重排、组装、生成、引用，Embedding 只支撑其中"把文本变成向量"这一环。反过来，RAG 也不是非向量检索不可，可以只用关键词检索，或者两者混合。
一句话：RAG ⊃ 向量检索 ⊃ Text Embedding。本文假设你已经了解 Embedding，重点讲的是 RAG 这条完整链路怎么把检索结果变成一个可信、可核实的回答。
主链路

从一份文件，到一句带引用的回答

跟着同一个例子走完全程：员工想知道 OA-2024-017《差旅管理办法》 里"一线城市住宿一晚最多能报多少"。点开每一步，看这份文件和这个问题分别经历了什么。整条链路分两个阶段——建索引在离线批量做一次，问答在线上每次请求都会跑一遍。

离线阶段 · 建索引（一次性 / 定期更新）
在线阶段 · 一次问答（每次请求都跑一遍）
切分策略

chunk 是检索的最小单位，切分决定能不能捞到对的那一段

切分质量直接决定后面所有环节的上限：切得不好，向量再准也白搭。拖动下面的滑块，看同一段《差旅管理办法》原文在不同切分参数下会被切成什么样子。

切出 - 个 chunk 原文长度 - 字符
⚠ chunk 太小：很可能把"3.2 住宿标准"这个标题和后面具体的城市数字拆到不同 chunk，检索命中其中一个数字时，模型看不出它到底是哪个标准、哪个城市的。
⚠ chunk 太大：一个 chunk 里混进了 3.1 交通标准、3.2 住宿标准、3.3 餐费标准好几个不同主题，向量语义被稀释，即使召回了也会带进大量无关内容。
✓ 这个大小基本能让"3.2 住宿标准"独立成段，同时不混入其他小节——这是本例比较合适的区间。

📐 标题层级 & 元数据

按文档的标题结构（如 "3. 差旅报销 → 3.2 住宿标准"）做切分锚点，并把标题路径、文档名、版本、更新日期、权限标签一起存进 metadata——这些字段既用于检索时的 filter，也是最终引用信息的来源。

✂️ 段落边界

尽量按语义完整的段落 / 句子切，不要在句子中间硬切断。宁可让相邻两个 chunk 稍微有重叠（overlap），也不要让一句话被拦腰截断在两个 chunk 之间。

📊 表格

表格按字符数硬切，很容易把表头和某一行数据拆开，变成一堆看不懂的孤立数字。更稳妥的做法：把每行转成一句自然语言描述（"一线城市：660 元/晚"），或者保留完整表头 + 整张表作为一个 chunk。

💻 代码块

代码块最好整体作为一个 chunk，哪怕超过常规大小上限也不要切开——代码的语义依赖完整上下文，一个函数被切成两半既不可读也不可执行。通常给代码块单独设置更宽松的 max size。

检索质量

向量检索管语义，关键词检索管精确，两个都要

向量检索擅长理解"住一晚能报多少"约等于"住宿报销标准"，但对编号、文件代号这类精确字符串不敏感。当查询里带着 "OA-2024-017" 这样的文件编号时，两种检索方式的差别会很明显。

召回之后，还有三道减噪工序

混合召回拿回 top-k 候选
→
Rerank更贵的模型精排
→
Filter按 metadata / 权限过滤
→
去重 + 压缩只留真正相关的句子

Reranker：先快后准

召回阶段追求"快"，通常一次拿回几十条粗筛候选；reranker 是一个更贵但更准的模型，对这几十条重新计算"和查询的真实相关性"并排序，把真正对的那条（"3.2 住宿标准"）推到最前面。

Metadata filter：权限和版本的第一道闸

检索前先按 metadata 硬性过滤——只搜"2024 版"、只搜当前用户有权限看的知识库范围，避免语义相似但版本已过期、或者用户本不该看到的内容混进候选列表。

Query rewrite：补全口语化提问

用户的提问常常省略上下文（多轮对话里的"那二线城市呢"），查询改写把它转成更适合检索的完整形式，或者拆成多个子查询分别检索再合并结果。

去重 + 上下文压缩

多路召回容易带回重复或高度相似的内容，去重后再对每条候选做压缩（只保留和问题相关的句子），减少无关内容占用的上下文窗口，也降低"重复强调=更可信"的错觉。

生成质量控制

检索得再准，生成这一步也可能把事情搞砸

即使召回和排序都做对了，模型仍然可能把不相关的召回内容当真、或者在找不到答案时硬编一个。生成阶段要守住四条规矩：

01只允许基于检索到的材料回答，不能补充模型自己"记得"的内容
02保留引用，每条结论尽量对应到具体来源，方便核实和点击跳转原文
03找不到答案就如实说找不到，而不是给一个听起来合理的错误答案
04判断召回内容是否真的回答了问题，而不是无脑总结所有检索到的片段
❌ 把召回噪声写成事实

提问："一线城市住宿一晚最多报多少" —— 除了 §3.2 住宿标准，检索还顺带召回了一条不相关的 §3.1 交通标准。

生成结果："一线城市住宿及交通合计每晚最多可报销 760 元（660 元住宿 + 100 元交通）。"

问题：模型把两个完全不同维度的报销标准强行加在了一起，编出了原文里根本不存在的"合计 760 元"。这不是检索错了，是生成阶段没有守住"只依据检索材料、不做自由推导"这条规矩。

✅ 有依据时：精确回答 + 引用

"一线城市住宿报销上限为 660 元/晚。
[来源: OA-2024-017 §3.2]"

✅ 没依据时：如实说明，不编造

提问变成"境外出差的住宿标准是多少"——"检索到的资料（OA-2024-017）只覆盖境内差旅，未找到境外住宿标准相关内容，建议确认是否存在《境外差旅管理办法》。"

Python 实现主链路

把上面的链路落成代码，大概长这样

只展示主链路的骨架，省去了框架选择、异常处理、批处理调度这些工程细节——重点是让每一步和前面讲的概念对上号。

# ---- 离线阶段：建索引 ----
docs = load_documents("./knowledge_base")          # 采集
docs = [clean(d) for d in docs]                     # 清洗：去页眉页脚、表格转文本

chunks = []
for doc in docs:
    for piece in split_by_heading(doc, max_chars=500, overlap=80):
        chunks.append({
            "text": piece.text,
            "doc": doc.name,                     # 如 "OA-2024-017"
            "section": piece.heading_path,       # 如 "3. 差旅报销 > 3.2 住宿标准"
            "version": doc.version,
            "acl": doc.acl_tags,                 # 权限标签
        })

vectors = embed_batch([c["text"] for c in chunks])   # 批量 embedding
vector_store.upsert(chunks, vectors)                  # 写入向量库（附带 metadata）
keyword_index.index(chunks)                           # 同时建关键词索引（如 BM25）


# ---- 在线阶段：一次问答 ----
def answer(query, user):
    q = rewrite_query(query, history=user.history)        # 查询改写

    vec_hits = vector_store.search(embed(q), top_k=20, filter={"acl": user.acl})
    kw_hits  = keyword_index.search(q, top_k=20, filter={"acl": user.acl})
    candidates = merge_and_dedup(vec_hits, kw_hits)       # 混合召回 + 去重

    ranked = reranker.rerank(q, candidates, top_k=4)      # 重排，只留最相关的几条

    context = assemble_context(ranked, max_tokens=1500)   # 上下文组装（可加压缩）

    prompt = build_prompt(
        query=q, context=context,
        rule="只依据 context 回答；找不到依据就说找不到；标注引用",
    )

    resp = llm.generate(prompt)

    return {
        "answer": resp.text,
        "citations": [c["doc"] + " " + c["section"] for c in ranked],
    }
工程落地边界

RAG 在真实项目里接什么、产出什么、不管什么

输入 / 输出

  • 输入：用户的自然语言问题（可能带对话历史）+ 一个已建好索引的知识库
  • 输出：一段基于检索内容生成的回答 + 对应的引用列表（chunk / 文档 / 章节）

前置条件

  • 知识库已完成采集、清洗、切分、embedding、建索引
  • 有基本的权限 / 租户体系（如果面向多用户）
  • 有一个可用的 LLM（本地部署或 API）

不该指望 RAG 解决

  • 复杂多步数值计算 / 精确逻辑推理——喂给模型的是资料，不会让它突然变得会算数或做复杂规划
  • 源头数据本身质量差、内容有误——RAG 不能提升知识库本身的正确性，原文错了，检索越准，答案越"自信地错"

不该指望 RAG 解决（续）

  • 强实时性事务操作，比如下单、改库存——这类需求应该走工具调用 / API，而不是"检索资料回答"
  • 完全开放的创造性生成任务（写诗、脑暴）——这类任务不需要"先查资料"这一步，加了反而束缚
