taskiq-python/taskiq · async distributed task queue

把 async 函数丢进队列,交给另一台机器上的 worker 去跑

taskiq 是一个为 asyncio 时代重写的分布式任务队列:像 Celery 一样把耗时任务从请求进程中剥离出去,但原生支持 async def、全量类型标注(PEP-612 自动补全),并与 FastAPI / AioHTTP 等异步框架直接集成。

pip install taskiq Python ≥ 3.10 MIT License broker 走插件:RabbitMQ / NATS / Redis / Kafka CLI:taskiq worker · taskiq scheduler
● 橙点 = TaskiqMessage(JSON)· ● 绿点 = 任务在 worker 内被执行并落盘结果 —— 这就是 taskiq 的全部主线
01 · 它是什么,为什么出现

Celery 的问题不是功能少,而是它不属于 asyncio 世界

当你的 Web 层已经是 FastAPI / AioHTTP,而任务队列还是 Celery 时,你会发现两套并发模型互相打架:Celery 的 worker 是同步模型,跑 async def 要靠变通;类型提示和 IDE 补全也基本失效。taskiq 就是为了填这个缝出现的。

它是什么

一个异步优先的分布式任务队列核心框架:定义任务、组装消息、收发消息、执行任务、存取结果、定时调度。灵感明确来自 Celery 与 Dramatiq,但从第一行就按 asyncio 设计,同时也能跑同步函数(丢进线程池)。

它不是什么

它不自带消息中间件——核心包只有用于开发和测试的 InMemoryBroker 和实验性的 ZMQBroker。生产可用的 RabbitMQ / NATS / Redis / Kafka broker 都是独立插件包。它也不是 Celery 那种带 canvas 工作流编排(chain / chord / group)的重型系统。

在同类中的位置

介于「重而全的 Celery」和「轻但绑死 Redis 的 arq」之间:比 arq 抽象更完整(broker / result backend / middleware / scheduler 全部可插拔),比 Celery 更贴近现代异步 Python(类型标注、FastAPI 式依赖注入)。

03 · 组件地图(也是扩展点地图)

  
七个抽象,全部可替换

  
taskiq 是框架而不是产品:taskiq/abc/ 目录里的每个抽象基类都是一个官方扩展点。整个插件生态(taskiq-redis、taskiq-aio-pika…)就是对这些基类的不同实现。展开看每个组件干什么、怎么扩展。


  

    ▸AsyncBroker两侧最核心的抽象:两端共用的消息通道,kick 发消息,listen 收消息
    

      
定义在 taskiq/abc/broker.py。自定义 broker 只需实现两个方法:kick(message) 把序列化后的消息推进外部系统(比如 Redis 的 PUB);listen() 是一个无限循环的异步生成器,从外部系统读消息。@broker.task 装饰器、middleware 挂载、startup/shutdown 事件也都长在 broker 上。核心包内置 InMemoryBroker(测试/本地开发,不走网络)与 ZMQBroker。

      
# 自定义 broker 的最小骨架
class MyBroker(AsyncBroker):
    async def kick(self, message: BrokerMessage) -> None: ...
    async def listen(self) -> AsyncGenerator[AckableMessage, None]: ...

    

  


  

    ▸Kicker客户端把一次函数调用变成一条消息;不可扩展,但可配置
    

      
定义在 taskiq/kicker.py。task.kiq(1, 2) 其实是 task.kicker().kiq(1, 2) 的简写。通过 kicker 链式 API 可以临时改变发送行为:with_broker() 换 broker、with_labels() 加标签、with_task_id() 指定 ID。这是唯一一个官方声明不可继承扩展的组件。

      
task = await my_task.kicker() \
    .with_broker(second_broker) \
    .with_labels(delay=1) \
    .kiq()

    

  


  

    ▸ReceiverWorker 端worker 内的执行引擎:解析参数、注入依赖、调用函数、处理 ack
    

      
定义在 taskiq/receiver/receiver.py。它消费 broker.listen() 吐出的消息:按类型标注解析/校验参数(可用 --no-parse 关闭)、解析依赖注入、执行 async 函数(或把同步函数丢进线程池)、按 --ack-type 决定何时向队列确认(收到时 / 执行完 / 结果保存后),最后把返回值交给 result backend。并发上限由 --max-async-tasks 控制。

    

  


  

    ▸AsyncResultBackend两侧worker 写结果,客户端读结果;默认实现是"丢弃"
    

      
定义在 taskiq/abc/result_backend.py。核心包只有 DummyResultBackend(什么都不存,is_result_ready 永远返回 True)——这是刻意的:很多任务是 fire-and-forget,不需要结果。需要 await task.wait_result() 拿返回值时,接一个真实实现,如 taskiq-redis 提供的 RedisAsyncResultBackend。

      
broker = AioPikaBroker("amqp://...").with_result_backend(
    RedisAsyncResultBackend("redis://localhost"),
)

    

  


  

    ▸TaskiqMiddleware两侧八个钩子横切整条链路:重试、监控、追踪都靠它
    

      
定义在 taskiq/abc/middleware.py,钩子覆盖消息全生命周期:startup / shutdown / pre_send / post_send / pre_execute / post_execute / post_save / on_error。内置实现(taskiq/middlewares/)已经展示了它的能力边界:SimpleRetryMiddleware 与 SmartRetryMiddleware(指数退避重试)、PrometheusMiddleware(指标)、OpenTelemetryMiddleware(链路追踪)、TaskiqAdminMiddleware(对接管理面板)。

      
broker = broker.with_middlewares(
    SimpleRetryMiddleware(default_retry_count=3),
)

    

  


  

    ▸TaskiqScheduler + ScheduleSource独立进程定时触发器:只负责"按时把任务 kick 出去",不执行任务
    

      
调度器(taskiq/scheduler/)从一个或多个 ScheduleSource(taskiq/abc/schedule_source.py)读取调度计划。内置 LabelScheduleSource 直接从任务装饰器的 schedule 标签读 cron 表达式(cron 解析靠依赖 pycron);插件生态里还有把计划存进 Redis 的动态调度源。注意:同一时刻只能跑一个 scheduler 实例,跑 N 个就会重复触发 N 次。

      
@broker.task(schedule=[{"cron": "*/5 * * * *", "args": [1]}])
async def heavy_task(value: int) -> int:
    return value + 1

scheduler = TaskiqScheduler(broker, sources=[LabelScheduleSource(broker)])

    

  


  

    ▸Serializer / Formatter两侧消息怎么变成字节:默认 JSON,可换 orjson / msgpack / cbor
    

      
taskiq/abc/formatter.py 决定 TaskiqMessage 对象与传输结构的映射,taskiq/abc/serializer.py 决定最终字节编码。这意味着 taskiq 不锁定消息格式——甚至可以做成与其他系统互通的格式。可选依赖 taskiq[orjson]、taskiq[msgpack]、taskiq[cbor] 提供现成实现。默认消息长这样:

      
{
  "task_id": "f6b1...",
  "task_name": "my_project.module1.task",
  "args": [1, 2, 3],
  "kwargs": {"a": 1},
  "labels": {"retry_on_error": true}
}

    

  


  

    ▸Dependencies + TaskiqStateWorker 端FastAPI 风格的依赖注入:任务函数直接 Depends 数据库连接池
    

      
依赖注入由姊妹库 taskiq_dependencies 提供(核心包的硬依赖之一)。配合 broker 的生命周期事件(WORKER_STARTUP / CLIENT_STARTUP / WORKER_SHUTDOWN / CLIENT_SHUTDOWN),典型玩法是:worker 启动时建好 Redis / DB 连接池放进 state,任务函数用 TaskiqDepends 取用——和 FastAPI 的心智模型完全一致,这也是它对 FastAPI 用户最友好的地方。

      
@broker.task
async def my_task(
    db_pool: Annotated[Pool, TaskiqDepends(get_pool)],
) -> None: ...

05 · 真实项目结构

  
读源码从哪里入手

  
仓库本体不大,核心包就是根目录下的 taskiq/。橙色是理解主线时最值得先读的文件,悬停任意一行可见说明。

  

    
taskiq/核心 Python 包(pyproject.toml 中 name = "taskiq")

    
├── abc/全部抽象基类:broker.py、result_backend.py、middleware.py、schedule_source.py、serializer.py、formatter.py —— 扩展点即在此

    
├── kicker.pyKicker:组装 TaskiqMessage,.kiq() 的真正实现

    
├── receiver/worker 端执行引擎:receiver.py 主循环、params_parser.py 按类型标注解析参数

    
├── brokers/内置 broker:inmemory_broker.py(测试)、zmq_broker.py、shared_broker.py

    
├── result_backends/仅 dummy.py —— 真实后端在插件包里

    
├── middlewares/simple_retry / smart_retry / prometheus / opentelemetry / taskiq_admin

    
├── scheduler/TaskiqScheduler 主循环与调度合并逻辑

    
├── schedule_sources/label_based.py:从任务标签读 cron 计划

    
├── cli/CLI 实现:worker/(含多进程 process_manager.py、--reload 热重载 watcher.py)与 scheduler/

    
├── message.py · task.py · labels.py数据模型:TaskiqMessage、AsyncTaskiqTask(get_result / wait_result)、标签

    
├── depends/ · context.py · state.py · events.py依赖注入入口、任务上下文、全局 state、生命周期事件

    
└── __main__.pyconsole script 入口:pyproject 里 taskiq = "taskiq.__main__:main"

    
docs/官方文档源码(guide/architecture-overview.md 是最好的架构入门)+ 可运行示例 docs/examples/

    
tests/pytest 测试套件

    
pyproject.toml运行时依赖仅 7 个:pydantic、taskiq_dependencies、pycron、anyio、aiohttp、packaging、typing-extensions

  







  
06 · 生态与部署形态

  
核心是框架,能力靠插件,进程分三种

  

    

      
插件生态(taskiq-python 组织下的兄弟仓库)

      
    
        
  • taskiq-aio-pika — RabbitMQ broker(官方生产推荐之一)
    • 
        
  • taskiq-nats — NATS / JetStream broker(官方生产推荐之一)
    • 
        
  • taskiq-redis — Redis broker + result backend + 动态调度源(结果后端的事实标准)
    • 
        
  • taskiq-aio-kafka — Kafka broker
    • 
        
  • taskiq-fastapi / taskiq-aiohttp — 框架集成:在 worker 里复用应用的依赖注入
    • 
        
  • 可选 extras:taskiq[reload] 热重载、taskiq[metrics]、taskiq[opentelemetry]、taskiq[orjson|msgpack|cbor]、taskiq[uv](uvloop)
    • 
      

    

    

      
部署时你在运维三种进程

      
    
        
  • 应用进程(FastAPI 等):只 import broker 并 .kiq(),记得启动时 await broker.startup()
    • 
        
  • worker 进程:taskiq worker myapp.tkq:broker -w 4,可水平扩展任意多副本;-w 控制单机子进程数,--max-async-tasks 控制每进程并发协程数
    • 
        
  • scheduler 进程(需要定时任务才有):taskiq scheduler myapp.tkq:scheduler,全集群只能一个实例
    • 
      

      
再加上外部消息系统(RabbitMQ / NATS…)与结果存储(Redis…),就是完整拓扑。测试环境用 InMemoryBroker 一键把三种进程折叠成一个。

    

  

  
常用 CLI(真实参数名,来自 taskiq/cli/worker/args.py)taskiq --help

  
# 启动 worker:4 个子进程,自动发现 tasks.py,代码变更热重载(需 taskiq[reload])
taskiq worker myapp.tkq:broker --workers 4 --fs-discover --tasks-pattern "**/tasks.py" --reload

# 关键运行参数
--max-async-tasks 100    # 每个 worker 进程的最大并发协程数
--max-prefetch 0         # 预取消息数
--ack-type when_saved    # 确认时机:when_received / when_executed / when_saved
--max-fails -1           # 子进程崩溃重启上限

# 启动调度器(只跑一个实例!)
taskiq scheduler myapp.tkq:scheduler







  
07 · 对比、边界与采用风险

  
该不该用它,取决于你站在哪

  

  

    
taskiqCeleryDramatiqarq

    
      
原生 async 任务✔ 核心设计✘ 有限/需变通✘ 同步模型✔

      
同步任务✔ 线程池执行✔✔✘

      
Broker 可插拔✔ RabbitMQ/NATS/Redis/Kafka…✔ RabbitMQ/Redis…△ RabbitMQ/Redis✘ 仅 Redis

      
类型标注 & IDE 补全✔ PEP-612,全量 typed✘ 较弱△△

      
依赖注入✔ FastAPI 风格✘✘✘

      
工作流编排(chain/chord)✘ 需自己组合✔ canvas 完善△ pipeline/group✘

      
生态成熟度 / 社区规模△ 较新,增长中✔ 十余年积累△ 稳定小巧△

    
  

  


  

    

      
适合

      
    
        
  • 技术栈已是 FastAPI / AioHTTP / aiogram 等 asyncio 生态,想要同一套并发模型和 DI 心智
    • 
        
  • 需要在 broker 上有选择权(比如公司已有 NATS / Kafka)
    • 
        
  • 重视类型安全和 IDE 体验的团队
    • 
        
  • 想学习"任务队列如何设计"的读者:代码量小、抽象干净,abc/ 目录就是教科书
    • 
      

    

    

      
不适合

      
    
        
  • 同步 Django + Celery 已稳定运行的存量系统——迁移收益有限
    • 
        
  • 重度依赖 Celery canvas(chord / group / chain)做复杂任务编排的场景
    • 
        
  • 只想"HTTP 响应后干点小事"的需求:FastAPI 自带 BackgroundTasks 更轻,不必引入消息中间件
    • 
      

    

    

      
采用前想清楚的成本与风险

      
    
        
  • PyPI 分类仍标注 Development Status :: Alpha,API 有演进空间,升级需读 changelog
    • 
        
  • 能力分散在多个插件包,broker / backend 插件的成熟度不一,选型要各自验证
    • 
        
  • scheduler 单实例约束意味着它是个单点,高可用需自行兜底(如 k8s 单副本 + 快速重启)
    • 
        
  • 周边工具(监控面板、社区问答)远少于 Celery,疑难问题更依赖读源码
    •
