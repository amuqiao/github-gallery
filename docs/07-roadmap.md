# 07 · 分期路线(Roadmap)

这篇回答:**这套系统按什么顺序造出来。** 它把前面各篇描述的完整蓝图,拆成 4 个可交付的
阶段,并解释排序背后的一条原则——**先地基后功能、可延后不重构**。

- **这篇负责**:每期的产出范围、期与期之间的依赖、排序理由。
- **这篇不负责**:具体实现细节(见对应的 [02](./02-domain-model.md) / [03](./03-architecture.md) /
  [04](./04-navigation-ux.md) / [05](./05-frontend.md) / [06](./06-api-contract.md))。
  这里只讲"什么时候做什么",不讲"怎么做"。

---

## 排序原则:先地基后功能,可延后不重构

一句话:**每一期都建立在上一期的稳定地基之上,后期功能只是叠加,不需要推翻前期结构重做。**

- **先地基**:Phase 1 先把分层架构、实体分表、仓储层落地。地基一旦稳,后续功能都是往上叠。
- **可延后**:一个功能如果**只依赖已建成的部分、不被其他功能依赖**,就可以放到后面做,
  且放后面也不会导致前面重写。
- 典型体现:**知识层(Phase 2)排在自动流(Phase 3)之前**——因为知识层只依赖「库」,
  不依赖抓取;而自动流是相对独立的输入端,晚点接上不影响已建成的库与知识层。
- 反例规避:如果先做自动流再补分层地基,就会在没有仓储层的临时结构上堆抓取逻辑,
  日后重构伤筋动骨。所以地基必须最先。

---

## Phase 1 · 地基重构(MVP)

**目标**:立起整个系统的骨架,让"手动收藏一个项目、分类打标、按需 AI 分析、在画廊里浏览"这条最小闭环能跑通。

**产出**

- 后端**四层 + 仓储层**落地(API / 服务 / 仓储 / 领域模型;见 [03](./03-architecture.md))。
- **实体分层**:`batch` / `candidate` / `repo` / `doc` 四表分开建立(见 [02](./02-domain-model.md))。
- **库的 CRUD + 筛选/搜索**:按 `category` / `tag` / `status` / `language` / `q` 筛选(见 [06](./06-api-contract.md))。
- **按需 AI 分析**:收藏晋升那一刻触发,AI 未配置时优雅降级(见 [01](./01-product-model.md) 的 AI 触发时机)。
- **前后端分离骨架**:FastAPI 纯 JSON API + React SPA;库画廊页与 repo 详情页(见 [04](./04-navigation-ux.md) / [05](./05-frontend.md))。

**为什么先做**:这是所有后续功能的地基。四层依赖方向、仓储层、实体契约在这里定型,
Phase 2/3/4 都在这套结构上叠加,不再重构。

## Phase 2 · 知识层

**目标**:让优质项目能沉淀多角度的深度文档,把"库"从项目清单升级为个人知识库。

**产出**

- **多角度详情文档**:`repo 1──N doc`,`doc_type` 覆盖 `ai-analysis` / `install-usage` /
  `explainer` / `notes` / `custom`(见 [02](./02-domain-model.md))。
- **Markdown 渲染**:doc 以 Markdown 源文本存储,渲染为 HTML 展示。
- **AI 起草文档**:按 `doc_type` 起草某类文档(`POST /api/repos/{repo_id}/docs/generate`)。
- 呈现上走 **Nested Doll**:库 → repo 详情页 → 多篇文档 tab 切换(见 [04](./04-navigation-ux.md))。

**为什么排在自动流之前**:知识层**只依赖已建成的「库」**(repo 已在 Phase 1 落地),
不依赖抓取。它是"往库里加深度"的纯叠加功能,先做能尽早产生价值,且不阻塞任何东西。

> 知识层暂不独立成 Tab,先合进「库」的详情页;等出现跨项目检索文档的需求再拆出来
> (可延后,不重构)——详见 [04](./04-navigation-ux.md)。

## Phase 3 · 自动流

**目标**:接上系统的"输入端",让新项目自动流进来,补全「流 → 库」的完整动线。

**产出**

- **定时抓取**:Trending / Search 抓进候选池(`daily-trending` / `weekly-search` 来源)。
- **流 feed 页**:按批次/日期/来源刷的时间线(见 [04](./04-navigation-ux.md) 的 Filtered View)。
- **收藏晋升闭环**:candidate → repo 的完整流程(`POST /api/candidates/{id}/save`),此刻触发 AI 分析。
- **归档区**:软删除的项目集中在此(`archived_at`;归档与硬删除的语义见 [01](./01-product-model.md))。

**为什么排在这里**:自动流是相对独立的输入端。库(Phase 1)和知识层(Phase 2)已经能靠手动贴 URL
运转;自动流是"把喂入自动化"的增强,晚接不影响已建成部分,因此可以放在知识层之后。

## Phase 4 · 增强(触发式)

**目标**:按真实需求出现的信号,增补高级能力。这一期**不预先排期,由触发条件驱动**。

**产出(命中触发条件才做)**

- **全文搜索**:库内容规模到需要更强检索时。
- **语义找相似**:出现"找相似项目"的需求时——这会触发数据库从 SQLite 换到
  **Postgres + pgvector**(升级触发条件见 [03](./03-architecture.md) 的 DB 选型)。
- **更多数据源**:加一个 `fetcher` 即可,不碰其他模块(见 [03](./03-architecture.md) 的 `ingest` 模块解耦纪律)。

**为什么放最后且触发式**:这些都是"规模/需求到了才值得做"的增强。提前做是过度设计;
而因为有仓储层与模块解耦,换库、加数据源都能局部完成,不引发全局重构——这正是
"可延后不重构"的兑现。

## 一图看全

```
Phase 1  地基重构(MVP)        四层+仓储 · 四表分层 · 库 CRUD/筛选 · 按需 AI · 前后端骨架
   │  地基定型,后续只叠加
   ▼
Phase 2  知识层                多角度 doc · Markdown 渲染 · AI 起草   ← 只依赖「库」
   │  往库里加深度,纯叠加
   ▼
Phase 3  自动流                定时抓取 · 流 feed · 收藏晋升闭环 · 归档区   ← 接上输入端
   │  输入端自动化,独立叠加
   ▼
Phase 4  增强(触发式)         全文搜索 · 语义相似(触发换 Postgres+pgvector) · 更多数据源
```
