# 05 · 前端架构与视觉体系

**这篇文档是什么**:定义 GitHub Gallery 前端的技术栈分层、选型理由与视觉取向,回答"前端用什么搭、
为什么这么搭、长什么气质"三个问题。

**不负责什么**:
- 页面层级、路由表、导航模式 → 见 [04-navigation-ux.md](./04-navigation-ux.md)
- REST 端点的路径/入参/出参细节 → 见 [06-api-contract.md](./06-api-contract.md)
- 领域实体字段定义 → 见 [02-domain-model.md](./02-domain-model.md)

**谁读**:负责前端搭建、选型评审、视觉走查的人。

## 1. 心智模型:先分清"分离"与"分层"

前端要处理两件不同的事,不要混在一起理解:

1. **前后端如何分离部署**(运行时关系,见 §2)
2. **前端内部技术栈如何分层**(选型依赖关系,见 §3)

一张图先立住整体骨架:

```
┌─────────────────────────────┐        ┌──────────────────────────┐
│   前端 SPA(React + Vite)    │  HTTP  │   后端 FastAPI            │
│   独立代码仓库位置 / 独立构建 │ ─────▶ │   纯 JSON API,不渲染页面  │
└─────────────────────────────┘  /api  └──────────────────────────┘
        ▲ 开发期:Vite dev server 代理 /api
        ▲ 生产期:FastAPI 静态托管 build 产物,单机即可跑
```

---

## 2. 前后端分离:两套生命周期,一次交付

- **职责边界**:后端 FastAPI 只出 JSON,不拼 HTML、不管页面路由;前端是完全独立的 SPA,自己管路由、
  状态、渲染。这样两边可以独立开发、独立测试,互不阻塞。
- **开发期**:前端跑 Vite dev server(带热更新),把请求路径 `/api/*` 代理到本地 FastAPI 进程,
  避免开发时手动处理跨域。
- **生产期**:前端执行 build,产出静态资源(HTML/JS/CSS);FastAPI 直接挂载并托管这份 build 产物。
  最终交付形态是**单进程、单机可跑**——这与产品定位"本地部署、单人使用"一致,不引入额外的
  Nginx/反向代理等运维复杂度。

| 阶段 | 前端角色 | 请求路径 | 部署形态 |
|---|---|---|---|
| 开发期 | Vite dev server(热更新) | 代理 `/api` → 本地 FastAPI | 两个进程并行 |
| 生产期 | 静态构建产物(HTML/JS/CSS) | FastAPI 直接托管 | 单机单进程 |

## 3. 技术栈分层:谁是地基、谁绑框架、谁与框架无关

这是本项目前端选型中用户最关心的一点,必须讲清楚**每样技术跟 React 框架的绑定强度**,
不能笼统地说"用了一堆库"。分层依据是:**越靠近渲染核心的技术,绑定越深;越靠近样式/展示层的技术,
越容易脱离框架独立存在。**

| 层级 | 技术选型 | 与框架的关系 | 说明 |
|---|---|---|---|
| 地基(必选) | **React + Vite** | 框架本身 | 组件模型、构建工具,整个前端的地基,不可替换 |
| 样式层(框架无关) | **Tailwind CSS** | 与框架无关 | 原子化 CSS 类名方案,本质是纯 CSS 输出,换成 Vue/Svelte 也能直接搬 |
| 组件增强层(绑定 React,选配) | **shadcn/ui** | 绑定 React | 不是黑盒组件库,而是把组件**源码**复制进项目;源码本身用 React 写,因此绑定 React,但外观 100% 可定制,不受组件库默认皮肤限制 |
| 动效层(绑定 React,选配) | **Framer Motion** | 绑定 React | 以 React hooks / 组件 API 提供动效能力(卡片入场、钻入/返回过渡、feed 局部刷新),脱离 React 无法直接使用 |
| 文档渲染层(详情页专用,选配) | **react-markdown** + 代码高亮 + 目录 | 绑定 React | 仅服务详情文档(doc.content 的 Markdown 渲染),不影响其他页面 |
| 装饰层(纯 CSS,选配) | 一款讲究的字体 | 与框架无关 | 通过 `@font-face` / CSS 变量引入,与技术栈完全解耦 |

**读法**:从上到下,绑定强度先"必选"、后"无关"、再回到"绑定"、最后回到"无关"——不是单调递增
或递减的关系,而是"地基必选,样式层可迁移,增强层为提升开发效率而绑定框架,装饰层始终独立"。

几点需要澄清的绑定关系,避免误解:

- **Tailwind 不因为用了 React 项目就变成"React 专属"**——它输出的是普通 CSS 类名,选它是因为
  与 shadcn/ui 的默认约定一致,搭配顺畅,不是因为技术上必须绑定。
- **shadcn/ui 不是安装一个 npm 组件库**,而是 CLI 把组件源码复制进代码仓库,因此"绑定 React"
  这件事具体到"这些组件文件本身就是用 React 写的",而不是"依赖某个 React 专属运行时机制"。
  这也是为什么它比 Ant Design / Material UI(MUI)更适合本项目——见 §4。
- **Framer Motion、react-markdown 是选配增强**,不是地基;去掉它们项目仍能跑,只是失去动效与
  文档渲染能力。地基只有 React + Vite 一项是不可替代的。

## 4. 视觉取向:为什么不是 Ant Design / MUI

产品对审美的要求是**一等需求**(见 [01-product-model.md](./01-product-model.md)),
目标气质是"克制高级",需要明确排除两种反面:

- ❌ **Ant Design 式的"企业通用"味**:默认皮肤辨识度高、组件规格统一但个性弱,一眼看出是"后台管理系统"。
- ❌ **渐变光效堆砌**:靠强视觉冲击(大渐变、玻璃拟态、炫光)制造"酷炫"感,容易显得浮躁、廉价。

高级感不来自某个组件库自带的皮肤,而来自四个可以逐一落实的要素:

| 要素 | 说明 |
|---|---|
| 克制配色 | 主色 + 中性灰阶为主,强调色少而准,不满屏撞色 |
| 一致间距节奏 | 卡片内边距、栅格间隙、板块留白遵循统一的间距刻度,不同页面观感一致 |
| 恰当微动效 | 用 Framer Motion 做卡片入场、页面钻入/返回、feed 局部刷新等**功能性**动效,不做无意义的炫技动画 |
| 好字体 | 一款讲究的字体作为纯 CSS 层的点睛,提升阅读质感 |

**为什么选 Tailwind + shadcn/ui,而不是 Ant Design / MUI**:

| 维度 | Ant Design / MUI | Tailwind + shadcn/ui |
|---|---|---|
| 组件来源 | 黑盒 npm 包,内部样式封装 | 组件源码直接复制进项目,完全可读可改 |
| 定制自由度 | 需要覆盖主题变量/深度改样式,容易"改不干净" | 源码在手,想改哪里改哪里,不受制于组件库版本 |
| 默认设计语言 | 自带强辨识度的"企业系统"皮肤 | 无默认皮肤,长相完全由项目自己的 Tailwind 配色/间距决定 |
| 与"克制高级"目标的契合度 | 低(需要大量反向覆盖才能摆脱默认味) | 高(从零定义外观,天然贴合定制诉求) |

结论:Ant Design / MUI 更适合"快速搭出标准后台"的场景;本项目要的是**独特的、经过设计的个人风格**,
因此选择"样式原子化(Tailwind)+ 组件源码可控(shadcn/ui)"的组合,把审美决定权留在项目自己手里。

## 5. 卡片视觉元素:从领域字段到界面表达

卡片是本产品最高频的视觉单元,其视觉元素**直接来自领域字段**(定义见
[02-domain-model.md](./02-domain-model.md) 与 [01-product-model.md](./01-product-model.md)),
不是额外发明的界面概念。梳理字段与视觉元素的对应关系:

| 视觉元素 | 来源字段 | 适用实体 | 说明 |
|---|---|---|---|
| 语言色点 | `language` | candidate、repo 均有 | 一个色点 + 语言名,展示项目主语言 |
| star 数 | `stars` | candidate、repo 均有 | 数值展示,体现项目热度 |
| 分类色标 | `category` | 仅 repo | candidate 不含 AI 字段(见 [02-domain-model.md](./02-domain-model.md)),因此流里的卡片**没有**分类色标,只有收藏晋升为 repo 后才有 |
| 状态徽章 | `status`(4 个取值:关注中/想学/正在学/在用) | 仅 repo | candidate 没有 status,只有"是否已收藏"的角标 |
| 已收藏角标 | `saved_repo_id` 是否非空 | 仅 candidate | 流里用来标记"这张候选卡片已经收藏进库" |

> **已定稿(取色方案)**:
> - **语言色点**:直接采用 GitHub Linguist 官方语言配色映射(现成、约定俗成、无需自造)。
> - **分类色标**:由分类名做稳定 hash,映射到一组固定的、克制的柔和色板(约 8–12 色),保证同一分类恒定同色、整体不刺眼。
> - **状态徽章**:4 态固定配色(用 Tailwind 色系表达语义)——`watching` → `slate`(中性观望)、`to-learn` → `amber`(待办提醒)、`learning` → `emerald`(进行中)、`using` → `violet`(强调/已落地)。
> - 具体 hex 落在实现期的 Tailwind theme token 里定义,以上语义与色系为准。

### 三处展示场景的差异化表达

同样的卡片元素,在三个页面场景里承担不同的表达重点(页面结构见
[04-navigation-ux.md](./04-navigation-ux.md)):

1. **画廊卡片(库 · Filtered View · 网格)**
   信息密度最高的场景:语言色点 + star + 分类色标 + 状态徽章**全部展示**,配合侧栏筛选,
   让用户一眼扫出"这批项目分别是什么语言、什么状态、什么分类"。

2. **流的时间感(流 · Filtered View · feed)**
   按批次/日期分组滚动,强调"时间脉络"而非"分类结构"——因为 candidate 不含分类/状态字段,
   卡片上只有语言色点、star、已收藏角标,视觉重心让位给批次分隔与时间戳,配合 Framer Motion
   做新批次插入时的局部刷新动效。

3. **详情页排版(库 → 详情 → 文档 · Nested Doll)**
   卡片元数据收进页面顶部的 header(语言、star、分类、状态一行呈现),页面主体让位给
   `doc.content` 的 Markdown 渲染——由 react-markdown + 代码高亮 + 目录组成,是"卡片元素退场、
   文档阅读体验登场"的场景。

### Framer Motion 的落点(与 [04-navigation-ux.md](./04-navigation-ux.md) 的导航模型对应)

- 卡片入场:画廊/feed 加载时的错落浮现
- 钻入/返回过渡:点击卡片进入详情页、返回列表页的过渡动效(对应 Nested Doll 导航)
- feed 局部刷新:新批次插入流时,不整页刷新,只对新增卡片做过渡

## 6. 契约同步:后端 OpenAPI → 前端 TS 类型

FastAPI 天然可以导出 OpenAPI schema;前端基于这份 schema **生成 TypeScript 类型**,
而不是手工在前端重复定义一遍接口类型。好处:

- 后端接口字段变化时,前端类型能同步更新,减少"后端改了字段、前端类型没更新导致运行时报错"的问题。
- 类型定义只有一个真源(后端 Pydantic 模型 → OpenAPI schema),前后端不会出现两套互相漂移的类型定义。

具体的接口路径与出入参字段以 [06-api-contract.md](./06-api-contract.md) 为准;本篇只约定
"契约同步"这一机制本身。

> **已定稿(工具与时机)**:用 `openapi-typescript` 从 FastAPI 的 `/openapi.json` 生成类型,配合
> `openapi-fetch` 做类型安全的请求调用。触发时机:**开发期手动脚本**(`npm run gen:api`),后端接口
> 有变动时重跑即可;不进构建关键路径,避免每次 build 都依赖后端在线。

## 7. 小结:一张表回顾分层与理由

| 问题 | 答案 |
|---|---|
| 前后端怎么分离 | FastAPI 纯 JSON API + 独立 SPA;开发期 Vite 代理、生产期 FastAPI 静态托管 |
| 地基是什么 | React + Vite,唯一必选、不可替代 |
| 样式层为什么独立 | Tailwind 是框架无关的原子化 CSS,选它是搭配习惯而非技术绑定 |
| 组件/动效为什么选配 | shadcn/ui、Framer Motion 绑定 React,是提升效率的增强,不是地基 |
| 为什么不用 Ant Design/MUI | 二者默认皮肤"企业通用"味强,与"克制高级"的审美目标冲突;shadcn/ui 源码可控更贴合定制诉求 |
| 卡片元素从哪来 | 直接映射领域字段(language/stars/category/status),不额外发明概念 |
| 前后端类型如何对齐 | FastAPI 出 OpenAPI,前端据此生成 TS 类型,单一真源 |
