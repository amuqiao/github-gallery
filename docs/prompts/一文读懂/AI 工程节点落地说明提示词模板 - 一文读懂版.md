# AI 工程节点落地说明提示词模板 - 一文读懂版

本文用于把《一文读懂》类内容从“概念解释”拉回“工程落地”：讲清一个 AI 能力如何端到端跑通，每个节点用什么依赖、模型、API 或服务实现，输入输出如何衔接，如何评估，后续如何替换和升级。

## 使用方式

默认只复制一个主模板：

- 想探索一个 AI 工程想法怎么落地：复制 `主模板 1`
- 想讲清一个已有工程怎么实现：复制 `主模板 2`

下面的纠偏补丁只在模型跑偏时追加，不需要每次都复制。

## 主模板 1：探索想法如何落地

~~~md
请按“AI 工程节点落地说明”的方式生成《一文读懂》交互式 HTML 内容。

当前主题：[填写你要探索的 AI 工程想法，例如：以图搜图、RAG、多模态检索、语音识别质检]

我的目标：
我不是要完整项目代码，也不是要后端工程脚手架。
我想知道这个 AI 能力如何从 0 到 1 落地：先用 Python 脚本 POC 跑通端到端链路，再理解小团队、中团队、企业级别如何升级。

请按下面顺序讲解。

1. 先给端到端链路
- 原始输入是什么。
- 最终输出是什么。
- 中间有哪些关键节点。
- 每个节点的输出如何成为下一个节点的输入。

2. 再讲每个关键节点如何落地
每个节点按这个格式写：

节点：
解决什么：
默认落地方式：
推荐依赖 / API / 模型 / 服务：
是否建议手写：
输入：
处理逻辑：
输出：
中间产物：
伪代码：
平替方案：
升级方案：
常见坑：

要求：
- 输入输出必须具体到数据形态，例如 `list[str]`、`image_path`、`ndarray[n, dim]`、`[(id, score)]`、JSON、CSV、SQLite 表。
- 伪代码只展示主逻辑，不写完整项目。
- 不要只说“使用 embedding / BM25 / 向量数据库”，必须说明用什么依赖、怎么计算、怎么保存、怎么查询。
- 如果有成熟依赖，不要暗示读者应该手写算法。

3. 讲清 POC 怎么跑通
- 准备哪些最小样例数据。
- 用 `uv` 管理依赖时大概需要哪些包。
- 每一步脚本读入什么，输出什么。
- 输出文件、索引文件、向量矩阵、JSON、CSV 或数据库表大概长什么样。
- 如何用 3 到 5 条样例验证链路确实跑通。

4. 讲清存储选型
- 文件系统 / 对象存储负责保存什么。
- 关系数据库负责保存什么。
- 向量索引 / 向量数据库负责保存什么。
- 全文索引负责保存什么。
- 图数据库什么时候才需要。
- POC 阶段哪些数据库可以不用。
- 数据量上来后，哪些部分升级到 PostgreSQL、pgvector、Qdrant、Milvus、Elasticsearch、OpenSearch、S3 / MinIO 等。

5. 讲清评估指标
按任务选择合适指标，例如：
- 检索 / RAG：Recall@K、Precision@K、MRR、NDCG、命中率、答案引用正确率。
- 以图搜图 / 相似图片检索：Recall@K、mAP、Top-K 人工相关性、去重准确率。
- 分类：Accuracy、Precision、Recall、F1、混淆矩阵。
- 生成：事实一致性、引用覆盖率、人工评分、幻觉率、格式通过率。
- 工程指标：延迟、吞吐、索引构建耗时、存储成本、API 成本、失败率。

每个指标要说明：
- 它衡量什么。
- POC 阶段如何低成本验证。
- 上线后如何持续监控。

6. 最后给升级路线
按 POC / 小团队 / 中团队 / 企业级别分层说明：
- 哪些组件先不要上。
- 哪些组件什么时候替换。
- 替换后解决什么问题。
- 替换会带来什么成本。

请避免：
- 只讲概念优缺点，不讲工程如何落地。
- 只画架构图，不说明每个节点输入输出。
- 直接生成完整项目代码或复杂服务架构。
- 把 POC、小团队、中团队、企业级方案混在一起。
~~~

## 主模板 2：讲清已有工程如何实现

~~~md
请按“AI 工程节点落地说明”的方式讲清这个已有 AI 工程、开源项目或系统实现。

当前对象：[填写项目名、仓库、论文工程、系统名或已有方案]

我的目标：
我不是要重新设计一个理想架构，也不是要泛泛介绍概念。
我想读懂这个工程真实是怎么跑起来的：用了哪些库、模型、API、服务和存储，每个节点输入输出如何衔接，哪些地方可以替换或升级。

请按下面顺序讲解。

1. 先给端到端数据流
- 原始输入是什么。
- 最终输出是什么。
- 中间有哪些关键节点。
- 每个节点的输出如何进入下一个节点。
- 哪些节点是离线构建，哪些节点是在线查询或推理。

2. 再讲每个关键节点的真实实现
每个节点按这个格式写：

节点：
当前实现：
解决什么：
输入：
处理逻辑：
输出：
中间产物：
关键依赖 / 模型 / API / 服务：
代码或配置里常见名称：
可替换点：
升级方案：
常见坑：

要求：
- 按真实实现解释，不要改写成推荐方案为主。
- 输入输出必须具体到数据形态。
- 不要只画架构图，要讲清每个节点如何落地。
- 不要生成完整项目代码，只给必要伪代码或流程片段。

3. 讲清依赖和组件职责
- 哪些库负责模型推理。
- 哪些库负责索引或检索。
- 哪些库负责数据处理。
- 哪些服务负责存储。
- 哪些组件只是工程封装，不是核心算法。

4. 讲清可替换点和升级路线
- 哪些节点可以本地替换。
- 哪些节点替换会影响上下游数据结构。
- 哪些节点适合从 POC 依赖升级到生产服务。
- 替换后解决什么问题，也会带来什么成本。

5. 讲清评估方式
- 这个工程应该用哪些指标判断效果。
- 需要准备什么测试集或样例。
- 哪些指标反映模型效果。
- 哪些指标反映工程质量，例如延迟、吞吐、成本、失败率。

请避免：
- 把已有工程讲成通用科普。
- 只列技术栈，不讲每个技术栈承担的节点职责。
- 只说“用了向量库 / 用了 embedding / 用了 BM25”，但不解释输入输出和落地方式。
~~~

## 纠偏补丁

这些片段只在模型输出跑偏时追加。

### 补丁 1：节点讲得太虚

~~~md
你刚才的输出仍然偏概念化。请重写关键节点说明。

每个节点必须补齐：
- 用什么成熟依赖、模型、API 或服务。
- 输入数据结构。
- 输出数据结构。
- 中间产物。
- 伪代码。
- 平替方案。
- 升级方案。

不要只写“使用 BM25”“使用 embedding”“使用向量数据库”。
例如 BM25 要说明可用 `rank-bm25`、`bm25s`、SQLite FTS、Elasticsearch 或 OpenSearch。
Embedding 要说明可用 `sentence-transformers`、CLIP / OpenCLIP、本地 embedding 模型或云 API。
~~~

### 补丁 2：没讲清存储选型

~~~md
请补充存储选型说明。

必须明确区分：
- 原始文件保存在哪里。
- 元数据和业务状态保存在哪里。
- embedding 保存在哪里。
- 关键词索引保存在哪里。
- 什么情况下才需要图数据库。

请分别说明 POC、小团队、中团队、企业级别的选择。
不要默认所有方案都需要向量数据库、关系数据库或图数据库。
~~~

### 补丁 3：没讲评估指标

~~~md
请补充评估指标。

不要只说“效果更好”或“准确率更高”。
请说明：
- 应该用哪些指标。
- 每个指标衡量什么。
- POC 阶段如何构造小样例验证。
- 上线后如何持续监控。
- 模型指标和工程指标分别是什么。
~~~

### 补丁 4：内容发散，需要收口

~~~md
请收口到工程落地链路。

最终内容必须让读者回答：
- 第一份输入数据是什么。
- 第一个脚本或节点做什么。
- 每一步输出什么。
- 下一个节点吃什么。
- 最小 POC 用哪些依赖能跑通。
- 哪些组件现在不用上，什么时候再升级。

不要继续扩展泛泛的背景、趋势、优缺点或完整工程架构。
~~~

## 示例标尺

下面示例用于校准生成粒度。重点不是代码完整，而是让读者知道“这个节点实际怎么做”。

### BM25 关键词召回

~~~text
节点：BM25 关键词召回

解决什么：
用关键词匹配补足 embedding 语义检索漏掉的精确词、编号、专有名词。

默认落地方式：
Python POC 用 `rank-bm25` 或 `bm25s`。
不建议手写 BM25，除非只是教学演示。

输入：
documents: list[str] 或 list[list[str]]
query: str

处理逻辑：
对 documents 和 query 做同样的分词 / 归一化。
建立 BM25 索引。
对 query 打分，取 Top-K。

输出：
[(doc_id, score), ...]
或带原文 chunk 的 Top-K 候选列表。

伪代码：
tokenized_docs = tokenize(documents)
bm25 = BM25Okapi(tokenized_docs)
scores = bm25.get_scores(tokenize(query))
top_k = argsort(scores)[-k:]

平替方案：
POC：rank-bm25 / bm25s
小规模：SQLite FTS / Whoosh
中大型：Tantivy / Elasticsearch / OpenSearch

常见坑：
中文没有分词。
文档和 query 分词规则不一致。
只用 BM25 会漏掉语义相似但字面不同的内容。
~~~

### Embedding 语义向量

~~~text
节点：Embedding 语义向量

解决什么：
把文本、图片、音频等对象变成可比较的向量，用于语义相似度、召回、聚类或去重。

默认落地方式：
文本 POC 用 `sentence-transformers` 或云 embedding API。
图像 POC 用 CLIP / OpenCLIP。
不建议自己训练 embedding 模型，除非已经有明确数据和评测闭环。

输入：
chunks: list[str]
或 image_paths: list[str]

处理逻辑：
加载模型。
批量编码输入。
可选：L2 normalize。
保存向量和原始对象 ID 的映射。

输出：
embeddings: ndarray[item_count, dim]
ids: list[str]
metadata: list[dict]

伪代码：
model = load_embedding_model()
embeddings = model.encode(inputs, normalize_embeddings=True)
save({"ids": ids, "embeddings": embeddings, "metadata": metadata})

平替方案：
文本 POC：sentence-transformers / bge / e5 / GTE
图像 POC：CLIP / OpenCLIP
API：OpenAI / Voyage / Jina 等 embedding API
大规模：批处理 + FAISS / Qdrant / Milvus / pgvector

常见坑：
chunk 切得太碎或太长。
没有归一化却直接按余弦相似度理解。
向量和原始对象 ID 的映射丢失，导致检索结果无法回到原文。
~~~

### 以图搜图最小链路

~~~text
原始输入：
query_image_path: str
gallery_image_paths: list[str]

节点 1：图片向量化
推荐实现：OpenCLIP / CLIP
输入：image_paths
输出：image_embeddings: ndarray[n, dim]

节点 2：向量索引
推荐实现：POC 用 FAISS 本地索引；在线服务可用 Qdrant / Milvus / pgvector。
输入：image_ids + image_embeddings
输出：vector_index + id 映射表

节点 3：相似图片召回
推荐实现：对 query 图片算 embedding，再在索引里 Top-K 搜索。
输入：query_embedding
输出：[(image_id, score), ...]

节点 4：元数据回查
推荐实现：POC 用 JSON / SQLite；生产用 PostgreSQL。
输入：image_id
输出：图片路径、标题、标签、业务字段、可访问 URL。

最终输出：
Top-K 相似图片列表，每项包含 image_id、score、thumbnail_url、metadata。

选型判断：
POC 不一定需要向量数据库，FAISS 本地索引即可。
需要业务字段、状态、权限时才引入关系数据库。
只有要表达复杂实体关系、路径推理、知识图谱时才考虑图数据库。
~~~

## 维护规则

- 本文只维护“AI 工程节点如何落地”的提示词，不维护具体领域完整方案。
- 主模板必须能单独复制使用，不依赖下面的补丁。
- 纠偏补丁只解决模型跑偏问题，不重复主模板。
- 新增示例时必须包含输入、输出、依赖、伪代码、平替和升级。
