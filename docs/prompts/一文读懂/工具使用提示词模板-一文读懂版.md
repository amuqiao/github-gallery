# 工具使用提示词模板 - 一文读懂版

本文维护工具使用类《一文读懂》专项提示词，适用于 FFmpeg、PySceneDetect、yt-dlp、ImageMagick、jq、curl、sox、pandoc 等主要作为 CLI、API、SDK 或库来调用的工具。重点补充指定使用场景下的能力契约、输入输出、最小调用、参数心智模型、工作流嵌入、结果验证和常见边界。

使用方式：直接复制下面代码块作为完整提示词使用；工具名称、使用场景、调用方式、典型输入输出、读者背景和期望深度由具体生成任务补充。多节点 AI pipeline 优先使用 AI 工程节点落地说明模板。

## 完整提示词

```md
为指定工具和指定使用场景生成《一文读懂》单文件交互式 HTML，核心目标是让读者从一个真实任务出发，看懂这个工具如何把输入处理成输出、如何正确调用、关键参数如何影响结果，并能把它嵌入自己的工作流。

建议：
- 以下维度按工具特点取舍，不要机械逐项展开；优先围绕一条最能解释工具价值的真实使用主线组织内容
- 从能力契约切入，先讲清这个场景下工具负责什么任务、输入是什么、输出是什么、典型使用者是谁，以及哪些事情不该交给它解决
- 围绕最小可运行调用展开，用一个真实但足够小的 CLI/API/SDK 例子展示从输入文件、参数、执行过程到输出产物的完整路径
- 讲清调用面，按主题说明 CLI、API、库函数、配置文件或脚本集成分别适合什么使用方式，不把文章写成入口大全
- 讲清参数心智模型，抓住最会改变行为、质量、速度、格式、边界或兼容性的少数关键参数，不要罗列完整参数手册
- 讲清结果如何验证：输出文件、日志摘要、元数据、可视化结果、抽样检查、对比命令或校验指标中，哪些最能判断工具是否真的做对了
- 讲清自动化调用契约：脚本或流水线如何判断成功/失败，`exit code`、`stdout/stderr`、输出产物、覆盖/追加行为、部分输出和幂等性中哪些最关键
- 讲清如何嵌入工作流：它通常放在 pipeline 的哪一步，前置输入如何准备，后续产物如何交给其他工具、脚本、服务或人工审核
- 讲清常见失败边界：路径、编码、格式、版本、依赖、权限、性能、精度、阈值、资源占用或平台差异按主题选择说明
- 重视对比和取舍，说明它和相近工具、手写脚本、GUI 软件、云服务或项目内置能力相比，什么时候适合用，什么时候不适合用
- 可根据工具类型灵活调整结构：媒体工具突出格式、编码、时间轴和产物验证；数据工具突出输入结构、过滤转换和输出契约；网络工具突出请求、响应、鉴权和错误码；AI 辅助工具只有在文章仍聚焦单工具调用层时使用本模板，重点放在输入质量、参数、推理结果和后处理
- 重视可视化：用输入输出对照、命令拆解、参数影响示意、工作流位置图、文件结构或错误路径呈现工具主线
- 善用交互：可通过命令分段高亮、参数切换、输入样例切换、输出预览、错误案例对照、验证步骤展开等方式让读者主动探索
- 示例尽量真实、最小、可验证，可包含命令/API 调用、输入样例、关键参数、输出片段、元数据、目录片段或最小脚本
- 单文件内联资源，离线可打开，自然中文表达即可，专业术语、命令、参数、代码、文件名、格式名、库名保留英文
- 首屏视觉贴合工具本身，让人一眼看到真实任务、输入输出和最主要的调用路径，而不是只展示标题或抽象装饰
```

## 维护规则

- 本模板只维护工具使用的对象差异：能力契约、调用入口、输入输出、关键参数、数据形态变化、工作流集成、结果验证、失败边界和使用取舍。
- 模板正文必须保持可独立复制使用，不依赖其他提示词片段。
- 模板应保持生成方向感，不要扩展成完整参数手册、源码审计、部署排障清单或项目架构分析；通用维度只作为取舍依据，具体任务应保留模型组织文章的空间。
- 如果目标是解释工具背后的概念机制，优先使用知识点模板；如果目标是研究项目结构或源码，优先使用开源项目模板；如果目标是多模型、算法阶段和工程节点协同形成的 AI 能力，优先使用 AI 工程节点落地说明模板。
- 对 FFmpeg 这类超大工具，默认围绕具体任务主线展开，例如转码、抽帧、滤镜、切片、封装转换或元数据检查，避免生成“读懂整个工具”的百科文章。
- 如果后续需要深入某个参数族、算法原理、部署排障或性能调优，单独新增专题提示词，不要把本模板变成全量操作手册。
