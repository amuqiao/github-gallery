# AI 工程落地方案提示词模板 - 一文读懂版

本文维护 AI 工程落地方案类《一文读懂》专项提示词，适用于读者已经知道一些相关概念，但还不知道如何把某个 AI 能力从想法变成可运行 demo、可验证 POC、可上线系统的场景。

本文重点不是讲 FastAPI 项目怎么分层，也不是写后端架构教程；重点是帮 Python 开发者判断技术路线、算法与模型、线上/线下链路、开源方案、厂商方案、本地方案、存储选型和团队规模演进。FastAPI 只是默认的 Python 服务化封装方式，用于把能力暴露成 API，不是文章主角。

使用方式：直接复制下面代码块作为完整提示词使用；目标能力、典型输入输出、数据规模、部署环境、读者背景和期望深度由具体生成任务补充。

## 提示词

```md
为指定 AI 工程能力生成《一文读懂》单文件交互式 HTML，核心目标是让读者从“我想实现这个能力，但不知道技术上怎么落地”的状态，走到能判断 demo 怎么跑通、POC 怎么验证、小团队怎么上线、中团队怎么扩展、企业级怎么治理。

默认读者与工程约束：
- 默认读者是 Python 开发者，优先给出 Python 可跑通的实现路线、依赖选择和伪代码
- FastAPI 是默认服务化封装方式，用于 POC 或生产服务暴露 API；不要把文章写成 FastAPI 项目分层、依赖注入或后端架构教程
- 可以讨论全栈方案、托管平台、低代码平台或厂商方案，但必须回到“Python 开发者如何跑通流程、如何选型、如何演进”
- 本模板不是要求覆盖所有维度；每次生成必须根据目标能力、数据规模、团队阶段和部署约束取舍，只展开会改变落地方案的关键决策
- 不要为了“更稳”添加 silent fallback、吞错默认值、空结果兼容或无需求的降级逻辑；异常、缺数据、权限失败和外部依赖失败应显式暴露

建议：

核心主线：
- 以下维度按目标能力特点取舍，不要机械逐项展开；优先围绕“目标能力 -> 最小可跑流程 -> 技术路线选型 -> demo/POC -> 生产演进 -> 风险边界”的主线组织内容
- 从一个具体能力切入，例如“以图搜图”“知识库问答”“语音相似检索”“图片自动打标”“合同信息抽取”“视频内容检索”等，先讲清输入是什么、输出是什么、用户怎么使用、成功标准是什么、哪些事情不由它解决
- 先给读者一条能跑通的最小链路：准备少量样例数据、选择一个可用模型或 API、写一个 Python 脚本完成核心处理、保存结果、发起查询、验证输出；让读者先知道第一版怎么动起来
- 再解释完整工程链路中哪些步骤是离线做的，哪些步骤是线上请求时做的。例如离线导入、清洗、切分、embedding、索引构建、批处理评测；线上查询、召回、重排、过滤、生成或结果返回
- 对每一步讲清“为什么需要它”和“什么时候可以先不做”，避免把 demo、POC 和企业级架构混在同一层

技术路线与选型：
- 对比常见实现路线：本地开源模型、云 API、厂商一体化方案、开源项目二次开发、自研 pipeline、传统算法或规则增强；说明各自适合的数据规模、质量要求、成本、延迟、隐私和团队能力
- 讲清模型怎么选：通用模型、领域模型、多模态模型、embedding 模型、reranker、分类模型、检测模型、ASR/TTS/视觉/LLM 模型分别适合什么任务；说明什么时候用本地模型，什么时候用云模型，什么时候先用 API 验证
- 讲清算法和工程模块怎么选：相似度检索、关键词检索、混合检索、重排、聚类、分类、规则过滤、阈值判定、后处理、人工审核分别放在哪一段链路里
- 讲清依赖和成熟模块：按职责列出可选 Python 库、模型推理运行时、向量索引库、向量数据库、关系数据库、对象存储、任务队列、数据处理库、评测工具和部署组件；不要只堆名称，要说明各自解决哪一类问题
- 讲清开源方案怎么借鉴：区分“直接使用项目”“只借模型”“只借索引/检索模块”“只借 UI/管理后台”“只借评测方法”；不要把文章写成开源项目列表
- 讲清厂商方案怎么判断：云模型 API、托管向量库、对象存储、Serverless、AI 平台、企业知识库平台或搜索平台分别减少了什么工程负担，又带来什么成本、锁定、隐私和可控性问题
- 讲清本地方案怎么判断：适合离线验证、隐私敏感、成本可控或内网部署的场景；同时说明本地模型、GPU/CPU、索引文件、数据更新、部署运维会带来的限制

数据、存储与线上/线下：
- 对“是否需要向量数据库、关系数据库、图数据库、对象存储”给出判断路径，而不是给固定答案
- 关系数据库通常负责业务实体、元数据、任务状态、权限、配额、审计和评测结果；对象存储通常负责原始文件和派生产物；向量索引或向量数据库负责相似度检索；图数据库只有在多跳关系、实体网络或关系推理是核心能力时才考虑
- 说明 demo 阶段可以用什么轻量替代，例如本地目录、JSON/SQLite、FAISS/Chroma、少量样例文件；同时说明这些替代方案到什么规模会遇到瓶颈
- 说明 POC 和生产阶段如何处理数据导入、增量更新、索引重建、版本管理、离线评测集和回滚
- 讲清线上请求链路如何保持简单：用户输入进入 FastAPI 或脚本入口，调用模型/索引/业务规则，返回结构化结果；只有当任务耗时、文件大、并发高或需要批处理时，才引入队列、worker 和任务状态

分阶段落地路线：
- 给出 demo 路线：一天内或最短时间跑通主链路，用最少组件验证“这个能力是否可行”；可以是 Python 脚本、Notebook、少量文件、本地模型或云 API
- 给出 POC 路线：验证真实数据、质量指标、延迟、成本、失败样本和用户反馈；可以加入简单 FastAPI、基础存储、批量导入、最小评测集
- 给出小团队上线路线：保留简单架构，补齐持久化、任务状态、基础权限、日志、配置、部署脚本和人工抽检；避免一开始引入过重平台
- 给出中团队扩展路线：引入更稳定的数据管线、队列/worker、对象存储、向量库或搜索引擎、监控、评测回归、灰度发布和成本观测
- 给出企业级路线：重点讲多租户、权限隔离、审计、合规、私有化部署、容量规划、索引重建、灾备、模型版本管理、人工审核和供应商替换策略
- 每个阶段都说明“新增了什么组件、解决什么问题、带来什么成本、什么时候不值得上”

评估指标与验收：
- 把“怎么评估这个 AI 能力是否可用”作为核心内容讲清楚；功能跑通只说明链路通了，不代表能力达标
- 按任务类型选择指标，不要只写“准确率”：检索/搜索类关注 Recall@K、Precision@K、MRR、NDCG、Top-K 命中率、误召回和漏召回；分类/识别类关注 accuracy、precision、recall、F1、confusion matrix、ROC-AUC 和阈值下的误报/漏报；生成/RAG 类关注答案正确性、引用命中率、faithfulness、context recall、幻觉率、拒答质量和人工评分；抽取/OCR/结构化输出类关注字段准确率、字段召回率、Exact Match、格式合法率和人工修正率；视觉/语音类按任务选择 mAP、IoU、Top-K accuracy、WER、CER、EER 等
- 同时给出工程指标和业务指标：延迟、吞吐、成本、失败率、资源占用、索引更新时间、人工节省时间、审核通过率、用户接受率、投诉率或误判成本，按场景取舍
- 区分 demo、POC、生产阶段的评估深度：demo 用少量人工样例验证方向；POC 建小型标注集和失败样本集；生产阶段做离线回归、线上抽样、人工审核闭环和指标看板
- 讲清评测集怎么构造：样本来源、正负例、难例、边界样本、业务高风险样本、标注规则、人工一致性和版本管理；不要只用随手挑的好样本验证
- 讲清指标达不到时的排查顺序：先看数据和标注，再看模型与 prompt，再看检索/索引/阈值，再看后处理和业务规则，最后再看服务架构

FastAPI 的位置：
- 只在需要服务化时讲 FastAPI：它负责接收请求、上传文件、触发任务、查询状态、返回结果或下载地址
- 给出 1-3 个关键 API 示例即可，例如提交任务、查询任务状态、执行一次检索或获取结果；不要展开成完整后端项目教程
- 如果任务可以用 Python 脚本或 Notebook 跑通，先展示脚本链路，再说明如何包成 FastAPI 服务
- 如果任务需要长时间处理，说明何时从 FastAPI `BackgroundTasks` 升级到独立队列/worker；不要默认所有 demo 都上复杂异步架构

验收、排查与风险：
- 讲清怎么判断方案可上线：核心能力指标达到目标、工程指标在预算内、失败样本可解释、高风险场景有处理策略、用户或业务方能接受结果
- 讲清常见失败模式：数据质量差、模型不适配、向量召回不准、阈值难设、索引过期、权限过滤缺失、云 API 成本过高、本地模型太慢、企业数据不能出内网
- 给出验收口径：哪些指标必须达标，哪些指标只是观察项，哪些需要人工复核，哪些失败可以接受，哪些失败必须阻断上线
- 明确哪些能力不该过度工程化：数据很少、频率很低、质量要求不高或只是个人验证时，优先用脚本、本地文件和轻量索引跑通

表达与呈现：
- 重视可视化：用 demo-to-production 路线图、线上/线下链路图、方案选型矩阵、存储职责对照表、模型/算法位置图、成本与复杂度阶梯图呈现工程主线
- 善用交互：可通过方案切换、团队规模切换、组件是否需要的决策树、线上/线下步骤切换、开源/厂商/本地方案对比、失败案例展开等方式让读者主动探索
- 示例尽量真实、最小、可验证，可包含 Python 伪代码、关键依赖、数据目录、模型调用、索引构建、一次查询、FastAPI 最小接口和评测样例
- 单文件内联资源，离线可打开，自然中文表达即可，专业术语、框架名、库名、模型名、数据库名、命令、代码、文件名保留英文
- 首屏视觉贴合目标能力本身，让人一眼看到“要实现什么能力、最小流程怎么跑、有哪些方案路线、不同阶段如何演进”，而不是只展示标题或抽象装饰
```

## 维护规则

- 本模板只维护“AI 能力如何工程落地”的方案型入口，重点是技术路线、模型算法、依赖组件、线上/线下链路、开源/厂商/本地方案、demo/POC、评估指标与团队规模演进。
- 本模板默认面向 Python 开发者。FastAPI 是默认服务化方式，但不是模板主角；不要把本文扩展成 FastAPI 后端架构、项目分层或 Web API 教程。
- 模板正文必须保持可独立复制使用，不依赖知识点、模型、工具、开源项目或补充提示词片段。
- 如果目标是解释一个已有复杂 AI 系统如何运转，优先使用 `AI工程系统提示词模板-一文读懂版.md`。
- 如果只是给知识点、模型、工具或开源项目补充少量实现视角，优先使用 `工程实现与方案选型补充提示词.md`，不要把所有主题都升级成本模板。
- 模板应按场景区分 demo、POC、小团队、中团队和企业级，不要把所有生产组件平铺成验收清单，也不要把具体厂商产品清单写成文章主体。
- 维护时优先收紧主线，不要继续累加同级清单；新增要求必须能帮助读者做落地决策，否则应放进具体生成任务而不是通用模板。
