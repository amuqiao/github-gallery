# 语言框架提示词模板 - AI Coding 版

本文维护语言、UI 框架、后端框架和开发生态类《一文读懂》专项提示词，重点补充“怎么开发、业内术语叫什么、工程结构怎么组织、如何向 AI 准确表达需求”。

使用方式：把下面代码块作为专项提示词，与 [一文读懂公共生成约束](一文读懂/公共生成约束.md) 的公共提示词组合使用；不要把公共的单文件、可视化、真实示例等要求重复散复制进本模板。

## 提示词

```md
为指定语言、UI 框架、后端框架或开发生态生成《一文读懂》单文件交互式 HTML，核心目标是让不熟悉该技术的人建立开发心智模型，掌握常用术语、组件/API 名称、工程结构和需求表达方式，并能更准确地进行 AI coding。

建议：
- 从一个真实开发任务切入，讲清这个技术栈如何把需求组织成项目结构、页面/接口、状态、数据流、持久化和可运行结果，避免写成语法大全或 API 清单
- 建立开发心智模型：讲清入口文件、目录结构、组件/路由/接口、状态与生命周期、异步任务、依赖注入、配置、构建、调试和测试的主路径
- 建立“中文需求 -> 框架术语”的映射：解释常见需求在该生态里通常叫什么，例如 sheet、dialog、Picker、DatePicker、List、Form、Toolbar、router、service、repository、schema、migration 等
- 讲清常用对象的职责边界：什么时候用、不要拿它做什么、和相近对象有什么区别，避免读者只背名字却不会选择
- 重视工程结构和架构词汇：讲清该生态常见分层、数据层、网络层、持久化、资源存储、缓存、错误处理、测试边界和发布流程，以及业内通常怎么命名
- 如果该生态存在多种主流方案，要讲清选择边界，例如 SwiftUI 中的 SwiftData、Core Data、GRDB + SQLite、FileAssetStore、Observable/ViewModel、Repository；FastAPI 中的 router-only、service layer、repository、unit of work 等
- 给出 AI coding 可直接复用的需求表达方式：把模糊中文需求改写成包含框架术语、文件位置、分层边界、状态流、错误处理和验证方式的 prompt
- 给出常见误说法和更准确说法，指出哪些描述容易让 AI 误解，应该改成该生态里更标准的组件、模式或 API 名称
- 示例尽量真实、最小、可验证，可包含目录片段、一个页面/接口/组件、状态变化、数据读写、CLI 命令、测试命令或构建输出
- 可视化和交互服务开发理解：可用目录树、状态流、请求链路、数据持久化流、组件选择表、架构对比或“需求到术语”对照表
- 单文件内联资源，离线可打开；自然中文表达，专业术语、API、类名、命令、文件名、库名和框架名保留英文
- 首屏视觉贴合该技术栈，让人一眼看到“我要开发什么、代码放在哪里、应该用哪些核心概念表达需求”
```

## 维护规则

- 本模板只维护语言/框架/生态的对象差异：开发心智模型、术语地图、工程结构、架构取舍和 AI coding 表达。
- 公共的一文读懂要求继续维护在 `一文读懂/公共生成约束.md`，不要在这里重复扩写。
- 如果某个经验只适用于单一技术栈，例如 SwiftUI 专属组件或 FastAPI 专属目录规范，优先放进生成任务的输入要求，不要写进通用模板。
- 如果后续需要更详细的 AI coding prompt 结构，单独新增公共片段或专项片段，不要把长示例堆进本模板。
