# 语言框架提示词模板 - AI Coding 版

本文维护语言、UI 框架、后端框架、全栈框架和开发生态类《一文读懂》专项提示词，重点补充“怎么开发、通用工程职责如何落到生态术语、工程结构怎么组织、如何向 AI 准确表达需求”。

使用方式：直接复制下面代码块作为完整提示词使用；具体语言、框架、读者背景和期望开发场景由生成任务补充。

## 提示词

```md
为指定语言、UI 框架、后端框架、全栈框架或开发生态生成《一文读懂》单文件交互式 HTML，核心目标是让不熟悉该技术的人建立开发心智模型，理解通用工程职责在该生态里的落点，掌握常用术语、组件/API 名称、工程结构和需求表达方式，并能更准确地进行 AI coding。

建议：
- 先判断对象类型：区分语言、UI/客户端框架、后端框架、全栈框架或开发生态；按类型裁剪重点，不要把 UI 组件、后端分层、语言语法或部署细节硬塞进不相关对象
- 从一个真实开发任务切入，讲清这个技术栈如何把需求组织成项目结构、入口、状态/数据流、持久化或外部依赖、可运行结果和验证方式，避免写成语法大全或 API 清单
- 建立开发心智模型：讲清入口文件、目录结构、UI/接口入口、路由/导航、状态与生命周期、异步任务、依赖注入、配置、构建、调试和测试的主路径
- 围绕通用工程维度组织内容：入口、路由、状态、数据流、网络/数据库、持久化、资源存储、缓存、错误处理、后台任务、权限、安全、测试、构建发布；只讲该技术栈真正相关的维度
- 把通用架构职责映射到生态术语：讲清这些职责在该技术栈里通常由哪些对象、目录、库或模式承担，例如 View/Component、Router/Controller、Service、Repository、DTO/Schema、Store、DAO、Migration、FileAssetStore、Background Job 等
- 建立“中文需求 -> 框架术语”的映射：解释常见需求在该生态里通常叫什么，例如弹窗、表单、列表、选择器、页面跳转、接口路由、后台任务、文件存储、数据迁移、测试替身等
- 讲清常用对象的职责边界：什么时候用、不要拿它做什么、和相近对象有什么区别，避免读者只背名字却不会选择
- 如果同一工程职责存在多种主流实现方案，要讲清选择边界和取舍，例如本地持久化、服务端状态、文件资产、网络层、仓储层、后台任务、依赖注入、测试替身等；示例可以引用具体生态，但不要让模板绑定某个框架
- 讲清版本和生态约定：说明示例面向的语言/框架版本、平台或运行时；如果不同版本存在推荐写法差异，要标出新旧方案边界
- 给出 AI coding 可直接复用的需求表达方式：把模糊中文需求改写成包含框架术语、文件位置、分层边界、状态流、错误处理和验证方式的 prompt
- 给出常见误说法和更准确说法，指出哪些描述容易让 AI 误解，应该改成该生态里更标准的组件、模式或 API 名称
- 示例尽量真实、最小、可验证，可包含目录片段、一个页面/接口/组件、状态变化、数据读写、CLI 命令、测试命令或构建输出
- 可视化和交互服务开发理解：可用目录树、状态流、请求链路、数据持久化流、组件选择表、架构对比或“需求到术语”对照表
- 单文件内联资源，离线可打开；自然中文表达，专业术语、API、类名、命令、文件名、库名和框架名保留英文
- 首屏视觉贴合该技术栈，让人一眼看到“我要开发什么、代码放在哪里、应该用哪些核心概念表达需求”
```

## 维护规则

- 本模板只维护语言/框架/生态的对象差异：开发心智模型、通用工程维度、生态术语地图、架构取舍和 AI coding 表达。
- 模板正文必须保持可独立复制使用，不依赖其他提示词片段。
- 如果某个经验只适用于单一技术栈、框架版本或平台运行时，优先放进生成任务的输入要求，不要写进通用模板。
- 如果后续需要更详细的 AI coding prompt 结构，单独新增专项片段，不要把长示例堆进本模板。
